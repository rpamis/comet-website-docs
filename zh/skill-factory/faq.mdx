关于 `/comet-any` Skill Factory 的创建流程、偏好配置、发布和分发的常见问题。

## 基础概念

<AccordionGroup>
  <Accordion title="我不懂 Bundle、Factory、composition 这些词">
    普通用户不需要懂。这些是 `/comet-any` 的内部后端概念。你只需要调用 `/comet-any`，它会在内部调用 CLI 维护确定性状态。第一层只有三种起点：基于 Comet 现有 Skill 的五阶段定制、创建全新 workflow Skill、整理已有 Skill。详见[Skill Factory 概览](/zh/skill-factory/overview)。
  </Accordion>

  <Accordion title="/comet-any 和 /comet 有什么区别">
    `/comet` 是经典 Spec 模式入口，驱动 open/design/build/verify/archive 五阶段项目变更流程。`/comet-any`（Skill Maker）是 Skill Factory，用来**创建、优化、组合可复用的 Skill Bundle**。两者是不同入口，但 `/comet-any` 的"基于 Comet 现有 Skill 的五阶段定制"可以以 `/comet` 为基础做增量调整（在受保护边界内增加 Required Skill Call、替换 producer 节点、关闭可选节点）。
  </Accordion>

  <Accordion title="为什么要生成 Bundle 而不是只生成一个 SKILL.md">
    多步骤、需要恢复、需要 guardrails、需要 runtime evals 或包含脚本副作用的 Skill，必须生成稳定组合 Skill Bundle（包含 `SKILL.md` + Engine Package + control plane：`scripts`/`rules`/`hooks`/`references`）。只生成 `SKILL.md` 会失去 Run 恢复和 runtime eval。
  </Accordion>

  <Accordion title="Skill Maker 确认页上的&quot;保留/新增/替换/关闭&quot;是什么意思">
    这是基于 Comet 现有 Skill 做五阶段定制（`customize-comet`）时的调整词汇，作用于 **Workflow Node**：**保留**节点原实现、**新增** Required Skill Call（要求节点内调用额外 Skill）、**替换** producer 节点（`design`/`plan`，必须 satisfy Output Schema）、**关闭**可选节点（只有 `review` 可关闭）。control 节点（`open`/`execute`/`verify`/`archive`）不能被替换实现。详见[Skill Factory 概览 · 受保护边界](/zh/skill-factory/overview#受保护边界基于-comet-现有-skill-的五阶段定制)。
  </Accordion>

  <Accordion title="Workflow Node 和 Required Skill Call 有什么区别">
    Workflow Node 是流程里一个可恢复的阶段（如 `execute`），它有一个**实现 Skill**（真正干活的 Skill）。Required Skill Call 是要求这个节点**内部额外必须调用**某个 Skill，但**不替换**节点的实现 Skill。例如要求 `execute` 节点必须调用 `elementui`（组件库），但 `execute` 的实现仍是 `comet-build`。详见[Skill Factory 概览](/zh/skill-factory/overview#workflow-contract所有路径的共同模型)。
  </Accordion>

  <Accordion title="Output Schema 是什么，为什么不能只看 Skill 名字">
    Output Schema 是节点必须产出的文件、状态或 evidence（如 `comet.design.v1`）。脚本、eval、readiness **只认 Output Schema，不认 Skill 名字**——这样替换 producer 节点的实现时，只要满足同样的 Output Schema，下游检查照样能通过。替换 producer 节点（`design`/`plan`）时必须声明 `satisfies`，否则校验报 `producer-missing-output-schema`。
  </Accordion>

  <Accordion title="workflow-protocol.json 是什么">
    `reference/workflow-protocol.json` 是生成包的**唯一运行事实源**，记录节点、边、Output Schema、state 和 evals。runtime、eval、review、publish readiness 全部读这一份协议，保证"创建时校验通过"和"运行时能恢复"指向同一个事实。详见[Skill Factory 概览 · 关键文件职责](/zh/skill-factory/overview#关键文件职责)。
  </Accordion>
</AccordionGroup>

## 偏好与组合

<AccordionGroup>
  <Accordion title=".comet/skill-preferences.yaml 和 .comet/skills.txt 是什么关系">
    0.4.0-beta.1 用项目级 `.comet/skill-preferences.yaml`（支持 advisory/strict 模式、prefer/require、策略）替代了旧的 `.comet/skills.txt`。详见[Skill 偏好与真实来源](/zh/skill-factory/preferences)。
  </Accordion>

  <Accordion title="advisory 和 strict 模式有什么区别">
    `advisory`（默认）可以补充目标需要的 Skill，但必须解释偏离原因。`strict` 是团队标准化模式，required Skill 缺失、歧义或禁止 scripts/hooks 时阻塞。
  </Accordion>

  <Accordion title="为什么组合方案要等我确认才生成">
    `/comet-any` 不能直接写 Bundle draft。它必须先展示"Skill Maker 方案确认页"，说明复用哪些 Skill、偏离原因、scripts/hooks 披露，你确认后才写 draft。这避免生成不符合预期的产物。
  </Accordion>

  <Accordion title="候选缺失或有多个来源怎么办">
    `/comet-any` 会暂停询问你，不会静默忽略或替你选择。你选择明确来源、移除缺失项或更新偏好后，它才会更新 Factory metadata 继续。`available` / `missing` / `ambiguous` 三类状态见[Skill 偏好 · 缺失和歧义候选](/zh/skill-factory/preferences#缺失和歧义候选)。
  </Accordion>

  <Accordion title="三种起点有什么区别，我该选哪个">
    三个起点对应三种 Skill Maker 意图：`customize-comet`（基于 Comet 五阶段做增量，如加组件库/白盒审查）、`new-skill`（从零创建全新 workflow-kernel）、`upgrade-existing`（整理已有 Skill 成可发布标准包）。想沿用 `/comet` 五阶段就选第一种；想做完全不同的流程就选第二种。详见[Skill Factory 概览 · 三种起点](/zh/skill-factory/overview#三种起点)。
  </Accordion>

  <Accordion title="skillMakerIntent 是什么">
    Skill Maker 意图（`skillMakerIntent`）是 plan.json 里标注你选了哪种起点的字段，取值 `customize-comet` / `new-skill` / `upgrade-existing`。不写时 `/comet-any` 会按 `workflow.kind` 和 `mode` 自动推断（`comet-five-phase-overlay` → `customize-comet`，`optimize` → `upgrade-existing`，其余 → `new-skill`）。
  </Accordion>
</AccordionGroup>

## 评估与发布

<AccordionGroup>
  <Accordion title="生成物会被自动分发到平台吗">
    不会。`/comet-any` 发布后会询问你是否分发，并先展示预览。只有你确认后才会真正写入平台。
  </Accordion>

  <Accordion title="为什么发布被阻塞了">
    常见阻塞原因（每个都有阻塞码）：`[candidate]` 还有 unresolved candidate、`[eval]` Eval 没跑或对应旧 hash、`[proposal]` proposal 未确认、`[control-plane]` 控制面不完整、`[draft]` 缺 hash、`[publish]` 缺 ready metadata。`comet publish status` 会直接展示 `Blockers:` 和恢复命令。完整的阻塞码表见[发布和分发 Skill · 阻塞码](/zh/skill-factory/publishing#阻塞码blocker-codes)。
  </Accordion>

  <Accordion title="分发前为什么要先跑 preview">
    preview 是强制检查，展示 planned files、unsupported capability、executable disclosures 和 `No files were written`。确认预览后才能移除 `--preview` 执行真实分发，避免误写文件。
  </Accordion>

  <Accordion title="Eval 通过了就能直接发布吗">
    不能。Eval 通过只是 readiness 的一个条件，还需要人工批准（`comet publish approve`）。Eval 通过且 hash 匹配、人工批准后才会进入 `ready` 状态。详见[发布和分发 Skill](/zh/skill-factory/publishing)。
  </Accordion>

  <Accordion title="运行 eval 需要什么环境">
    需要 `uv`、Python 3.11+、Docker，以及 `ANTHROPIC_API_KEY`（或 `ANTHROPIC_AUTH_TOKEN`）。核心 Comet 运行时不需要这些，只有 `comet eval` 需要。完整准备步骤见[评估快速上手 · 运行前你需要准备什么](/zh/eval/quickstart#运行前你需要准备什么)。
  </Accordion>
</AccordionGroup>

## 恢复与排障

<AccordionGroup>
  <Accordion title="做到一半中断了怎么办">
    直接对 Agent 说"继续上次的 Skill 创建"。`/comet-any` 会扫描可恢复状态，展示名称、状态、next action 和上次确认的组合方案摘要，让你选择继续哪一个。恢复时的 hash 漂移处理见[创建 Skill 的完整流程 · 恢复中断流程](/zh/skill-factory/workflow#恢复中断流程)。
  </Accordion>

  <Accordion title="偏好文件改了，旧组合方案还能用吗">
    `advisory` 模式会给 warning，让你选择继续旧组合方案或重新生成。`strict` 模式默认阻塞，要求你确认继续或重新生成。这就是 `preferenceHash` 漂移。
  </Accordion>

  <Accordion title="resolved-skills.json 是什么，为什么要看它">
    `reference/resolved-skills.json` 记录两件事：组合方案基于哪些真实 Skill、它们的 hash 和状态（`available`/`missing`/`ambiguous`）；以及每个 Workflow Node 绑定的实现 Skill、Required Skill Call 和 Output Schema。它是"不是按名字猜的"的证据，也能反查节点到 Skill 的绑定。准备发布或审查时优先看它。
  </Accordion>

  <Accordion title="我能手工编辑 Bundle 状态或内部 JSON 吗">
    不要。`/comet-any` 通过后端记录结构化证据，手工编辑会破坏 hash 绑定和 readiness 校验。需要排查后端状态时用只读的 `comet bundle status` / `comet publish status`。
  </Accordion>

  <Accordion title="drift-conflict 是什么状态">
    当一个已经 ready 的产物，draft hash 和 ready hash 都发生变化时会进入 `drift-conflict`，带 `conflict: {draftHash, readyHash}`。这时需要重新生成。只有一个 hash 变了会直接回退到 `draft`。
  </Accordion>
</AccordionGroup>
