`comet guard` 是 Classic 的阶段检查命令。它会检查当前 phase 需要的文件、字段和验证证据，决定能否进入下一阶段。

<Note>
  本页命令由 Agent 在后台调用，你不需要手动运行。日常开发只需在对话中输入 <code>/comet</code> 提需求、回答 Agent 的提问，或说“继续”。本页供你在终端排查问题、编写脚本或接入其他 Agent 平台时查阅。
</Note>

## 基本形式

```bash
comet guard <change-name> <phase>
comet guard <change-name> <phase> --apply
```

不带 `--apply` 时只检查，不改任何状态，你也可以在终端自己运行。带 `--apply` 时，检查通过后会调用 `comet state transition` 推进 phase；每个阶段结束时，阶段 Skill 调用的就是这个形式。

## 常见检查

- open: proposal、design、tasks 和 delta spec 是否完整。
- design: Design Doc 是否存在。
- build: `build_mode`、`isolation`、`tdd_mode`、`review_mode` 等是否满足约束，并运行自动检测到的项目构建检查。
- verify: 验证报告和验证结果是否可用。
- archive: 是否已通过验证并完成最终确认。

## 构建检查

build 阶段不再读取 `build_command` 或 `verify_command` 配置字段。guard 会根据项目文件自动检测构建方式，例如 `package.json` 中的 `npm run build`、Maven 或 Cargo。

如果 change 的 `.comet.yaml` 里仍然保留 `build_command` / `verify_command`，guard 会把它们当作未知字段拒绝。需要固定团队级验证命令时，建议放进项目自己的脚本。无法自动推断入口时，由 Agent 或 CI 脚本先实际运行命令，再通过 `comet state record-check` 记录证据；guard 会核对这份记录。

<Warning>
  guard 失败时不要直接改状态绕过。先补齐缺失的证据，或回到对应阶段。
</Warning>

<Note>
  安装包仍包含 <code>comet-guard.mjs</code> 兼容 launcher，但 Agent 指令、脚本集成或终端排障应优先使用 <code>comet guard</code>。
</Note>
