---
title: '持久化、审批与未知结果'
description: '保留 Run 身份与当前批准，并在重试前核对已派发操作的真实结果。'
---

恢复时先读取原 Run，区分待执行、正在执行、等待用户、已知失败和结果未知。每一种状态都有对应的处理方式。

## 继续同一个 Run

使用文件 Store 时，新进程重新注册相同工作流版本、执行器和验证器，然后读取原 Run ID。不要另建一个 Run 来重复执行已经完成的动作。

应用按身份与版本保留固定包；活动 Run 需要的旧版本在升级后仍保留。依赖内容发生变化时，恢复原依赖或重新确认新的应用版本。

| 当前情况          | 处理方式                                 |
| ----------------- | ---------------------------------------- |
| pending Action    | 使用配置的执行端口领取并执行             |
| pending Wait      | 展示当前提案，提交实际用户决定或所需证据 |
| 已知失败          | 修正失败原因，按允许的重试路径继续       |
| running / unknown | 先核对原执行者和外部系统的结果           |
| 需求或提案变化    | 修订并取得当前提案的新批准               |

## 结果未知时先核对

派发后断连，外部操作可能已经发生。例如报告已经提交到外部服务，但宿主没有成功保存回报。这时不能再次调用发布来判断结果。

宿主的核对接口查询原 Action 的实际结果。已执行时回报同一动作的 Outcome；确认未执行、且原执行者已经停止时，附可核对的证据后重试。无法确认时保留现场。

完整应用可以通过 `reconcileApplicationSkill` 调用已配置宿主的核对能力，取得原动作结果后再回报；这个接口不会重发操作。

SDK 保存 Run 和 claim，不会把本地记录与外部服务变成一个原子事务。需要业务幂等键或查询接口时，由宿主与外部服务实现。

## 数据保存在哪里

基础 Runtime 的 `createFileRuntimeStore` 使用你指定的 `rootDir`。

通过 Comet CLI 使用 Native、Classic 和 SDK 应用时，机器本地的执行数据保存在用户 Comet 数据目录，按项目 checkout 和 Git worktree 隔离。默认根目录为 `~/.comet`，可以用 `COMET_DATA_DIR` 指定；Windows 默认位于用户目录下的 `.comet`。指定的用户数据根必须在当前工作区之外，不能设为项目子目录。

需求、Spec、入口 Skill 和用户可读的状态投影继续保留在项目内。具有完整 portable checkpoint 的 SDK change 可以在复制后恢复；不需要手工复制或编辑本机锁、事务和 Run JSON。

## 宿主与安装能力

真实 Skill 执行要求宿主具备声明的加载、交接和授权能力。平台安装预览会列出缺失能力与需要激活的 Hook。文件写入安装目录成功，不等于宿主已经执行、Hook 已经生效或业务已经验收。

完整应用安装与升级见 [comet application](/zh/cli/application)。日常运行状态可通过 [Dashboard](/zh/dashboard/overview) 观测；推进和用户决定仍使用原 Run 的执行入口。
