Comet Native 不是把 Classic Spec 模式删掉几个阶段，也不是把一套长 Prompt 压缩成短 Prompt。它来自一个更根本的问题：**当编码模型已经能够自主调查、设计、实现和调试时，工作流还应该替它规定多少过程？**

我们的答案经历了多轮修正。最后留下的边界是：需求和验收条件要详细，执行方法要轻；模型负责判断和实现，Runtime 负责机械事实、恢复、安全边界和证据新鲜度。

这篇文章保留真实演进过程，包括被否决的方向和仍未得到实验回答的问题。它不是把开发历史改写成一条从一开始就完全正确的路线。

## 起点：Spec 没有失去价值，HOW 变得过重

Classic Spec 模式解决过真实问题。能力较弱的模型面对复杂任务时，明确的 Open、Design、Build、Verify、Archive 阶段，以及计划、TDD、调试和审查协议，可以减少漏读文件、跳步骤和无证据完成。

但同一套约束放到强模型上，会产生新的成本：

- 模型已经能根据仓库事实选择实现方法，却仍要回答多组模式选择；
- 多个阶段 Skill 反复加载相似上下文，并在交接时损失信息；
- 流程文件和实现文件一起增长，用户很难区分真正需求与执行脚手架；
- “完成所有步骤”容易替代“满足目标并拿出证据”。

因此 Native 没有否定 Spec。它把 Spec 重新定义为**给模型足够的信息和完成条件**，而不是规定模型每一步怎样思考。

<Note>
  Native 与 Classic 保持为两套独立产品。Native 服务于能够自主执行的强模型；Classic
  服务于需要明确方法指导的模型。两边没有自动升级、转换或共享 change。
</Note>

## 为什么一个很短的澄清 Prompt 反而有效

早期讨论受到 grill-me 类 Prompt 的启发，但 Native 从未把它作为外部依赖。真正值得保留的不是某个 Skill 名称，而是它把对话压力集中到少数高价值动作：

1. 找出真正会改变结果的未知决定；
2. 一次只问最重要的一个；
3. 给出推荐答案和理由；
4. 解释每个选项对范围、兼容性、风险或用户体验的实际影响；
5. 把答案沉淀成可执行条件，而不是只留在聊天里。

它效果好，恰恰因为没有用长问卷稀释注意力。Native Shape 沿用了这个原则，但增加两个限制：先调查仓库里能直接得到的事实；明确任务没有高影响未知项时允许隐式确认，不能为了“走完澄清流程”制造问题。

最终的完成标准也更严格：另一个没有原对话的强模型，只读 brief、完整目标规格和仓库事实，就应该能够实现并验收，不必猜测用户可见行为。

## 2026-07-14：先切断概念混合

第一轮设计先确定了几条产品边界：

- Native 使用 Comet 自有 `comet/`，不借用 OpenSpec change；
- 项目可以把产物根指定为 `docs` 等相对路径；
- Native 与 Classic 状态、选择和归档完全隔离；
- Native 不依赖 Superpowers、OpenSpec、grill-me 或其他外部 Skill；
- 一个 `/comet-native` Skill 根据当前 phase 继续，不拆成多个阶段 Skill；
- Shape、Build、Verify、Archive 只表达结果状态，不增加 Plan、TDD、Debug、Review 必经阶段。

为什么坚持一个 Skill？因为阶段顺序已经由 Runtime 确定性表达。再拆成四个 Skill，只会重新引入 Skill 选择、阶段路由和上下文交接。强模型需要的是同一个行为入口根据磁盘状态继续，而不是每到一个阶段重新加载一套方法规范。

第一版 Runtime 优先交付机械事实：项目配置、change 状态、四阶段守卫、完整目标规格、trajectory、选择、归档和自带 Runtime。它不替模型思考，但保证模型读到的阶段和目录是可复现的。

## 2026-07-15：从“有状态”到“一致状态”

第一版很快暴露一个问题：状态分散在 `change.yaml`、Run state、trajectory 和 checkpoint 中，只保证每个文件格式正确还不够。如果进程恰好在两次写入之间退出，不同文件可能各自合法、彼此矛盾。

Phase 1.5 引入 transition journal，把一次阶段推进拆成可以幂等恢复的写入序列。Runtime 先记录确定的前后状态，再依次更新 Run、change、trajectory 和 checkpoint；下一次 `next` 或 doctor 可以从 journal 继续，而不是猜测哪一份文件才是真的。

这一轮形成了一个持续保留的分工：

| 问题                           | 归属                     |
| ------------------------------ | ------------------------ |
| 如何实现、测试和调试           | 强模型                   |
| 用户必须决定什么               | Skill 的轻量澄清协议     |
| 哪个阶段、哪些输入、是否可恢复 | Runtime                  |
| 模型是否真的更好               | Eval，而不是 Prompt 自述 |

## 2026-07-16：先修正评估口径，再谈性能

早期 Native 和 0.4.0 Classic 的样本数量、运行窗口与耗时计算方式不同，不能直接比较。尤其是旧报告只使用每个样本最后一个 `result.duration_ms`，会漏掉多轮模型调用的前序耗时。

我们随后把 Native 对齐到 Classic 已运行的 16 个业务任务，每个任务重复 3 次，并按 `task_id + repetition` 严格配对。耗时改为累加样本内全部顶层 result。

对齐结果显示，两组 `pass@3` 都达到 16/16；Native 在 strict pass@1、`pass³` 和修正耗时上给出较好的方向性结果。可是两边不在同一运行窗口，机器负载和服务时段没有完全受控，因此这些数字不能证明“删掉某个阶段直接带来多少加速”。

这个修正影响了后续所有 Wave：先明确业务验证与 workflow 验证各自的契约；先保证样本身份和时间口径可信；没有真实模型 artifact 时，只把 fixture 和 validator 通过写成机械覆盖，不把它包装成模型行为结论。

## 从 58 个想法收敛为 14 + 1 个能力

当我们继续追问“Native 还能怎样服务强模型”时，Runtime、UX 和 Eval 三个方向一度展开了 58 个检查点。逐项产品化会让 Native 重新变重，因此最终把它们压缩为 14 个纵向能力和 1 个跨波次边界。

### Wave A：基础安全与指标可信

状态升级到 schema v3，并加入 migration journal、revision/CAS、baseline/current snapshot 和受保护的 Run I/O。旧状态不能被新 Runtime 静默当成最新证据；必须由 doctor 受控迁移。

这不是增加用户步骤，而是让 Runtime 能区分三种情况：可以继续、必须迁移、已经损坏。

### Wave B：判断结果可续跑，阶段内进度可恢复

原来的 `next: auto` 只是人类可读提示，无法告诉宿主应该继续当前 Skill、等待用户还是先修 Runtime。Wave B 把它变成结构化 continuation，并加入同阶段 checkpoint。

`continue-same-skill` 不表示后台 daemon 自动运行模型。它只是让宿主或下一次会话知道：上下文可以压缩，但仍应回到同一个 Native Skill 和同一个 change。

### Wave C：验证报告必须仍然有效

仅仅保存一份 `verification.md` 不足以证明完成。报告可能对应旧需求、旧实现或旧的验收集合。

Wave C 把 evidence 绑定到三类事实：

- 从 brief 和完整目标规格派生的 contract/Acceptance ID；
- 从基线、当前文件和声明产物派生的 implementation scope；
- 当前 change revision。

这些输入变化后，旧 pass、旧 receipt 和 partial allowance 都会 stale。Runtime 不规定模型用什么测试框架，但能回答“这份结论当时验证的是哪一份需求和哪一组实现”。

### Wave D：允许自主修复，也能跨会话停下来

强模型应当自主修复 Verify failure，但“继续尝试”不能退化成无限循环。Native 不读取思维链，而是用失败分类、失败检查 ID、contract 和 scope 形成语义签名。

相同 scope 下第三次出现相同失败时转为 manual stop；单个 episode 达到 12 次 failure 时 hard stop；真实 scope 进展会结束旧 episode。这样停止条件依赖证据进展，而不是机械计算经过了多少次 phase transition。

### Wave E：只承诺当前 Native root 内可证明的并行安全

第一版曾考虑用 Git branch、HEAD 和 changed paths 帮助判断并行 change。安全复审后，这条路径被完全删除。

原因很简单：用户可能不使用 Git、仓库可能处于 detached HEAD、未跟踪文件仍然重要，而且 Git 关系不能证明两个模型没有语义冲突。最终冲突判断只使用 Runtime 已拥有的 capability、operation、base hash、contract 和有界 implementation scope。Native 不自动创建 worktree，也不把 Git 猜测升级为安全保证。

### Wave F：Dashboard 只读，不成为第二套 Runtime

Dashboard 可以展示阶段、证据新鲜度、checkpoint、continuation、归档就绪和冲突摘要，但它只消费 Runtime projection。它不重新计算状态、不缓存第二份事实，也不提供推进按钮。

这个边界看起来保守，却避免了最难排查的一类问题：CLI 认为 change 在 Verify，Dashboard 却因为缓存或独立规则认为它已经 Archive。

### 跨波次边界：拒绝通用命令执行器

“让 Runtime 执行项目测试并签发 receipt”看起来很有吸引力。它也意味着处理 shell 解析、环境变量、凭据、子进程树、超时、输出截断、平台差异和命令注入，最终会把 Comet 变成一个新的任务执行平台。

这条方案被否决。最终的 `comet native check` 只执行 Comet 内置、窄范围、可重建的只读文本策略，不调用 Git、shell、项目脚本、外部 Skill 或任意进程。真实测试仍由模型按仓库和风险决定。

## 轻，不等于 Runtime 简单

Native 的用户流程只有四个阶段，但 Runtime 内部并不草率。真正的复杂度被放在“水面以下”：

- 配置、change、brief/spec、Run、trajectory、journal 和目录枚举分别有硬预算；
- 输入使用受保护句柄读取，打开前后复核文件和父目录身份；
- status/list、findings 和 Acceptance ID 使用内容绑定的分页 cursor；
- Build/Verify 先完成纯检查，再持久化最终 evidence，失败尝试不留下伪结论；
- Archive 先 dry-run，再用 preflight hash 提交；
- 目录删除先改名到事务 quarantine，恢复时继续或回滚；
- 摘要、理由和跳过说明在持久化前执行长度限制与凭据形态脱敏。

这些机制会增加实现代码，却不会增加模型必须遵循的阶段或用户必须填写的表单。**轻量的目标是减少认知协议，不是牺牲事实一致性。**

## 被明确删除的方向

为了防止未来迭代悄悄把 Native 变回 Classic，我们把非目标也作为产品边界保留：

- 不拆成多个阶段 Skill；
- 不依赖外部 Skill；
- 不提供 Native 到 Classic 的升级或转换；
- 不新增 Plan、TDD、Debug、Review 必经阶段；
- 不在 Runtime 内调用 LLM；
- 不运行后台 daemon；
- 不自动管理 Git branch/worktree；
- 不提供任意 shell 命令执行和签名；
- 不让 Dashboard 成为写入面；
- 不把 checkpoint 扩张成项目管理系统。

这些能力不是“以后都要做的 backlog”。若未来要重新打开其中任何一项，必须先证明它不会破坏 Native/Classic 的边界。

## 现在可以确认什么，还不能确认什么

当前实现已经能机械证明：状态和证据有 schema/CAS 约束；中断 transition、Archive 和 root move 可以按 journal 恢复；旧证据会在输入变化后 stale；repair 有语义停止；并行冲突和 Dashboard projection 复用同一 Runtime 事实。

仍不能仅凭这些测试宣称：

- 模型面对没有显式提示的隐藏决定时，召回率已经达到某个水平；
- continuation 在所有宿主中都会自动续跑；
- repair 协议一定降低真实任务的 token 或耗时；
- Dashboard 已经提高团队协作效率；
- Wave A–F 相对其他工作流有稳定的真实模型胜率。

这些问题需要新的真实模型实验，而不是更多静态断言。历史 Native/0.4.0 对齐实验提供方向性证据；Wave A–F 当前的 fixture、validator 和对抗性测试证明机械契约可执行，但不能替代真实行为测量。

## 最终原则

Comet Native 的演进最后收敛成一句话：

> 把“怎么完成”交给强模型，把“完成的条件、事实和不可逆边界”交给 Runtime。

因此 Native 可以同时拥有详细需求、真实状态机、自动推进、恢复、验证证据、并发保护和安全归档，又不要求模型为了工作流本身执行一套笨重的方法清单。
