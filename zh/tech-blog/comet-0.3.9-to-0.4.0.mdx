0.3.9 的 Comet 是一个优秀的"五阶段工作流层"——它把 OpenSpec 和 Superpowers 串成一条可恢复的开发流水线，靠 Bash 脚本守护阶段边界。但用着用着，几个根本性的限制越来越明显：

- Windows 用户必须装 Git Bash 或 WSL 才能跑完整流程；
- 想组合多个 Skill 成一个可复用、可分发的包，只能手写一个 `SKILL.md`；
- 没有办法量化"这个 Skill 到底好不好"，发布全凭感觉；
- 中断后回来，路由全靠 Agent 重新读提示词"猜"一次。

0.4.0-beta.1 针对这四个痛点做了一次系统性重构。这篇文章不讲功能清单（那是 [changelog](/zh/changelog/v0.4.0-beta.1) 的活），而是讲**每个决策背后的原因**。

## 一、为什么把 Bash 运行时换成 Node

这是 0.4.0 最大的改动，也是最受 Windows 用户欢迎的改动。

**0.3.9 的状态**：状态机、阶段守卫、交接、归档这些核心逻辑由 7 个 Bash 脚本承担。逻辑本身没问题，但"必须有一个兼容 Bash 的 shell"这个前提，把相当一部分用户挡在了门外。Windows 上要么装 Git Bash，要么用 WSL；路径转义、shell 差异、可执行权限丢失（macOS 上那个经典的 `100644` → `100755` 问题）都是反复出现的隐患。

**0.4.0 的决策**：把所有脚本重写为 Node `.mjs` 启动器，背后由一份共享的 TypeScript 运行时（`domains/comet-classic/`）支撑。每个 `.mjs` 是一个自包含的 esbuild 单文件包，把 `yaml` 等依赖一并内联。

**为什么这样改**：

| 动机 | 0.3.9 | 0.4.0 |
| --- | --- | --- |
| 跨平台 | Windows 需要 Git Bash/WSL | 仅需 Node.js 20+ |
| 路径可靠性 | shell 转义、CRLF、可执行位 | Node 原生处理 |
| 实现一致性 | 散落的 shell 逻辑 | 单一 TypeScript 转移语义表 |

关键在于"单一转移语义表"：`comet-state transition` 和 `comet-guard --apply` 现在共享同一份 `classic-transitions.ts`，所以两条推进路径的行为完全一致，不会再出现"guard 放行了但 state 拒绝"这种不一致。

<Info>
  对老用户来说最重要的承诺：<strong>所有 <code>/comet*</code> 命令的行为不变</strong>。你不需要改用法，底层从 Bash 换成了 Node，但工作流还是那条工作流。
</Info>

## 二、为什么做意图帧（Intent Frame）

**0.3.9 的状态**：`/comet` 入口靠 Skill 正文里一段自然语言规则判断该走 `full`/`hotfix`/`tweak`。问题是这段规则**不可解释、不可复核、不可恢复**。路由错了，你不知道是哪个信号出了问题；中断后重新进来，Agent 只能重新猜一次。

**0.4.0 的决策**：把"用户想干什么"变成一个结构化的 `CometIntentFrame`，再由运行时按固定优先级重新评分，给出可解释的最终路由。

**为什么这样改**：核心矛盾是"信任问题"。旧做法信任 Agent 自己提的路由建议；新做法**不信任建议，只信任证据**——运行时拿意图帧里的置信度、风险信号、仓库上下文重新算一遍，和 Agent 的建议不一致时，把分歧写进诊断日志。

最体现这个设计的是**风险信号优先于口头流程**：你说"走 hotfix"，但如果命中了 `public_api_change`，运行时会停下来问你，而不是放行一个影响外部契约的轻量流程。这是 Comet 的安全底线——宁可多问一句，不替你赌一条高风险的近路。

详见[意图识别与路由](/zh/concepts/intent-routing)。

## 三、为什么把 Skill 创建做成一个平台

**0.3.9 的状态**：想组合多个 Skill 成一个可复用的包？你只能手写一个 `SKILL.md`，把调用链描述成自然语言。这样的"包"没法带依赖、没法带规则和 hooks、没法被评审、没法被分发——它只是个提示词文件。

**0.4.0 的决策**：`/comet-any` 不再只产出 `SKILL.md`，而是生成一个**稳定的组合 Skill Bundle**——带 `workflow-protocol.json`（唯一运行事实源）、`resolved-skills.json`（真实来源证据）、Engine 四件套、required 控制面（scripts/rules/hooks），甚至平台原生文件（如 Claude Code custom agents）。

**为什么这样改**：因为"组合 Skill"这件事，本质上和"写一个提示词"不是一回事。一个可复用、可分发、可评审的 Skill 包，需要：

1. **确定性骨架**——路由表、运行时脚本、manifest 必须可复现，不能每次生成都变；
2. **可评审的创作内容**——入口的决策核心、节点的指导，是 LLM 写的，但必须能被人审、被证据门禁；
3. **发布证据链**——eval 证据绑定当前 draft hash，人工批准绑定当前 hash，分发前强制预览。

这三点决定了 `/comet-any` 必须是一个有创作协议（lane DAG）、有 Auto/Authored 分区、有 readiness 门禁的完整平台，而不是一个提示词生成器。

详见[Skill Creator 完整流程](/zh/skill-creator/workflow)。

## 四、为什么做 eval 和 dashboard

**0.3.9 的状态**：Skill 好不好全凭感觉。你写了个工作流 Skill，团队成员用不用得上、稳不稳定、token 花得值不值——没有量化手段。一个变更跑到一半卡住了，只能去翻 `.comet.yaml` 自己猜状态。

**0.4.0 的决策**：把评估（`comet eval`）和可视化（`comet dashboard`）做成一等公民。

**为什么这样改**：

- **eval 解决"好不好"**：用 `pass@k`（能力上限）和 `pass^k`（可靠性下限）区分"偶尔能做对"和"每次都能做对"。对工作流类 Skill——用户会反复跑的东西——可靠性比能力更重要。三套 rubric（generic/comet-workflow/authoring-skill）让不同类型的 Skill 按匹配的维度打分，而不是一刀切。失败归因（harness/workflow/task/model）帮你区分"是 Skill 的问题还是环境的问题"。

- **dashboard 解决"卡在哪"**：把每个变更的阶段进度、产物、任务、verify 状态、风险信号、Git 上下文放进一个只读浏览器界面。`--json` 和 `GET /api/dashboard` 让同一份快照能被脚本和 CI 消费。这把"诊断卡住的变更"从翻文件变成了看面板。

eval 和 dashboard 共享同一个运行时证据路径——`comet status`、`comet doctor` 报告的问题，就是脚本实际会拦截的问题。这让 Comet 的"可恢复性"从口号变成了可验证的承诺。

## 五、状态为什么拆成三层

**0.3.9 的状态**：所有状态塞在一个 `.comet.yaml` 里——用户可读的工作流字段和机器管理的运行态检查点混在一起。结果是用户容易误改机器字段，机器字段变化也污染了人类可读的投影。

**0.4.0 的决策**：每个变更的状态拆成三层：

| 文件 | 归属 | 内容 |
| --- | --- | --- |
| `.comet.yaml` | 用户可读 | 工作流投影（`workflow`/`phase` 等）+ `run_id` 链接 |
| `.comet/run-state.json` | 机器管理 | 运行态检查点：当前步骤、迭代、待处理动作 |
| `.comet/state-events.jsonl` | 追加式审计 | 成功转移的完整记录 |

**为什么这样改**：单一职责。用户能直接看懂"现在在哪个阶段"，但碰不到机器字段；机器字段由运行时原子写入，`comet-state set` 会拒绝直接写它们；审计日志只追加不覆盖，给你一条可追溯的状态历史。旧变更首次读取时自动迁移，无需手动处理。

## 这一切指向什么

如果把这五项改动放在一起看，0.4.0 的主线很清晰：**Comet 从一个"工作流层"变成了一个"工作流 + Skill 平台"**。

- 运行时跨平台了（Node），所以平台能落地到更多环境；
- 路由可解释了（意图帧），所以平台的行为可信任；
- Skill 可组合、可评审、可分发了（`/comet-any` + Bundle），所以平台能产出可复用资产；
- 质量可量化了（eval）、状态可观测了（dashboard），所以平台能自我改进。

0.3.9 解决了"怎么让一条工作流可恢复"；0.4.0 解决了"怎么让工作流和 Skill 成为一个可信赖、可扩展的平台"。这是这一次大版本跃迁真正想做的事。
