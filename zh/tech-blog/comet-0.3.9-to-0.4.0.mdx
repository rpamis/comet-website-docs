0.3.9 使用 Bash 脚本连接 OpenSpec 与 Superpowers，并保存五阶段状态。0.4.0 主要处理两类问题。

第一类来自现有运行时：

- Windows 需要 Git Bash 或 WSL；
- `/comet` 依靠 Agent 读取自然语言规则选择路由，缺少结构化诊断记录；
- `.comet.yaml` 同时保存用户可读字段和机器运行状态。

第二类是尚未提供的产品入口：

- 缺少创建、组合和分发自定义 Skill 的入口；
- 缺少统一的 Skill 评估命令和发布证据；
- change 的产物和状态需要分别查看多个目录。

0.4.0-beta.1 重写运行时，并增加 Skill Creator、Eval 和 Dashboard。完整功能清单见 [Changelog](/zh/changelog)，本文记录各项改动的背景和边界。

## 一、Node 运行时

0.3.9 的状态机、阶段守卫、交接和归档逻辑由 7 个 Bash 脚本承担。Windows 需要 Git Bash 或 WSL，同时需要处理路径转义、CRLF、shell 差异和可执行权限。

0.4.0 将脚本改写为 Node `.mjs` 启动器，由共享的 TypeScript 运行时（`domains/comet-classic/`）提供实现。每个 `.mjs` 都是 esbuild 生成的单文件包，`yaml` 等依赖一并内联。

这是 0.4.0 最大的重构，也直接解决了 Windows 用户需要 Git Bash 或 WSL 的限制。

| 动机 | 0.3.9 | 0.4.0 |
| --- | --- | --- |
| 跨平台 | Windows 需要 Git Bash/WSL | 仅需 Node.js 20+ |
| 路径可靠性 | shell 转义、CRLF、可执行位 | Node 原生处理 |
| 实现一致性 | 散落的 shell 逻辑 | 单一 TypeScript 转移语义表 |

`comet-state transition` 和 `comet-guard --apply` 共享同一份 `classic-transitions.ts`，避免两条推进路径使用不同的阶段条件。

<Info>
  <code>/comet*</code> 入口保持不变；这次修改替换底层运行时，不要求用户改用新的工作流命令。
</Info>

## 二、路由上下文（Routing Context）

0.3.9 的 `/comet` 入口根据 Skill 正文中的自然语言规则选择 `full`、`hotfix` 或 `tweak`，没有保存分类信号和评分结果。

0.4.0 将请求转换为结构化路由上下文（实现类型名为 `CometIntentFrame`），再由运行时按固定优先级重新评分。

路由上下文保存置信度、风险信号和仓库状态。运行时重新评分后，如结果与 Agent 建议不一致，会将分歧写入诊断日志。

风险信号优先于用户指定的轻量预设。例如，请求指定 hotfix 但命中 `public_api_change` 时，运行时会暂停并请你确认是否继续。

详见[意图识别与路由](/zh/concepts/intent-routing)。

## 三、Skill Creator

下面三节介绍 0.4.0 新增的产品入口。

0.3.9 只提供预置的 `/comet` 系列命令，没有创建、组合和分发自定义工作流 Skill 的入口。

0.4.0 增加 `/comet-any`，用于创建、优化或组合 Skill，并生成包含运行、评审和分发产物的 Bundle。

一个可评估、评审和分发的 Skill 包包含以下内容：

1. **确定性骨架**——路由表、运行时脚本、manifest 必须可复现，不能每次生成都变；
2. **可评审的创作内容**——入口的决策核心、节点的指导是 LLM 写的，但必须能被人审，并有证据支撑评审；
3. **发布证据链**——eval 证据绑定当前 draft hash，人工批准绑定当前 hash，分发前强制预览。

`/comet-any` 生成以下 Skill Bundle：

```text
<bundle-draft>/
  bundle.yaml
  skills/<entry-skill>/
    SKILL.md                    # 用户调用的入口
    comet/
      skill.yaml                # 内部运行计划
      guardrails.yaml           # 由偏好和风险策略生成的约束
      checks.yaml               # 运行完成度检查
      eval.yaml                 # Eval manifest
    reference/
      resolved-skills.json      # 真实 Skill 来源、hash、选择证据
      composition-report.md     # 组合方案、偏离解释、风险
    scripts/                    # 稳定推进流程的控制面
  rules/
  hooks/
```

常用流程如下：

```text
/comet-any 创建 -> comet eval 验证 -> comet creator status/next
  -> comet publish review/approve/run -> comet publish distribute --preview
  -> comet publish distribute
```

`/comet-any` 还会读取项目级偏好（`.comet/skill-preferences.yaml`），包括优先复用的 Skill、缺失和歧义策略，以及 scripts/hooks 策略。写入 Bundle draft 前会展示组合方案并等待确认。

详见[Skill Creator 完整流程](/zh/skill-creator/workflow)。

## 四、Eval

`/comet-any` 生成 Skill 后，还需要检查它在任务中的行为。`comet eval` 运行任务校验器，生成 rubric、pass 指标和失败归因，并将结果绑定到发布候选的 hash。

0.3.9 没有统一的 Skill 评估命令，也没有与发布状态绑定的量化结果。

0.4.0 的 `comet eval` 使用 pytest 驱动任务，并保存可比较的检查结果和诊断指标。

评估结果会进入发布门禁：缺少当前 draft hash 的 eval 证据、eval 失败或证据对应旧 hash 时，均不能 publish。rubric 和失败归因用于确定后续修改范围。

eval 用两个关键指标区分“能力”和“可靠性”：

| 指标 | 含义 | 回答的问题 |
| --- | --- | --- |
| `pass@k`（能力上限） | k 次独立尝试里**至少成功一次**的概率 | "这个 Skill 能不能做到？" |
| `pass^k`（可靠性下限） | k 次独立尝试里**全部成功**的概率 | "能不能每次都做到？" |

两个指标一起使用，可以区分“多次尝试中能够成功”和“每次尝试都成功”。`pass@k − pass^k` 的差值用于观察重复运行差异，但仍需结合任务数和检查结果解释。

为了让不同类型的 Skill 按匹配的维度打分，eval 提供三套 rubric：

| Profile | 用途 | 维度 |
| --- | --- | --- |
| `generic` | 任意 Skill | 7 维度（完成度、Skill 调用、产物、指令遵循、交互、效率、安全边界）|
| `comet-workflow` | Comet 工作流 | 9 维度（含主流程证据、阶段守卫、规格漂移、可恢复性）|
| `authoring-skill` | `/comet-any` 生成包 | 11 维度 |

失败时，eval 还会做**失败归因**，把失败分到四类，告诉你下一步该修什么：

- `harness`——多半是 eval 环境、Docker、路径问题；
- `workflow`——多半是 Skill 执行流程没达到预期（**该修 Skill**）；
- `task`——多半是任务定义、验证条件问题；
- `model`——多半是模型行为、工具使用不稳定。

普通用户两步走：先用 `--collect` 低成本地做发现性预检，再用 `--html` 跑真实评估，拿到可浏览的报告。

```bash
comet eval ./generated-skill/comet/eval.yaml --collect
comet eval ./generated-skill/comet/eval.yaml --html
```

详见[评估任意 Skill](/zh/eval/quickstart)。

## 五、Dashboard：查看产物和状态

一次 change 会在 `openspec/changes/`、`docs/superpowers/` 和 `.comet/` 中生成 proposal、design、tasks、plan、verifyReport、handoff 和 checkpoint。`comet dashboard` 在本地只读界面中汇总这些产物和状态。

0.3.9 需要逐个打开 YAML 和关联目录查看 change 状态。

0.4.0 的 `comet dashboard` 启动本地只读界面，集中显示每个 change 的产物、阶段和检查结果。

dashboard 将产物按来源分成三组，并显示已生成、未生成或不适用：

| 分组 | 产物 | 来源 |
| --- | --- | --- |
| **OpenSpec** | proposal、design、tasks、deltaSpec | 变更目录内的规格文件 |
| **Superpowers** | designDoc、plan、verifyReport | `docs/superpowers/` 下的设计/计划/审查证据 |
| **Comet** | `.comet.yaml`、handoff、checkpoint、brainstorm、subagentProgress | `.comet/` 里的中间产物 |

每个产物会标记为**已生成**（可预览）、**未生成**（预期但还没创建）或**无需生成**（当前模式或阶段不适用）。

除了产物，dashboard 还在同一块面板上呈现阶段进度、任务进度、verify 状态、下一步动作建议、风险信号和 Git 上下文。同一份快照还能被脚本和 CI 消费：

```bash
comet dashboard . --json          # 输出一次快照，用于脚本/CI
comet dashboard . --port 4399     # 指定端口
GET /api/dashboard                # HTTP 接口，同一份快照
```

eval、dashboard、`comet status` 和 `comet doctor` 读取同一套运行时状态与检查结果，避免界面和命令使用不同判断口径。

详见 [Dashboard 概览](/zh/dashboard/overview)。

## 六、状态分层

0.3.9 的 `.comet.yaml` 同时保存用户可读的工作流字段和机器管理的运行态检查点。

0.4.0 将每个 change 的状态拆成三层：

| 文件 | 归属 | 内容 |
| --- | --- | --- |
| `.comet.yaml` | 用户可读 | 工作流投影（`workflow`/`phase` 等）+ `run_id` 链接 |
| `.comet/run-state.json` | 机器管理 | 运行态检查点：当前步骤、迭代、待处理动作 |
| `.comet/state-events.jsonl` | 追加式审计 | 成功转移的完整记录 |

三层文件分别承担用户投影、机器状态和审计记录。机器字段由运行时原子写入，`comet-state set` 会拒绝直接修改；审计日志只追加不覆盖。旧 change 首次读取时自动迁移。

## 版本范围

0.4.0 的范围从 Classic 五阶段运行时扩展到 Skill 创建、评估和状态查看：

- `/comet-any` 生成可评估和分发的 Skill 包；
- `comet eval` 生成评估结果并接入发布门禁；
- `comet dashboard` 汇总 change 的产物和状态；
- Node 运行时提供跨平台命令；
- 路由上下文记录分类依据；
- 分层状态支持恢复和审计。

这些入口共享 Bundle hash、评估证据和运行时状态，但各自承担不同职责。后续版本的行为以当前文档和 Changelog 为准。

> 想看完整的逐条变更，见 [0.4.0-beta.1 changelog](/zh/changelog)。
