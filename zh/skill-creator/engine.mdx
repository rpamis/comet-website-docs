入口 Skill 告诉 Agent 怎样完成业务工作。SDK Run 保存实际步骤、动作、决定和结果；平台集成将当前应用与文件工具事件关联起来。

## 业务内容与执行协议

Agent 根据目标写完整 `SKILL.md` 与业务 Rule，例如输入如何整理、阶段必须产出哪些文件、如何检查结论和来源。

SDK 在这些正文后追加执行协议和通用保护规则，并装配固定的 Runtime。协议规范了如何读取当前运行记录（Run）、获取待执行动作、回传执行结果以及等待用户确认。Prompt 中写了“已经批准”并不能替代用户实际的交互确认（Wait）。

## Rule / Hook 的作用

分发时会安装平台共享的 Rule/Hook，保留无关的用户配置。支持 Hook 的平台会把可归属到当前工作流的文件写入操作交给当前工作流检查；平台不支持或需要激活的能力会在预览中说明。

共享保护规则处理当前动作、批准与写入范围。它不会仅凭 Skill 文字自动推导“报告来源必须齐全”这样的业务条件，也不构成操作系统沙箱。

## 业务验证器的作用

阶段产物契约要求真实文件、内容、结构和摘要。业务验证器进一步检查特定业务条件。它们由创作 Agent 编写并固定，Creator 用正常和异常样例验收。

```text
执行 Skill → 检查实际产物 → 检查业务条件 → 接受当前结果 → 允许依赖工作继续
```

缺少文件、业务校验失败，或完成后文件发生变动时，不能沿原证据进入下游工作。详细配置见 [阶段产物与业务验收](/zh/sdk/artifact-validation)。

## 宿主执行与未知结果

宿主必须实际加载声明的 Skill、完成需要的交接，并按当前授权调用工具。能力缺失时不能把步骤静默删掉或冒称已经执行。

派发后回传中断时，保留原 Action、attempt 和领取凭据，先核对真实结果。文件已经写入、消息已经发送或外部发布已经发生时，重复执行可能产生额外副作用。

## Dashboard 只提供观测，不推进流程

Dashboard 展示保存的步骤、决定、执行尝试、产物和证据。它不会自行批准提案或推进 Runtime。界面中的决定选项用于说明当前等待点支持哪些决定，实际决定仍由原宿主获取并提交。
