Comet Any 将多步业务流程打包成完整的 SDK Skill 应用。应用不仅包含可读的入口说明和业务规则，还包含负责管理步骤执行、用户审批、阶段产物和断点恢复的 Runtime。

## 谁负责什么

| 参与者 | 负责的内容 |
| --- | --- |
| 创作 Agent | 读取本地已有 Skill，编写完整入口、业务 Rule、执行逻辑、业务验证器和验收用例。 |
| SDK | 编排工作流、锁定版本与依赖、补充执行协议，保存运行记录并检查动作、审批和产物。 |
| Agent 平台 | 加载 Skill、完成任务交接、调用工具、向用户发起确认并核对外部结果。 |
| 分发命令 | 预览并安装平台 Skill 入口、共享 Rule/Hook 以及 Runtime 依赖。 |

SDK 的通用执行协议不能代替业务规则。例如“报告必须包含来源”既要写进业务规则，也要落实到业务验证器中，不能只靠一句提示语就假定系统会自动拦截。

## 应用由什么组成

完整应用包以 `application.json` 为入口，锁定应用标识、版本、入口 Skill、执行模块和所依赖的已有 Skill。创作方案必须包含完整的 `SKILL.md` 和 `rules/workflow-guard.md`，也可以附带引用的 Markdown 参考文件。

平台安装的入口指向这份锁定版本的应用包。安装成功不等于验证通过：Comet 会把文件安装、Skill 加载、动作完成、本地自动验收和平台实测的结果分开记录，不能互相替代。

## 三种组合类型

**Native 扩展**在 Native 流程允许的节点（普通候选、父任务、子任务或集成检查通过后）追加自定义工作，同时保留原有的 Builder、独立 Verifier、用户批准和归档约束。

**Classic 组合**基于 Classic 的 `full`、`hotfix`、`tweak` 三种预设流程，在保留必要文档和阶段确认的前提下增加或替换 Skill。

**独立应用**自行定义工作流图、Schema、状态、分支、并行和子流程，验收规则也由应用自身定义。例如用户拒绝发布本地周报时，流程会沿拒绝分支正常结束，但不会生成最终发布文件。

三种类型的完整教程见 [定制 Native](/zh/skill-creator/native-customization)、[定制 Classic](/zh/skill-creator/classic-customization) 和 [组合任意 Skill](/zh/skill-creator/standalone-composition)。

## 确认后锁定哪些内容

确认前会展示完整规则、执行步骤、依赖清单、输出条件、失败处理和能力限制。用户批准针对的是整份方案，不能用内容摘要或旧版本的批准代替。

编译后会锁定应用内容和依赖版本。如果文件或依赖中途被修改，流程不会直接继续；需要保留当前记录并恢复原内容，或修订方案后重新确认。

## 阶段文件如何拦截后续步骤

应用会声明每个步骤必需的输出文件和内容要求，并由业务验证器核对业务条件。SDK 会检查文件是否存在、内容校验摘要是否一致；只要文件缺失、业务校验失败或文件后续被改动，阶段结果就不能作为通过依据，下游步骤也无法继续。

完整说明见 [阶段产物与业务验收](/zh/sdk/artifact-validation)。日常使用从 [快速上手](/zh/skill-creator/getting-started) 开始；需要自行接入 Agent 平台时阅读 [SDK 总览](/zh/sdk/overview)。
