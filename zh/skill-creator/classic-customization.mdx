---
title: '用 Any 定制 Classic 工作流'
description: '选择 full、hotfix 或 tweak，用团队 Skill 替换阶段执行，并追加有产物和恢复路径的检查。'
---

你的团队使用 Classic 的 Spec 流程，但已有自己的 API 设计 Skill 和兼容性审查 Skill。用 `/comet-any` 创建 Classic 组合应用，让团队 Skill 执行指定工作，同时保留 Classic 的阶段文档、真实检查、用户批准和归档要求。

本教程创建一个 full 应用：用团队 Skill 执行 Design，并在 Verify 的检查通过后追加接口兼容性审查。应用安装完成后，用一个小接口改动验证它。

## 1. 选择基础流程

| 流程   | 适合的任务                                   | 定制前确认什么                                          |
| ------ | -------------------------------------------- | ------------------------------------------------------- |
| full   | 需要完整需求、设计、实现、验证和归档的功能。 | 哪个阶段执行 Skill 被替换，原阶段输入和文档要求是什么。 |
| hotfix | 范围明确的局部缺陷。                         | 是否仍适合快速修复，新增工作放在哪个允许的检查位置。    |
| tweak  | 单个 change 的轻量调整。                     | 新要求是否已经超出轻量调整，应否改用完整流程。          |

替换针对执行 Skill。领域机器检查、用户批准和归档步骤不能作为普通 Skill 替换。追加步骤也只能放在原流程允许的检查位置，不能仅靠入口文字把 Verify 或 Archive 移走。

本例选择 full。若希望保留已有 Design Skill、只增加设计审查，请明确说“追加审查”，避免把整个设计执行绑定替换掉。

## 2. 准备设计和审查 Skill

先安装 Comet 并运行 `comet doctor`。Creator 使用 Codex 或 Claude Code 的实际加载与交接能力。

本例使用项目内的两个目录：

```text
team-skills/
  api-design/
    SKILL.md
    references/api-conventions.md
  api-compatibility-review/
    SKILL.md
```

替换为你的实际路径。设计 Skill 需要读懂当前需求、已有接口和项目规范，生成 Classic 所需的实际设计文档。兼容性审查应能比较旧、新接口行为，说明调用方影响，并产生可验证的报告。

如果现有 Skill 只会输出聊天总结，先要求 Agent 说明如何适配阶段文件。仅把它改名为“Classic Design”不能使输出自动符合阶段要求。

## 3. 提交定制目标

在项目 Agent 会话中输入：

```text
/comet-any
把本次创作命名为 classic-api-review，创建 Classic full 组合应用。
读取 ./team-skills/api-design 和 ./team-skills/api-compatibility-review 的真实内容。
用团队 API 设计 Skill 替换 full 流程中的 Design 执行 Skill。
它必须读取当前需求和已有接口，产出原 Design 阶段要求的完整文档。
在 Verify 的实际检查通过后追加兼容性审查，再进入原 Archive 路径。
生成 reports/api-compatibility.md，包含“接口变化”“调用方影响”“验证依据”“结论”。
行为变化必须逐项说明兼容性；未处理的破坏性变化或缺少验证依据时不通过。
失败时保留实现和报告，修复后重新执行受影响检查与兼容性审查。
保留原阶段用户批准、真实检查和归档条件，不代替我提交或推送 Git。
先展示完整方案和正常、异常验收样例，安装到 Codex 项目前再单独请我确认。
```

Agent 会根据 full 的实际步骤选择执行绑定和允许的检查位置。你无需手写步骤 ID，但需要确认“替换 Design 执行”与“新增兼容性检查”是两项不同的工作。

## 4. 阅读替换前后的职责

| 原工作                  | 定制后谁执行                     | 保留的要求                                 |
| ----------------------- | -------------------------------- | ------------------------------------------ |
| Design 阶段的设计编写。 | 团队 API 设计 Skill。            | 当前需求输入、必要设计文档和用户确认。     |
| Build 的实现与检查。    | 原 Classic 执行与检查入口。      | 实际代码、检查计划、真实命令与当轮证据。   |
| Verify 的验证。         | 原验证步骤，再追加兼容性 Skill。 | 原验证报告与检查，以及新增审查的真实产物。 |
| Archive 与交付。        | 原 Classic 流程和执行宿主。      | 当前批准、归档证据及实际 Git 交付授权。    |

确认前让 Agent 展示设计 Skill 接收哪些输入、生成哪些文件，以及新增审查读取哪个已通过的验证结果。产物路径按实际方案确定，不应写进 Runtime 控制目录或覆盖核心状态文件。

想进一步修改阶段执行方式，可以要求设计 Skill 增加接口版本策略、错误码规范等指导。涉及新增职责、产物或失败条件时，把变化放进完整方案重新确认，不能只改一段入口说明。

## 5. 让异常样例验证业务检查

要求临时项目覆盖以下场景：

| 场景                                             | 预期行为                                     |
| ------------------------------------------------ | -------------------------------------------- |
| 新增可选参数，旧调用仍通过，报告有检查依据。     | 兼容性审查通过。                             |
| 报告四节完整，但删除旧字段且没有迁移或验证依据。 | 业务检查拒绝，不能因格式正确而通过。         |
| 必需设计或审查文件缺失。                         | 阶段产物检查拒绝。                           |
| 审查后接口或检查输入发生变化。                   | 原证据不能证明当前结果，需要重验受影响工作。 |

经典流程的原检查不会被新增报告替代。兼容性 Skill 回报成功，也不能把失败的测试命令变成通过。

本地验收之后可选择模型 Eval，关注团队设计 Skill 是否实际生成阶段文件、审查是否识别破坏性变化，以及失败后能否继续修复。跳过模型 Eval 会保留跳过状态，见 [创作、验收与安装](/zh/skill-creator/workflow)。

## 6. 安装后跑一个接口任务

检查完整包导出目录、平台入口、固定依赖和 Rule/Hook，确认安装当前预览。应用与默认 Classic 入口分开使用；入口名称以安装结果为准。

加载新应用的入口 Skill，提出：

```text
使用已安装的 classic-api-review 应用，为列表接口增加可选分页参数。
现有调用方不传参数时仍保持原行为。
设计文档需说明默认值，验证报告与兼容性报告需包含旧调用和新调用的实际检查依据。
```

在 Design 阶段核对团队 Skill 的实际文档，再提交当前设计决定。Build 和 Verify 使用真实命令；兼容性报告不通过时先修复并重验，不能为了进入 Archive 填写“已完成”。

最后仍需确认实际交付范围。批准本地归档、提交、推送或 PR 是不同选择，应用创作或安装的批准不替代业务任务的交付批准。

## 7. 恢复与修改应用

创作中断时读取原记录：

```bash
comet creator status classic-api-review --project . --json
comet creator next classic-api-review --project . --json
```

如果中断的是已经安装应用的业务任务，继续原应用 Run，而非再次执行 Creator 创建一个同名流程。执行结果未知时核对原操作，详见 [恢复与未知结果](/zh/sdk/recovery)。

以后更换团队设计 Skill 或改审查条件时，提供原应用包、明确新增要求，并重新准备和确认版本。升级保留活动 Run 使用的旧版本。hotfix、tweak 要改成完整流程时，要求 Agent 使用领域允许的升级路径，不直接改状态文件里的 profile。
