---
title: '用 Comet Any 定制 Classic 工作流'
description: '基于 full、hotfix 或 tweak 预设流程，用团队 Skill 替换阶段执行，并追加带产物和恢复路径的检查。'
---

你的团队使用 Classic 的 Spec 流程，同时已有自己的 API 设计 Skill 和兼容性审查 Skill。用 `/comet-any` 可以创建 Classic 组合应用，让团队 Skill 接管指定阶段的执行工作，同时保留 Classic 原有的阶段文档、自动检查、用户批准和归档要求。

本教程创建一个 `full` 应用：用团队 Skill 执行 Design 阶段，并在 Verify 检查通过后追加接口兼容性审查。安装完成后，用一个小型接口改动来试运行。

## 1. 选择基础流程

| 流程 | 适合的任务 | 定制前先确认 |
| --- | --- | --- |
| `full` | 需要完整需求、设计、实现、验证和归档的功能。 | 要替换哪个阶段的执行 Skill，原阶段的输入和文档要求是什么。 |
| `hotfix` | 范围明确的局部缺陷。 | 是否仍适合快速修复，新增检查放在哪个允许的节点。 |
| `tweak` | 单个 change 的轻量调整。 | 新增要求是否已超出轻量调整范围，是否应改用完整流程。 |

替换仅针对各阶段的执行 Skill。内置的自动检查、用户确认和自动归档步骤不能被替换。追加的检查也只能挂在原流程允许的节点，不能仅靠修改入口文字把 Verify 或 Archive 删掉。

本例选择 `full`。如果想保留原有 Design Skill、只增加设计审查，请在描述中明确写“追加审查”，避免把整个设计阶段的执行 Skill 替换掉。

### 哪些阶段的执行 Skill 可以定制

你只需说明要改哪个阶段以及想怎么做，Comet Any 会整理对应步骤、替换关系和输入输出要求。如果一个阶段包含多个执行步骤，方案会分别列出，不会只替换其中一个就当成整个阶段已替换。

| 执行位置 | 适用流程 | 可以定制什么 | 必须保留什么 |
| --- | --- | --- | --- |
| Open 的需求整理 | `full`、`hotfix`、`tweak` | 替换需求调查、问题澄清和文档编写的 Skill。 | 原范围要求、必要文档和对应的用户确认。 |
| Design 的上下文衔接与设计文档 | `full`；轻量流程升级到 `full` 后 | 用团队 Skill 编写架构、接口或数据设计。 | 原交接输入、设计产物、检查与批准。 |
| Build 的配置与计划 | `full`；轻量流程升级到 `full` 后 | 定制实现指导和任务计划编写。 | 原计划要求和计划证据检查。 |
| Build 的实现执行 | `full`、`hotfix`、`tweak` | 换用团队实现或测试先行的 Skill。 | 代码改动、允许的工作范围和自动检查。 |
| Verify 的验证报告执行 | `full`、`hotfix`、`tweak` | 换用领域验证 Skill，组织测试和报告。 | 原验证报告要求与命令执行结果，不替换内置自动验收。 |
| Archive 的交付提案与执行指导 | `full`、`hotfix`、`tweak` | 定制交付说明、提交摘要和按批准执行交付的 Skill。 | 当前交付批准、归档预检查、自动归档和交付结果核验。 |

### 哪些节点可以追加检查

| 原流程中的节点 | 可以追加什么 | 适用范围与限制 |
| --- | --- | --- |
| Open 产物检查通过后 | 需求完整性、业务约束或领域审查。 | 所选流程；原用户确认仍按该流程处理。 |
| 已批准 Open 产物复核通过后 | 进入设计前的需求审查。 | `full`；不替代对已确认内容的复核。 |
| Design 文档检查通过后 | 架构、接口、安全或可维护性审查。 | `full`，或轻量流程升级后的 `full` 路径。 |
| Build 计划检查通过后 | 任务覆盖、依赖或实现范围审查。 | `full`，或升级后的 `full` 路径。 |
| Build 自动检查通过后 | 代码质量、性能或额外回归检查。 | `full`、`hotfix`、`tweak`；原检查失败时不能用扩展通过来绕过。 |
| Verify 自动检查通过后 | 接口兼容性、合规或交付前业务审查。 | `full`、`hotfix`、`tweak`；通过后继续进入原 Archive 条件。 |
| 同一检查节点内的多个扩展 | 调整新增检查的先后顺序。 | 不能跨阶段移动步骤，也不能改变原有内置检查的顺序。 |

新增检查都要声明输出文件、通过条件和失败处理方式。需要同时定制多个阶段时，可以组合多项替换与追加；Comet Any 会列出每项的执行位置及与原流程的关系，由你确认后再构建。

## 2. 准备设计和审查 Skill

先安装 Comet 并运行 `comet doctor`。Comet Any 需要运行在支持加载 Skill 和任务交接的平台上（目前支持 Codex 和 Claude Code）。

本例假设项目内有以下两个目录：

```text
team-skills/
  api-design/
    SKILL.md
    references/api-conventions.md
  api-compatibility-review/
    SKILL.md
```

使用时替换为你的项目路径。设计 Skill 需要读懂当前需求、已有接口和项目规范，生成 Classic 所需的完整设计文档；兼容性审查 Skill 应能对比新旧接口行为、说明对调用方的影响，并输出可校验的报告。

如果现有 Skill 只会在聊天中给出文字总结，请先让 Agent 说明如何适配成阶段输出文件。仅仅把它改名为“Classic Design”，输出并不会自动满足阶段要求。

## 3. 提交定制目标

在项目 Agent 会话中输入：

```text
/comet-any
把本次创作命名为 classic-api-review，创建 Classic full 组合应用。
读取 ./team-skills/api-design 和 ./team-skills/api-compatibility-review 的内容。
用团队 API 设计 Skill 替换 full 流程中的 Design 执行 Skill。
它必须读取当前需求和已有接口，产出原 Design 阶段要求的完整文档。
在 Verify 的检查通过后追加兼容性审查，再进入原 Archive 路径。
生成 reports/api-compatibility.md，包含“接口变化”“调用方影响”“验证依据”“结论”。
行为变化必须逐项说明兼容性；未处理的破坏性变化或缺少验证依据时不通过。
失败时保留实现和报告，修复后重新执行受影响检查与兼容性审查。
保留原阶段用户批准、自动检查和归档条件，不代替我提交或推送 Git。
先展示完整方案和正常、异常验收样例，安装到 Codex 项目前再单独请我确认。
```

Agent 会根据 `full` 流程的步骤结构选择替换位置和扩展节点。你不需要手写步骤 ID，但要确认“替换 Design 执行”与“追加兼容性检查”是两项分开的工作。

## 4. 核对定制前后的职责

| 原工作 | 定制后谁执行 | 保留的要求 |
| --- | --- | --- |
| Design 阶段的设计编写 | 团队 API 设计 Skill。 | 当前需求输入、必要设计文档和用户确认。 |
| Build 的实现与检查 | 原 Classic 执行与检查流程。 | 代码改动、检查计划、命令运行结果与当轮证据。 |
| Verify 的验证 | 原验证步骤，通过后追加兼容性审查 Skill。 | 原验证报告与检查，以及新增审查的输出文件。 |
| Archive 与交付 | 原 Classic 流程和 Agent 平台。 | 当前批准、归档证据以及 Git 提交或推送的明确批准。 |

确认前让 Agent 展示设计 Skill 接收哪些输入、生成哪些文件，以及新增审查会读取哪一份已通过的验证结果。输出文件路径按方案约定放在项目目录内，不要写入 Runtime 控制目录或覆盖核心状态文件。

如果想进一步细化设计阶段的执行方式，可以要求设计 Skill 增加接口版本策略、错误码规范等指导。只要涉及新增职责、输出文件或失败条件，就需要放进完整方案重新确认，不能只改几句入口说明。

## 5. 用异常样例验证业务检查

要求在临时项目中至少覆盖以下验证场景：

| 场景 | 预期行为 |
| --- | --- |
| 新增可选参数，旧调用仍通过，报告有检查依据。 | 兼容性审查通过。 |
| 报告四节齐全，但删除旧字段且没有迁移或验证依据。 | 业务检查拒绝，不能因格式完整而通过。 |
| 必需的设计或审查文件缺失。 | 阶段产物检查拒绝。 |
| 审查完成后接口代码或检查输入发生变化。 | 原证据不再有效，需要重验受影响步骤。 |

新增报告不能替代 Classic 的原有检查。即使兼容性 Skill 返回通过，也不能把失败的测试命令变成通过。

本地验收通过后可选择运行模型 Eval，重点观察团队设计 Skill 能否按要求生成阶段文件、审查能否识别破坏性变化，以及失败后能否顺利修复。如果选择跳过模型 Eval，系统会记录跳过状态，见 [创作、验收与安装](/zh/skill-creator/workflow)。

## 6. 安装后试跑一个接口任务

核对完整应用包的导出目录、平台入口、已锁定的依赖和共享 Rule/Hook，确认安装预览。定制应用与默认 Classic 入口分开使用，入口名称以安装结果为准。

加载新应用的入口 Skill，发起一个小型接口改动：

```text
使用已安装的 classic-api-review 应用，为列表接口增加可选分页参数。
现有调用方不传参数时仍保持原行为。
设计文档需说明默认值，验证报告与兼容性报告需包含旧调用和新调用的检查依据。
```

在 Design 阶段核对团队 Skill 生成的设计文档后再确认。Build 和 Verify 阶段执行真实测试命令；兼容性审查不通过时先修复并重验，不能为了进入 Archive 直接标记“已完成”。

最后仍需确认交付范围。本地归档、Git 提交、推送或创建 PR 是不同的操作选项，创作或安装应用时的确认不能代替业务任务的交付批准。

## 7. 恢复与升级应用

创作中途中断时，用原名称查看状态并继续：

```bash
comet creator status classic-api-review --project . --json
comet creator next classic-api-review --project . --json
```

如果中断的是已安装应用的业务任务，请继续原来的应用运行记录（Run），不要重新运行 `comet creator` 新建同名流程。遇到执行结果未回传时先核对原操作，详见 [恢复与未知结果](/zh/sdk/recovery)。

以后要更换团队设计 Skill 或修改审查条件时，向 Comet Any 提供原应用包和新的改动要求，重新生成并确认新版本。升级不会影响正在运行中的旧任务。如果想把进行中的 `hotfix` 或 `tweak` 升级为 `full` 流程，请让 Agent 按正常升级路径处理，不要手动修改状态文件里的流程类型。
