<Tip>
  创建、优化或组合 Skill 时，先在 Agent 里调用 <code>/comet-any</code> 并按提示确认。
  评估、发布、分发和恢复会由流程引导。
  除非你在做排障或自动化集成，否则不需要先理解底层命令、内部状态和生成物结构。
</Tip>

本页覆盖 `/comet-any` 最常见的四类问题：创建流程、偏好配置、发布分发和中断恢复。

## 基础概念

<AccordionGroup>
  <Accordion title="/comet-any 和 /comet 有什么区别">
    `/comet` 是经典 Spec 模式入口，用来完成一个项目变更。`/comet-any` 是 Skill Creator，用来创建、优化或整理可复用 Skill。

    如果你想做产品功能、修 bug 或改项目代码，用 `/comet`。如果你想把某套工作流沉淀成可复用 Skill，或在 `/comet` 五阶段基础上增加团队规则，用 `/comet-any`。
  </Accordion>

  <Accordion title="三种起点怎么选">
    按你的目标选：

    - **基于 Comet 现有 Skill 的五阶段定制**：想沿用 `/comet` 的五阶段，只增加组件库、审查规则或团队约束。
    - **创建全新 workflow Skill**：想把一套新流程做成可复用 Skill。
    - **整理已有 Skill**：已经有一个 Skill，但想补齐评估、发布、恢复和分发能力。

    不确定时，先描述目标。`/comet-any` 会在方案确认页说明推荐起点。
  </Accordion>

  <Accordion title="我需要理解 Workflow Node、Output Schema 这些词吗">
    普通使用不需要。你只需关注方案确认页里的每一步做什么、会调用哪些 Skill、哪些能力会被增加或关闭。

    这些词是进阶设计和排障用的。如果你要替换某个阶段的实现、做全新工作流，或审查生成物为什么能恢复和验证，再看[Skill Creator 概览](/zh/skill-creator/overview)。
  </Accordion>

  <Accordion title="为什么不是只生成一个 SKILL.md">
    轻量单步 Skill 可以只靠一个 `SKILL.md`。
    但多步骤 Skill 往往还要具备恢复状态、验证证据、发布门禁、脚本契约和分发预览。
    `/comet-any` 会按这些需求生成完整包，让 Skill 可以评估、评审、发布和恢复。

    你不需要手工维护这些内部文件。正常入口仍然是 `/comet-any`、`comet creator status/next` 和 `comet publish`。
  </Accordion>

  <Accordion title="确认页上的保留/新增/替换/关闭是什么意思">
    这是 `/comet-any` 在生成前给你的变更摘要：

    - **保留**：继续使用原来的流程步骤。
    - **新增**：在某一步里要求额外调用指定 Skill。
    - **替换**：替换允许被替换的产出步骤。
    - **关闭**：关闭可选步骤，例如某些审查环节。

    基于 `/comet` 定制时，核心控制步骤不能随便替换。方案确认页会把能做和不能做的部分列出来。
  </Accordion>
</AccordionGroup>

## 偏好与方案

<AccordionGroup>
  <Accordion title=".comet/skill-preferences.yaml 是什么">
    它是项目级 Skill 偏好文件，用来告诉 `/comet-any` 优先复用哪些 Skill、哪些 Skill 必须满足，以及遇到缺失、歧义、脚本或 hooks 时怎么处理。

    第一次使用时你可以不写。`/comet-any` 会扫描当前平台的 Skill，并建议是否保存默认偏好。想手写时再看[Skill 偏好与真实来源](/zh/skill-creator/preferences)。
  </Accordion>

  <Accordion title="advisory 和 strict 模式有什么区别">
    `advisory` 是默认模式。
    它会尽量按偏好组合，也允许为了目标补充额外 Skill，并给出偏离理由。

    `strict` 适合团队标准化场景。
    required Skill 缺失、来源歧义或策略禁止的 scripts/hooks 都会触发阻塞，必须由你明确处理。
  </Accordion>

  <Accordion title="为什么方案要等我确认才生成">
    因为 `/comet-any` 生成的是可复用 Skill，不是一次性回答。
    它会先展示方案确认页，让你检查起点、复用 Skill、缺失或歧义候选、可执行能力披露和将生成文件。

    你确认后才会写入草稿。选择修改方案或取消时，不会写入生成状态。
  </Accordion>

  <Accordion title="候选 Skill 缺失或有多个来源怎么办">
    `/comet-any` 会暂停询问你，不会静默忽略，也不会替你选来源。

    你可以选择明确来源、移除缺失项、更新偏好，或在允许的情况下说明为什么忽略。处理完之后，它才会继续生成方案。
  </Accordion>

  <Accordion title="我能指定必须使用某个 Skill 吗">
    可以。你可以在目标描述里直接说，也可以把它写进 `.comet/skill-preferences.yaml` 的 `require`。

    如果这个 Skill 找不到或有多个来源，`/comet-any` 会停下来让你确认。它必须读取真实 `SKILL.md` 和相关引用，不能只按名字猜能力。
  </Accordion>
</AccordionGroup>

## 评估与发布

<AccordionGroup>
  <Accordion title="生成后会自动分发到平台吗">
    不会。发布后 `/comet-any` 会询问你是否分发，并且必须先展示 preview。只有你确认 preview 后，才会真正写入目标平台。
  </Accordion>

  <Accordion title="Eval 通过了就能直接发布吗">
    不能。Eval 通过只是发布前证据。还需要当前草稿 hash 匹配、人工批准通过，并且目标平台能力满足要求。

    最简单的判断方式是运行 `comet creator next <name>` 看下一步，或运行 `comet creator status <name>` 看完整 readiness、blockers 和 evidence。
  </Accordion>

  <Accordion title="为什么发布被阻塞了">
    常见原因包括：候选 Skill 还没解决、方案还没确认、当前版本没有通过 eval、人工批准缺失、生成物不完整、平台能力不满足，或可执行能力还没披露确认。

    不需要手工判断内部状态。先看 `comet creator next <name>`，它会给出推荐下一步。需要完整上下文时再看 `comet creator status <name>`。阻塞码表见[发布和分发 Skill](/zh/skill-creator/publishing#阻塞码-blocker-codes)。
  </Accordion>

  <Accordion title="分发前为什么必须先 preview">
    preview 会展示计划写入文件、目标平台不支持能力、脚本或 hooks 等可执行披露。
    同时会明确显示 `No files were written`。

    这一步是防误写的硬门禁。确认 preview 结果后，才能执行真实分发。
  </Accordion>

  <Accordion title="运行 eval 需要什么环境">
    需要 `uv`、Python 3.11+、Docker，以及 `ANTHROPIC_API_KEY`（或 `ANTHROPIC_AUTH_TOKEN`）。核心 Comet 运行时不需要这些，只有 `comet eval` 需要。

    完整准备步骤见[评估快速上手 · 你要准备什么](/zh/eval/quickstart#你要准备什么)。
  </Accordion>
</AccordionGroup>

## 恢复与排障

<AccordionGroup>
  <Accordion title="做到一半中断了怎么办">
    直接对 Agent 说"继续上次的 Skill 创建"。`/comet-any` 会先扫描可恢复状态，展示名称、状态、下一步、阻塞原因和上次确认的方案摘要。

    如果你只想看下一条命令，运行 `comet creator next <name>`。如果想看完整状态，运行 `comet creator status <name>`。详见[创建 Skill 的完整流程 · 恢复中断流程](/zh/skill-creator/workflow#恢复中断流程)。
  </Accordion>

  <Accordion title="偏好文件改了，旧方案还能用吗">
    取决于当前模式。
    `advisory` 往往给出 warning，并让你选择继续旧方案或重新生成。
    `strict` 更严格，可能直接阻塞并要求你明确确认。

    如果不确定，运行 `comet creator next <name>`，按推荐下一步处理。
  </Accordion>

  <Accordion title="生成后我又改了文件怎么办">
    再次运行 `comet creator status <name>` 或 `comet creator next <name>`。Comet 会重新计算当前版本状态，旧 eval 或 approval 如果不再匹配当前版本，就不会继续推进发布。

    安全做法是按提示重新评估、重新批准或重新生成，不要手工改内部状态文件。
  </Accordion>

  <Accordion title="我能手工编辑创建状态或内部 JSON 吗">
    不建议。`/comet-any` 会把方案、偏好、eval 证据、approval 和发布状态绑定到当前版本。手工改内部 JSON 容易让 hash 和 readiness 失效。

    查看创建状态用 `comet creator status`，看下一步用 `comet creator next`，发布评审用 `comet publish review`。只有深度审计或排障时，才需要查看高级后端命令。
  </Accordion>

  <Accordion title="我不想自己跑 eval 和 publish 命令怎么办">
    可以全程只在 Agent 里调用 `/comet-any`。
    它会主动推进评估、评审、发布和分发预览，并在需要你确认的节点暂停。

    文档中的 CLI 命令主要用于排障、自动化和中断后的快速恢复。
  </Accordion>
</AccordionGroup>
