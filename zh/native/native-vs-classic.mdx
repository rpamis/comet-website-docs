---
title: 'Native 还是 Classic：如何选择'
description: '根据模型能力、工程规范和团队协作方式，选择 Native 或 Classic 工作流。'
---

用强推理能力的主流模型、且不需要固定工程流水线时，建议用 **Native**。团队有严格的研发规范审计要求，需要规范技术方案、实施计划、TDD 和代码审查各步骤时，建议用 **Classic**。

Native 只锁定业务目标和验收证据，具体怎么实现交给模型；Classic 则管住目标定义、整个实现流程和中间各阶段文档。两者面向不同的协作方式。

## 怎么选

| 你的情况 | 建议 | 原因 |
| --- | --- | --- |
| 用云端旗舰模型，不用本地部署的 20B/30B 或更小的模型 | **Native** | 模型能自己推导和实现，不需要套用繁重的固定流程 |
| 希望尽量少切换阶段、少写过程文档 | **Native** | 只有目标确认、代码实现、逐项验收、归档四个阶段 |
| 团队要求每次改动都有完整的设计文档、实施计划和测试用例 | **Classic** | 五阶段状态机会把每一处工程规范和阶段产物固定下来 |
| 所用模型需要明确的步骤指导 | **Classic** | 阶段守卫和专用 Skill 会在每个步骤持续纠正模型 |
| 同一个仓库里既有大型重构，又有日常小改动 | **同时启用** | 在项目配置里同时启用两套工作流，不同类型的变更各用各的 |

<Tip>
  模型推理能力强、团队也不强制走形式化文档流程时，建议首选 Native。更看重过程可追溯，或需要模型严格执行既定规范时，选 Classic 更稳妥。
</Tip>

## Native：轻量迭代，看证据验收

Native 把重心放在「交付目标和最终验收标准」上，具体怎么做交给模型：

- **聚焦交付目标**：在 Shape 阶段定清目标边界、非目标（Non-goals）和核心验收场景，不写冗长的形式化设计文档。
- **Builder 提交候选实现**：模型自己权衡测试和实现方式。Builder 不能自己宣布完工，只能提交一份候选实现。
- **Verify 逐条验收**：对照最初的请求、全部验收项和真实命令日志逐条核对。新建任务可以在同一会话里完成验收，也可以另开独立审查。
- **针对未通过项的修复循环**：有用例没通过时，Verifier 带着报错信息把任务退回 Build，由 Builder 针对性修复，直到全部通过或达到重试上限。

```text
Shape → Build → Verify → Archive
          ↑         |
          └─ 修复循环 ┘
```

面对复杂架构任务，模型可以按需调用特定 Skill 协助排查，项目初期不会被塞进大量前置约束。

## Classic：全流程规范和约束

Classic 面向对交付流程和审计追溯要求较高的团队，用状态机分阶段推进：

- **阶段文档驱动**：依次走完 Open（需求提案）、Design（技术方案 Design Doc）、Build（任务清单实施与 TDD）、Verify（规范核验）和 Archive（归档合并与经验保存）。
- **阶段守卫检查**：每个阶段都由固定脚本校验，前一阶段的产物满足要求才能进入下一阶段。
- **统一工程规范**：系统把 OpenSpec 与 Superpowers 的研发规范注入会话上下文，要求任务拆细、先写测试、从多个方面审查代码。

```text
Open → Design → Build → Verify → Archive
```

全阶段管控让大型团队在代码演进上更规范、更一致，代价是中间阶段的上下文开销、文档体积和人工确认轮次都会增加。

<Tip>
  **模型和上下文的考虑**：
  - **强推理模型**：建议用 Native，交付链路更短，交互轮次更少，Token 消耗更低。
  - **本地部署或较小的模型（如 20B/30B 级别）**：建议用 Classic。这类模型的上下文较短，Classic 在每个阶段生成的结构化文件能避免长会话被截断后忘记目标，通过分阶段任务引导模型完成交付。
</Tip>

## 实际使用中的差别

以“为用户个人中心增加头像上传”为例：

用 **Native** 时：Comet 先在 Shape 阶段和你确认上传大小限制、失败回退方式等关键分歧，然后由模型自己写代码和测试。Agent 会判断哪些测试仍然有效，补跑必要的检查，最后由 Verify 按全部验收项核对。发现问题立即退回修复；全部通过且你确认接受后归档。

用 **Classic** 时：这个需求会被拆成 Open、Design、Build、Verify、Archive 五个阶段。系统依次生成方案文档、任务清单，按 TDD 编码并触发多轮审查，模型必须在每个阶段提交合格产物、通过阶段守卫后才能往下走。

| 对比 | Native | Classic |
| --- | --- | --- |
| 管控重点 | 业务目标、完工标准和证据 | 整个实施过程、阶段文档和规范检查 |
| 实现方式 | 模型自己权衡 | 按既定配置和阶段规范执行 |
| 怎么判定完工 | 真实命令日志 + Verify 逐项核对 | Verify 阶段比对代码与规格设计 |
| 需要你参与的节点 | 主要是目标定义和关键业务决定 | 需要逐步确认设计方案、实施计划和阶段成果 |
| 默认上下文 | 轻量，按需加载高级工程 Skill | 把 OpenSpec 与 Superpowers 的核心规则全部注入 |
| Token 开销 | 交互轮次少，文档开销小 | 产物多，确认轮次多，整体消耗更大 |
| 适合的模型 | 能自主拆解和推理的强模型 | 需要明确步骤指导或阶段约束的模型 |

## 同一个项目里同时用两套

团队里不同场景的需求差别很大时，可以在同一个项目里同时启用两套工作流：

```bash
comet init --workflow both
```

`.comet/config.yaml` 中的 `default_workflow` 决定 `/comet` 默认进入哪一套。这个配置只影响新任务，不会把已有的 Native change 改成 Classic，也不会反过来改 Classic change。两套工作流各自管理自己的 change、状态机、阶段守卫和文档。

## 最后的判断

- **模型推理能力强，希望少写过程文档、以证据判定交付**：用 Native。
- **研发管理要求必须做架构评审、任务拆解、TDD 和代码审查，走 SDLC 流程**：用 Classic。
- **两类需求都有**：同时启用，把更常用的设为默认。

文中提到的模型名称只是算力参考。Comet 不会去探测模型名称后自行切换工作流，最终怎么走完全取决于你的项目配置。
