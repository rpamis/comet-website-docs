title: 'Native 还是 Classic：如何选择'
description: '基于底层模型能力阶梯、工程规范约束与团队协作范式，科学挑选最契合的 Native 或 Classic 工作流。'
---

当使用具备强推理能力的主流前沿模型、且不强求死板的固定工程流水线时，推荐优先选用 **Native**。若团队有严格的研发规范审计要求、希望规范化把控技术方案、实施计划、TDD 与代码审查各个步骤时，推荐选用 **Classic**。

Native 专注锁定业务目标与交付验收证据，具体实现路径充分交由大模型自主探索；Classic 则对目标定义、工程落地全流程及中间各阶段文档进行全方位强管控。二者面向截然不同的开发协作范式。

## 30 秒极速选型指南

| 你的实际场景 | 推荐选型 | 核心考量依据 |
| --- | --- | --- |
| 使用具备深度推理能力的强模型 | **Native** | 模型具备自主推导与代码落地能力，无须机械套用繁重固化的工程流程 |
| 追求极简敏捷，希望最大限度减少阶段切换与过程文档 | **Native** | 全链路仅设立目标对齐、代码实现、逐项验收与归档四个精简闭环 |
| 团队要求每次改动必须沉淀详实的方案设计、实施计划与测试用例 | **Classic** | 经典的五阶段状态机会刚性固化每一处工程规范与阶段交付物 |
| 所用模型能力稍弱，需要手把手分步引导 | **Classic** | 阶段 Guard 守卫与专用 Skill 能够在每个细分步骤对模型实施持续纠偏 |
| 同一个代码仓库中既有大型规范重构，又有轻量日常迭代 | **同时启用** | 在项目配置中声明双流并存，不同特性的变更可各自挑选最适合的工作流 |

<Tip>
  若所用模型推理能力充沛，且团队并未强行推行形式化文档流程，强烈建议首选 Native。若你更看重软件工程的过程可追溯性、或需要强制模型严格执行指定的规范方法，选用 Classic 则更为稳妥。
</Tip>

## Native：轻量迭代与客观证据验收

Native 将全盘重心收敛至「交付目标与最终验收标准」，具体的实现手法完全赋予模型探索自由：

- **聚焦核心交付价值**：在 Shape 阶段精准界定目标边界、非目标（Non-goals）与核心验收场景，坚决杜绝撰写冗长形式化的过度设计文档。
- **Builder 提交代码候选**：模型自主权衡并挑选最合理的测试与实现策略。Builder 绝无自行宣布完工的特权，仅能提交代码候选快照。
- **Verify 逐条严密验收**：严格对照初始提示词、全量验收项与真实命令日志逐条裁判。新创建的任务支持在同会话内闭环验收，亦可按需发起物理隔离的独立审查。
- **缺陷针对性修复闭环**：若存在用例未通过，Verifier 会携带详实的报错堆栈将任务退回 Build 阶段，由 Builder 展开针对性排错修复，直至全量绿灯或触达熔断预算。

```text
Shape → Build → Verify → Archive
          ↑         |
          └─ 修复循环 ┘
```

面对复杂架构任务，模型可按需调用特定 Skill 辅助排查，绝不会在项目初期被强行塞入大量流程化的前置约束。

## Classic：全生命周期工程治理与规范约束

Classic 专为对研发协作流程与审计追溯有着极高要求的团队打造，提供分阶段严格推进的确定性状态机治理：

- **阶段文档契约驱动**：依次严格走完 Open（需求提案）、Design（技术方案 Design Doc）、Build（任务清单实施与 TDD）、Verify（规范核验）以及 Archive（归档合并与经验沉淀）。
- **刚性 Guard 门禁校验**：每个阶段均由确定性脚本执行强校验，前置阶段的技术产物若未完全达标，绝对无法偷跑迈入下一阶段。
- **统一企业级工程实践**：系统自动将 OpenSpec 与 Superpowers 研发规范注入会话上下文，强制贯彻任务原子化拆解、单元测试先行与多维度代码审查。

```text
Open → Design → Build → Verify → Archive
```

全阶段治理最大化保障了超大型团队在代码演进上的规范度与工程一致性，但也会相应增加中间阶段的上下文开销、过程文档体积以及人工确认轮次。

<Tip>
  **模型选型与上下文考量**：
  - **前沿强推理模型**：强烈建议优先使用 Native，端到端交付速度快数倍，有效会话交互轮次更少，Token 消耗大幅下降。
  - **私有化或较小规模模型（如 20B/30B 级别）**：建议使用 Classic。这类模型有效上下文较短，Classic 在各个独立阶段生成的结构化文件能有效避免长会话截断导致遗忘目标，通过清晰的分步任务引导模型稳扎稳打交付。
</Tip>

## 两种工作流在实战中的差异呈现

以“为用户个人中心增加头像上传功能”为例：

若选用 **Native**：Comet 会率先在 Shape 阶段向你确认上传体积限制、失败回退策略等核心业务分歧点，随后模型自主完成业务编写与测试。Agent 会依据现场真实评估哪些测试依然有效，并通过工具链补跑必要检查，最后由 Verify 依据全量验收契约严格裁定。发现缺陷立即退回修复；全量通过且你确认接受后即刻完成归档。

若选用 **Classic**：该需求会被严谨分解为 Open、Design、Build、Verify 和 Archive 五个独立步进。系统会依次生成方案文档、任务清单、推进 TDD 编码并触发多轮审查，模型必须在每个阶段提交合规产物并通过 Guard 校验后方可向前演进。

| 核心对比维度 | Native 工作流 | Classic 工作流 |
| --- | --- | --- |
| 治理核心侧重 | 业务目标、完工标准与客观证据链 | 工程实施全过程、阶段文档产物与规范门禁 |
| 落地实现路径 | 赋予模型自主权衡探索自由 | 严格按既定配置与阶段规范指令执行 |
| 交付完工判定 | 真实命令执行日志 + Verify 逐项核验 | Verify 阶段全面比对代码实现与规格设计 |
| 人工交互节点 | 聚焦把关核心目标定义与关键业务决议 | 需分步确认设计方案、实施拆解计划及阶段成果 |
| 默认上下文包 | 轻量精简，各类高级工程 Skill 按需动态加载 | OpenSpec 与 Superpowers 核心规约全量注入系统上下文 |
| Token 资源开销 | 交互轮次极少，过程文档开销小，经济高效 | 阶段产物丰富，确认轮次更多，整体消耗偏大 |
| 最契合模型段 | 具备极高自主拆解与逻辑推理能力的前沿模型 | 需要手把手步骤引导、或必须遵守死板规范的模型 |

## 同一工程内支持双流并存

若团队内部不同场景的需求差异巨大，完全可以在同一项目中同时激活两套工作流：

```bash
comet init --workflow both
```

`.comet/config.yaml` 中的 `default_workflow` 决定统一入口 `/comet` 默认进入哪套体系。该配置仅用于新任务路由，绝不会把既有的 Native change 篡改为 Classic，亦不会反向侵入 Classic change。两套工作流在项目内各自独立管理所属的 change、状态机、阶段 Guard 与文档产物。

## 最终决策核对表

- **若模型推理能力强劲，希望减少繁琐的过程文档并纯粹以客观证据裁决交付**：果断选用 Native。
- **若企业研发管理规定必须严守架构设计评审、任务细拆、TDD 与代码审查流水线**：果断选用 Classic。
- **若上述两类需求在项目中兼而有之**：配置双流共存，并将最常用的流设为默认值。

相关模型名称仅作为算力梯度的参考。Comet 绝不会越权探测模型名称并私自漂移工作流，最终流转方式始终完全受控于你的项目配置。
