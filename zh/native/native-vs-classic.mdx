---
title: 'Native 与 Classic 如何选择'
description: '对比 Native 与 Classic 的完成判定、执行开销、阶段取舍和适用场景。'
---

Native 和 Classic 不是轻重档位，也不是同一个工作流的两个版本。Native 面向能自主规划、实现和修复的强模型；Classic 面向需要更细阶段和方法约束的任务。

## 一句话区分

- **Native**：模型自主选择计划、实现、测试和审查方法；Runtime 只强制 Shape、必要检查、新 Verifier、Loop 和安全归档。portable 状态和用户文档可跨设备恢复。
- **Classic**：通过 OpenSpec 与 Superpowers 提供 open → design → build → verify → archive 五阶段治理，明确组织设计、计划、TDD、调试和 review。

## 谁负责完成判定

Native 不信任 Builder 的“完成”声明。Build 只提交 handoff，Runtime 运行必要检查，再分派新的只读 Verifier 覆盖全部验收项；失败回 Build，达到上限就等待用户。Classic 则用各阶段 Guard 和正式任务/报告推动流程。

## 执行开销

Native 不在 Verify 阶段扫描或指纹化整个项目，也不在 Archive 正常路径重复检查。相同候选下已完成的检查会复用，长命令输出流入本机日志。Classic 的优势是方法更明确，代价是需要更多阶段上下文和过程产物。

## 产物和恢复

Native change 的主要用户产物是 brief、完整 Specs、`comet-state.yaml` 和 `verification.md`；本机执行状态、日志、锁和事务放在 `.comet/runtime/native/`。换设备时从 portable YAML 恢复，缺失的本机 overlay 会重建。

Classic 继续使用自己的 `.comet.yaml`、OpenSpec 目录、Superpowers 计划和 Classic Runtime。两边的 change、Guard 和目录不会混用。

## 选择建议

| 场景                               | 建议                                                               |
| ---------------------------------- | ------------------------------------------------------------------ |
| 强模型能自主调查、实现并判断测试   | Native                                                             |
| 需要逐阶段指导、TDD、计划和 review | Classic                                                            |
| 同一项目两种任务都有               | `comet init --workflow both`，由 `.comet/config.yaml` 选择默认入口 |
