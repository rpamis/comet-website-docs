Native 不规定固定的 TDD 或审查方法，但对验证结果有确定性要求：结论必须对应当前 brief、spec 和真实 implementation scope，未运行的检查不能写成通过。

## Implementation scope

Build 完成时，模型提交真实项目相对路径。Runtime 将这些产物、当前 change contract、创建时 baseline 与当前项目 snapshot 一起做内容寻址，形成 implementation scope，并派生稳定的 Acceptance ID。

Git 项目的 snapshot 只包含 tracked 与未被 ignore 的 untracked 文件，并把 submodule/gitlink 作为原子条目；非 Git 项目使用有界物理树 provider。当前 snapshot 不完整时，Runtime 不会把缺失路径猜成删除。变化明细超过预算时只展开有界项，其余由带计数与内容 hash 的 `scope-detail-overflow` 表示。

Current snapshot 沿用 change 创建时写入 baseline manifest 的 include/exclude policy。这保证 baseline 与 current 比较的是同一范围；实现中途修改项目配置只能影响新 change，不能让当前 change 的变化消失。快照执行预算可以提高，但范围身份不随预算变化。若被排除的路径后来成为真实实现依赖，应更新需求边界并建立覆盖完整范围的新 baseline，而不是继续复用旧 scope。

若 Runtime 无法证明范围完整，它会停在 Build 并返回 partial scope hash 与未归属项。优先补充 artifact 或消除未归属变化；只有用户明确接受 Runtime 允许授权的具体缺口时，才能用同一个 hash、理由和 `--confirmed` 推进。`git-selection-changed` 必须等 Git index 稳定后重试，绝不可授权。`git-enumeration-limit` 应先判断受影响文件是否属于范围：属于范围就提高 snapshot 预算或清理无关项目内容，不属于范围则为后续 change 配置明确 exclude。仅当恢复不可行、Runtime 返回带计数与内容 hash 的可授权 scope，且用户理解未知尾部风险时，才可使用普通 partial 协议。非 Git 项目的 `physical-selection-changed` 与 `physical-enumeration-limit` 分别要求等待项目树稳定或缩小项目树；两者都无法绑定未知尾部，不能授权。任何完整性失败都不能靠手改 evidence 绕过。

## verification report

`verification.md` 至少记录：

- 实际运行的命令与结果；
- 跳过项和原因；
- 已知限制与总体结论；
- 每个 Runtime Acceptance ID 对应的项目内证据引用，或诚实的 `skipped_reason`。

可选的 `comet native check` 只执行有界、只读的文本卫生扫描。它不调用 Git、shell、测试脚本或外部 Skill，也不替代项目测试。结果保存为内容寻址 receipt。

## 证据失效

验证结论会绑定 brief、target spec、implementation scope、revision、report snapshot 和可选 receipt。任一输入发生变化，旧证据都会变成 stale。

若在 Verify 中发现 contract 或项目 snapshot 已变化，status 会返回只含摘要的 `next`。运行该命令受控退回 Build，并封印新 scope；只有 brief/spec contract hash 也变化时才重新确认。仅项目 snapshot 或 implementation 变化时保留原 approval，不制造额外确认。不要在旧 scope 上提交结论；进入 Archive 后报告、receipt 或其他绑定事实变化时使用同一回退协议，不能复用旧 pass。

## 修复为什么有上限

Verify fail 会回到 Build。Runtime 从已校验的 acceptance matrix 中返回 failed/missing acceptance 和失败检查；下一轮先处理这些缺口，不会直接重试 Verify。

重复失败签名由当前 contract、排序后的 failed/missing Acceptance ID 和失败检查 ID 组成：

- 同一语义缺口第二次出现时告警；
- 第三次出现且没有语义进展时进入 `repair-stagnation-stop` 恢复分支；
- 缺口减少、失败检查转绿或缺失证据变为当前有效证据，才算语义进展；
- 修改文件、改变 implementation scope 或重写说明，但失败集合不变，不会重置停滞计数；
- 仍有 override 时，Agent 必须先提出一个明确的新修复假设；同一失败签名最多允许 override 一次；
- 同一 contract 默认最多接受 5 次 Verify fail；可以通过 `.comet/config.yaml` 的 `native.max_verify_failures` 设置大于等于 1 的整数。override 或验证预算耗尽后才要求用户决定。

重复缺口恢复与总失败预算彼此独立。只有用户确认后的 contract 变化才会开始新的目标周期；普通实现变化不会清空累计次数。

这使强模型可以连续修复，同时避免把代码活动误当成完成进展。进入恢复分支后，Agent 根据 finding 形成新假设；只有 continuation 明确要求用户决定时，才让用户调整范围、约束或终止。任何情况下都不能弱化检查、提前进入 Archive 或伪造 pass。
