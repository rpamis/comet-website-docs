很多时候单测全绿，但交付结果仍然不对——要么写代码时悄悄砍掉了边界条件，要么文档路径和格式没按要求放，要么修一个问题引入了回归。

Native 的 **Verify** 阶段不只看测试命令的退出码，而是对照**你最初的原始请求**、已确认的 `brief.md`、目标 Specs 以及**每一条验收项**逐一核验，确保最终交付的正是你确认要的东西。整个验收和修复循环由 Agent 与 Runtime 自动衔接，你只需在关键节点决定是否要求独立审查、是否接受结果，或者是否需要调整需求。

## 一、Verify 到底核验什么

进入 Verify 后，验收者会按顺序核对四个维度：

1. **对照原始请求防漂移（`requestReview`）**：新建任务时，Agent 会把你的原始请求原话保存在 Run 中并直接交给 Verifier。Verifier 先读原始请求，再对照 Specs 和代码，检查是否有需求遗漏、未经确认的范围缩减或接口行为偏移。
2. **核对逐条验收项**：覆盖当前 change 的全部已确认验收 ID，每条必须给出独立结论和可复核依据。
3. **核对明确约定的产物位置与格式**：如果 `brief.md` 中明确规定了某些文件的存放路径、必需章节或格式，Verify 会直接检查原位置的文件内容，不能拿另一个文件中的同类内容代替；缺项或路径不符不能判定通过。
4. **把 Builder 交接作为线索而非结论**：Builder 提交的修改摘要、检查记录和已知限制只用来辅助定位，Verifier 必须独立核对实际代码与结果。

## 二、选择审查方式：当前会话还是独立审查

你可以按改动风险选择是否需要独立审查——日常只需在对话里告诉 Agent，不需要手敲参数：

| 审查方式 | 你在对话里怎么选 | 后台机制与适用场景 |
| --- | --- | --- |
| **当前会话只读审查（默认）** | 正常推进，无需额外说明。 | 后台采用 `--review current-session`，当前会话切换到只读角色完成 Verify，报告记为 `self-reviewed`。适合改动清晰、风险可控的任务。 |
| **独立会话只读审查** | 在对话中说明“这个改动请做独立审查”。 | 后台采用 `--review independent`，保留待领取的 Verify 任务，由不同于 Builder 的独立只读会话领取并提交结论。适合复杂改动或关键模块。 |

两项硬约束确保审查不流于形式：

- **要求不可被悄悄撤回**：只要你明确要求独立审查，或者 Builder 提交了独立审查标记，Runtime 就会将该要求持久化为 `requireIndependentReview: true`。后续步骤即使省略参数，也必须由独立只读会话领取。
- **Verify 全程只读**：无论当前会话还是独立会话，Verify 阶段都禁止修改业务代码（Hook Guard 也会拦截）。发现缺陷必须返回 Build 修复，再提交新候选重新验收。

## 三、运行检查、复用证据与状态值规范

### 1. 由 Agent 平台直接执行命令

构建、单测、类型检查、Linter 或端到端测试均由 Agent 直接调用平台工具运行，Runtime 不会替 Agent 重复跑普通命令、不托管命令 PID，也不凭文件哈希机械决定是否跳过测试。如果项目记忆或策略中注入了激活的验证命令（`<verification command="...">`），Agent 也会将其纳入本次 Verify 检查。

每次检查记录到 `checks` 中时，包含三项内容：

- `name`：检查名称；
- `result`：实际结果；
- `note`：执行的命令、工作目录、退出状态及日志引用。

如果已有检查仍适用于当前代码和运行环境，可以直接引用已有结果；受代码改动影响、此前未跑过或运行环境已变化的检查必须补跑。

### 2. 合法状态值一览

Runtime 严格校验回报中的枚举值，不能把未运行或未知结果写成通过：

| 字段位置 | 合法值 | 规则说明 |
| --- | --- | --- |
| Builder 检查记录（`checks[].result`） | `passed`、`failed`、`not-run` | 失败、超时、未执行和结果未知都不能算通过。 |
| 逐条验收项（`acceptance[].result`） | `passed`、`failed`、`blocked` | 每条验收 ID 恰好出现一次；`failed` 和 `blocked` 必须说明原因。 |
| Verifier 总判定（`verdict`） | `pass`、`fail`、`blocked` | 总判定必须与逐条结论一致：只要有一条 `failed` 或 `blocked`，总判定就不能是 `pass`。 |

注意：**单测全通过只证明测试覆盖到的行为**。不在测试覆盖范围内的验收项（如文案细节、错误码映射、文档章节或配置兼容性），仍需用代码核对或实际运行结果作为依据。

### 3. 示例：一轮失败与修复复验

以 `login-error-message` 的第 1 轮 Verify 为例：

| 验收项 | 实际证据 | 结论 |
| --- | --- | --- |
| A1：密码错误时显示“账号或密码错误”。 | 界面测试模拟服务端返回 401，页面渲染的提示文案与约定一致。 | `passed` |
| A2：触发限流时显示“尝试次数过多，请稍后再试”。 | 界面测试模拟服务端返回 429，页面仍落入默认密码错误分支。 | `failed` |

A2 未通过导致本轮总判定为 `fail`，Runtime 将未通过项带回 Build。Builder 补齐 429 分支并提交第 2 轮候选后，Verifier 会重点核验 429 行为，同时确认同一段错误处理代码没有破坏 401 提示；未受影响的接口测试可以直接引用原记录，前端界面测试则针对新候选重新运行。

## 四、编辑代码或文档后，旧检查还有效吗

在 Build、Verify 或待归档阶段发生手动编辑时，Comet 不会因为文件字节变动就一刀切作废所有批准和检查，而是由 Agent 读取 Git 差异、改动原文和相关调用链来判断影响：

| 编辑情况 | 对已有批准和检查的影响 |
| --- | --- |
| 仅排版、注释或文档措辞微调，未改变产品行为和验收含义 | 保留原 Run、批准和有效检查证据，无需为记账重跑 Build 或 Verify。 |
| 改动涉及代码逻辑、测试输入、依赖配置或运行环境 | 仅补跑受影响的检查，并更新受影响的验收结论。 |
| 补跑的新检查出现失败、超时或结果未知 | 一律以最新结果为准并保留失败记录，绝不用历史通过覆盖最新失败，也不把旧结果写成刚跑过。 |

## 五、修复循环、失败上限与验收后处理

Verify 提交结论后，Agent 会向你同步结果，由你用自然语言决定下一步（对应指令由 Agent 在后台自动执行）：

| 验收结论 | 后续动作 |
| --- | --- |
| **全部通过（`pass`）** | Runtime 生成或更新 `verification.md`。开启 `native.archive_confirmation: automatic` 且满足四项安全条件，或你已事前委托通过即归档时，自动进入 Archive；否则等你回复确认后再归档。 |
| **实现未达标（`fail`）** | 未达到失败上限时自动回到 Build 修复（`iteration` 加 1）；再次进入 Verify 时仍覆盖全部验收项。 |
| **缺少外部条件（`blocked`）** | Agent 说明缺少的环境、权限、密钥或外部资料；你补齐条件后告诉 Agent 继续验收，保留当前候选和有效检查。 |
| **Verifier 平台执行出错或不可用** | 保留候选和有效检查，你在对话中让 Agent 重试验收即可（仅递增 `attempt`，不消耗代码实现轮次）。 |
| **发现需求或验收标准本身要改** | 直接在对话中说明需求变动，Agent 退回 Shape 展示变化摘要，重新确认后再继续。 |

### 失败上限与进展判断

- **失败预算**：`.comet/config.yaml` 中的 `native.max_verify_failures` 控制同一个已确认验收目标允许的最大真实 Verify 失败次数（默认 `5`）。达到上限时，Runtime 暂停自动修复循环，交给你决定换思路继续修、调整范围还是取消任务。
- **不做机械进展惩罚**：多轮修复时，即使未通过的验收项 ID 集合暂时相同或没有缩小，Runtime 也不会因此强行弹窗中断，而是由 Agent 结合实际改动与报错判断修复方向。

### 关于 `verification.md`

`verification.md` 是 Runtime 根据结构化验收结论生成的阅读视图。直接编辑这份 Markdown 文件**不会改变** Runtime 中保存的验收结论；如果报告文件写入失败，已提交的结构化验收结论依然保留，后续继续推进时会自动重新生成。

归档与 Git 交付细节见 [归档与交付](/zh/native/archive-and-delivery)，异常排障见 [Native 任务恢复](/zh/native/recovery-playbook)。
