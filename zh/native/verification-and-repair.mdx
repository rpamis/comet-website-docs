Native 不规定固定的 TDD 或审查方法，但对验证结果有确定性要求：结论必须对应当前需求、规格和真实实现范围，未运行的检查不能写成通过。

## 实现范围

Build 完成时，模型提交真实项目相对路径。Runtime 将这些产物、当前 change 的需求契约、创建时基线与当前项目快照一起做内容寻址，形成实现范围，并派生稳定的验收项 ID。

Git 项目的快照只包含已跟踪与未被忽略的未跟踪文件，并把 submodule/gitlink 作为原子条目；非 Git 项目使用有界物理树提供器。当前快照不完整时，Runtime 不会把缺失路径猜成删除。变化明细超过预算时只展开有界项，其余由带计数与内容哈希的 `scope-detail-overflow` 表示。

当前快照沿用 change 创建时写入基线清单的 `include`/`exclude` 策略。这保证基线与当前快照比较的是同一范围；实现中途修改项目配置只能影响新 change，不能让当前 change 的变化消失。快照执行预算可以提高，但范围身份不随预算变化。若被排除的路径后来成为真实实现依赖，应更新需求边界并建立覆盖完整范围的新基线，而不是继续复用旧范围。

若 Runtime 无法证明范围完整，它会停在 Build 并返回部分范围哈希与未归属项。优先补充产物或消除未归属变化；只有用户明确接受 Runtime 允许授权的具体缺口时，才能用同一个哈希、理由和 `--confirmed` 推进。`git-selection-changed` 必须等 Git 索引稳定后重试，绝不可授权。`git-enumeration-limit` 应先判断受影响文件是否属于范围：属于范围就提高快照预算或清理无关项目内容，不属于范围则为后续 change 配置明确的 `exclude`。仅当恢复不可行、Runtime 返回带计数与内容哈希的可授权范围，且用户理解未知尾部风险时，才可使用普通部分范围协议。非 Git 项目的 `physical-selection-changed` 与 `physical-enumeration-limit` 分别要求等待项目树稳定或缩小项目树；两者都无法绑定未知尾部，不能授权。任何完整性失败都不能靠手改证据绕过。

## 验证报告

`verification.md` 至少记录：

- 实际运行的命令与结果；
- 跳过项和原因；
- 已知限制与总体结论；
- 每个 Runtime 验收项 ID 对应的项目内证据引用，或诚实的 `skipped_reason`。

可选的 `comet native check` 只执行有界、只读的文本规范扫描。它不调用 Git、shell、测试脚本或外部 Skill，也不替代项目测试。结果保存为内容寻址凭据。

## 证据失效

验证结论会绑定需求简述、完整目标规格、实现范围、修订版本、报告快照和可选凭据。任一输入发生变化，旧证据都会失效。

若在 Verify 中发现需求契约或项目快照已变化，`status` 会返回只含摘要的 `next`。运行该命令受控退回 Build，并封印新范围；只有需求简述与规格的需求契约哈希也变化时才重新确认。仅项目快照或实现变化时保留原批准，不制造额外确认。不要在旧范围上提交结论；进入 Archive 后，报告、凭据或其他绑定事实变化时使用同一回退协议，不能复用旧通过结论。

## 修复为什么有上限

Verify 失败会回到 Build。Runtime 从已校验的验收矩阵中返回未通过或缺失的验收项和失败检查；下一轮先处理这些缺口，不会直接重试 Verify。

重复失败签名由当前需求契约、排序后的未通过或缺失验收项 ID 和失败检查 ID 组成：

- 同一语义缺口第二次出现时告警；
- 第三次出现且没有语义进展时进入人工停止；
- 缺口减少、失败检查转绿或缺失证据变为当前有效证据，才算语义进展；
- 修改文件、改变实现范围或重写说明，但失败集合不变，不会重置停滞计数；
- 存在一个明确的新假设时，同一失败签名最多允许显式越过一次；
- 同一需求契约默认最多接受 5 次 Verify 失败；可以通过 `.comet/config.yaml` 的 `native.max_verify_failures` 设置大于等于 1 的整数。

重复缺口停止和总失败预算彼此独立，因此工作流可能在达到总预算前停止。只有用户确认后的需求契约变化才会开始新的目标周期；普通实现变化不会清空累计次数。

这使强模型可以连续修复，同时避免把代码活动误当成完成进展。达到停止条件后，应让用户决定范围、约束或是否终止，而不是弱化检查、提前进入 Archive 或伪造通过结论。
