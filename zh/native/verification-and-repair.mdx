---

Native 不要求固定的 TDD 或审查方法，但不接受“我做完了”作为验收结果。**Builder 负责实现，Runtime 负责执行检查，新的只读 Verifier 负责逐项判断，Runtime 负责决定是否完成。**

## Verify 的实际顺序

1. Builder 提交 handoff：说明已完成的实现、相关 brief/Spec 和准备交给验收的候选。
2. Runtime 解析当前完整验收列表，解析必要检查计划，并在短状态更新中登记本次 attempt。
3. Runtime 执行必要检查；同一候选下已完成且匹配的检查直接复用，不重复跑。命令输出流入本机日志，报告只保留安全的摘要。
4. Runtime 分派新的只读 Verifier。Verifier 必须对每个 A1…An 恰好给出一次结果；漏项、重复项、未知 ID 或把 Builder 自己的自报结果当成验收都会被拒绝。
5. Runtime 根据结果进入 `pass`、回 Build，或等待用户处理的状态。Archive 正常路径不会再次运行这些检查。

Verifier 不能使用 Builder 的上下文替自己背书。能提供独立 subagent 的宿主会分派新的 execution；只有 Skill 协调、没有可信独立 execution 时，Runtime 会明确标记“语义验收不可用”，并在归档前要求用户确认降级结果。

## 检查和报告

必要检查由 Runtime 根据项目和 change 的正式内容解析，不由 Agent 通过一段“已通过”的文字替代。检查结果至少包含命令状态、退出码、耗时和可读摘要；完整 stdout/stderr 留在本机日志，长输出会截断预览而不会单独使有效结果失败。

如果确实需要额外检查，Verifier 在当前 attempt 通过 `request-checks` 请求 Runtime 执行。Runtime 会去重相同计划、限制请求轮数，并把新的结果返回给 Verifier；Agent 不应自己伪造检查结果或把第三方命令的输出直接写成通过。

`verification.md` 是 Runtime 从 `comet-state.yaml` 生成的用户报告，包含检查、逐项验收、限制和结论。它可以重建；缺失报告不是绕过 Verify 的理由。

## 失败如何回到 Build

只要有验收项失败、检查失败、Verifier 漏项或结果不完整，Runtime 就把明确的缺口写入下一轮 continuation，并把 change 返回 Build。下一轮优先修复失败项，再由新的 Builder handoff 和新的 Verifier 重新验收；不能在原 attempt 上反复提交一个“通过”。

Loop 只把真实收敛算作进展：未解决验收项严格减少、失败检查变为通过，或已明确补齐缺失信息。只是改写说明、重复同一命令或在不同失败集合之间来回切换，都不会无限延长循环。

## 停滞和错误预算

`comet-state.yaml` 会保存 `iteration`、`attempt`、`no_progress_count`、`failed_iteration_count`、`execution_failure_count` 以及有限的 history。相同或退化的未解决集合会增加停滞计数；连续的 Runtime 执行错误也会增加错误计数。达到上限时，状态会变为 `await-user` 或 `blocked`，并给出具体的 `resolution_action`，而不是继续消耗时间。

用户可以在需求确实改变时回到 Shape，或者在实现没有变化且外部阻塞已经解决时确认重试 Verifier。普通的“再试一次”不会清除历史，也不会把旧的通过结果直接带到新候选。

Skill 协调的 Verifier 通过后，Runtime 会等待一次明确的用户决策，三个选项互斥：

| 决策                     | 结果                                                             |
| ------------------------ | ---------------------------------------------------------------- |
| `--accept-result`        | 接受当前 Verify 结果，进入 Archive                               |
| `--revise-implementation` | 保留已确认的需求，回到 Build 修订实现                            |
| `--revise-requirements`  | 用户可见目标或验收标准变化时回到 Shape，更新正式产物后重新确认   |

决策命令携带 continuation 签发的 `--expected-state-version` 和 `--expected-action` 守卫，状态过期或动作不匹配时会拒绝执行；新目标周期开始后，旧的归档授权会失效。

`--revise-requirements` 不仅可以在 Verify 之后使用；当 Archive 停在 `archive-ready` 等待时也可以使用。它会把 change 返回 Shape，开始新的目标周期，使旧的验证结果和归档授权失效，同时保留 change workspace。

## 可靠性边界

Runtime 能保证命令确实执行、非零退出不能当作通过、验收列表不能漏项，以及同一候选的检查不会无意义地重复。它不能替模型判断测试是否足够有意义，也不能观察没有被宿主暴露的后台进程或 IDE 写入。无法提供独立 Verifier 时，Dashboard 和报告会明确显示降级状态，不会伪装成独立语义验收。
