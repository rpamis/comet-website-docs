Verify 严格对照原始提示词诉求、已敲定的 `brief.md`、各能力 Specs 规范及全量验收项，客观裁判代码实现是否真正达标。Builder 单方面声称“已完成”或单纯的某条自动化测试命令返回 0，不能单独作为交付通过的终审结论。

## 新建任务的标准验收流程

新创建的 Native 任务支持由当前会话直接接取 Verify 职责并完成验收。Agent 会结合任务敏感度与你的配置指引，按需决定是否拉起隔离的独立审查；若你在提示词中明确要求“必须独立审查”，则必须严格交由符合隔离要求的执行者完成。生成的验收报告会如实记录本次实际采取的审查方式，同一会话内的验收会按实际审查方式记录。历史存量任务严格维持创建时刻的验收与恢复契约。

1. **Build 阶段提交候选**：Builder 完成代码实现、自测检查并封装完整的交接材料，全量业务验收统一收敛至 Verify 阶段，避免在 Build 阶段无谓重复相同的形式化审查。
2. **Agent 运行必要检查**：常规的本地构建脚本与测试套件直接借由 Agent 平台的工具链执行，系统如实记录实际执行的指令、工作目录、运行结果以及因故未执行的遗漏项。Agent 负责复核既有测试证据是否依然适用于当前代码，仅针对缺失或受改动波及的模块补跑测试；Runtime 不再繁重托管这些外部命令进程，亦不通过文件指纹来草率决定跳过测试。
3. **Verify 逐条核验全量验收项**：审查员优先研读原始诉求，随后深入比对 Specs 规范、代码改动与测试日志。凡是遗漏初始诉求、未经批准私自缩减实现范围、或仍存业务疑问的代码，一律禁止标记为通过。针对每条用例分别记录 `passed`（通过）、`failed`（失败）或 `blocked`（受阻），并详述判定证据与潜在局限。
4. **人类确认接受交付结论**：全量验收项通过后，系统挂起等待你亲自确认接受当前代码候选与验收结论。只有在你事前已明确授权“验收通过后自动接受并归档”时，Agent 才可继续流转；任何测试失败、环境阻塞或底层执行报错均不可能触发自动接受。

Agent 在执行中严格采用当前 Runtime 返回的任务上下文、结果模板与下一步指令。在提交裁决时，系统会核验代码版本哈希、审查者身份与验收集合，历史旧任务的审查记录不可冒充当前代码的有效证据。

## 验收未通过时的针对性修复机制

当代码实现未能满足需求、或自动化基线检查报错时，状态机会安全退回至 Build 阶段，引导 Builder 聚焦修复未通过项并全面评估其波及范围。若排查中发现业务目标或验收标准本身存在矛盾或发生实质性改变，则必须退回至 Shape 阶段重新触发确认门禁。若缺失必要的人工业务决策或外部环境凭证，系统主动挂起并清晰列明卡点。

修复后仍须覆盖当前 change 的全部验收项，无需运行与当前变更无关的测试。依然有效的历史检查证据在当前轮次予以安全复用，仅针对受影响或缺失的环节补齐证据链。当失败轮次、无进展停滞次数或进程崩溃次数触达配置上限时，Runtime 会强制熔断停机，杜绝无意义的 Token 死循环消耗。

## 验证报告渲染与归档交付

`verification.md` 图文并茂地呈现了真实执行的命令、逐项用例裁决、审查执行方式、潜在边界风险与未执行测试清单。该 Markdown 文件属于面向人类的只读视图快照，开发者手动润色排版会被系统安全保留；但请注意：直接编辑该报告不可能反向推动底层 Run 实例或篡改机器判定的状态结论。

当全量用例通过并经由你确认接受后，流程进入归档收尾，归档预检机制会对当前代码、已获批准的材料与客观证据链进行最终一致性复核。普通的文档格式优化在经由 Agent 评估影响后，可以完好继承已有的验收通过结论，仅按需刷新受波及的检查；一旦涉及业务需求或核心源码的实质修改，必须依照实际影响回退至对应阶段重测。详情请参阅[归档与交付](/zh/native/archive-and-delivery)以及[中途修改文档后的继续策略](/zh/guides/mid-workflow-changes#编辑后继续当前任务)。

## 差异化验证结论的处理矩阵

每次 Verify 阶段执行收尾时，Runtime 均会将现场归纳至下表所列的标准分支之一。多数分支由状态机全自动推演闭环；少数分支会主动挂起等待人类裁决。请先对准当前命中的分支，即可明确应对举措：

| Verify 裁决现场 | 开发者感知到的现象 | 你需要采取的操作 | 流程后续流转目标 |
| --- | --- | --- | --- |
| 具备强隔离证明的最终全量验收全绿 | 状态机跃迁为 `archive-ready` | 无需任何操作，Runtime 自动推进 | 携带已固化的完整证据链流转至 Archive 准备交付 |
| 最终 Verifier 判定全部通过，但当前平台无法向 Runtime 提供两进程隔离的证据 | Runtime 触发挂起，抛出三选一互斥选项 | 三选一：`--accept-result`、`--revise-implementation` 或 `--revise-requirements` | 接受结论进入 Archive；退回 Build 针对性优化代码；或退回 Shape 重新对齐目标 |
| 存在标记为 `failed` 的未通过用例 | 状态机标记为 `repairing` | 无需手动选择，系统自动退回 Build | 携带精准报错日志回退至 Build，修复后生成新候选 |
| 存在标记为 `blocked` 的硬性阻碍 | 状态机切入 `await-user` | 补充业务决议或输入所需的外部凭证 | 补齐现场后，重新唤起 Verifier 进行评测 |
| Verifier 审查进程自身遭遇系统崩溃 | 状态机呈现 `verify-ready` 或 `blocked` | 暂不干预，系统会自动重试；若连续崩溃超限则安全停机 | 重试成功则继续流转，重试失败则等待人工排查环境 |
| Agent 平台完全无法拉起语义 Verifier | 状态机切入 `await-user`；即便所有测试跑通亦仅能得到降级结论 | 二选一：`--retry-verifier` 重新尝试，或 `--confirmed` 接受降级结论 | 重新发起一次审查尝试，或明确接受降级结论后流转归档 |

“业务验收未通过”与“审查进程自身崩溃”属于性质截然不同的问题。前者代表代码实现有缺陷或需求设计存疑，后者则表明底层测试基础设施存在环境故障。Runtime 在底层严格分流度量，不把基础设施的抖动误判为业务逻辑失败。

需要开发者通过终端参数做出明确选择的挂起场景仅有上表中的特定两处，各个选项的详细语义详述如下。

## 人工裁决：接受当前成果或调整需求

当由客户端 Skill 唤起的最终 Verifier 裁定全量验收项均已达标，但当前 Agent 平台由于能力限制无法向 Runtime 提供能够自证审查者与 Builder 隔离的强凭据时，Runtime 会主动暂停并向你呈上三个互斥选项：

| 备选参数 | 实际执行效果 |
| --- | --- |
| `--accept-result` | 明确认可当前的测试结论，正式放行流转至 Archive 归档 |
| `--revise-implementation` | 既定业务需求不变，安全退回 Build 阶段继续针对性重构代码 |
| `--revise-requirements` | 退回 Shape 需求阶段，重新修正系统的外在目标或验收准则并重新确认 |

上述三项决策统一通过 `comet native next` 命令行接口提交：

```bash
comet native next <change> --accept-result
comet native next <change> --revise-implementation
comet native next <change> --revise-requirements
```

在执行接受结论的同时，亦支持合并声明最终的交付策略（例如 `--accept-result --finish keep`）。Comet 会先在终端打印当前所在的工作区实际路径及各选项的预期影响，随后严格依照你的选择向下推演；完整的交付选项说明请参考 [归档与交付](/zh/native/archive-and-delivery)。

若当前 Agent 平台完全不具备唤起独立语义 Verifier 的能力，即便本地所有的自动化测试脚本全部返回 0，系统亦仅能输出“降级验收结论”。此时 Runtime 会安全挂起并提供两难抉择：**重试验收**（`comet native next <change> --retry-verifier`，安全保留当前代码候选与已完成的测试日志，仅重新唤起审查进程）或**接受降级结论**（在充分知情并确认后，通过带有 `--confirmed` 动作的指令强行放行）。一旦你确认接受，最终生成的验证报告中会永久保留降级印记，明确警示该变更未经隔离的独立审查。

对应的两条执行命令如下：

```bash
comet native next <change> --retry-verifier
comet native next <change> --confirmed
```

所有决策类指令在底层均强制携带 `--expected-state-version` 与 `--expected-action` 双重校验。若状态版本已发生跃迁、或操作指令脱胎于历史旧页面，Runtime 会阻断执行，避免陈旧决策污染最新现场。

## 局部缺陷修复后必须重新触发全量回归

当你选定 `--revise-implementation` 或因存在 `failed` 项导致任务被退回 Build 阶段后，系统将严格遵循以下工序推进排错与再验收。

在捕获到测试失败或用例未通过时，Runtime 会将详尽的失败堆栈与错误归因写入最新的 continuation 契约中，驱动状态机退回 Build。Builder 依据具体的失败诱因排查代码缺陷，补齐受波及验收用例的自查证据，随后提交全新的代码候选快照。若遭遇的是 `blocked` 挂起项，Runtime 会优先等待人类决策或外部资源补齐，不将信息缺失误当作代码 Bug 乱改。

Builder 在修复阶段重点处理两部分内容：

- 上一轮验收中未通过的验收项；
- 由 Builder 主动声明由于本次修复可能受到逻辑波及的邻近验收项。

仍然适用的既有自查结论予以安全继承，而底层的自动化检查仅在输入参数、执行命令、工作目录、运行环境及日志完好有效时才被允许复用。一旦源码或测试参数发生了变动，受波及的命令必须无条件当场重测。

修复后的全新代码候选快照将交由新拉起的 Verifier 会话在单轮中全量覆盖 A1 至 An 的所有验收用例。全量验收通过后直接流转至接受结论或归档阶段，不在无意义的重复测试上空耗资源。全量验收覆盖当前 change 声明的全部验收项。

## Supervisor 复合变更在集成工作区完成最终全链路验收

Supervisor 复合任务旗下的各个子任务（child）必须依次在状态机中达成 `active`、`verified` 与 `integrated`。某个子任务独立跑通自身的小范围验收，不代表整项 Supervisor 复合交付已经合规达标。

只有当全部子任务的代码均已成功 Merge 合流至集成 worktree 后，Runtime 会在该集成分支上真实运行全套集成测试，并全面覆盖初始声明的 100% 验收范围。若集成后的整体验收未通过，Runtime 会保留集成分支的当前状态，依据真实未通过的缺陷项自动追加一个增补修复子任务，并退回 Shape 阶段引导你核准该修复边界；此前已成功集成入库的子任务不受任何破坏。

## 验证报告缺失时的一键重建

`verification.md` 专门将 `comet-state.yaml` 中的机器状态格式化排版为图文并茂的人类技术报告，包含真实命令日志、逐条用例裁决、潜在风险警示、环境局限及最终裁决。底层的验收结论在状态机落盘的同时即已固化于 YAML 中，因此若该 Markdown 文件遭遇意外丢失、写入被操作系统截断或版本落后，随时可无损重建。

在更换开发机后，旧设备上的单机临时执行态不可跨机信任。在目标机器上，处于 `verify-ready` 状态的代码候选会自动重跑全套测试并唤起全新的 Verifier；即便在旧机器上已处于 `archive-ready` 状态，切换新机器后亦会先退回 Verify 阶段，在新环境真实代码上重新核验一遍。恢复期间产生的测试执行不计入失败轮次或无进展停滞指标。

## 凡无法由机器客观闭环的事项交由人类裁决

Runtime 在底层能够百分之百确定命令是否真实调用、进程退出码是否合法、验收项是否无一遗漏、以及返回结论是否绑定当期代码哈希与评测轮次。在常规的 Archive 流程中，系统直接采纳已获核准的验收结论，归档时无需重复运行已有有效结果的测试。

但若某项测试结论深度依赖于“测试用例自身的设计是否合乎业务常理”，或是受制于平台未能暴露的外部网络接口、后台守护进程状态，Runtime 便无法单凭自身完成全自动流程。一旦检测到平台无法拉起独立的语义审查者，Dashboard 看板与控制台输出会坦诚透明地指出系统当前的盲区，并将“是否放行接受当前成果”的最终裁决权严正交还给人类开发者。

## Verifier 底层通信协议详解（进阶参考）

上述的人机交互均深植于底层的状态机通信协议之上。开发者日常无需死记硬背下述报文细节；仅当你需要深究结论如何推导、系统边界如何裁定、熔断上限如何贯彻时，再行研读本参考。

### 三层立体验证架构

| 验证防护层 | 核心职责与定位 | 产出结论的系统消费方式 |
| --- | --- | --- |
| Builder 深度自查 | 逐条核验已声明验收用例的实现位置、证据与代码局限 | 若发现漏项或未完成则保持在 Build 阶段，不越权充当独立验收 |
| Runtime 沙盒检查 | 在受控环境中真实调用测试套件、编译脚本与静态扫描 | 记录命令退出状态和检查结果 |
| Verifier 独立裁判 | 以纯只读视角严格对照业务规范逐项给出裁决 | 最终裁决直接决定是流转归档、退回修复还是挂起等待 |

Builder 负责提供代码落地与自查线索，Runtime 负责证明测试确实在真实环境中跑通，Verifier 负责客观评判业务功能是否满足预期。最终的交付结论必须由 Verifier 独立出具。

### 代码候选携带完整自查快照迈入 Verify

Builder 在完成单轮编码后，必须逐条对照全量验收用例进行完整自检：核心逻辑是否落地、对应于哪个文件的哪一行代码、有哪些单元测试或日志可以支撑、当前是否存在已知的边界局限。一旦发现遗漏，必须在 Build 阶段就地补齐。常规变更无需强行增设前置的预审角色，但 Verifier 的独立核验始终不可逾越。

自检完毕后，Builder 会向 Runtime 提交一份结构清晰的 `handoff` 交付快照，标准包含：

- 本轮迭代的具体实现摘要；
- 本次改动涉及并覆盖的验收 ID 清单；
- 研发期间实际调用或跳过的开发期检查命令；
- 当前已知架构缺陷与边界限制；
- 针对每项已确认验收用例的代码落地点与测试证据映射。

Runtime 会将这份 `handoff` 持久化落盘至 `comet-state.yaml`，并强绑定当期代码候选快照哈希、`iteration` 轮次及 Builder 身份标识。`handoff` 仅代表当前待检代码的交付自述；最终是否达标，以正式 Verify 的结论为准。

### 标准执行序：先触发客观检查，再唤起逐条核验

代码候选迈入 Verify 阶段后，流程严格遵循以下确定性工序推演：

1. **锁定验收评估集合**：正式 Verifier 全量覆盖当前代码候选的全部验收项，排错摘要中清晰标注上一轮未决用例与本次修复可能影响的波及面。
2. **触发客观沙盒检查**：Runtime 执行测试、编译或其他指定命令，完整记录状态码、退出码、执行耗时与日志。若项目中配置了项目策略（详见[项目知识](/zh/plugins/project-rules)），其绑定的验证检查亦会在此处严格执行，只有真实通过才能将对应策略晋升为强制生效（enforced）。
3. **注入结构化上下文**：在命令执行成功的同一原子响应中直接返回 `verifierDispatch` 报文，打包当前工作区绝对路径、需求规范与证据链实际位置、当期验收集合、防伪回执凭证及真实测试日志，无需任何二次网络查询或重复调度。
4. **唤起只读 Verifier 审查员**：Verifier 在沙盒中保持严格只读权限，对当前验收集合中的每个验收 ID 给出且仅给出一次确定性结论。
5. **鉴权并固化测试结论**：Runtime 严格核验代码候选哈希、执行者身份凭证、轮次水位、`attempt` 尝试次数与验收集合的一致性，核准无误后推导状态机下一步。

Verifier 在执行审查时会先研读当前用例场景、`brief.md` 需求设计、全量 Specs 规范、真实代码改动以及 Runtime 的客观测试日志，最后才将 Builder 的 `handoff` 作为排查参考。这一阅读顺序最大化消除了开发者主观陈述可能带来的心理暗示。

每个 `scopeId` 必须在裁决报文中出现且仅出现一次，枚举值被严格约束为：

- `passed`：代码实现已完全满足该项验收契约；
- `failed`：代码实现未能达标，必须退回 Build 阶段针对性返工；
- `blocked`：因缺失人工业务决策、外部不可抗力或前置数据未就绪，暂时无法做出判定。

任何包含漏评项、重复评定、出现未定义 ID、身份凭证被篡改或延迟到达的历史旧报文，均会被 Runtime 断然拒绝。若仅属于报文字段格式轻微排版瑕疵，Verifier 可修正原报文后原样重新提交以接续推进当前任务。禁止将旧任务的历史结论强行套用新身份冒名顶替。只有在全部 Runtime 检查通过的前提下，Verifier 才被允许提交全量通过的结论。

### 优先等待在途任务，禁止重复派发

任务调度包内嵌了防伪的启动回执机制。当尚未收到明确的启动回执前，Agent 会优先向平台核对任务是否已被接纳并尝试找回在途任务；一旦确认启动成功，系统会保持静默等待同一个 Verifier 收敛。回执轻微延迟到达或外部等待工具单次超时，不等于任务自身执行失败。只有在平台明确回传进程退出错误、执行硬性超时、任务句柄彻底丢失或正常退出后未能产生合规数据包时，系统才会合规记录错误并遵循指引发起重试。

### 增补测试依然由 Runtime 统一接管执行

若 Verifier 判定当前的现有证据链不足以支撑结论，可通过标准的 `request-checks` 动作向 Runtime 发起增补测试申请。Verifier 仅负责陈述需要执行哪些命令，实际的 Shell 调用依然由 Runtime 统一在沙盒中代理执行并归档日志。

增补测试属于当前 Verifier 这同一次 `attempt` 的生命周期延伸，不会导致 `attempt` 计数被错误递增。Runtime 会智能复用当前代码候选已执行成功的相同测试，精准过滤冗余请求，并将全新日志交付回同一个 Verifier 审查员。单次 `attempt` 内最多放行 `2` 轮增补测试申请，避免无节制追加命令引发上下文膨胀。针对允许安全重放的测试命令支持在配额内显式重跑，但请注意：断言失败即代表业务逻辑有 Bug，系统不会自动无休止空循环重试。

完整的 `stdout` 与 `stderr` 日志安全归档在本机的运行日志中，呈现给人类的图文报告仅保留结论与必要摘要。对冗长的终端输出仅在预览层进行折叠截断，底层的测试判决依据依然完好保留。

### 设立容错熔断预算红线

Runtime 严格通过连续两轮间“未解决缺陷集合是否实现真实收敛”来客观度量进展。只有在当期遗留的未解决项数量少于上一期、且没有引入任何全新次生缺陷的前提下，才被认定为有效进展。

- 连续两轮未能观察到缺陷收敛时，Runtime 强制要求 Builder 撤换排障思路；
- 连续三轮依然毫无实质突破时，状态机立即切入 `await-user` 安全熔断；
- 累计失败轮次触碰配置项 `native.max_verify_failures`（默认上限为 `5` 次）时，立即切入 `await-user` 挂起等待人类介入；
- Verifier 审查进程自身因环境异常连续崩溃达到 `3` 次时，切入 `blocked` 挂起等待排查。

上述健康指标均由底层 Runtime 自动维护更新。重复执行同一命令、仅修改注释或重新提交相同的错误日志，都不会清除已有的失败记录。
