Supervisor Change 是 Native 工作流专为大型复杂需求量身打造的并行交付模式。它严格依照最终验收准则，将宏观目标合理拆解为可独立编码与验证的子任务（child）。底层由 Runtime 统一编排任务拓扑依赖、创建物理隔离的 Git worktree、沉淀各分支执行证据链、串行集成代码分支，并在最后触发全链路终审验收。

无论微观上拆分为多少个子任务，对外交付的主线始终保持单一闭环。所有子任务代码成功合流至集成分支后，主任务必须针对整体目标重新发起最终 Verify 验收。任何单个 Agent 声称完工、局部子模块测试通过、或者代码提前 Merge 到临时分支，绝不代表整项交付已宣告完结。

## 子任务统一纳管与交付保障

| 核心特性 | 实际工程价值 |
| --- | --- |
| 依循验收项精准拆解 | 每个子任务承接明确具体的验收用例，杜绝“前端先随便做做、后端看着改改”等边界模糊的伪分工 |
| 基于依赖拓扑自动调度 | Runtime 仅激活前置条件已全量达标的子任务，杜绝条件不成熟的下游任务盲目抢跑 |
| 物理工作区严格隔离 | 每个子任务独占专属的独立 Git worktree，彻底消除多个 Agent 并发改动相互踩踏的风险 |
| 执行凭据强绑定防篡改 | 任务上下文包、集成基线 Commit 与 `runId` 构成不可伪造的三元凭证，迟到或重复的异地回调直接拦截 |
| 最终全局严密回归验收 | 所有子任务代码陆续集成完毕后，针对系统完整目标实施无死角的最终全量验收 |

以“企业级权限管理模块”为例：系统可自然拆分为权限底层 API、可视化授权配置看板以及操作审计日志组件。这三个子模块虽可独立编写与局部自测，但它们最终服务于统一的产品功能，必须通过代码合流与端到端联合验收。此类任务正是 Supervisor Change 的最佳用武之地。

## 严格基于可交付成果拆解任务

Comet 会在 Shape 阶段正式定稿前，审慎评估当前需求是否具备拆解价值。唯有同时满足以下四个严苛条件，才会主动推荐升级为 Supervisor Change 架构：

- 整体目标至少可自然解耦为两个能够独立编码与独立验收的业务结果；
- 原始需求中的每一条验收用例均能被无缝划分至对应的子任务名下，不留死角；
- 各子任务之间的输入输出契约与依赖拓扑能够清晰表达；
- 并行推进或分阶段交付确实能够显著缩短整体端到端的交付周期。

需求篇幅较长或清单条目繁多，并不直接等同于适合拆分。若各个模块频繁在同一个底层热点核心文件中并发修改，或者拆解导致的跨会话沟通与集成成本超过了并行收益，保持单个 Native Change 顺序演进更为稳健。而对于完全没有共同验收诉求的互斥特性，应直接建立平行的独立 Change。

拆解方案统一固化在 `children.yaml`（RC1 版本采用 `comet.native.children.v2` 规范）。其中的 `acceptance_index` 忠实沉淀了直接从 `brief.md` 派生的全量验收用例，包含每条用例的唯一 ID、需求来源与规范定义；每个子任务仅需声明自身的唯一名称、依赖前置项以及负责覆盖的验收 ID 集合。Runtime 会严格校验名称碰撞、悬空依赖、死循环依赖拓扑及验收漏项。

## 拆分方案与协作模式的人工裁决

在正式核准方案前，Comet 会向你完整呈现整体目标、子任务拆解矩阵、依赖流向图与验收项映射表。你可以灵活微调拆解粒度、一键退回至单 Change 模式，或选定后续的推进方式：

| 选项编号 | 推荐协作模式 | 执行机制与实际影响 |
| --- | --- | --- |
| A | 多会话协同推进（推荐） | 当前主会话专职负责全局调度统筹；优先调度 Codex 独立会话或 Claude Code Agent Teams 并发攻坚，平台不支持时自动降级采用 subagent |
| B | 单会话顺序推进 | 不建立额外的外部独立会话或 Agent 团队；由当前会话严格依照依赖拓扑序，在同一窗口内依次攻坚各子任务 |

协作模式的差异仅影响子任务的物理运行载体；任务拆解粒度、依赖拓扑、质量准则及最终集成标准在两种模式下完全等价。在核准 Supervisor 拆解方案时，Runtime 会将你的决定固化为 `coordination_mode` 沉淀至 `comet-state.yaml`。后续断点恢复或需求重构重新进入 Shape 时会自动沿用该偏好，不重复打扰。

在获得你的明确授权前，Runtime 绝不会提前创建任何子任务、worktree 或跨会话进程。当检测到拆分为两个及以上子任务时，单纯回复“确认”绝不能替代对协作模式的明确选定。

当全景方案与两种备选模式一同呈现时，建议一次性给出明确决议（如“确认当前方案，采用 A 多会话协作”）。若仅简短回复“A”，仅代表选定了执行模式，不代表全量批准方案；若后续对拆解用例或依赖进行了修订，必须重新确认。

## 每个子任务独占物理隔离的工作区

Shape 方案获批后，Runtime 会率先为主任务建立专用的集成分支与集成 worktree，随后以该集成分支的 HEAD Commit 为基线，为各个待就绪的子任务准备好物理隔离的独立 worktree 与专属任务包。

每个派发的独立任务包均标准化内嵌：

- 该子任务的角色定位与负责覆盖的验收 ID 集合；
- 独占绑定的物理工作区绝对路径；
- 当前集成分支的代码基线 Commit 哈希；
- 严密防伪、用于回传校验执行结果的 `runId` 凭据；
- 前置依赖完成条件及明确的停机退出指标。

Runtime 会通过 `readyChildren` 动态告知主会话哪些子任务的前置依赖已达成、可以即刻开工。在多会话模式下，默认最多并发推进 2 个在途子任务（支持在 Dashboard 或通过 `native.max_parallel_children` 弹性调节）；单会话模式下始终按拓扑序串行推进。

参数调整自后续新派发任务起生效，绝不粗暴掐断当前已经在途的子任务，亦不会违规跳过依赖前置条件。若下调并发配额，系统会从容等待在途任务收尾。详细配置说明请参阅 [Supervisor 子任务并发配置](/zh/native/configuration#supervisor-子任务并发)。

## 在 Codex 中通过多会话并发攻坚

在 Codex 中选定多会话协作后，当前会话自动升格为总调度中枢（Supervisor）。它负责任务拆解分发、轮询进度、排障阻断、指示 Runtime 串行集成各分支代码，并主持最终的全链路验收。主会话绝不亲自下场侵入子任务专属的 worktree 中修改代码。

命中 `readyChildren` 的各个子任务会交由前台可见的独立任务执行。独立任务复用当前工程上下文，直接入驻 Runtime 预先拉起的子工作区，无需二次新建目录。子任务 Agent 报告编码完成后，代码仍须通过子任务自身的 Verify 审查与 Runtime 集成校验；主会话始终以集成后的客观状态为准推进下一步。

## 在 Claude Code 中借助 Agent Teams 并行推进

在 Claude Code 的交互式终端环境中，可无缝利用 Agent Teams 特性并发驱动不同子任务。在 PowerShell 中可通过环境变量一键激活：

```powershell
$env:CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS="1"
```

当前主会话充当 Team Lead，为 `readyChildren` 中的每个子任务分配带有规范命名的 Teammate 协作智能体。Teammate 严格限定在 Runtime 指定的子工作区内编码，严禁越权私自新建工作区、抢跑尚未解锁依赖的子任务、直接篡改主干分支或递归拉起嵌套团队。

Agent Teams 专职负责并发会话进程的生命周期，而 Native Runtime 始终统筹工作区拓扑、状态机演进、验证裁决与分支集成：所有任务进度以 Runtime 磁盘记录为唯一真理，主任务最终验收亦由其严密主持，Teammates 之间的消息同步仅作为状态推演的辅助参考。

## 严守“先完成验证，后允许集成”铁律

每个子任务必须严格走完 `active（编码中）→ verified（验收达标）→ integrated（已入集成分支）` 的状态生命周期：

1. **子任务编码交付**：Builder 在子任务专属 worktree 中完成代码实现，提交绑定当期 `runId` 的交付快照；
2. **子任务局部验收**：Verifier 审查代码 Commit 并逐条比对该子任务名下的验收项。新创建的任务支持在同会话内闭环审查；若项目配置了强隔离审查门禁则必须严格遵守；
3. **交付凭据鉴权**：Runtime 严格比对会话角色、不可伪造的 `runId` 及状态版本号，坚决拒绝任何不合法的越权提交；
4. **原子化集成合流**：验证通过后，Runtime 自动将该子任务的 Commit 合并入 Supervisor 的集成分支，并触发集成构建检查。

子任务绝不单独触发 Archive 归档，亦无权直接擅自 Merge 主任务分支。单纯由 Agent 在口头上宣称“我已搞定”绝不能作为集成依据；若子工作区尚存未提交的散落文件，系统一律判定为尚未准备好。唯有当 Runtime 在底层将状态敲定为 `integrated` 后，依赖它的下游子任务才会正式进入 `readyChildren` 就绪池。

## 全量集成后的全链路终审验收

当全量子任务均顺利达成 `integrated` 状态后，Runtime 会立即拉起主任务的全局最终 Verify 阶段。最终验收严格在集成 worktree 中执行全套集成测试，并全面覆盖初始整体目标声明的 100% 验收范围。

唯有当最终 Verify 全量变绿后，Supervisor Change 方获准步入 Archive 归档阶段。开发者可自由在 Native 归档选项中选择保留本地工作区、本地合并入主干、推送到远端或自动发起 PR（详细参数请参考[归档与交付](/zh/native/archive-and-delivery)），主干分支在最终交付授权前绝不会被提前污染。

若最终全局 Verify 遭遇失败，Runtime 会完好保留集成分支案发现场，绝不粗暴打散已成功集成的子任务。流程会基于实际未通过的缺陷用例，自动追加一个命名唯一的“修复子任务”，动态校准整体验收矩阵，并退回 Shape 阶段引导你快速确认该增补修复范围。在最后一个子任务合流后，亦允许在父级目录直接微调修正代码，最终 Verify 会真实记录核验的最终集成分支 Commit；若恢复时遭遇中断，系统会自动补全或重跑最终验证。

## 韧性断点自愈与任务还原

全局子任务拓扑、当前就绪池 `readyChildren`、集成状态与下一步动作均实时落盘于 Runtime 状态中，主会话在遭遇会话重置或接续任务时，可通过 `comet native status <supervisor-change> --details --json` 瞬间读出完整现场。开发者日常只需发送“继续当前任务”，底层的状态还原与链路串联全权由主会话自适应完成。

在触发恢复时，Comet 严格以持久化在磁盘上的 `coordination_mode` 为准，绝不重复生成已存在的子任务或 worktree。`multi-session` 继续拉起多会话协作，`single-session` 继续由主会话顺序推进。

若原先绑定的 Codex 独立会话或 Claude Code 团队进程已丢失，Comet 会即刻重新扫描 Runtime，并在 `multi-session` 模式下智能退火采用 subagent 机制接续。针对已派发但在外失联的孤儿任务，系统会通过 `supervisor-cancel` 强制废弃旧版 `runId` 凭证，重新封包并分发全新 `runId` 重新调度；旧任务迟到的异地响应会被彻底拦截丢弃。若当前环境连 subagent 亦无法拉起，Comet 会如实打印底层卡点，绝不私自倒退为单会话模式。
