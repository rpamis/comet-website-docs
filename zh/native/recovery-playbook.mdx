排查异常时先不要改动文件：完整保留未提交改动与状态文件，再让 Agent 读取 `comet native status <change-name> --details --json` 与 `comet native doctor <change-name> --json` 的结构化输出。新创建的任务均依据底层的 SDK Run 与有效的跨端检查点恢复；本机的私有运行态记录集中落盘于用户主目录下的 Comet 全局数据目录中，按具体工作区隔离。

## SDK 任务的精准恢复工序

1. **核对环境基线**：核准所属工程根目录、Git worktree、绑定的 change 名称以及应用版本。
2. **加载挂起 Action 与下一步**：读取当前 Action 与 `continuation` 指引。处于待执行状态的任务依照记录继续推进；对于执行中突发失联或结果未知的任务，必须先回溯核查原会话上下文、底层进程存活状态以及文件层面的实际副作用。
3. **针对性补测，复用有效资产**：严格仅重跑已失效或缺失的测试项，完好保留依然有效的测试证据与已敲定的人工决策。若业务需求发生变化，必须回退至 Shape 阶段重新触发确认门禁。
4. **遵循 Runtime 指令修复**：只有在 Runtime 明确给出可恢复指令时才可执行自愈。禁止私自强删原 Run 实例、手动篡改检查点文件或在状态里伪造虚假的测试全通结果。

当需求文档或业务代码经过人工手动修改后，应先让 Agent 扫描当前差异，并遵循 Runtime 规划的安全路径平滑收敛。外在业务需求的漂移必须重新确认；凡受到代码改动波及、或无法自证依然有效的测试必须重新执行。在接续推进中断的归档事务时，系统具备幂等性，已完成的检查与 Spec 主干更新不重复执行。

`native archive --recover` 仅专门处理由 Runtime 明确识别出的归档挂起、集成交付或临时工作区清理中断。如果操作结果未知，该命令不会将操作标记为完成。当本机所有运行态数据彻底丢失且缺乏有效检查点时，应安全保留业务代码，遵循 Doctor 给出的排障分支逐步恢复，不可凭空宣称原验收结论依然合法。深层协议细节请参考 [SDK 恢复协议](/zh/sdk/recovery)。

Native 具备对绝大多数日常中断的全自动自愈能力。系统会完整保留在 Git 仓库中有据可查的业务需求、代码实现水位及逐条验收结论，仅针对性重跑已经丢失的本机临时进程或瞬态证据。你可直接在对话中示意接续，Runtime 会立即重读磁盘现场、校验工作区完整性，并给出确定的下一步操作建议。

恢复依据保存在仓库文件中：`brief.md`、各能力 Specs 规范、`comet-state.yaml` 与 `verification.md` 完整记录了所有已确认的交付成果；`.comet/runtime/native/` 只保存当前机器上的临时执行记录，随时可以按需重建。

## 自动化断点自愈机制

每次重新接续 Change 时，Native 均会自动比对 Git 仓库文件与本机执行流水：

1. 准确定位 Change 所绑定的真实分支与 Git worktree 实际路径；
2. 完整读取最近一次成功落盘的 `comet-state.yaml`；
3. 审查在途运行的后台命令、测试脚本或 Verifier 审查任务是否已异常中断；
4. 按需安全重建缺失或陈旧的本机执行缓存；
5. 基于当前已掌握的客观证据推进当前阶段，或回退至需要重新校验的断点。

若 Shape 或 Build 阶段的本机缓存丢失，Native 会在原阶段就地接续，已确认的需求决策与验收项清单不丢失。由于 Verify 与 Archive 强依赖当机执行证据，若此时相关凭证缺失，系统会稳妥重跑当期代码的各项测试。

## 会话异常中断应对指南

会话上下文被压缩或窗口关闭，并不代表后台的长时间测试进程已经失败。在同一台机器上重新接续时，Agent 会先检查原检查命令或 Verifier 进程是否仍在后台运行：若任务仍在执行，则继续保持等待；只有在确认进程崩溃、任务通信句柄丢失或退出后未产生合法产物时，才会触发重试。若更换了机器或本机缓存损坏，则基于 Git 中已提交的文件恢复。

| 遭遇中断的节点 | Native 状态机的自愈策略 |
| --- | --- |
| Shape 需求定义阶段 | 完整重载已持久化的所有决策与存疑项，平滑继续需求澄清 |
| Build 代码实现阶段 | 完整保留既定需求边界与当前已写的代码，从当前文件继续编码 |
| Verify 处于 `verify-ready` | 安全复用依然有效的代码快照与基线结论，重跑缺失测试并唤起新 Verifier |
| Verify 处于等待裁决阶段 | 先尝试找回并等待原 Verifier 响应；确认进程失联后，针对当前代码快照重新评测 |
| Archive 归档就绪阶段 | 安全退回 Verify，针对最终同步后的代码重新复核全量验收项 |
| 幂等无副作用检查执行中 | 直接针对性重新执行该项自动化检查 |
| 包含外部副作用且无法幂等重放的测试 | 强制回退至 Build 阶段，生成全新的候选快照后再行审慎验证 |

因断点恢复引发的测试重跑纯属“执行级自愈”，代码实现失败计数与连续无进展计数保持原样不变。仅在真实唤起全新 Verifier 时，审查尝试次数才会合规递增。

## 跨设备接续推进

在更换开发机前，请确保在 Git 仓库中完整提交并推送了以下内容：

- 业务源码以及所属的特定分支或 Git worktree；
- Change 目录内部的 `brief.md`、各 capability Specs 以及 `comet-state.yaml`；
- （可选）已渲染好的 `verification.md` 图文报告；
- （若使用了自定义产物目录）项目全局配置 `.comet/config.yaml`。

在新设备上克隆或拉取仓库后，Native 会基于上述文件完整重建本机的临时执行态。旧机器上的后台进程与旧会话上下文安全停留在原设备；新机器完全基于仓库内可核实的确定性证据创建全新的执行环境。

已流转完成的 Shape 与 Build 阶段成果完整保留。若 Change 在旧机器上正处于 Verify 审查中、或已处于等待 Archive 归档状态，新设备会针对同步到本地的代码重跑验收。在恢复期间，既有的验收失败次数与无进展停滞指标均保持原样锁定。

在旧机器上未执行 `git commit` 或未推送的代码无法凭空还原。若拉取后的代码无法完全跑通既定验收项，新拉起的 Verifier 会客观指出未通过的具体用例，并驱动 Change 稳妥退回 Build 阶段继续补齐。

## 工作区拓扑与分支恢复

Native 启动时会自动扫描 Git 中登记的所有 worktree，优先绑定与 Change 关联的分支。即便你在终端中处于仓库的主根目录，Runtime 亦能准确识别出 Change 实际所在的子目录，并引导 Agent 在正确的沙盒中作业。

若当前所在分支、worktree 模式或工程根路径与落盘元数据发生分歧，Runtime 会立即终止写入并明确打印预期目录。若原目录依然存在，Agent 会平滑切换至正确路径；若 worktree 此前被手动删除但 Git 分支依然完好，Native 会自动重建该 worktree。

只有在出现以下真实歧义时，才需要开发者介入确认：

- 绑定的分支被外部重命名，或被其他并发分支合并覆盖；
- 本地扫描发现多个同样符合条件的歧义工作目录；
- 原 Git 分支与关联目录均已彻底丢失；
- 同一个 Change 的状态机元数据在两个不同路径下检测到版本冲突。

此时你可以指定信任的实际路径、从 Git 历史检出或终止该 Change。Runtime 会安全封存当前文件，等待你的明确授权。

## Archive 事务级归档恢复

Archive 归档操作在底层会依次有序推进：更新系统主 Spec、写入终态元数据、渲染最终验证报告，最后将 Change 整体迁入归档历史目录。Runtime 在底层通过事务机制追踪每一步执行水位；若进程在中途遭遇强杀或机器掉电，重启后随时可从已成功的断点安全接续。

重新触发同一个处于中断状态的 Archive 时，Native 会严格比对底层事务账本与真实磁盘文件：

- 事务记录与文件一致时，平滑从下一步继续流转；
- Change 核心已归档成功、但 Git 工作区收尾动作受阻时，安全保留归档成果，并精准输出 Git 纠偏指令；
- 检测到 active 与 archive 目录同时并存时，保留双侧现场，触发挂起等待排查；
- 多个并发 Change 同时声明同一份 Spec 时，暂停推进并等待开发者裁决归档次序。

若工作区收尾失败发生在 Archive 写入之后，表明 Change 已经在元数据层面完成了归档。此时请依照系统返回的 `recoveryArgs` 参数核查 Git 现场，继续完成分支 merge、push 或创建 PR 流程。

若项目配置的 `commit-msg` Git Hook 拦截了 Commit 内容，Agent 会严格尊重项目 Hook 约定，通过 `--commit-message` 或 `--merge-message` 纠正未竟步骤的文案格式，再重新执行恢复指令。已成功的 Commit 与主 Spec 发布不会重复执行，先前选定的交付策略亦无需重新选择。Status 与 Doctor 诊断命令会清晰展示具体哪一步未走完，不会将已归档的 Change 错误当成丢失目录去发起二次迁移。

若你此前已在终端中手动完成了 Git Commit 或 Merge，请先执行 `doctor` 评估现场。只有在 Runtime 能够证明本地改动、Commit 记录与交付策略完全契合时，`doctor --repair` 才会安全清理掉本地多余的暂存记录；而远端推送与 PR 创建始终由 Archive 与远端平台核对为准。归档目录的存在，不能简单盲信为 Git 交付已全量完成。

## 验证报告的一键重建机制

`verification.md` 负责将 `comet-state.yaml` 中的机器状态格式化渲染为图文并茂的人类报告。若该 Markdown 报告文件被误删、写入遭遇意外截断或版本稍显滞后，Native 随时可根据底层权威 YAML 状态重新渲染。

若仅是报告文件丢失，但底层的状态元数据与本机执行流水能够相互印证，恢复过程仅轻量补齐 Markdown 报告即可。但若在流转至 Archive 前夕连本机的执行凭证也一并丢失，Native 会返回 Verify，重新运行检查并记录结果。

这一设计既减少了不必要的重测耗时，又从架构上避免了在缺乏客观证据的情况下将未经检验的代码轻率归档。

## 必须交由开发者亲自裁决的场景

在面临可能引发代码意外覆盖、产生不可逆外部副作用或错误归档的临界点时，Native 会放弃自动推进，主动停机：

| 异常现场 | 开发者所需决策或处理的事项 |
| --- | --- |
| 本地工作区与 Change 绑定发生分歧 | 核对并指定正确的 Git 分支或 worktree 路径 |
| 多个并发推进的 Change 同时改动了同一份能力 Spec | 明确裁决谁先归档入库的先后次序 |
| 跨端 Git 同步时产生业务代码或文档冲突 | 在编辑器中手动解冲突并提交，随后通知流程继续验证 |
| 针对外部第三方平台的网络操作结果无法确证 | 登入远端控制台核对实际状态，随后决定重试或跳过 |
| 连续排错失败轮次触碰配置熔断阈值 | 评估是继续在当前思路上深究、微调需求范围还是终止 |
| active 目录与 archive 归档目录状态自相矛盾 | 保留当前目录和运行状态，执行 `comet native doctor` 诊断 |
| 历史旧版本 Change 急需格式迁移 | 遵循 Runtime 提供的标准化迁移指令执行元数据升级 |

`await-user` 标明下一步在等待你作出业务决定；`blocked` 则表明在当前环境下缺失安全的推演路径。Runtime 在挂起时会同步打印阻塞根因、责任归属方以及系统允许执行的合规修复动作。

## 离线状态查阅与一键诊断

日常正常的中断恢复完全由 Native 自动完成。若需要深入了解系统底层细节或排障，随时可在终端中执行：

```bash
comet native show <change-name>
comet native status <change-name> --details --json
comet native doctor <change-name>
```

`show` 与 `status` 直观展示正式技术产物、工作区路径、各用例验收进度以及下一步指引。`doctor` 深度检查数据迁移、事务完整性、目录映射与状态机一致性。请格外注意：`doctor --repair` 仅在诊断报告给出了清晰经过校验的修复动作时才被允许执行。

在整个恢复处置周期中，请交由 Runtime 接管 `comet-state.yaml`、本机运行态缓存、并发锁与事务。严格遵循 `continuation`、`recoveryArgs` 或 `doctor` 返回的标准动作推演，即可完好保护已有成果与故障第一现场。
