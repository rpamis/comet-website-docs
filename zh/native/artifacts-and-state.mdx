Native 工作流将业务需求与验收文档妥善保留在项目工程内，而将 SDK 底层的运行态数据存放于用户主目录下的 Comet 全局数据目录中。新创建任务的执行生命周期均由 SDK Run 统一纳管。

正式的技术文档、实施计划与测试报告均不再受内置字节上限截断。当文件读取遭遇异常时会如实报告错误原因，绝不拿陈旧缓存充当完整材料。

## SDK 默认存储布局

```text
<project>/
  .comet/config.yaml
  .comet/current-change.json
  <artifact-root>/comet/changes/<change-name>/
    brief.md
    specs/<capability>/spec.md
    comet-state.yaml
    verification.md
```

`<artifact-root>` 会根据项目配置文件及 Runtime 实际返回的解析路径动态确定。本机的 Run 实例、执行日志与事务锁均按 Checkout 分支与 Git worktree 实行严格物理隔离，并不强求项目内必须包含 `.comet/runtime/native/` 目录。状态视图内的有效断点检查点可用于直接唤醒并恢复原 Run，文档正文由开发者与 Agent 按规范共同维护，报告与机器状态元数据则由 Runtime 自动刷新。详细恢复条件请参考 [SDK 持久化与恢复](/zh/sdk/recovery)。

Native 将开发者需要阅读、评审与版本同步的内容集中于 change 目录，而将纯粹的机器执行过程解耦至项目级 Runtime。日常开发中你通常只需关注 `brief.md`、`spec.md`、`comet-state.yaml` 与 `verification.md` 即可。

`native.artifact_root` 支持灵活自定义为工程内的相对路径（如 `artifacts/comet/`）。`.comet/config.yaml` 与 `.comet/current-change.json` 随项目版本绑定；而 `.comet/runtime/native/` 纯属内部运行时目录，默认被 `.gitignore` 自动忽略，既不会被复制进 change 归档包，亦不属于需要提交的版本文档。

## 三类核心用户可读文件

### `brief.md`（需求与设计摘要）

`brief.md` 明确约定了本次变更的最终目标、覆盖范围、明确非目标（Non-goals）、已确认的人工决策、待决问题、验收场景样例以及验证期望。它是 Shape 阶段的核心任务契约，开发者可随时直观查阅或直接编辑。

对于轻量改动，只需填充最核心的四大章节：`Outcome`、`Scope`、`Non-goals` 与 `Acceptance examples` 即可。当有真实增量信息时，再补充约束条件、架构决议、待敲定细节或特殊测试要求；切勿为了形式上的完整强行机械填写大量的“无”。

`Scope` 下的 `## 目录结构` 章节用以梳理拟改动的模块与关键文件路径，拆分为 `### 新建`、`### 修改`、`### 删除` 与 `### 明确不建` 四个子模块。每个路径使用一句话简要阐述其核心职责或改动点；若包含层级归属可使用树形结构，独立文件直接列出即可，无改动的子项注明“无”。单文件极简任务仅需列出目标路径，无需赘述展开文件树。

目录结构需随同完整的 Shape 方案一并敲定。在已确认的模块边界内增加常规辅助性文件无需重新发起流程确认；但若改动范围发生扩散或核心职责划分发生重构，必须先更新目录拓扑及相关决策，再行确认方案。0.4.5 版本前已核准的 change 保留既有规则与推进状态，仅在重新进入 Shape 确认时才执行新规范。

在手动编辑 `brief.md` 或 `spec.md` 时，请格外留意验收项的解析机制：Runtime 仅从两处严格提取有效验收项——即 **brief 顶层的 Acceptance examples 验收样例**，以及 **Spec 中以 `Scenario:` 命名的标准验收场景**。常规描述段落、普通无序列表或零散的 WHEN/THEN 语句均不会被识别为正式验收项。因此，若要增删或修正验收边界，请务必在这两处采用规范结构进行维护。

当 Spec 场景与 brief 中既有的验收项表述同一行为时，可在场景正文单独声明 `Acceptance: A1` 或 `验收：A1`，直接复用当前 brief 的真实验收编号。单个场景仅允许绑定一个编号，避免重复衍生相同验收项；对于新增的业务行为，则应设立全新独立场景。显式引用并不会跳过完整的 Spec 审查，Verifier 仍会严格核验场景中的行为与约束。

按新版规范确认的 Shape 允许自由优化 brief 与 Spec 的纯 Markdown 排版，绝不会引发实现进度的意外丢失。只有在目标、边界、核心验收文本或子任务发生实质性调整时，才需退回 Shape 阶段重新确认；历史旧 change 完整沿用原有规则。若章节排版格式有误，Runtime 会明确指出需要修正的具体文档。

### `specs/<capability>/spec.md`（能力规格说明）

capability 指代系统中一项高内聚的独立功能特性（例如“头像上传”或“会话超时策略”）。Spec 严格按能力维度进行组织，每个 capability 占据独立子目录，其下的 `spec.md` 描述该项能力在归档合并后的全量系统规格。在归档阶段，Runtime 会依声明执行 `create`（新建）、`modify`（全量覆盖）或 `remove`（在受控路径内安全移除）。若需显式废弃某项 capability，请运行 `comet native spec remove` 登记删除意图——若仅在物理磁盘上删除该 Spec 文件，系统将不会视为正规废弃，归档时仍按该 Spec 存在处理。当并行的多个 change 尝试并发变更同一个 capability 时，系统会停顿要求先确立归档先后次序，杜绝静默文件覆盖。

### `comet-state.yaml`（跨设备持久化状态源）

这是实现跨平台、跨设备无损接续的核心可信凭据。它忠实记录了以下维度的现场数据：

- 当前所处的工作流阶段与内部运行状态；
- Native Loop 演进进度：`iteration` 代表代码实现的迭代轮次（Builder 每次提交全新候选时递增）；`attempt` 代表针对同一份代码候选的验收验证尝试次数；
- 全量验收项清单及其测试结论；
- Builder handoff 交付快照：Builder 在提交候选实现时留下的交接说明，清晰阐释本次涉及的改动点并声明受影响的验收项；
- 必要的健康检查摘要、Verifier 裁决结论及阻塞诱因；
- 最近 50 条原子操作审计轨迹以及下一步操作建议。

在遭遇会话重置、切换工作设备或上下文被压缩后，新接手的 Agent 虽无先前的聊天历史，但只需优先解析该文件，便能按照记录的下一步指引（`continuation`，详细字段语义请参考[任务推进与中断恢复](/zh/native/continuation-and-checkpoints)）无缝接续。

### `verification.md`（人类可读验证报告）

这是由 Runtime 基于底层状态自动渲染的可视化报告，详实呈现了测试命令执行记录、逐条验收核验明细、潜在风险警示、环境局限及最终裁决。该文件属于可随时重新生成的展示型快照，并非状态机推演的直接输入源；即使文件丢失或版本落后，Runtime 随时可基于 `comet-state.yaml` 一键无损重建。

## 本机 Runtime 运行时机制

`.comet/runtime/native/` 仅承载四类纯本机的瞬态数据：执行状态快照（Overlay）、诊断日志、并发操作锁以及可恢复事务上下文。并发操作锁仅在单个操作指令执行的生命周期内被持有，旨在防范多个进程并发篡改同一 change，执行完毕即刻释放。该目录即便因换机或系统清理而彻底缺失，Runtime 也能完全基于 Git 仓库内同步的 YAML 规范完成重建，绝不把本机执行状态作为跨设备恢复的硬性依赖。操作日志主要便于排查底层命令的 stdout/stderr 详情，不能替代面向业务交付的 `verification.md`。各类文件在系统内部的组件归属请参考 [Native Runtime 体系架构](/zh/native/runtime)。

`.comet/current-change.json` 仅作为快捷标记，用于声明下一次免参数调用归属于哪个 workflow/change，绝不限制整个工程只能并行存在一个 active change。状态查询完全是只读操作；在多任务并行且需要精准锚定时，推荐显式指定 `comet native select <change-name>`。

## 跨设备与跨端断点接续

你无需手动运行恢复命令。在目标新设备上拉取 Git 仓库代码后，直接对 Agent 发送“继续刚才的需求”即可。Comet 会率先通过自动化恢复探测定位到关联的 active change，Agent 会根据 Runtime 返回的工作区绑定信息及下一步动作建议，全自动完成状态加载、环境校准与流程接续。

跨设备同步必须包含：项目业务代码、`.comet/config.yaml`、`brief.md`、各能力 Specs 规范以及 `comet-state.yaml`。若当前已生成 `verification.md`，推荐一并推送到 Git；即便遗漏，Runtime 亦能根据 `comet-state.yaml` 一键重建，绝不阻塞 Shape 或 Build 阶段的正常恢复。由于 `.comet/runtime/native/` 纯属本机私有执行态，无需也不应跨设备复制。

当目标机器缺少 Runtime 缓存，或本地执行状态已过期失效时，Runtime 会基于 `comet-state.yaml` 记录的拓扑自动完成重建。遭遇意外中断的未竟测试将被当作中断安全处理；必须重新执行的基线检查会自动重跑，任何无法确保幂等安全复用的 Verifier 结论或 `archive-ready` 标记均会重新触发严密核验。整个恢复过程完全不依赖旧机器上的 `state.json`，更不会因拷贝了陈旧的 Runtime 缓存而轻率完成归档。

只有在代码未拉取最新提交、本地 Git 分支或 worktree 与当前 change 绑定冲突、存在多个同样符合条件的歧义工作区，或者本地 active/archive 目录命名撞车时，Comet 才会暂停并向你抛出精准的选择题等待排查。

下列命令仅在需要深入排障或查阅详细内部状态时使用，日常推荐直接启动 Comet Dashboard 掌控全局：

```bash
comet native status <change-name> --details
comet native doctor <change-name>
```

## 归档与最终交付

归档流转时的核心交付策略选择（保留工作区 / 本地合并 / 推送远端 / 发起 PR / 暂缓处理）请参阅[归档与交付](/zh/native/archive-and-delivery)。

## 归档完成后的现场收敛

当 change 成功完成归档后，最终沉淀在 Git 仓库中的仅包含面向人类与团队协作的 `brief.md`、Specs 规范、`comet-state.yaml` 以及详实的 `verification.md`。位于 `.comet/runtime/native/` 中属于该 change 的临时机器目录会被自动清理；历史版本遗留的机器产物仅通过兼容适配器维持只读兼容，绝不会渗入新的 Native 流程中。
