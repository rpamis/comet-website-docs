Native 把需求文档、目标 Specs、状态检查点和验收报告保存在项目仓库中，把完整的运行记录（Run）保存在本机用户数据目录中。你想了解一个 change 约定了什么看 `brief.md`，想看验收证据看 `verification.md`，想了解当前阶段和下一步直接在对话里问 Agent（或用终端只读查看）。

## 找到 change 的实际目录

以下以 `login-error-message` 为例。默认产物根目录是 `docs`，可在 `.comet/config.yaml` 中通过 `native.artifact_root` 调整：

```text
docs/comet/
  changes/login-error-message/
    brief.md
    specs/authentication/spec.md
    specs/authentication/delta.yaml
    capability-association.yaml
    comet-state.yaml
    verification.md
  specs/authentication/spec.md
  archive/
```

说明：

- `delta.yaml` 和 `capability-association.yaml` 在修改项目已有能力（capability）时出现；
- 首次 Verify 通过并生成报告前，`verification.md` 可能尚未出现；
- Supervisor Change 还会包含 `children.yaml`。

日常开发时，Agent 会自动按配置解析这些路径，你不需要手动查路径；如果想在终端查看某个 change 的正式文档路径和摘要，可以运行只读命令 `comet native show <change-name>`（加 `--json` 可看 `artifacts` 里的全部路径）。已归档的材料保存在 `docs/comet/archive/` 对应日期目录中。

## 在 Shape 中维护的需求文档

<span id="briefmd" />

### `brief.md`

`brief.md` 记录目标、范围、明确排除的非目标、硬约束、影响交付的用户决定和验收依据。描述工程范围时，可以按任务需要用目录树、列表或表格列出要新增、修改或删除的关键模块。涉及用户决策的待确认问题用 `[blocking]` 标记，回答后立即同步回正文并移除标记。如果需求来自外部 PRD 或本地文档，还会在 `# Scope` 下维护 `## Source coverage` 来源覆盖表。

### 目标 Spec 与 `delta.yaml`

change 目录里的 `specs/<capability>/spec.md` 描述归档后这项能力应有的完整行为——既写清本次修改，也保留该能力仍然有效的既有规则：

- **新能力**：由 Agent 直接编写完整目标 Spec。
- **修改已有能力**：Agent 在 `delta.yaml` 中维护需求级增删改（引用稳定的需求 ID），Runtime 基于项目当前正式 Spec 自动生成完整目标 Spec 供 Shape 评审和 Verify 核验。
- **移除已有能力**：在对话中告知 Agent 移除该能力（后台通过 `spec remove` 登记），直接删文件无法记录移除意图。

以登录提示为例，项目的 `docs/comet/specs/authentication/spec.md` 是已生效的正式规范；change 目录下的目标 Spec 用于评审与验收，直到 Archive 阶段才会由 Runtime 合入项目正式 Specs。

### `children.yaml`

Supervisor Change 用 `children.yaml`（`comet.native.children.v2`）记录各子任务的名称、依赖顺序（`depends_on`）以及覆盖的验收 ID（`covers`）。子任务只引用编号，不重复抄写验收正文；父任务保留全部验收要求。详见 [Supervisor Change](/zh/native/supervisor-change)。

## 由 Comet 自动维护的状态与报告

以下文件由 Runtime 维护，请勿手工编辑（编辑它们无法推进 Run，Hook Guard 也会拦截 Agent 直接改写）：

| 文件或记录 | 存放位置 | 用途 |
| --- | --- | --- |
| `comet-state.yaml` | change 目录。 | 记录阶段、验收状态，并在关键边界保存恢复检查点（`run_checkpoint`）。 |
| `verification.md` | change 目录，归档后随 change 保存。 | 结构化验收结论的只读阅读视图，展示逐项结论、检查命令、审查方式和已知限制。 |
| `capability-association.yaml` | change 目录（关联已有能力时）。 | 记录当前 change 关联的项目能力标识；需撤销关联时告诉 Agent 处理。 |
| `.comet/current-change.json` | 当前项目的 `.comet/`。 | 记录当前工作区选中的工作流与 change，用于 Hook 路由与默认归属。 |
| 本机 Run 和执行记录 | 默认位于 `~/.comet` 下按工作区隔离的目录（可用 `COMET_DATA_DIR` 自定义）。 | 保存完整执行历史、动作领取、用户决定与事务日志；主工作区与各 Git worktree 分开保存。 |

## 判断哪些内容需要随项目同步

- **需要随 Git 同步**：业务代码、正式需求材料（`brief.md`、目标 Specs、`delta.yaml`、`children.yaml`）、含恢复检查点的 `comet-state.yaml`、已生成的 `verification.md`，以及使用非默认产物目录时的 `.comet/config.yaml`。归档后，归档目录与更新后的项目正式 Specs 一并提交。
- **仅保留在本机**：`.comet/current-change.json` 和用户主目录下的本机 Run 目录不需要提交到 Git。如果任务还在执行中，请保留本机记录，以便核对未回传的结果和未完成的事务。

跨设备恢复和异常排障详见 [Native 任务恢复](/zh/native/recovery-playbook)。
