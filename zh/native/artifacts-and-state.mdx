---
title: 'Native 产物与状态'
description: '理解 Native 的用户文档、可跨设备恢复的状态，以及本机 Runtime 文件各自负责什么。'
---

Native 把用户需要阅读和同步的内容放在 change 目录，把执行过程放在项目级 Runtime。你通常只需要看 brief、Spec、`comet-state.yaml` 和 `verification.md`；不要手工创建或修改 Runtime 文件。

## 项目布局

默认布局如下：

```text
<project>/
  .comet/
    config.yaml
    current-change.json
    runtime/native/
      changes/<change-name>/state.json
      logs/
      locks/
      transactions/
  docs/comet/
    specs/
    changes/
      <change-name>/
        brief.md
        comet-state.yaml
        specs/<capability>/spec.md
        verification.md
    archive/
      YYYY-MM-DD-<change-name>/
```

`native.artifact_root` 可以改成项目内其他相对目录，例如 `artifacts/comet/`。`.comet/config.yaml` 和 `.comet/current-change.json` 仍属于项目级边界；`.comet/runtime/native/` 由 Runtime 管理并默认忽略，不应复制到 change 目录或提交为用户文档。

## 三类用户可读文件

### `brief.md`

brief 说明目标、范围、非目标、已确认的用户决定、未解决问题、验收示例和验证期望。它是 Shape 阶段的工作说明，用户能直接阅读和修改需求。

### `specs/<capability>/spec.md`

每个 Spec 描述归档后 capability 的完整行为。归档时 Runtime 会按声明执行 `create`、`modify` 或 `remove`：创建、完整替换，或在受控路径内删除。并行 change 如果都要改同一 capability，会先停下来要求确定归档顺序，不会自动覆盖。

### `comet-state.yaml`

这是跨设备恢复的稳定状态。它记录当前阶段和状态、Loop 的 iteration/attempt、完整验收项及结果、Builder handoff、必要检查摘要、Verifier 结论、阻塞原因、有限历史和下一步动作。新 Agent 先读它，再按 continuation 执行，不依赖上一轮聊天内容。

### `verification.md`

这是 Runtime 根据状态生成的用户报告，包含实际检查、逐项验收、风险、限制和结论。它是可重建的展示文件，不是推进阶段的输入；缺失或落后时，Runtime 可以从 `comet-state.yaml` 重建。

## 本机 Runtime

`.comet/runtime/native/` 只保存本机执行 overlay、日志、短时锁和可恢复事务。它可能因换设备或清理而缺失；Runtime 会依据同步的 YAML 重建，而不会把本机 overlay 当成跨设备事实。日志适合排查命令输出，不能替代 `verification.md`。

`.comet/current-change.json` 只表示下一次写入归属哪个 workflow/change，不限制项目只能有一个 active change。状态查看是只读的；需要明确归属时使用 `comet native select <change-name>`。

## 跨设备恢复

同步项目代码、`.comet/config.yaml`、`brief.md`、Specs 和 `comet-state.yaml`。如果已经生成报告，也一并同步 `verification.md`，但缺失报告不应阻止 Shape 或 Build 恢复。目标设备先确认 artifact root、分支或 worktree 匹配，再运行：

```bash
comet status
comet native status <change-name> --details --json
comet native doctor <change-name>
```

正在执行的本机检查会被视为中断；Verify 或 `archive-ready` 的旧结果会按 Runtime 的恢复策略重新确认，不会因为复制了一个旧 `state.json` 就直接归档。代码未同步、分支不匹配或 active/archive 目录冲突时，Runtime 会停下并给出明确的用户动作。

## 归档后

成功归档的 change 只保留 brief、Specs、`comet-state.yaml` 和 `verification.md` 等用户可读内容。`.comet/runtime/native/` 中该 change 的本机执行目录会清理；旧版本遗留的机器文件只通过迁移或只读适配器处理，不会成为新 Native 流程的输入。
