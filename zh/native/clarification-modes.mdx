Native 在进入 Build 前设置 **Shape 澄清阶段**，将口头需求整理成边界清晰、可验证的行为规格与验收项，在编码前锁定边界行为、失败回退和范围约束。

配置项 `native.clarification_mode` 控制提问节奏，支持 `batch`（默认）和 `sequential` 两种模式。无论选哪一种，最终产物格式一致，且都必须经过你的最终确认才能进入 Build。

## 先分清哪些该问你，哪些不该问

Native 不会把所有细节都抛给你做选择题，而是先按三类信息分流（详细边界见 [哪些决定需要你确认](/zh/native/decision-ownership)）：

1. **可调查事实**：仓库现状、现有接口、工具能力、依赖默认值和运行环境。由 Agent 直接查代码或并行派发只读调查完成，不打扰你。
2. **用户决定**：不同选法会实质改变输出、默认行为、失败结果、交付范围或不可逆影响，且无法从现有文档和项目规则可靠推断。这类才向你提问。
3. **实现选择**：不影响用户可见结果的算法、内部结构和代码组织方式。由 Agent 自行决定。

如果你把 PRD 文档、本地文件、附件或外部链接作为需求来源，Agent 会先按源文档覆盖边界整理完整来源条目，再针对里面的歧义、遗漏或未说明限制向你提问。如果材料只是拿来做排错、取证或实现参考，则不会触发源文档全量覆盖流程。

## Batch 与 Sequential 模式对比

在 `.comet/config.yaml` 中切换：

```yaml
native:
  clarification_mode: batch # 可选：batch（默认） | sequential
```

| 澄清模式 | 每轮怎么问 | 适合的场景 |
| --- | --- | --- |
| **`batch`（默认）** | 一次提出当前前置事实已查明、前置决定已明确、且彼此独立的全部问题。 | 需求大方向清晰，各个决策点耦合度不高，希望少来回几轮对话就定稿。 |
| **`sequential`** | 每轮只提一道影响面最大的问题，等你回答并更新依赖后，再推导出下一题。 | 需求还在探索阶段，前面一个答案会直接改变后续方案分支，甚至让后面的问题不再存在。 |

中途修改这项配置只影响下一轮提问方式，`brief.md` 中已经写下的决定和还没回答的 `[blocking]` 问题都会原样保留。

## 问题排序与动态依赖管理

对于简单需求，Agent 直接列出待确认项和必要依赖即可，不强行套用复杂的节点结构；当多个决定互相影响、前置选择会改变后续分支时，Agent 会在工作内存中维护一棵动态依赖决策树（不会为此生成额外的 Runtime 状态文件）。

一道问题只有同时满足三个条件，才会进入本轮可提问集合：

1. 它依赖的上游用户决定已经明确；
2. 回答它所需的代码库事实已经查明；
3. 它不依赖本轮里其他还没回答的问题。

等待某项代码调查时，只暂停依赖该事实的分支，其他独立问题和调查照常推进。每收到你的一个回答，Agent 会立刻重算受影响的后续分支，避免问出已经被前置选择淘汰的无效问题。

## 提问格式与交互工具自动回退

为了让你一眼看清差异，每个问题都会把抽象需求写成具体的“输入 → 输出”或“触发条件 → 结果”，包含三要素：**需要决定的差异**、**推荐方案与理由**、**各选项的实际影响**。

- **优先使用结构化提问组件**：当存在两个及以上清晰选项，且当前 Agent 平台提供 `AskUserQuestion` 等结构化提问工具时，优先用组件发问；单选项严格互斥，只有允许组合多个兼容特性时才用多选。组件调用成功后直接等待，不会再重复输出一遍纯文本。
- **自动回退到编号文本**：遇到开放式问题、平台无组件、组件调用报错，或者 `batch` 模式本轮题数超出组件支持的上限时，会**整批回退到编号文本格式**，不会为了迁就组件限制把同一轮问题拆成多次零散提问。

Batch 文本提问固定使用稳定的 `Q1`、`Q2` 题号（标注“单选”“多选”或“开放回答”）。如果你一轮里只回答了部分题目，未回答项会保留原题号进入下一轮，不会重新编号打乱记忆：

```markdown
💬 **Q1｜头像上传失败时的页面行为（单选）**

上传接口返回失败时，需要确定头像区域的展示状态。

| 选项 | 方案 | 实际影响 |
| --- | --- | --- |
| A | 保留原头像并提示失败 | 用户不会丢失旧头像，失败后可直接重试。 |
| B | 清空头像预览 | 视觉更直接，但用户需要重新选择文件。 |

💡 **推荐回答：A（保留原头像并提示失败）**

推荐理由：避免临时网络波动让用户误以为原有头像已被删除。
```

对于事实不足的开放题，Agent 只说明需要你补充什么信息或格式，不会编造推荐选项；对于 Supervisor 协作模式、工作区隔离这类已有固定选项的问题，保留原选项标识和完整影响。

## 回答立即写入正式文档

聊天记录只用来沟通，项目里的文件才是中断恢复的依据。收到你的回答后，Agent 会立刻把已确认的结论写入 `brief.md` 的 **Decisions** 章节，同步更新目标 Spec 和验收项，并移除已解决项；只答了一半或仍含糊的内容会保留在 **Open questions** 中（一个回答只确认你明确说清的部分）。

`sequential` 模式记录当前待确认项：

```markdown
## Open questions

- [blocking] 头像上传失败时，保留原头像还是清空？
```

`batch` 模式保留稳定题号：

```markdown
## Open questions

- [blocking] Q1: 头像上传失败时，保留原头像还是清空？
- [blocking] Q2: 是否允许用户删除现有头像？
```

即使当前问题列表已空，也不代表自动结束澄清——Agent 还会核对是否遗漏隐含假设、边界条件和异常分支，确认全部覆盖后再发起最终确认。

## 进入 Build 前的最终确认与变更重审

满足以下条件后进入最终确认：所有影响可见结果的决定已明确、隐含假设已核实、`brief.md` 中已无 `[blocking]`、改动涉及的目录结构已写清、且验收项具体可验证无重复。

1. **提交验收条目**：Agent 从正式文档整理验收项与摘要提交给 Runtime，CLI 分配稳定验收 ID（大型需求在此前会评估是否拆分为 [Supervisor Change](/zh/native/supervisor-change)）。
2. **展示完整 Shape 等待确认**：Agent 呈现完整方案——**目标与范围**、**关键决定**、**逐条验收项**和**非目标边界**，等待你明确同意。最终确认本身不会写成一条普通的 `[blocking]` 问题。
3. **带保护参数推进到 Build**：你在对话中明确同意后，Agent 会在后台自动调用确认命令（附带状态版本与预期动作校验参数；多子任务 Supervisor 同时附带所选协作模式），使流程进入 Build。

你最初提出的需求描述不能代替这次最终确认。如果你在最后一步提出补充或推翻了某项决定，Agent 会更新文档并重新发起确认，旧方案的确认立刻失效。

### 中途需求变化后的重新确认

如果是在 Build、Verify 或待归档阶段因为需求变化回到 Shape 重新确认，Agent 会先对照上次已批准的方案给你一份**变化摘要**：

- 新增、删除和修改了哪些行为；
- 影响了哪些验收项；
- 哪些已有代码和检查还能保留，哪些步骤需要重做。

看完变化摘要后，确认的对象仍是**完整的当前 Shape**。如果缺少可信的旧方案可供比对，Agent 会如实说明无法逐项对比，不会编造差异或宣称“其余不变”。

## 中断后继续澄清

澄清中途关闭对话或切走窗口，重新进入项目在对话中直接继续原任务即可。Native 会从 `.comet/config.yaml` 和 `brief.md` 恢复当前的澄清模式、已写下的决议以及带原题号的待确认项。日常不需要手动输入命令，直接在对话里继续即可；如果你想自己在终端离线查看当前文档与状态，可以运行下面两条只读命令：

```bash
comet native show <change-name>
comet native status <change-name> --details
```
