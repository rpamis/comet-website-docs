Native 在识别出需要人工裁决的关键分歧后，会基于问题间的逻辑依赖动态编排澄清轮次。配置项 `native.clarification_mode` 负责控制每轮发问的节奏与并发度；两种模式底层共享统一的正式产物规范，且在正式进入 Build 阶段前均需完成最终需求确认。

新项目默认采用 `batch` 模式。若需求尚处探索阶段，且前置答案可能颠覆后续设计分支时，可平滑切换为 `sequential` 模式。

人工决策点的判定准则及上游文档覆盖规则请参考 [哪些决定需要你确认](/zh/native/decision-ownership)。

## Sequential 与 Batch 模式对比

在 `.comet/config.yaml` 中即可灵活切换澄清模式：

```yaml
native:
  clarification_mode: batch
```

| 澄清模式 | 提问交互机制 | 适用业务场景 |
| --- | --- | --- |
| `batch`（默认） | 批量聚合提出当前批次所有前置条件具备、彼此独立的决策点 | 各项选择之间耦合度较低，希望尽量减少会话往返频次 |
| `sequential` | 严格按依赖拓扑逐题发问，收到反馈后重新推导后续题目 | 前置决策会直接影响后续的技术路线、选项分支或发问范围 |

在项目中随时切换模式仅影响后续轮次的提问节奏。`brief.md` 中已记录的 `[blocking]` 问题继续保持有效，未回答的议题继续挂起等待。

## 基于动态决策树生成问题

Native 在运行时会在内存中构建一棵依赖决策树。每个节点清晰记录一项人工裁决、其依赖的前置事实或上游决策、代码库调查依据以及当前解析状态。决策树仅存于 Agent 的执行内存中，Runtime 仅在物理磁盘上持久化真实未决的卡点。

一个澄清问题唯有满足以下全部条件时，才会进入当期的就绪问题集合：

1. 该问题所依赖的上游人工决策均已确定；
2. 回答该问题所需的代码库事实或运行环境依赖已完成探查；
3. 该问题不依赖当前批次中其他尚未解答的平行问题。

在 `sequential` 模式下，系统会从就绪集中挑选一道最核心的问题抛出。若有多个问题同时就绪，优先处理下游扩散面最广、对最终用户感知影响最深的关键项。在 `batch` 模式下，系统会一次性收集完整的就绪集合打包提问。针对代码库的独立背景调查支持并行发起；若 Agent 平台不支持并发，则由当前 Agent 逐项串行调研。无论收到人类答复还是获得新的代码调查结论，Native 均会即时重算决策树，确保后续问题永远与最新确认的事实对齐。

## 提问聚焦真实行为与影响范围

Native 会自动将模糊或口语化的诉求转译为具象、可执行的技术行为，例如清晰定义“输入 → 输出契约”或“边界触发条件 → 系统响应动作”。每道问题均规范包含三个要素：

- **核心议题**：当前亟待敲定的系统外在行为或架构决策；
- **官方建议**：综合考虑现有工程约束、设计权衡给出的推荐解；
- **影响分析**：不同分支选项对于工期、范围、性能或潜在风险的实际影响。

当 Agent 平台支持结构化交互工具时，Native 会在选项边界清晰且可直接执行时优先唤起交互组件。`sequential` 模式每次发起单题交互；`batch` 模式则在单次请求中承载当期的完整题目组。若全量问题超出平台组件的承载上限，Native 会平滑回退至编号文本格式，完整保留所有选项、推荐建议与影响评估。

单选机制严格用于互斥方案的选择。唯有在同一项决定天然允许组合多个兼容特性时，才会启用多选。一旦结构化组件调用异常，当前会话在后续轮次中会自动切换为稳定性更高的纯文本交互，保持问题编号与答复心智的一致。

## 回答即时落盘为正式规格

对话交互仅负责收集意图，物理磁盘上的制品才是断点恢复的唯一依据。Native 收到你的回复后，会即时更新 `brief.md` 中的 **Decisions** 章节、补充完整的目标 Spec 并刷新对应的验收测试项。任何含糊、留白或仍需进一步深究的存疑项，会继续保存在 **Open questions** 中。

`sequential` 模式记录当前聚焦的卡点：

```markdown
## Open questions

- [blocking] 头像上传失败时，保留原头像还是清空？
```

`batch` 模式使用稳定编号组织本轮问题：

```markdown
## Open questions

- [blocking] Q1: 头像上传失败时，保留原头像还是清空？
- [blocking] Q2: 是否允许用户删除现有头像？
```

若你仅答复了其中部分问题，已答复项会完成收敛，其余未答复项保留原有稳定编号，下一轮推演将基于你已有的决策继续计算新的决策树。

## 进入 Build 阶段前的最终确认门禁

当决策树上的所有分歧项均已澄清完毕后，Native 会对收集到的代码事实、既定决策、默认回退行为、边界条件、异常分支以及底层假设做最终全量复核，并向你呈现一份结构清晰的最终需求摘要。内容包括：

- 最终目标与交付范围；
- 核心技术与业务决策；
- 严谨的逐条验收项；
- 明确的非目标边界（Non-goals）。

最终确认环节不会在 `brief.md` 中登记为普通的 `[blocking]` 问题。Native 会指示 Runtime 在底层将 Shape 状态边界固化，并返回 `await-user` 挂起状态；Agent 会打印完整的需求全景摘要，等待你给出最终核准指令。

在你明确确认后，Native 才会携带 `--confirmed` 标志执行继续命令正式流转至 Build。Runtime 针对 `sequential` 与 `batch` 采取完全一致的门禁检查；只要未获得你对最终需求摘要的明确授权，change 绝不会私自跳入 Build。若在最后阶段你对摘要提出了新的补充或推翻了某项决议，旧的授权立即作废，Native 会重新整理并生成新的确认摘要。

## 跨会话与断点接续

在重新拉起项目或接续推进某个 change 时，Native 会自动读取 `.comet/config.yaml` 与 `brief.md`，精准恢复当前的澄清模式、已敲定的决议列表以及仍在等待回答的阻塞项。你只需在对话框中像往常一样阐述你的选择，底层的断点状态装载完全由 Native 自动处理。

若想在终端中核对当前记录，随时可以执行：

```bash
comet native show <change-name>
comet native status <change-name> --details
```

Native 会将你的自然语言答案准确映射到 `brief.md` 中的 Q1、Q2 编号，即时固化入物理文档，再自动计算下一轮提问。在中途修改澄清模式只会调整后续的交互频率，既有的阻塞项内容与编号完全平滑继承。
