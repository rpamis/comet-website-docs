description: '用一个头像上传需求走完 Shape、Build、Verify、Archive，展示新 Verifier 和 Loop 如何工作。'
---

这一篇用“为用户资料页增加头像上传”走完 Native 的四个阶段，并展示一次验收失败如何回到 Build，再由新的 Verifier 通过。

## 需求起点

```text
/comet 为用户资料页增加头像上传能力
```

`/comet` 根据项目配置进入 `/comet-native`。Skill 先读取现有 change 和 `.comet/config.yaml`，没有歧义时创建新的 change。

## Shape：明确需求

Agent 调查现有资料页、上传接口、图片格式和错误处理，只向用户询问会改变产品行为的决定，例如：

- 头像大小和格式限制；
- 上传失败时是保留旧头像还是清空；
- 是否需要裁剪和预览。

确认后，change 目录会有 `brief.md`、完整 target Spec 和 `comet-state.yaml`。新项目默认 Batch，一轮询问当前前提已经具备的问题。

## Build：实现并交接

Agent 自主选择实现和测试方式，修改源代码和测试文件。完成后提交 Builder handoff，列出已完成内容和需要 Runtime/Verifier 关注的验收项；不能在 handoff 中直接声明最终通过。

## Verify：检查和新的 Verifier

Runtime 根据 brief 和 Spec 解析 A1…An，执行必要检查，例如：

```text
pnpm test --filter profile
pnpm lint
```

检查结果一次写入本机日志并在状态中保留摘要。随后 Runtime 分派新的只读 Verifier。假设第一次 Verifier 发现 A3：失败上传时没有保留旧头像。

Runtime 会把 change 返回 Build：

```text
status: build
loop.iteration: 2
next: repair A3, then submit a new Builder handoff
```

Agent 修复 A3 后，再由新的 Verifier 对完整 A1…An 逐项作答；不能只提交 A3，也不能复用第一次失败的 execution。

## Archive：只做归档工作

当全部验收通过，Runtime 生成 `verification.md`，按 Spec 更新 canonical 文档并移动 change。正常 Archive 不重新跑检查，也不要求用户读取本机日志。若配置为 required，Skill 会在移动前等待一次明确确认。

归档后的用户可读内容是 brief、Specs、`comet-state.yaml` 和 `verification.md`；`.comet/runtime/native/` 的本机执行目录会清理。

## 中断后继续

如果会话在 Verify 中断，下一次输入 `/comet 继续`，或运行：

```bash
comet native status avatar-upload --details --json
```

Runtime 从 YAML 恢复 iteration、acceptance 和 continuation。缺失的本机 overlay 会重建；代码或 branch/worktree 不匹配时会等待用户，不会偷偷使用另一个目录。
