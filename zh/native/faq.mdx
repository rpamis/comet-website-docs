## 基础与选型

<AccordionGroup>
  <Accordion title="Native 与 Classic 应该怎么选？">
    使用云端强推理大模型时，优先选 Native：模型本身具备较强的代码理解和方案拆解能力，Native 只把控“需求与验收边界”和“基于真实证据的验收”，把具体实现方式交还给模型。如果模型能力偏弱，或团队需要按固定五阶段文档与计划逐步推进，可选 Classic（结合 OpenSpec 与 Superpowers）。两套工作流都可以在 `.comet/config.yaml` 中按项目启用或切换。
  </Accordion>

  <Accordion title="Native 需要安装 OpenSpec、Superpowers 或其他外部 Skill 吗？">
    不需要。Native 内置了完整的 Shape、Build、Verify、Archive 流程与 SDK Runtime。只有选用 Classic 工作流时，才需要安装 OpenSpec 和 Superpowers。
  </Accordion>

  <Accordion title="日常使用 Native 需要自己记住并手动输入 comet native 命令吗？">
    不需要。日常开发全程在 Agent 对话中用自然语言交互（从 `/comet <你的需求>` 开始），所有创建 change、推进阶段、提交验收、确认保护参数等底层 `comet native ...` 命令都由 Agent 在后台自动调用。只有在你想脱离对话于终端查看进度（`comet status` / `comet native doctor`）或跨检出迁移 Supervisor 子任务（`comet native transfer`）时，才需要自己在终端运行命令。
  </Accordion>

  <Accordion title="为什么 Builder 说写完代码后还不能直接归档？">
    Builder 提交的代码只是“候选实现”，必须经过 Verify 对照你的原始请求、正式 Specs 和全部验收项逐条核查。常规任务可在当前会话以只读角色完成验收（报告记为 `self-reviewed`），也可以要求独立只读会话审查；全部通过后，按你的确认或自动归档策略才会进入 Archive。详见 [验证与修复](/zh/native/verification-and-repair)。
  </Accordion>

  <Accordion title="Verify 阶段需要补跑额外测试命令怎么办？">
    Agent 会直接通过平台工具运行所需的构建、单测、类型检查或静态扫描，并将命令、工作目录、退出状态和日志引用如实记录到验收证据中。Runtime 不会重复执行普通命令，也不接受伪造或未运行的检查充当通过。
  </Accordion>

  <Accordion title="为什么新项目默认采用 Batch 澄清模式？">
    `batch` 模式每轮一次性提出所有前置条件已明确、彼此独立的决策点，减少对话来回次数；如果需求还在探索阶段、前置答案会直接影响后续分支，可以在 `.comet/config.yaml` 中切换为 `sequential` 逐题澄清。无论哪种模式，进入 Build 前都需要你确认完整的最终 Shape。
  </Accordion>

  <Accordion title="缺失 verification.md 会影响中断恢复或跨设备继续吗？">
    不会。`verification.md` 只是 Runtime 根据结构化验收结论生成的阅读视图；本机 Run 和仓库里的 `comet-state.yaml`（含 `run_checkpoint`）、`brief.md` 及目标 Specs 才是恢复依据。报告文件缺失时会自动按已有结论重新渲染，不会丢掉验收记录，也不能通过手工编辑这份 Markdown 来改变验收结论。
  </Accordion>

  <Accordion title="仓库里的 comet-state.yaml 和本机 Run 目录有什么区别？">
    本机完整 Run 存放在用户主目录的 Comet 数据目录中（默认 `~/.comet`，按工作区与 Git worktree 隔离），实时记录每次动作领取、回报与事务日志，不需要提交到 Git。仓库内的 `comet-state.yaml` 用于展示业务状态，并在关键边界写入带防篡改校验的恢复检查点（`run_checkpoint`，已脱敏令牌并将运行中动作降级为 `unknown`），用于跨设备或本机记录丢失时恢复。
  </Accordion>

  <Accordion title="支持多个独立 Native Change 同时并行开发吗？">
    支持。你可以先在同一分支规划多个 Shape，并在确认时暂缓开工；等到实际开工时，若同一目录还有其他活跃任务，Runtime 会自动为你建好独立分支和 Git worktree 并交接过去；也可以一开始就直接用独立 worktree 创建。如果两个并行任务改动了同一份能力 Spec，Archive 阶段会做需求级检查并在存在冲突时暂停让你确定归档顺序。详见 [多 Change 并行与冲突控制](/zh/native/multi-change-and-conflicts)。
  </Accordion>
</AccordionGroup>

## Supervisor Change

<AccordionGroup>
  <Accordion title="什么场景适合用 Supervisor Change，什么场景该拆成多个独立 Change？">
    当一个大目标可以拆成两个及以上可独立编码、独立验证的子任务，且最终需要合入集成分支做统一全量验收时，适合用 Supervisor Change（有先后依赖的分层重构同样适用）。如果几个需求互不依赖、可以各自独立上线，直接建多个独立 Native Change 更合适；如果改动高度集中在同一个核心文件里，保持单个 Change 顺序推进即可。
  </Accordion>

  <Accordion title="Supervisor 的多会话和单会话推进有什么区别？">
    两者的子任务拆分、依赖顺序、子验收和集成规则完全一致，区别只在执行载体：`multi-session` 由主会话统筹，按平台能力用独立会话或 Claude Code Agent Teams 并发推进（默认上限 `2`，可通过 `native.max_parallel_children` 调整，不支持时自动改用 subagent）；`single-session` 由当前会话按依赖顺序逐个完成（并发固定为 `1`）。选择会保存在 `comet-state.yaml` 中，后续恢复时直接沿用。
  </Accordion>

  <Accordion title="多会话推进的子任务如果窗口断开或会话丢失怎么办？">
    回到原工作区让 Agent 继续即可。Comet 会先向原平台核对子任务是否仍在运行，绝不会把会话断开当成已完成；如果原独立会话或 Agent Team 不可用，会在 `multi-session` 下自动改用 subagent 继续，不会私自降级为单会话。需要跨机器或跨检出搬迁正在开发的子任务时，可使用 `comet native transfer export/import`。
  </Accordion>
</AccordionGroup>

## 恢复与故障排查

<AccordionGroup>
  <Accordion title="在 Verify 通过后或等待归档时，需求又变了怎么办？">
    在对话里直接说明变动即可。只要只是修补原需求的内部实现，Agent 会走实现修订回到 Build，保留已确认的 Shape；如果改变了用户可见行为或验收标准，只要归档写入还没执行，Agent 都能退回 Shape，先展示前后变化摘要再请你重新确认，已有代码会原样保留。详见 [需求变化后继续推进 Native Change](/zh/native/scenarios/requirement-changes)。
  </Accordion>

  <Accordion title="更换设备或清理了本机缓存后怎么恢复任务？">
    只要仓库里提交了代码、`comet-state.yaml`、`brief.md`、目标 Specs（以及自定义根目录时的 `.comet/config.yaml`），在新设备拉取仓库后回到对话让 Agent 诊断，确认检查点有效后，由 Agent 在后台调用 `comet native doctor <change-name> --repair --confirmed` 即可恢复原 Run（离线排障时也可在终端手动运行），已完成的 Shape 和 Build 不会重做。
  </Accordion>

  <Accordion title="升级 Comet 后，之前创建的兼容模式（Compat）或旧版 change 会受影响吗？">
    不会。升级不会强行迁移仍在进行的旧 change，也不会改动它们的既有状态和验收约定；新建的 change 自动使用新版 SDK Runtime。如果已结束的历史 Run 提示需要完成存储分区收尾，同步升级 CLI 与平台 Hook 后让 Agent（或在终端）执行一次历史迁移即可，详见 [Native 任务恢复](/zh/native/recovery-playbook)。
  </Accordion>

  <Accordion title="终端离线排障的标准只读命令是什么？">
    先保留当前工作区现场，不要手改 `comet-state.yaml` 或 `.comet/current-change.json`，运行只读诊断查看状态和具体阻塞项：

    ```bash
    comet status
    comet native status <change-name> --details --json
    comet native doctor <change-name> --json
    ```

    根据返回的诊断项按 [Native 任务恢复](/zh/native/recovery-playbook) 对应场景处理即可。
  </Accordion>
</AccordionGroup>
