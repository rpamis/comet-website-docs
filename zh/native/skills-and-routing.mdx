title: '单 Skill 与入口路由'
description: '理解 /comet 如何按项目配置进入 Native，以及 /comet-native 如何在单个 Skill 中持续推进。'
---

一个入口、一个 Skill，跨会话从磁盘继续。Native 不把工作流拆成多个 Skill，也不在阶段之间传递会丢失的上下文：单个 `/comet-native` 读完磁盘状态，就能从当前阶段继续。它不依赖 OpenSpec、Superpowers 这类外部 Skill。

## 用户入口

最常用的入口是 `/comet`。它只读 `.comet/config.yaml`，按 `default_workflow` 转发到对应工作流：

```yaml
schema: comet.project.v1
default_workflow: native
workflows:
  - native
  - classic
```

想跳过路由直接进 Native，或者排查"为什么没进 Native"这类问题，就用 `/comet-native`。它由宿主 Skill 调用，不是 shell 命令；底层命令统一是 `comet native ...`。

<Note>
  Comet 不看任务大小、提示词或模型名去猜该用哪种模式。换默认模式改配置即可，切换入口不会迁移已有
  change。
</Note>

## 单 Skill 如何覆盖四个阶段

Native 的四个阶段（Shape → Build → Verify → Archive）共用同一个 `/comet-native`，不需要像 Classic 那样在多个阶段 Skill 之间交接。每次进入，Skill 都重新读配置、selection、`comet-state.yaml`、brief、target spec 和当前仓库状态，然后从当前阶段继续。

由此带来几点好处：

- **没有上下文交接损耗**。阶段之间不需要生成 design context、压缩投影或 handoff 文档来传递状态，所有事实都写在文件里，Skill 重新读取即可。
- **跨会话不丢进度**。会话中断后重新进入，Skill 从磁盘的 continuation 恢复到中断前的精确位置，不依赖聊天记忆。
- **阶段衔接由 Runtime 控制**。阶段之间靠结构化的 `continuation` 衔接：通过就继续，遇到需要你决定的地方就停下等你，遇到阻塞走恢复流程。

四阶段各自的职责和必要结果，见 [Native 工作流](/zh/concepts/native-workflow#四阶段)。

## 写入归属

Comet 用 `.comet/current-change.json` 记录当前在写哪个 change，保证一次写入只落在一个需求上，减少写错需求和重复阻塞。`status` 和 `show` 是只读的，不会擅自改这个指向，所以查状态不会意外把后续写入绑到别的需求。

如果选中的 change 已经被删或归档，Comet 会让你从当前活跃的 change 里重新选一个：

```bash
comet native select <change-name>
```
