Native 不把 Shape、Build、Verify、Archive 拆成四个 Skill，也不加载 OpenSpec、Superpowers 或其他外部方法 Skill。它由一个 `/comet-native` Skill 读取磁盘状态，在同一入口内完成调查、澄清、实现、验证和归档。

## 用户入口

正常情况下使用 `/comet`。入口只读取 `.comet/config.yaml`，按 `default_workflow` 确定性转发：

```yaml
schema: comet.project.v1
default_workflow: native
workflows:
  - native
  - classic
```

`/comet-native` 是显式目标，适合诊断路由或明确要求进入 Native。它是宿主 Skill 调用，不是 shell 命令。Runtime 命令统一使用 `comet native ...`。

<Note>
  Comet 不根据任务大小、提示词或模型名称猜测模式。修改默认模式要改项目配置；切换入口不会迁移现有
  change。
</Note>

## 一个 Skill 如何覆盖四个阶段

每次进入后，Skill 会重新读取配置、当前选择、`comet-state.yaml`、需求简述、目标规格和当前仓库事实，然后根据阶段继续：

| 阶段    | Skill 的职责                                         |
| ------- | ---------------------------------------------------- |
| Shape   | 调查事实，清空用户决定，固定需求简述与完整目标规格   |
| Build   | 让模型自主选择实现方法，提交真实项目产物形成实现范围 |
| Verify  | 按验收与风险运行检查，写入逐项证据                   |
| Archive | 两步预检，更新正式规格并归档 change                  |

阶段转换会返回结构化后续动作。只有 `continue` 才会在当前调用中接着工作；`await-user`、`blocked`、`manual` 或 `done` 会分别等待用户、处理阻塞、停止自动修复或结束。

## 写入归属

`.comet/current-change.json` 记录当前写入属于哪个工作流和 change。项目只有一个共享 Hook Router，一次原子写入最多交给一个 Guard。存在多个活跃 change 时，先显式选择：

```bash
comet native select <change-name>
```

只读 `status` 和 `show` 不会暗中改变当前选择。这样，读取状态不会意外把后续写入绑定到另一个需求。
