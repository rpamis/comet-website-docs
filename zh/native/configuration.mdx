Comet 将全局与工作流配置集中存储于项目根目录的 `.comet/config.yaml`。在执行 `comet init` 初始化时会自动生成开箱即用的基准配置，绝大多数项目无需手动干预。仅当你希望定制默认工作流、产物语言、需求澄清模式、记忆机制或交付策略时，才需按需调整。

## 推荐的 Native 配置

以下配置非常适合采用中文作为交付文档的新建项目：

```yaml
# 配置格式版本，由 Comet 统一管理
schema: comet.project.v1
# /comet 统一入口默认启动 Native 工作流
default_workflow: native
# 项目已激活的工作流清单
workflows:
  - native
# 自然语言恢复探测开关，在新会话疑似要继续旧任务时执行只读探测
ambient_resume: true

# 个人记忆能力（Native 与 Classic 双流共享）
memory:
  # 允许 Comet 从每一次变更交付中提炼个人偏好与经验
  learning: true
  # 在关联任务中基于语义检索并注入已有的个人记忆
  retrieval: true

# 项目知识来源提供方
knowledge:
  provider: local

# Native 工作流核心配置
native:
  # change 变更、Spec 规格与验证报告的归档根目录：<artifact_root>/comet/
  artifact_root: docs
  # 新建 change 的 brief、Spec 及验证报告的目标语言
  language: zh-CN
  # batch：每轮批量聚合提问；sequential：单题递进式发问
  clarification_mode: batch
  # automatic：Verify 验收通过后自动归档；required：增加一道人工终审确认门禁
  archive_confirmation: automatic
  # 同一需求允许的连续验证失败上限，触顶后主动挂起等待人工裁决
  max_verify_failures: 5
  # 多会话 Supervisor 模式下，允许并发推进且未完成集成的子任务上限
  max_parallel_children: 2
```

套用上述配置后，运行 `/comet` 将默认进入 Native 工作流，变更文档统一存储至 `docs/comet/` 目录，全流程采用中文生成正式规格与报告，并以批处理（Batch）模式推进需求澄清。

<Tip>推荐优先运行 `comet init --workflow native` 自动生成配置，后续通过 `comet update` 保持配置模式与最新规范对齐。</Tip>

## 默认工作流与自然语言恢复选项

| 核心字段 | 默认设定 | 对开发流程的实际影响 |
| --- | --- | --- |
| `schema` | `comet.project.v1` | 配置文件结构规范版本，由 Comet 框架底层管理 |
| `default_workflow` | 初始化时选定 | 决定 `/comet` 统一入口默认分发至 Native 还是 Classic |
| `workflows` | 初始化时选定 | 明确声明项目所启用的工作流类型（支持 `native`、`classic` 或双流并发） |
| `ambient_resume` | `true` | 当用户在日常对话中表达“继续刚才的任务”时，自动唤起只读恢复探测 |

`default_workflow` 仅用于分发顶层总入口，不会破坏性地将已有的 Native change 篡改为 Classic，亦不会反向迁移 Classic change。

若项目需要同时深度支持两套工作流，可直接执行：

```bash
comet init --workflow both
```

若希望彻底关闭自然语言触发的被动探测，将其配置为 `false` 即可：

```yaml
ambient_resume: false
```

此时显式调用 `/comet` 依然会严格依照 `default_workflow` 精准路由。

## Native 工作流核心参数

| 配置项 | 可选值 / 默认值 | 行为与影响说明 |
| --- | --- | --- |
| `native.artifact_root` | 项目相对路径；默认 `docs` | 约定 change、Spec 与报告集中存储在 `<artifact-root>/comet/` |
| `native.language` | `en` \| `zh-CN`；默认 `en` | 决定新创建 change 的 brief、Spec 以及验收报告的落盘语言 |
| `native.clarification_mode` | `batch` \| `sequential`；默认 `batch` | 决定需求澄清是按批次集中提问，还是单题递进式深度确认 |
| `native.archive_confirmation` | `automatic` \| `required`；默认 `automatic` | 决定 Verify 阶段全量通过后，是否必须额外经过人工批准才可归档 |
| `native.max_verify_failures` | 正整数；默认 `5` | 连续触发验收失败的最大容忍轮次，超限后主动熔断并挂起等待排查 |
| `native.max_parallel_children` | 正整数；默认 `2` | Supervisor 架构在多会话并发模式下的子任务并发上限；单会话模式固定为 `1` |

### Supervisor 子任务并发上限

支持在 **Dashboard → 设置 → Comet 配置 → Native 工作流 → Supervisor 子任务并发上限** 中进行可视化调节，亦可直接编辑配置文件：

```yaml
native:
  max_parallel_children: 4
```

默认并发阈值为 `2`。该配额统计已派发且尚未由 Runtime 完成代码集成收尾的活跃子任务数；前置的任务拓扑依赖仍需严格满足，单会话模式下始终按拓扑序严格串行。参数调整仅对后续派发的任务生效，正在运行的子任务会继续执行。若将配额下调至当前在途数量以下，系统会等待多余的子任务退出，再按新配额调度后续任务。

处于 Builder 实现、Verifier 验收或等待集成状态的子任务均会计入配额，待 Runtime 完成集成收尾后自动归还名额；开发者无需且不应为子任务单独发起 Archive 归档。

配置读取严格以主任务所在的主工程为准，子任务关联的临时 Git worktree 中的历史配置不会反向污染主任务。全局用户配置仅作为全新工程初始化的模版，不会强行覆写已有工程。SDK 流程严格遵循该项约束；兼容模式（Compat）下仍支持通过显式的 `--max-parallel` 参数进行单次动态覆盖。详见 [Supervisor Change 架构指南](/zh/native/supervisor-change)。

### 产物存储根目录

`artifact_root: docs` 对应项目实际路径 `<project>/docs/comet/`；`artifact_root: .` 则直接对应 `<project>/comet/`。路径必须严格限定在当前工程根目录下。

当已有项目需要迁移产物根目录时，切勿直接手动修改 YAML 或自行移动文件。请交由 Runtime 执行环境自检、安全迁移与断点元数据刷新：

```bash
comet native root show
comet native root move docs
```

### 文档生成语言

`native.language` 用于锁定后续新建 change 的文档生成语言。已有 change 始终沿用其创建时绑定的语言标记，不会因全局配置变更而发生非预期的自动翻译或覆写。

```yaml
native:
  language: zh-CN
```

### 需求澄清交互模式

- `batch`：聚合本轮所有前提明确、彼此解耦的决策点集中提问，减少对话往返，适合节奏紧凑的常规迭代。
- `sequential`：每轮仅抛出一道最核心或影响面最广的议题，待人类裁决后再行推导后续方案，非常适合前置答案可能颠覆后续路线的探索性需求。

无论采取哪种模式，系统均会先探查代码库客观事实，并在正式迈入 Build 阶段前呈现完整的目标、边界、决策点、验收场景与非目标清单供你最终核准。在开发中途切换模式不会导致 `brief.md` 中尚未作答的 `[blocking]` 卡点丢失。

### 归档审批门禁

- `automatic`：当 Verify 最终验收全部通过后，Runtime 自动完成归档交付。
- `required`：最终验收全部通过后，流程在归档前额外挂起，等待开发者给出最终授权。

`automatic` 仅控制是否跳过归档动作本身的二次确认，不会越权替你擅自完成 Git merge、push 或创建 PR。若任务启用了独立 branch 或 Git worktree 隔离，Comet 依然会向你呈现明确的交付策略选择题，选项详情请参阅[归档与交付](/zh/native/archive-and-delivery)。

### 验证容错熔断上限

`max_verify_failures` 限制了在同一份既定需求下，允许代码实现连续验证失败的重试轮次上限。一旦达到该阈值，Native Loop 会主动挂起并向你汇报死锁现场，由你决定是继续重试、微调需求范围还是终止，避免由于逻辑死循环无谓空耗 Token 预算。

若遇到 Runtime 底层命令崩溃、缺失必要的外部网络凭证或不可恢复的状态冲突，系统会精准返回 `await-user` 或 `blocked` 明确卡点，切勿试图通过调大计数上限来掩盖真实错误。

## 变更讲解页面（Change Walkthrough）

`change_walkthrough` 属于 Native 与 Classic 双流共用的功能开关，默认值为 `true`。在 Classic 模式下，Build 阶段完成后会自动渲染独立的 `walkthrough.html` 变更解说页；而在 Native 模式下，仅当你明确要求输出可视化变更说明时才会触发生成。该独立单页能直观比对前后行为差异、高亮核心代码段并附带可选架构拓扑图，Verify 阶段会在同页面即时同步真实的测试结论，最终由 Archive 阶段妥善留存。

生成图形化讲解会额外消耗一定量的上下文与 Token。若团队倾向于纯文本输出或希望减少生成耗时，可在配置文件顶层将其关闭：

```yaml
change_walkthrough: false
```

亦可在 **Dashboard → 设置 → Comet 配置** 中可视化切换 **变更说明** 选项。项目的初始化与版本升级均会完整保留你的个性化选择。关闭该功能不会清理已生成的历史页面，更不会削弱核心的自动化验证防护。

## 个人记忆机制

`memory` 能力原生支持 Native 与 Classic 双工作流，出厂默认全量开启：

| 字段 | 核心职责与能力 |
| --- | --- |
| `memory.learning` | 授权 Comet 自动从每次变更的交付复盘中汲取通用的个人开发偏好与协作经验 |
| `memory.retrieval` | 授权 Comet 在遇到语义相关的任务时，自动检索并注入已记录的个人画像记忆 |

若希望仅消费既有记忆而不让 Agent 自动记录新经验，可配置为：

```yaml
memory:
  learning: false
  retrieval: true
```

## 项目知识与企业级 RAG

`knowledge.provider` 默认设为 `local` 本地模式。Comet 会深度解析代码库拓扑，你也可以显式追加项目中的架构设计与规范文档：

```yaml
knowledge:
  provider: local
  local:
    include:
      - docs/architecture/**/*.md
      - packages/*/README.md
```

`knowledge.local.include` 仅接收当前工程内部的 Markdown 文件匹配规则（Glob）。路径统一采用正斜杠 `/`，不得跨越工程根目录边界，匹配到的文档会自动合并进内置知识库中。

若企业团队内部已搭建了成熟的统一 RAG 知识库微服务，可对接为远程 Provider：

```yaml
knowledge:
  provider: remote
  remote:
    endpoint: https://knowledge.example.com
    token_env: COMET_KNOWLEDGE_TOKEN
    scope: engineering
    timeout_ms: 5000
```

`endpoint` 必须填写企业服务对外暴露的真实完整 URL 地址，Comet 会直接向其发起标准 `POST` 请求（示例中的占位域名需替换为真实接口）。

远程通信必须强制采用安全 HTTPS 协议（仅本地 `localhost` 与回环地址允许使用 HTTP 调试）。`token_env` 请配置存储鉴权 Token 的系统环境变量名，禁止将敏感凭据直接明文硬编码在配置文件中。请求超时时间支持配置在 `100` 至 `30000` 毫秒区间。

## 阶段 Hook 写入白名单（高级选项）

`hook.allow_paths` 是面向 Native 与 Classic 的高级白名单通道。它允许特定的目录在原本受到只读保护的工作流阶段中依然允许被写入，默认值为空数组。

例如，在 Shape 需求设计阶段，系统默认禁止 Agent 修改业务源码；若团队约定在 Shape 期间需协同将研讨纪要写入 `docs/team-notes`，可通过如下配置放行：

```yaml
hook:
  allow_paths:
    - docs/team-notes
```

路径必须为相对于项目根目录的相对路径，并以正斜杠 `/` 分隔。配置 `docs/team-notes` 将递归放行该目录下的全部子文件。

<Warning>
  该配置会直接穿透对应目录的阶段写保护机制。不要为了绕过 Shape、Verify 或 Archive 的正常合规拦截而随意放行业务源码目录。`.comet` 全局目录、Native 正式产物区以及 Classic 产物区均受核心状态机硬隔离保护，不受该白名单豁免。
</Warning>

## 定制 Pull Request 发起命令

在默认行为下，当归档阶段你选定“推送并创建 PR”时，Comet 会直接调用 `gh pr create --fill`，提取 Commit 摘要自动组装标题与描述。但若团队仓库对 PR 规范有强硬约束（例如必须携带包含特定关联 Issue 字段的 Checklist 模版），或是提 PR 后需联动触发特定的远端流水线，默认的 `--fill` 可能会被 CI 拦截。通过 `native.finish.pull_request`，你可以替换为仓库专属的自动化脚本，Comet 负责调度脚本并接收交付结果，其余交付环节保持标准一致：

```yaml
native:
  finish:
    pull_request:
      provider: repository-command
      command: [pwsh, -NoProfile, -File, scripts/comet-create-pr.ps1]
      timeout_ms: 120000
```

此时 PR 的标题生成、模版组装及仓库特异的合规校验全权交由自定义脚本接管；而底层的代码 Commit、远端推送、已有 PR 幂等查重、Base/Head 分支一致性核验以及异常重试，依然由 Comet 稳定兜底。

遵循以下硬性约束：

- `provider` 当前仅支持配置为 `repository-command`。
- `command` 必须是一个非空的命令行参数数组；首项必须是环境变量 PATH 中的可执行程序或相对于当前项目的相对路径，禁止使用绝对路径。
- `timeout_ms` 默认超时时间为 `120000` 毫秒（2 分钟），最大允许放宽至 `600000` 毫秒（10 分钟）。
- 脚本会在项目根目录下被唤起执行，通过标准输入（stdin）接收 `comet.native.pull-request-finish-input.v1` 版本的 JSON 数据包，并通过标准输出（stdout）返回 `comet.native.pull-request-finish-result.v1` 格式的执行结果。
- 即使启用了自定义 PR 脚本，本地依然需要安装并完成 GitHub CLI（`gh`）的登录授权，以供 Comet 独立核验远端分支与 PR 交付状态。
