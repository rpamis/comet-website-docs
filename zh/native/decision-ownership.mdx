Native 严格仅在真正的人工选择点才会暂停：即存在两个及以上合理方案，且不同选项会切实改变系统的外在表现或产品结果。凡是能在代码库中查明的事实，均由 Agent 自主调研；凡属于内部技术实现细节，均由 Agent 在既定目标与规范边界内自主裁定。

你负责定义并把关目标、边界、默认行为与验收准则，Agent 负责在明确的框架内制定并落地最佳实现方案。

## 三类信息与其处理边界

Shape 阶段会首先对输入信息按权责归属进行严格分类：

| 信息类型 | 处理方式 | 典型示例 |
| --- | --- | --- |
| 可调查事实 | 由 Agent 自主从代码、配置、文档、工具或运行环境中查明 | 现有后端接口支持哪些图片格式与体积上限 |
| 用户决策点 | 必须交由你确认系统的最终外在行为与交互体验 | 上传失败时是保留旧头像还是直接清空 |
| 内部实现选择 | 由 Agent 在已确认的架构边界内自主权衡确定 | 选用哪款底层图片裁剪与压缩工具库 |

一个议题要被定性为必须由用户确认的选择点，必须同时满足以下三条硬性门槛：

1. 存在两个或更多合理且具备可行性的技术方案；
2. 不同的选项会实质性改变用户可见结果、默认回退行为、异常处理机制、业务范围、潜在风险或不可逆影响；
3. 你的初始提示词、正式系统规格、已有项目文档及工程规则均未对此作出明确约定。

任何不满足上述条件的问题绝不会拿来打扰你：凡能在仓库中推导出的事实，Agent 会自行查明；若只有一个合理可行解，Agent 阐明理由后直接推进。只有在遭遇执行错误或状态死锁时，Native 才会触发 `blocked` 挂起，报告阻塞状态以及需要你处理的事项。

## 直接提供大型 PRD、本地文件或外部链接时的处理

当以本地文件、代码片段、外部链接或原型附件作为需求输入源时，Native 会完整解析其内容，并建立严格的来源覆盖矩阵：

- 依循文档标题、段落、列表、表格、代码块、示例用例、约束声明与超链接细致拆解为离散的来源单元；
- 将每个来源单元如实标记为 `complete`（已完整读取并明确归类）、`partial`（仅解析了局部切片）或 `unavailable`（受当前运行权限或网络限制无法读取）；
- 将所有需要落地的具体业务诉求严格映射至完整目标 Spec 中，并逐一绑定至少一个正式验收编号（Acceptance ID）；
- 将纯背景说明、明确非目标以及已被新指令废弃的内容分别归档并阐述剔除原因；
- 凡是读取失败、解析残缺、缺少规格映射或仍存逻辑歧义的内容，统一作为 `[blocking]` 卡点挂起。

上述事实矩阵完整沉淀在 `brief.md` 的 **Scope** 章节中。超长文档会流式分块读取，但每一块内容均会被即时登记录入来源矩阵，绝不会因上下文截断而漏掉任何细节。Native 会提炼高层需求摘要以便于你通览全局，但最终的完工判定始终以逐项映射表为准：确保每个来源单元均在 Spec 中有据可查并对应明确的验收测试项。

若你提供的参考资料明显属于排障报错日志、测试凭据、审查意见或既有代码范例，Native 会严格按其参考用途消费，绝不会误当成新增的业务需求；若材料意图不够明确，会率先向你求证该材料是否作为需求源。

## 澄清问题的组织与推进

Native 会率先完成仓库事实调研，随后基于决策间的依赖拓扑生成发问序列。每道问题均会客观陈述推荐建议与各个备选项的利弊得失。配置项 `native.clarification_mode` 决定是单题递进式发问（`sequential`），还是按批次聚合抛出（`batch`）。

详细的批处理规则、问题稳定编号与断点恢复机制，请参阅 [Sequential 与 Batch 澄清模式](/zh/native/clarification-modes)。

## 最终全量确认与流转 Build 门禁

当决策树上的所有人工选择点均澄清收敛后，Native 会统筹汇总目标定义、交付范围、架构决议、逐条验收项与非目标清单，向你呈上一份全景需求摘要。唯有当 Runtime 收到你对该摘要的明确核准授权后，才正式放行 change 由 Shape 阶段流转至 Build 阶段。

针对超大规模的复合需求，系统还会自动评估是否适合拆解为 Supervisor Change 架构。若发现多个业务结果可以独立落地、具备并行推进价值或存在清晰的上下游依赖，Native 会主动给出拆解建议，由你确认子任务切分与执行节奏。

<Warning>
  “保持现有行为”原则仅适用于系统中已然存在的既有逻辑。对于全新引入的特性，必须白纸黑字写清预期行为。邻近模块的设计风格、依赖库的默认配置及最小改动原则可供 Agent 推导出推荐方案，但最终外在表现必须由你的裁决敲定。
</Warning>

## Build 阶段之后需求发生变动时的应对原则

- **代码实现遗漏，但初始需求与验收范围不变**：退回 Build 阶段针对性修正代码。
- **系统外在行为、交互模式或验收基准发生变化**：退回 Shape 阶段重新更新正式规范，并重新触发确认门禁。
- **冒出了与当前任务解耦的全新想法**：应当为新诉求单独新建一个 change，保持当前在途变更边界的专注与稳定。
