Native 只在真正的用户选择点暂停：存在两个或更多合理选项，而且不同选择会改变最终结果。仓库中可以查清的事实由 Agent 调查；内部实现方式由 Agent 在已确认的目标和约束内决定。

这套边界让 Agent 保留实现自主性，同时确保目标、范围、默认行为和验收标准仍由你确认。

## 三类信息，三种处理方式

Shape 会先判断每项信息由谁负责：

| 类型 | 处理方式 | 示例 |
| --- | --- | --- |
| 可调查事实 | Agent 从代码、文档、工具或运行环境中查明 | 当前接口支持哪些图片格式 |
| 用户选择 | 由你确认最终行为 | 上传失败后保留原头像还是清空 |
| 实现选择 | Agent 在已确认的边界内自主决定 | 使用哪个图片处理库 |

一个问题同时满足以下条件时，才会成为用户选择点：

- 存在两个或更多合理、可执行的选项；
- 不同选项会改变用户可见结果、默认行为、失败结果、范围、风险或不可逆影响；
- 你的要求、正式规格、项目文档和项目规则都无法给出可靠答案。

只有一个合法方案时，Agent 会说明依据并继续。遇到执行错误或缺少安全的下一步时，Native 会报告阻塞，让你了解当前状态和所需处理。

## 哪些问题需要你选择

以“为用户资料页增加头像上传”为例：

| 需要你选择 | 交给 Agent |
| --- | --- |
| 上传失败时保留原头像还是清空 | 使用哪个 HTTP 客户端 |
| 是否允许用户删除已有头像 | 图片裁剪放在前端还是后端 |
| 头像最大尺寸和格式限制 | 临时文件保存在哪里 |
| 是否需要服务端压缩 | 使用 sharp 还是 jimp |

左侧决定产品如何工作，右侧影响内部实现。Agent 会在实现过程中处理右侧事项，并持续满足已经确认的结果。

## 直接提供 PRD、文件或链接时

文件、附件、链接或本地路径构成需求来源时，Native 会读取完整内容，并建立来源覆盖：

- 按标题、段落、列表、表格、代码块、示例、约束、链接和边界记录来源单元；
- 将每个来源单元标记为 `complete`、`partial` 或 `unavailable`；
- 把需要实现的内容映射到完整目标 Spec，并关联至少一个验收 ID；
- 将背景、非目标和已被新要求替代的内容分别归类并说明原因；
- 将无法读取、只读取一部分、缺少映射或仍有歧义的内容保留为 `[blocking]`。

来源覆盖记录在 `brief.md` 的 **Scope** 中。分块读取只改变处理顺序，最终仍覆盖完整来源。需求摘要可以帮助理解上下文，正式映射负责证明每项要求已经进入 Spec 和验收范围。

用于排错、取证、审查或实现参考的材料按其原用途处理。用途不明确时，Native 会先确认它是否构成需求来源。

## 问题如何进入澄清轮次

Native 会先调查事实，再根据决定之间的依赖关系组织问题。每道题都说明推荐方案和各选项的实际影响。`native.clarification_mode` 决定一轮提出一道题，还是集中提出本轮所有已经就绪的问题。

Sequential、Batch、问题编号和跨会话恢复的完整规则见 [Sequential 与 Batch 澄清](/zh/native/clarification-modes)。

## 确认后进入 Build

所有用户选择处理完成后，Native 会汇总目标、范围、关键决定、验收项和非目标，并请你确认完整理解。Runtime 收到明确确认后，才允许 change 从 Shape 进入 Build。Sequential 和 Batch 使用相同的确认门禁。

大型需求还会检查是否适合拆成 Supervisor Change。多个结果能够独立实现和验证，并且存在明确依赖或并行价值时，Native 会给出拆分建议，由你确认子任务和推进方式。

<Warning>
  “保持现有行为”适用于已经存在的结果。全新行为仍需要明确语义。相邻功能、依赖默认值和最小改动原则可以帮助 Agent 形成推荐方案，最终结果由你的选择确定。
</Warning>

## Build 后需求发生变化

- **实现遗漏，需求保持不变**：返回 Build 修复。
- **用户可见行为或验收标准发生变化**：返回 Shape，更新正式需求并重新确认。
- **新要求与当前需求无关**：为它创建另一个 change，保持当前范围稳定。
