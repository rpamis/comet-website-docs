Native 只在真正的人工选择点才会暂停：即存在两个及以上合理方案，且不同选项会切实改变系统的外在表现或产品结果。凡是能在代码库中查明的事实，都由 Agent 自主调研；凡属于内部技术实现细节，都由 Agent 在既定目标与规范边界内自行决定。

你负责定义并把关目标、边界、默认行为与验收准则，Agent 负责在这个框架内选择并实现具体方案。

## 三类信息与其处理边界

Shape 阶段会先按归属把输入信息分成三类：

| 信息类型 | 处理方式 | 典型示例 |
| --- | --- | --- |
| 可调查事实 | 由 Agent 自主从代码、配置、文档、工具或运行环境中查明 | 现有后端接口支持哪些图片格式与体积上限 |
| 用户决策点 | 必须交由你确认系统的最终外在行为与交互体验 | 上传失败时是保留旧头像还是直接清空 |
| 内部实现选择 | 由 Agent 在已确认的架构边界内自主权衡确定 | 选用哪款底层图片裁剪与压缩工具库 |

一个问题必须同时满足以下三条，才算需要你确认的选择点：

1. 存在两个或更多合理、可行的技术方案；
2. 不同选项会实际改变用户可见结果、默认回退行为、异常处理机制、业务范围、潜在风险或不可逆影响；
3. 你的初始提示词、正式系统规格、已有项目文档及工程规则都没有对此作出约定。

任何不满足上述条件的问题不会拿来打扰你：凡能在仓库中推导出的事实，Agent 会自行查明；若只有一个合理可行解，Agent 阐明理由后直接推进。只有在遭遇执行错误或状态死锁时，Native 才会触发 `blocked` 暂停，报告阻塞状态以及需要你处理的事项。

## 直接提供大型 PRD、本地文件或外部链接时的处理

如果你把本地文件、代码片段、外部链接或原型附件作为需求来源，Native 会完整解析其内容，并建立来源覆盖矩阵：

- 按文档标题、段落、列表、表格、代码块、示例用例、约束声明与超链接，把内容拆成独立的来源单元；
- 将每个来源单元如实标记为 `complete`（已完整读取并明确归类）、`partial`（仅解析了局部切片）或 `unavailable`（受当前运行权限或网络限制无法读取）；
- 把所有需要实现的具体业务需求映射到完整目标 Spec 中，并逐一绑定至少一个正式验收编号（Acceptance ID）；
- 把纯背景说明、明确非目标以及已被新指令废弃的内容分别归档，并说明剔除原因；
- 凡是读取失败、解析残缺、缺少规格映射或仍有逻辑歧义的内容，统一标为 `[blocking]` 待处理项。

上述来源覆盖矩阵完整记录在 `brief.md` 的 **Scope** 章节中。超长文档会流式分块读取，但每一块内容都会即时登记到来源覆盖矩阵，不会因上下文截断而漏掉任何细节。Native 会提炼高层需求摘要，方便你快速了解全貌；但最终判断是否完成，始终以逐项映射表为准：每个来源单元都要在 Spec 中有据可查，并对应明确的验收测试项。

如果你提供的参考资料明显是排障报错日志、测试凭据、审查意见或既有代码范例，Native 只把它们当作参考，不会误当成新增的业务需求；如果材料的用途不明确，Native 会先向你确认它是否作为需求来源。

## 澄清问题的组织与推进

Native 会先完成仓库事实调研，再根据决策之间的依赖关系确定提问顺序。每道问题都会说明推荐方案和各个备选项的利弊。配置项 `native.clarification_mode` 决定是单题递进式提问（`sequential`），还是按批次一起提出（`batch`）。

详细的批处理规则、问题稳定编号与断点恢复机制，请参阅 [Sequential 与 Batch 澄清模式](/zh/native/clarification-modes)。

## 最终全量确认与流转 Build 门禁

决策树上所有需要你选择的问题都有结论后，Native 会汇总目标定义、交付范围、架构决议、逐条验收项与非目标清单，向你展示完整的需求摘要。只有 Runtime 收到你的明确确认后，才会放行 change，由 Shape 阶段进入 Build 阶段。

针对超大规模的复合需求，系统还会自动评估是否适合拆解为 Supervisor Change 架构。如果多个业务结果可以独立实现、值得并行推进，或存在清晰的上下游依赖，Native 会主动给出拆解建议，由你确认子任务切分与执行节奏。

<Warning>
  “保持现有行为”原则仅适用于系统中已经存在的逻辑。对于全新引入的特性，必须在文档中明确写清预期行为。邻近模块的设计风格、依赖库的默认配置及最小改动原则可供 Agent 推导出推荐方案，但最终外在表现必须由你决定。
</Warning>

## Build 阶段之后需求发生变动时的应对原则

- **代码实现遗漏，但初始需求与验收范围不变**：退回 Build 阶段针对性修正代码。
- **系统外在行为、交互模式或验收基准发生变化**：退回 Shape 阶段更新正式规范，并重新触发确认门禁。
- **出现了与当前任务解耦的全新想法**：为这个新需求单独新建一个 change，让当前进行中的 change 保持在原来的边界内。
