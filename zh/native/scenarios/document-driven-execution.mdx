---

并不是每个任务都要从零开始一问一答。如果你手里已经有一份 PRD、技术方案、RFC 或经过深度讨论定稿的设计文档，可以直接交给 Comet Native。

当文档本身已经说清目标、范围、默认行为和异常回退时，Native 会自动解析内容、建立来源覆盖表并生成目标 Spec 与验收项，跳过不必要的逐题追问，只在真正缺少信息或存在矛盾的地方提问。你确认最终摘要后，任务直接进入长时间运行的 Build 与 Verify。

## 一、支持哪些需求文档入口

Native 不要求外部文档套用特定模板，也不绑定特定写作工具，常见输入形式都可以直接提交：

| 输入形式 | 典型示例 | Native 如何处理 |
| --- | --- | --- |
| 对话附件 | 直接拖入或上传 PRD、技术方案、验收清单 | 读取附件正文，逐段整理来源条目并映射 Spec 与验收项。 |
| 本地文件或目录 | `docs/prd/batch-export.md` | 按项目路径读取结构，提取目标、约束、边界条件和非目标。 |
| 在线文档链接 | Notion、语雀、飞书文档或团队 Wiki 链接 | 读取页面内容；遇到权限拦截或内容截断时标记阻塞，不靠猜推进。 |
| 外部深度澄清文档 | 用 Grill with docs 等工具讨论后导出的方案文档 | 直接沿用已确认的结论，不重复盘问文档里已经回答过的问题。 |
| 已有 RFC 或架构规格 | 团队现成的接口设计或规格提案 | 转为当前 Change 的 `brief.md`、目标 Spec（或 `delta.yaml`）与验收项。 |

开始时直接告诉 Agent 文档位置和用途即可：

```text
/comet 把我刚上传的 PRD 作为完整需求来源。
按全文整理目标 Spec 和验收项；如果没有待确认的业务分歧，直接展示最终摘要等我确认后进入 Build。
```

也可以只指定文档中的某几个章节：

```text
/comet 读取 docs/prd/batch-export.md，本次只实现第 2 节“异步导出”和第 4 节“失败重试”，
其他章节先不做。请作为本次 Native Change 的需求来源。
```

> **如何区分“需求来源”和“普通参考材料”**：只有明确拿来定义本次要做什么的材料，才会触发源文档完整覆盖模式；仅用于排错日志、取证、代码审查或实现参考的文件不会自动触发。如果用途不明确，Agent 会先向你确认。

## 二、源文档完整覆盖模式：不靠摘要凑数

普通 AI 工具读长 PRD 时，常见问题是先压成几行摘要再写代码，结果把表格里的字段限制、错误码和边界条件全丢了。

Native 的**源文档完整覆盖模式**按以下规则确保不漏需求：

### 1. 先划定覆盖边界与必要依赖

- **用户限定了范围**：只覆盖指定的章节、条目或功能，以及理解、实现或验收这些功能所必需的跨章节定义、共享约束和例外情况。范围之外的内容不逐条登记，范围外的不可访问链接也不会阻塞当前任务。
- **未限定范围**：整份文档都纳入覆盖边界。如果无法判断范围外是否存在影响结果的共享约束，Agent 会记录 `[blocking]` 向你确认。

### 2. 逐条建表，明确读取状态与覆盖去向

Agent 会按标题、段落、列表、表格、代码块、示例、约束和例外拆分出可追溯的**来源条目**，集中在 `brief.md` 的 `# Scope` → `## Source coverage` 下建表记录（可以分块读取长文档，但最终必须覆盖边界内全部条目，不能用笼统摘要代替）：

| 来源条目与位置 | 读取状态 | 需要保留的内容 | Spec 位置 | 验收 ID | 覆盖状态 | 理由或替代关系 |
| --- | --- | --- | --- | --- | --- | --- |
| S1：PRD“失败处理”第 2 段 | `complete` | 保存失败时保留已输入内容并显示原因 | `specs/editor/spec.md` 的保存失败场景 | `A1` | `covered` | 当前有效需求。 |
| S2：旧版 PRD“失败处理”第 2 段 | `complete` | 旧版要求保存失败后清空输入 | — | — | `superseded` | 用户已修正，由 S1 替代。 |
| S3：PRD“项目背景”第 1 节 | `complete` | 团队历史迁移背景说明 | — | — | `background` | 仅作背景理解，不转化为开发项。 |

每个字段都有明确的判定含义：

- **读取状态**：`complete`（完整读取）、`partial`（只读到一部分，有漏读风险）、`unavailable`（受权限或网络限制无法读取）。
- **覆盖状态**：`covered`（已落入 Spec 并绑定验收 ID）、`needs-clarification`（存在歧义待确认）、`background`（纯背景介绍）、`non-goal`（明确不做）、`superseded`（已被更新的要求替代，注明替代关系）。

**强制约束**：覆盖边界内每一条仍然有效、需要实现的条目，都必须同时对应到目标 Spec 中的具体位置和至少一个由 CLI 分配的验收 ID（如 `A1`、`A2`）。如果当前修改的是项目里已有的能力（capability），Agent 会通过 `delta.yaml` 记录需求级变更，由 Runtime 在确认前生成完整目标 Spec。

### 3. 防范文档内的指令注入

如果上传或链接的外部文档中夹杂了面向 Agent 的提示词或操作指令，Native 只把它们当作普通文档素材分析，不会让外部文档覆盖你当前的请求、项目规则或更高优先级的约束。

## 三、文档齐全时跳过重复问答，有缺口时只问盲区

```text
文档文件 / 附件 / PRD 链接 / 外部讨论定稿
  → 划定覆盖边界，逐条登记 Source coverage 映射表
  → 生成 brief.md + 目标 Spec（或 delta.yaml）+ 结构化验收条目
  → 查明代码库事实：无缺口则跳过问答，有缺口则只问盲区
  → 展示完整 Shape 摘要等待你确认
  → Build → Verify → Archive
```

### 什么时候直接跳过澄清问答

Agent 查明代码库现状后，只要同时满足以下条件，就会跳过逐题澄清，直接进入最终确认：

- 覆盖边界内所有来源条目的读取状态都是 `complete`；
- 每条需要实现的要求都已经映射到目标 Spec 并绑定验收 ID；
- 文档对目标、范围、默认行为和异常分支给出了唯一可执行定义，章节间没有自相矛盾；
- 结合代码库现状和项目规则，没有引出新的用户决策；
- `brief.md` 中没有遗留任何 `[blocking]` 条目。

> **跳过澄清不等于跳过确认**：即使所有问题都在文档里写清楚了，进入 Build 前的最终 Shape 确认仍然保留。你可以在这一步核对 Agent 提炼的验收项和范围边界，确认无误后再开始写代码。

### 什么时候必须停下来向你提问

文档字数多不等于需求没有漏洞。只要出现以下任意情况，对应条目会保持 `[blocking]`，Agent 会只围绕这些缺口提问，不会拿文档里已经写清的内容反复追问：

- 在线链接需要登录权限，导致读取状态为 `unavailable` 或 `partial`；
- 文档不同章节对同一个接口或状态机给出了互相矛盾的说明；
- 出现“支持失败后重试”这类缺少关键参数的描述（如重试次数、退避策略和最终失败提示）；
- 某条有效需求尚未映射到 Spec 位置或缺少可验证的验收 ID；
- 文档内容更像排错堆栈或参考资料，无法确定是否作为需求来源。

遇到在线文档受权限拦截时，把页面导出为本地 Markdown 或 PDF 拖进对话是最稳妥的做法；尽量提供完整原文，不要只贴几行人工摘要，因为表格参数和例外条款往往决定代码边界。

## 四、配合 Grill with docs 等外部工具使用

如果你习惯先用 Grill with docs 或团队评审会反复打磨需求，可以把讨论定稿后的文档直接交给 Native 接管执行：

```text
/comet 将 ./docs/grilled/session-security.md 作为完整需求来源。
生成 Native Spec 和验收项，确认后直接推进开发与验收。
```

前置研讨工具负责把产品思路谈透，Native 负责把定稿文档转成结构化验收条目、隔离 worktree 开发、对照原始需求全量验收、以及跨会话断点恢复。

## 五、确认之后开始长时间运行的开发

确认最终 Shape 后，后续开发、验收与归档由 Agent 和 Runtime 持续推进：

- 按你的隔离配置准备好 Git 分支或 worktree；
- 大型跨模块 PRD 在确认前可评估拆分为 [Supervisor Change](/zh/native/supervisor-change)，按依赖并行开发子任务；
- Builder 编码后用平台工具运行构建和测试，在后台自动向 Runtime 提交候选实现；
- Verify 对照原始请求、正式文档和全部验收项逐条核验，不通过则带着失败依据回 Build 修复；
- 会话中断、上下文压缩或换设备后，基于 `comet-state.yaml` 检查点和仓库文件恢复原进度；
- 全部通过后按确认策略完成 Archive 归档与 Git 交付。

整个开发过程中，只有在出现新的业务分歧、外部资源不可达、达到失败上限或需要确认验收与 Git 交付时，才会停下来请你决定。

## 六、按需求成熟度选择起点

| 当前手里有什么 | 推荐做法 | 实际体验 |
| --- | --- | --- |
| 只有一个初步想法 | 直接输入 `/comet` 走内置澄清 | Agent 先查代码，再用 `batch` 或 `sequential` 帮你理清决策并生成规格。 |
| 一份较完整的 PRD 或设计稿 | 直接提交本地文件或链接，指定覆盖范围 | 自动生成来源覆盖表和目标 Spec，只围绕缺口和冲突提问。 |
| 外部工具讨论定稿的文档 | 声明为完整需求来源 | 跳过已明确的问题，核对最终摘要后直接进入 Build。 |
| 团队已有的正式 Spec 与用例 | 作为需求来源导入 | 建立来源与验收 ID 映射，直接接入 Build、Verify 与 Archive。 |
