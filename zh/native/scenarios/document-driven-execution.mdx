---
title: "直接投递 PRD：让 Native 从文档进入长程执行"
description: "支持直接投递文件、附件、PRD 链接或深度讨论文档，Comet Native 全自动解析并映射系统目标 Spec；在文档完备时跳过无谓澄清，确认后一键迈入长程执行。"
---

Comet Native 原生支持接收各类本地文档、对话附件、在线 PRD 链接或架构设计，并自动将其中的业务诉求精准转译为严谨的目标 Spec 与逐项验收用例。当输入文档已清晰阐明业务目标、工程边界、正向交互及异常回退逻辑时，Native 会智能跳过已明确的既有问题。待你核准全景需求摘要后，change 将直接迈入长程 Build 实施阶段。

业务需求既可以通过 Native 内置的 Sequential（递进单题）或 Batch（批量聚合）澄清机制逐步推导形成，亦可先借助 Grill with docs 等专项工具完成高强度的推演对齐，再将最终定稿的文档交付给 Comet。Native 会深度校验来源覆盖矩阵、未决卡点与验收边界，随后接管后续的工程化流转。

## 一份文档即可直接作为 Native 的需求输入源

系统支持丰富多元的需求投递形态：

| 输入形式 | 典型示例 | Native 对应的解析机制 |
| --- | --- | --- |
| 会话附件上传 | 直接上传 PRD、技术方案或验收 Checklist 附件 | 深度流式解析附件正文，建立来源覆盖映射并自动生成 Spec |
| 本地文件或目录 | `docs/prd/batch-export.md` | 依据文件结构提取业务目标、用例、约束声明与非目标 |
| 在线 PRD 页面链接 | Notion、语雀、飞书文档或团队内部 Wiki 地址 | 爬取页面富文本；若遇到权限阻碍或内容截断，主动挂起并说明缺口 |
| Grill with docs 产物 | 经过高强度推演研讨后产出的深度澄清文档 | 将已对齐的决策作为事实源，不重复盘问文档中已解答的既有细节 |
| 存量架构 Spec 规范 | 团队内部既有的 RFC 架构提案或核心设计文档 | 精准转译为当前 Change 适用的目标 Spec 规范与验收测试项 |

在对话初始直接说明该文档的用途：

```text
/comet 把我刚上传的 PRD 作为完整需求来源。根据全文生成 Spec 和验收项；
没有未决的用户选择时，展示最终摘要让我确认，然后直接进入 Build。
```

若提供在线链接，亦可直截了当表达意图：

```text
/comet 按这个 PRD 完成功能，并把它作为 Native Change 的需求来源：
https://example.com/product/batch-export-prd
```

## Native 自动将自然语言文档升格为正式系统规格

Native 不仅是简单摘抄一段粗糙的文本摘要。系统会细致遵循文档标题、段落、列表、表格、代码块、示例用例、约束声明及超链接将全文拆解为离散的来源单元，并如实标注其解析完整度：

- `complete`：内容已全量解析并完成结构化归类；
- `partial`：仅读取了局部切片，仍存遗漏关键细节的潜在风险；
- `unavailable`：受当前平台权限限制或外部网络阻碍无法正常抓取。

随后，Native 会自动生成并持久化三类正式技术制品：

| 正式产物路径 | 核心承载内容 | 工程协同职责 |
| --- | --- | --- |
| `brief.md` | 业务目标、边界范围、来源映射、架构决议、待敲定卡点、验收样例与非目标 | 供人类快速复核 Native 对原始文档的理解偏差 |
| `specs/<capability>/spec.md` | 当前 Change 拟交付的完整系统能力契约与具体验收场景 | 作为后续 Build 编码与 Verify 审查的权威事实基准 |
| 验收项清单 | 具备稳定唯一编号、外在可观察、可裁决的测试用例 | 严格约束模型实现、自动化检查与独立的只读 Verifier |

所有需要编码落地的来源单元必须在目标 Spec 中建立映射，并至少绑定一个正式验收 ID。纯背景介绍与非目标说明虽然在分类中完整保留以备查阅，但不会被误当成代码任务。当新文档推翻了旧需求时，Native 会将陈旧单元标记为 `superseded`，并精准重定向至最新的有效结论。

```text
文档文件 / 附件 / PRD 链接 / Grill with docs 成果
  → 全量流式解析与来源覆盖矩阵构建
  → 组装 brief + 目标 Spec + 严谨验收项
  → 针对真实盲区进行靶向提问
  → 最终需求摘要全景确认门禁
  → Build 阶段 → Verify 阶段 → Archive 归档
```

## 文档完备时跳过无谓的逐题澄清

Native 会先自主探查代码库、环境工具链中能够确证的客观事实。在完成来源矩阵映射后，若同时满足以下全部条件，系统将自动跳过冗余的问答流程：

- 所有可访问的输入内容均已全量读取且无缺失；
- 每一项有效的业务诉求均已映射至 Spec 与验收集合；
- 文档对交付目标、边界范围、默认行为及异常分支均给出了唯一可执行的定义；
- 文档上下文内部各章节之间逻辑自洽，无自相矛盾之处；
- 代码库现有事实与项目既有规则未引出全新的架构抉择；
- 不存在标记为 `partial`、`unavailable`、未映射或存疑的阻塞项。

此时表明 Native 已完整理解需求并完成了正式规格建模，系统会自动跳过冗余的逐题问答，直接向你呈现一份全景需求摘要。内容涵盖交付目标、工程边界、核心决议、逐条验收项与非目标清单。待你给出明确的核准授权后，Runtime 即刻放行 change 迈入 Build 实施阶段。

<Note>
  “跳过澄清”仅代表智能省去了不必要的提问等待。进入 Build 前的最终需求确认门禁始终严格保留，确保 Native 提炼出的系统规格与你投递的原始初衷绝对一致，随后才由 Runtime 稳步推进长程实施。
</Note>

## 文档存在盲区时仅围绕缺口精准提问

文档篇幅浩繁并不直接等同于需求无懈可击。遇到以下情况时，系统依然会在底层生成 `[blocking]` 卡点：

- 外部链接需要企业内部 SSO 登录鉴权，当前 Agent 无法访问；
- 文件损坏、排版无法识别或内容遭遇截断；
- 不同的章节对同一个接口或系统交互给出了自相矛盾的表述；
- 诸如“支持失败后重试”等口语化描述，缺失会改变系统行为的具体语义（如重试上限、回退延迟）；
- 核心要求未能找到清晰的 Spec 映射或缺少对应的验收用例；
- 投递的材料更像是排错堆栈、方案评审参考或遗留代码片段，作为需求输入的意图模糊。

Native 严格聚焦于上述盲区发起针对性提问，不拿文档中已明确写清的细节重复提问。一旦收到你的决策答复，最新结论会即时写入 `brief.md`、更新目标 Spec 并刷新验收项，随后平滑引导至最终确认环节。

若遇到外部链接受权限拦截，最便捷的应对方式是将在线文档导出为本地 Markdown 或 PDF 文件后直接拖入对话。高层摘要无法替代原始正文，因为被忽略的表格参数、限制条件往往深度决定着最终代码的边界。

## 配合 Grill with docs 实施深度澄清

Native 的需求澄清协议可在常规对话中引导需求收敛。若你更倾向于借助类似 Grill with docs 的工具进行深度推演，可以先在专门的会话中对齐产品方案、异常处理、底层假设与非目标，整理为一份设计文档。

随后将该文档交付给 Comet 即可：

```text
/comet 将 ./docs/grilled/session-security.md 作为完整需求来源。
生成 Native Spec 和验收项，确认后把这个长程任务执行完成。
```

Comet Native 并不强制绑定任何特定的研讨工具，亦不强求外部文档套用 Comet 专有的排版模板。它纯粹将外部文档作为客观需求输入源，严把覆盖度、逻辑歧义与验收完整性关卡，随后接管长程执行。因此，你可以自由沿用团队偏好的前置研讨工具，同时获得 Native 的断点恢复与确定性校验能力。

## 将 Native 作为高韧性长程任务执行中枢

在需求方案完成最终确认后，你便可从繁琐的“流程应该怎么推”中抽身，将精力聚焦于最终交付物的商业价值。Native 在幕后将全自动推进：

- 自动创建并绑定专用的 Git 分支、worktree 及沙盒工作区；
- 遵循 Spec 规范自主规划代码实现策略，并实时固化任务演进水位；
- 真实调用底层编译与测试，提交具备自证证据的 Builder 代码候选；
- 唤起只读 Verifier 审查员，严格对照全量验收项实施无死角核验；
- 若出现测试未通过，携带精准堆栈退回 Build 针对性修复，并重新回归受影响模块；
- 即使遭遇会话崩溃、上下文被平台压缩或换机办公，基于 Git 仓库文件恢复现场；
- Verify 的全部检查通过后，执行 Archive 归档与既定交付动作。

全程仅在遇到全新的业务决策分歧、网络资源不可达、不可自愈的死锁或最终归档授权时，系统才会暂停提示你介入。常规的代码实现权衡、阶段跃迁与故障自愈均由 Agent 与 Runtime 稳定闭环。

## 遵循需求成熟度科学选择入口

| 当前输入物特征 | 推荐使用方式 | 预期的交互体验 |
| --- | --- | --- |
| 脑海中只有一个初步的雏形想法 | 直接启动 Native 原生澄清 | Native 主动调研代码事实，借助 Sequential 或 Batch 逐步梳理收敛出完备需求 |
| 已有一份较为详实的 PRD 文档 | 直接投递本地文件或在线链接 | Native 全自动完成 Spec 规格建模，仅针对未决盲区与关键选择点向你提问 |
| 已完成外部工具的高强度推演 | 直接交付研讨产出的定稿文档 | 智能跳过已明确的既有问题，全景需求确认后一键直通长程执行 |
| 团队已有正式的 Spec 契约与用例 | 将其声明为系统完整需求来源 | Native 自动构建来源映射矩阵，快速接入 Build、Verify 与 Archive 交付闭环 |

Native 既支持从简短的想法开始逐步澄清，也支持直接承接团队已有的成熟方案；无论从何处出发，最终都会进入 Native 的长程执行流程。
