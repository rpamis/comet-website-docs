## 为什么必须由父任务统一把关

这次重构跨越查询解析、SQLite 倒排索引、知识单元数据模型、插件事件、CLI、Dashboard 前端和评测脚本。尽管不同层可以分阶段实现，但最终必须共同满足五条全局约束：

1. **检索与降级**：Local Provider 默认结合 SQLite FTS5 全文索引与 ripgrep 混合召回，环境不支持 FTS5 时自动回退到纯文本检索；
2. **与个人记忆严格隔离**：项目知识（Project Knowledge）和个人记忆（Personal Memory）各自独立存储、独立维护所有权与 Token 预算；
3. **来源可核查**：提取出的每条项目知识都绑定具体文件来源，不能凭空编造，也不能替代对当前代码的直接核对；
4. **故障隔离**：索引异常、文件权限受阻或适配器报错时，不能阻塞正常的开发工作流；
5. **全端一致**：CLI、Dashboard、上下文注入、Retrieval Eval 与 Agent A/B 测试共用同一套能力边界。

这五条约束靠单个模块的单元测试无法证明，必须等全部子任务合入集成分支后，在父任务里做端到端的全量验收。

## 按真实数据流拆出 3 个功能子任务

在 `children.yaml`（`comet.native.children.v2` 格式）中，整体方案按数据依赖拆成三个顺序递进的功能子任务：

| 子任务名称 | 前置依赖 | 负责交付内容 | 独立实现提交 |
| --- | --- | --- | --- |
| `project-knowledge-hybrid-retrieval` | 无 | 查询规划、SQLite 分块索引、混合召回管道、索引生命周期管理与 Retrieval Eval 评测 | `d42226fb` |
| `project-knowledge-units` | `project-knowledge-hybrid-retrieval` | 知识单元数据模型、规则化事实提取、来源校验与一跳关系网络 | `efe007c9` |
| `project-knowledge-learning-management` | `project-knowledge-units` | 变更后受控学习流、插件事件接入、显式知识共享、CLI 管理命令、Dashboard 视图与 Agent A/B 测试 | `cca74993` |

依赖链路如下：

```text
project-knowledge-hybrid-retrieval（混合检索基础模块）
  → project-knowledge-units（知识单元模型与提取）
    → project-knowledge-learning-management（学习流、CLI 与 Dashboard）
```

这里有一个值得注意的实战经验：**Supervisor Change 不只适合“完全无依赖的纯并行”任务，同样适合有严格上下游依赖的分层重构**。Runtime 只有在上游子任务通过子验收并合入集成分支后，才会把下游子任务放进就绪队列，确保下游始终基于上游已验收集成的代码提交开工，不会对着未定型的接口盲写。

## 隔离 worktree 开发与串行合入集成分支

三个子任务各自在独立的 Git worktree 中编码与验收，不直接修改目标主分支，而是通过验收后由 Runtime 依次合入 Supervisor 的集成分支。仓库记录了三次清晰的集成提交：

| 集成提交 | 合并内容 |
| --- | --- |
| `6a230657` | 合入 `project-knowledge-hybrid-retrieval`，新增 19 个核心文件，建立 SQLite 索引、CLI 骨架与检索评测基础模块。 |
| `576f4c25` | 合入 `project-knowledge-units`，引入知识单元数据模型、提取管道及配套单元测试。 |
| `be58f9cc` | 合入 `project-knowledge-learning-management`，打通学习流、管理命令、Dashboard 页面与 Agent A/B 评测。 |

把“子任务局部实现提交”和“父级集成分支合并提交”分开记录，让每一步都可追溯：Runtime 能明确判断哪个候选已经通过局部验收、集成分支是否已经满足下游依赖，也能拦截过期或重复的回调。

## 父级全局 Verify 查出两轮跨模块缺口

三个功能子任务全部合入后，流程并没有直接归档，而是进入父级全局 Verify。归档中的 `verification.md` 记录了随后发现的两轮真实缺陷：

| 周期 | Verify 结论 | 暴露的跨模块问题 |
| --- | --- | --- |
| 周期 2 | `failed` | 前期方案调研的部分关键要求没有完整落到代码里，存在实现缺口。 |
| 周期 3 | `failed` | 知识来源校验边界、多 worktree 隔离、上下文激活条件、增量构建开销及端到端评测覆盖仍不完整。 |

这些问题横跨三个子模块，单个模块的单测查不出来。如果为了修它们去打散已经合入的三个子任务，既破坏了已验证的边界，又很难界定新一轮改动范围。Runtime 保留了当前集成分支的成果，让父任务回到 Shape 补充验收范围，并调整子任务计划。

## 追加修复子任务定向补齐缺口

在最终的 `children.yaml` 中，父任务没有重开前三个子任务，而是追加了第四个专门补齐验收缺口的修复子任务：

```yaml
- name: project-knowledge-closure
  depends_on: [project-knowledge-learning-management]
  covers: [A4, A8, A10, A15, A19, A20, A27, A29, A30, A31]
```

`project-knowledge-closure` 专门针对父级 Verify 暴露出的 10 项验收缺口（来源边界、定向增量刷新、激活条件、多 worktree 隔离与端到端评测）。在提交 `3cd0c25b` 中，它集中补齐了知识单元解析、学习流、插件集成、文件持久化与两个评测脚本的边界问题，同时完整保留了前三个子任务的既有提交。

## 49 项全量终审与区分无关测试噪音

进入第 4 个周期的第 2 轮 Verifier 审查时，全部验收通过。`verification.md` 记录了完整证据：

- **49 项端到端验收用例全部 `passed`**；
- 子任务局部验证、父级串行集成和父级全套检查全部完成；
- 专项测试、Native 框架测试、TypeScript 类型检查与生产构建全部通过；
- 独立代码审查（Code Review）指出的 3 项高风险隐患全部修复，无遗留严重阻塞。

还有一个贴近真实工程的细节：跑全仓测试时，仓库里一条与知识引擎无关的历史基线测试（`/comet` Skill 长度限制）触发了告警。Verify 如实记录了这条外部历史问题，没有把它误判成本次特性的功能缺陷，也没有因为无关噪音掩盖本次 49 项核心验收的真实证据。

## 统一归档，向主干呈现一次干净合并

父级全量验收通过后，Runtime 生成归档提交 `de780ce2`，再通过提交 `58b6dfb2` 将 `comet/agent-project-knowledge-engine` 统一合入 `040rc1` 分支。对外主干只看到一次完整、经过终审的合并：

```text
3 个功能子任务（各自独立 worktree 开发与验证）
  → 3 次串行合入父级集成分支
  → 2 轮父级全局 Verify 暴露跨模块缺口
  → 追加 1 个修复子任务（project-knowledge-closure）定向补齐
  → 49 项验收全部 passed
  → 统一 Archive 归档并合入 040rc1
```

## 从这次案例看何时用 Supervisor Change

| 工程机制 | 在本案例中的实际作用 |
| --- | --- |
| 按依赖拆分与调度 | 下游子任务等上游合入集成分支后才开工，避免基于未定型接口返工。 |
| 独立 worktree 隔离 | 每个子任务在独立目录开发与测试，不直接动目标分支，由 Runtime 统一合入。 |
| 父级全量终审 | 局部单测通过不等于整体达标，合入后由父级对照 49 项端到端要求做最终审查。 |
| 可追加修复子任务 | 全局终审发现跨模块缺口时，通过追加命名修复子任务定向解决，不破坏已有集成基线。 |

判断是否采用 Supervisor Change，不只看“能不能同时开多个窗口省时间”，更看三件事：**模块依赖是否清晰、各段改动能否隔离验证、以及最终是否需要围绕同一个大目标做统一终审**。
