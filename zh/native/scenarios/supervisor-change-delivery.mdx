本文真实复盘 Comet 官方仓库中已经顺利交付的 `agent-project-knowledge-engine` 变更。该任务于 2026 年 8 月 22 日正式归档并合并入 `040rc1` 分支。案例中的目标定义、子任务（child）切分、拓扑依赖、Git Commit 哈希与各项验收数据均直接取自仓库的物理审计记录。

本次变更对 Project Knowledge（项目知识库）进行了彻底重构：早期版本仅在检索时简单通过 ripgrep 实时扫描本地文档；重构后，它演进为 Agent 可以深度依赖的底层代码理解中枢。最终交付涵盖 SQLite FTS5 与 ripgrep 混合召回、结构化项目知识单元、受控学习机制、管理 CLI、Dashboard 可视化大盘以及严密的评估套件。

## 以宏观整体目标贯穿多个实施阶段

项目知识引擎的重构横跨查询解析、倒排索引、数据建模、插件生命周期事件、CLI 命令、WebUI 与测试评测。各模块虽然在物理上支持分阶段实施，但必须共同收敛于一个核心产品目标：**在大幅降低 Agent 重复摸索耗时的同时，确保一切结论依然以当前代码、配置及自动化测试为绝对可信基准**。

父级 Change 统领并牢牢锁定了以下全局边界：

- Local Provider 默认采用 SQLite FTS5 全文索引与 ripgrep 混合召回，在 FTS5 环境不可用时提供优雅平滑降级；
- Project Knowledge（项目知识）与 Personal Memory（个人画像记忆）实行严格的所有权隔离、独立存储与独立 Token 预算；
- 所有提取的项目知识必须强绑定当前的物理文件来源，绝不可凭空臆测，更不可取代实时的代码核对；
- 索引故障、文件权限受阻或语义适配器异常绝不可反向阻塞正常工作流；
- CLI 工具、Web 控制台、生成的技术资产、Retrieval Eval 评测及 Agent A/B 测试均共享同一套能力边界。

上述硬性约束唯有在全量子任务合流后开展端到端统筹验收，方能严密确证。各个子模块哪怕各自的单元测试全部通过，亦无法单独证明宏观产品目标已经成立。

## 依循真实依赖解耦出三个 Feature Child

归档中的 `children.yaml` 严格遵循 `comet.native.children.v2` 规范。最初的架构实施方案依循真实的数据流向，被拆分为三个顺序递进的 feature child：

| 子任务标识（Child） | 前置依赖 | 核心交付物与工程职责 | 独立实现 Commit |
| --- | --- | --- | --- |
| `project-knowledge-hybrid-retrieval` | 无 | 查询规划引擎、SQLite 分块索引、混合召回管道、索引生命周期管理及 Retrieval Eval 评测框架 | `d42226fb` |
| `project-knowledge-units` | hybrid retrieval | 知识单元数据模型、确定性事实提取器、来源物理校验及拓扑一跳关系网络 | `efe007c9` |
| `project-knowledge-learning-management` | knowledge units | 变更复盘自适应学习流、Plugin Event 钩子、显式知识共享、CLI 运维指令、Dashboard 视图与 Agent A/B 测试 | `cca74993` |

这三个子任务在拓扑上构成了单向依赖流水线：

```text
project-knowledge-hybrid-retrieval（混合检索基座）
  → project-knowledge-units（知识单元抽象）
    → project-knowledge-learning-management（上层运维与管理）
```

Supervisor Change 原生支持完全解耦任务的并发推进，同样深度支持此类按拓扑依赖分阶段实施的大型工程。Runtime 在调度时仅将前置条件全部达成的 child 移入 `readyChildren` 就绪池。后续子任务始终基于前序集成后的最新基线 Commit 开展编码，彻底杜绝了基于尚未定型的接口进行空中楼阁式盲目开发。

## 每个 Child 在隔离工作区中沉淀可集成资产

三个 feature child 分别入驻各自物理隔离的 Git worktree 中完成编码与测试验证。它们无权直接侵入目标主分支，而是遵循规范统一合流入 Supervisor 专属的集成分支。

代码仓库中完整记录了三次真实的串行集成提交：

| 集成 Commit 哈希 | 集成交付成果与物理变更 |
| --- | --- |
| `6a230657` | 合流 hybrid retrieval 模块，新增 19 个核心文件，奠定 SQLite 索引、CLI 骨架与检索评测底座 |
| `576f4c25` | 合流 knowledge units 模块，引入确定性提取管道、知识单元持久化模型及配套单测套件 |
| `be58f9cc` | 合流 learning management 模块，贯通学习流水线、管理指令集、可视化看板大盘与 Agent A/B 框架 |

每个子任务的局部业务开发 Commit 与集成分支的合流 Commit 分层清晰存档。Runtime 藉此精准判别特定代码候选是否已通过局部核验、当前集成分支是否已具备完整的依赖前提，以及异步迟到的异地响应是否依然合法。

## 父级全局 Verify 暴露跨模块缝隙

在三个 feature child 陆续合流入集成分支后，父级主任务并未草率宣布归档。归档目录中的 `verification.md` 忠实记录了随后遭遇的两轮验收失利：

| 目标周期编号 | Verify 裁决结论 | 全局审查捕获的核心跨模块缺陷 |
| --- | --- | --- |
| 周期 2 | failed 未通过 | 前期方案调研的部分关键结论尚未完全反映在实际代码中，存在实质性设计缺口 |
| 周期 3 | failed 未通过 | 知识来源的可信度校验、多工作区物理隔离、规则激活门禁、增量构建性能开销及全量评测覆盖率依然欠缺 |

这些缺陷并非局限在某单个子任务内部，而是典型的跨模块协同缝隙。若此时粗暴打散并重新激活已经集成的历史子任务，势必破坏已获确认的架构边界，亦难以对全局新暴露的验收范围进行清晰界定。Runtime 会保留集成分支的当前状态，让主变更返回 Shape 阶段，补充验收用例并调整子任务清单。

## 追加 Closure Child 定向收敛真实缺陷

在最终归档定稿的 `children.yaml` 中，架构师增设了第四个专职攻坚子任务：

```yaml
- name: project-knowledge-closure
  depends_on: [project-knowledge-learning-management]
  covers: [A4, A8, A10, A15, A19, A20, A27, A29, A30, A31]
```

`project-knowledge-closure` 靶向聚焦父级 Verify 暴露出的全部具体缝隙，包括来源边界控制、定向增量刷新、上下文激活门禁、多 worktree 隔离容灾及端到端评测闭环。后续的修复代码严格圈定在既定验收范围内，专注补齐代码实现与客观测试证据链。

其中，提交 `3cd0c25b` 彻底攻克了最后一轮审查边界缺陷，一口气覆盖了知识单元解析、学习流程流转、插件联动集成、底层文件持久化以及两个核心评测脚本。该子任务为复杂的跨模块系统缝隙单独划定了清晰的排错战场，同时最大化捍卫了前三个 feature child 的既有成果。

## 全链路终审覆盖 49 项业务行为

进入第四个目标周期的第二轮 Verifier 审查时，测试全线飘绿。最终沉淀的 `verification.md` 权威记录：

- 49 项端到端业务验收用例全部达成 `passed`；
- 所有子任务局部核验、父级分支合流与父级全套构建检查均合规走完；
- 聚焦针对性测试、Native 框架测试、TypeScript 类型校验及生产打包构建全数通过；
- 独立代码审查（Code Review）指出的 3 项高危架构隐患已全量修复；
- 确认不存在任何未决的 Critical 严重缺陷或遗留卡点。

在执行全量仓库测试时，系统敏锐捕获到一个与本次知识引擎改动完全解耦的既有 `/comet` Skill 长度基线报警。归档审查机制并未将这一外部历史包袱当成本次特性的缺陷，亦未让无关的外部环境抖动掩盖本次核心功能的全套专项客观证据。

## Archive 阶段一次性原子交付入主干

当父级主任务彻底跑通全链路 Verify 审查后，系统生成了不可变的归档提交 `de780ce2`。随后通过提交 `58b6dfb2`，正式将 `comet/agent-project-knowledge-engine` 完整并入 `040rc1` 发版分支。

整项宏观大型交付在对外主干上仅呈现一次干净、纯粹的原子化合并：

```text
3 个并行实施的 Feature Child
  → 3 次依序分支合流
  → 2 轮父级全局 Verify 暴露隐患
  → 1 个专职收敛缝隙的 Closure Child
  → 49 项业务验收全部通过
  → 流转 Archive 归档
  → 一键合入 040rc1 主线
```

## 从实战复盘中提炼架构拆解准则

本次真实交付全方位诠释了 Supervisor Change 架构的四项核心支柱：

| 核心工程机制 | 案例中的落地实践 |
| --- | --- |
| 依赖拓扑驱动 | 下游子任务严格在上游核心基座合流至集成分支后方准开工 |
| 物理工作区隔离 | 每个子任务在专有 Git worktree 中自研自测，最后由 Runtime 统一接管合流 |
| 父级全链路终审 | 局部单元测试通过后仍需整体验收，在集成分支上严密核验全盘业务目标与跨模块边界 |
| 容错闭环可追加 | 面对全局终审暴露的跨领域缝隙，通过增补 closure child 靶向收敛，绝不篡改历史集成基线 |

选用 Supervisor Change 架构的核心衡量准绳，在于整体目标是否需要拆分为多个能够独立自测验证的技术结果，且在宏观层面依然保有不可逾越的最终端到端终审验收。子任务能够并发推进仅能带来时间效率上的收益；而真正决定是否拆解的关键，在于**依赖拓扑是否清晰、代码候选能否物理隔离，以及最终交付能否进行全链路统一验收**。
