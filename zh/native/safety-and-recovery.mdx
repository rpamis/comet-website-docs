description: '深入了解 Native 的阶段准入守卫、任务归属鉴权、客观检查执行及事务级故障自愈机制。'

Native 借助刚性的阶段守卫（Guard）、不可伪造的任务身份标识与可恢复的原子事务全面管控交付全流程。Agent 负责理解需求意图、执行环境自测并研判代码变更的实际影响；Runtime 则在底层如实记录人类决策、稳步推演状态机并收敛最终的归档交付。

## 写入操作的任务归属判定

`.comet/current-change.json` 明确标识了当前免参数调用归属于哪套 workflow 及具体的 change。同一个项目支持按需启用多套工作流，但某一项具体的需求必须严格归属至单套流程中。平台的 Hook Router 在核验当前归属后，仅按需唤起匹配该流程的专用 Guard 插件。

当未显式指定归属且工作区仅存在唯一活跃任务时，系统会自动推断归属。若检测到存在多个候选任务、索引损坏或当前工作区与绑定记录脱节，系统会主动抛出选择题引导你明确目标，不会按默认配置猜测。若需在终端中手动校准归属，可运行 `comet native select <change-name>`。

## 阶段感知的文件变更拦截机制

- **Shape 需求设计阶段**：统筹业务目标、架构方案与逐条验收准则，必须等待开发者正式授权核准后，方放行进入代码实现。
- **Build 代码开发阶段**：严格在当前任务绑定的沙盒工作区内完成编码。Supervisor 架构下的各个子任务仅被允许在其专属的 Git worktree 中写入，主会话专门负责全局依赖协调与成果串行集成。
- **Verify 质量验收阶段**：审查员以只读视角严格对照初始诉求与全量验收项逐一裁决，禁止在审查过程中顺手修改业务代码；一旦发现缺陷，必须将现场带回 Build 阶段针对性排查。
- **Archive 最终归档阶段**：依据已获确认的交付结论与既定策略执行收敛，禁止借归档之机擅自扩大改动面或夹带无关文件。

日常的文档微调依照配置项 `native.document_writes` 统一处置。系统默认安全保留你的手动编辑，并由 Agent 评估实际影响面：单纯的排版润色不会粗暴作废已有的审批；若业务目标或验收标准发生实质变化，则退回重新确认；若实现细节调整，则提交新的代码候选；若测试命令调整，则针对性补跑受波及的用例。若启用了严格的 `revert` 策略，则依据 Guard 守卫给出的拒绝原因与自愈指引处理。详情请参阅[中途修改文档后的继续策略](/zh/guides/mid-workflow-changes#编辑后继续当前任务)。

## 面向可观察写入的前置安全防线

Hook 机制仅能捕获 Agent 平台公开暴露的文件写入事件与目标路径，并非操作系统层面的硬隔离沙盒。由 IDE 底层功能、第三方后台守护进程或平台未暴露通道直接触发的文件修改，可能无法在第一时间被 Hook 拦截。因此，后续由 Agent 主动发起的代码自审，以及 Runtime 对任务归属、工作区一致性与交付完整性的多重严格校验依然是必不可少的安全底线。

当 Agent 平台要求显式启用或授予 Hook 信任权限时，请务必先满足平台的安全要求；单纯在编辑器中安装插件并不等同于 Hook 已成功取得系统信任。

## 由 Agent 驱动的命令检查机制

常规的开发构建命令与测试套件直接借助 Agent 平台的工具链执行，系统会如实记录真实的调用指令、工作目录、执行耗时与返回码。Runtime 不再繁重托管这些外部系统进程，不强行绑定底层操作系统 PID，不空转等待所谓的停止回执，亦不再单凭文件散列特征机械决定是否跳过测试。

Agent 会结合现场客观研判既有测试是否依然适用于当前的代码候选与运行环境，在安全复用有效证据的同时，精准补跑受改动波及的必要验证。需要格外强调的是：单元测试通过不等于业务验收完成；Verify 阶段依然必须针对原始诉求与全量验收用例进行逐条裁决。若工程显式配置了隔离的独立审查，则必须严格满足隔离门禁。详细规范请参阅[验证与修复](/zh/native/verification-and-repair)。

## 工作区写入互斥与事务现场保护

每个 workspace 在同一时间切片内仅允许由单一执行者维护其状态机，并行派发的子任务通过完全独立的 Git worktree 实现隔离。标准工作流不再滥用繁琐的全局跨进程死锁，亦无需开发者手动清理僵尸锁。

在触发目录迁移与 Archive 归档时，系统会扫描是否存在未决的底层事务。一旦检测到尚待恢复的中间步骤、来源存疑的异常目录或工作区绑定冲突，系统会先启动原事务自愈。切勿试图通过强制删除状态文件或事务日志来绕过系统的安全阻塞。

## 实际路径与文件身份凭据鉴权

所有正式的技术文档与工作流状态机必须严格存放于 Runtime 指定的合法路径中。目录迁移、符号链接处理、归档历史路径映射以及工作区归属均由对应入口严格校验。技术文档的篇幅演进不再受内置字节上限截断，若文件读取遭遇异常会如实回显根因，不拿陈旧切片充当全量材料。

针对实际路径、文件写入与业务事务的校验，并不意味着 Runtime 会为每一次普通编辑在后台无节制地拍摄全量快照。切勿手动拼凑本机临时状态、随意篡改执行凭据或直接从无关任务中拷贝日志。

## 具备强容灾韧性的事务级归档

Archive 归档机制完整封存了原 Run 标识、已核准的验收结论、授权交付边界以及实时的 Git 交付水位。若在归档途中遭遇断电或异常中断，重启后系统会先核验底层的事务账本，依据建议动作继续归档；已执行成功的步骤不重复执行，面对结果未知的远端网络调用则优先校验现场真实状态。

若检测到 active 目录与 archive 归档目录同时共存、事务记录损坏、本地目录被其他程序占用或多个并发任务发生语义冲突，系统会第一时间安全保护现场并精准暴露阻塞原因。系统主 Spec 的更新与代码 Git 交付均受到确定性检查防护，不允许通过反复重建同名任务来粗暴覆盖未竟的底层事务。详细指引请参考[归档与交付](/zh/native/archive-and-delivery)。

## 基于原任务上下文的无损断点恢复

触发断点恢复时，系统会精准锚定原先的 change 标识与底层 Run 实例。正式技术文档与有效检查点构成了跨设备无损迁移的依据，单机私有的执行态数据则严格按 Git Checkout 分支与 worktree 实施隔离；文件路径始终以 Runtime 现场计算返回的绝对路径为准，彻底解耦对旧版本机目录布局的依赖。

若检测到原 Agent 任务仍在后台稳定运行，系统会保持静默等待其平稳执行完毕。等待工具响应超时不等于任务失败，禁止擅自重复派发。只有在捕获到明确的进程退出错误、任务失联或产物异常时，才严格依照标准恢复工序执行自愈。详细推演请参阅[任务推进与中断恢复机制](/zh/native/continuation-and-checkpoints)。

## 零副作用的只读恢复探测机制

`comet resume-probe` 以严格只读的模式智能识别当前会话意图与可恢复的任务上下文，不修改当前 change，更不会私自切换 Git 分支。若检测到多个候选任务或意图模糊，系统会暂停并请你做出选择；若未扫描到任何关联的活跃任务，系统保持普通对话状态。在配置文件中声明 `ambient_resume: false` 即可随时停用针对日常自然语言的被动探测。

## 统一系统诊断与应急自愈入口

在日常开发流转中，始终以 Runtime 实时返回的最新任务建议为准。当怀疑系统偏离或遇到阻塞时，推荐在终端执行：

```bash
comet status
comet native status <change-name> --details --json
comet native doctor <change-name>
```

若提示工作区不匹配，优先切换回系统建议的目标路径；若历史指令被拦截，重新获取最新的 continuation 动作；若版本升级迁移或归档流程中断，严格依照诊断命令回显的自愈路径推进。若诊断未输出明确的自动化修复动作，请保留当前工作区和运行状态，避免手动修改状态文件。
