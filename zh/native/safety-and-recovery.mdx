Skill 负责引导模型，Runtime 负责把关键边界落到可检查的状态和文件。两者职责不同：文案不能代替 Runtime 的检查，Runtime 也不会替模型判断一个测试是否有意义。

## 一次写入只属于一个 change

Comet 会把可观察的写入归属到当前选择的 workflow/change，一次写入最多交给一个 Guard。`.comet/current-change.json` 只记录当前请求归属，不限制 active change 的数量。没有可信项目上下文的遗留全局 Hook 保持中性，不会把另一个项目的 change 当成当前目标。

这套保护只覆盖宿主能观察到的写入。shell、IDE、后台进程或平台没有暴露给 Hook 的写入可能无法即时归属；下一次 Runtime 状态检查仍会拒绝不一致的结果，并要求回 Build、Shape 或用户处理。

## Portable 状态与本机 Runtime

跨设备稳定边界是 `comet-state.yaml`、brief、Specs 和可重建的 `verification.md`。它保存阶段、Loop、验收、handoff、必要检查、Verifier 结论、阻塞和下一步。

`.comet/runtime/native/` 只保存本机 `state.json`、日志、短时锁和事务。设备切换、文件缺失或 overlay 版本不匹配时，Runtime 从 YAML 重建；不会把旧机器的执行状态当作当前完成证明。

## Build 与 Verify 的安全边界

- Builder 只能提交 handoff，不能直接写入通过结论；
- Runtime 亲自执行必要检查，非零退出或超时不能当成通过；
- 新 Verifier 必须覆盖完整 A1…An，漏项、重复项和未知项都会被拒绝；
- Verify 失败回 Build，新的实现必须由新的 Verifier 重新验收；
- 正常 Archive 不重新运行 Verify，只应用 Spec、生成报告并移动 change；
- 没有独立 Verifier execution 时，报告和 Dashboard 显示降级状态，归档前需要用户确认。

## 环境感知恢复

`comet resume-probe` 是只读探针，只查看配置默认的工作流：

| 结果           | 含义                           |
| -------------- | ------------------------------ |
| `auto_resume`  | 目标唯一且请求明确要继续       |
| `ask_user`     | 有多个候选或归属不明确         |
| `out_of_scope` | 当前请求不表示要进入恢复工作流 |
| `none`         | 没有可恢复的 change            |

配置损坏、代码未同步、branch/worktree 不匹配或 active/archive 布局矛盾时，探针停下并给出原因，不会扫描另一套工作流或猜测目录。`ambient_resume: false` 只关闭普通请求的自动探测；显式 `/comet` 不受影响。

## Dashboard 的职责

Dashboard 只读展示 portable YAML 的阶段、Loop、验收、检查、阻塞、历史和用户文档，并在匹配时补充本机 overlay。它不推进、修复或归档，也不读取原始日志和执行身份；所有状态变更都通过 Native CLI/Runtime 完成。
