Skill 让模型遵守需求和阶段约定，Runtime 用可验证的状态、证据和事务检查兜底。前者是"该怎么做"，后者是"必须怎么做"——光有文案规则不能算硬约束，Runtime 才是不可绕过的状态机。

## 一次写入只属于一个 change

Comet 在你写的文件背后做了一道归属检查：一次写入最多落在一个 change 上，减少写错需求和重复阻塞。

具体怎么分流，取决于当前选中哪个 change 以及配置里启用了哪套工作流。读状态、查进度这类只读操作不会触发写入检查，所以你可以放心用 `status`、`show`，不会意外把后续写入绑到别的需求上。

需要注意的是，这套保护覆盖的是 Comet 能感知到的写入。对于 shell、外部进程或平台没暴露给 Hook 的写入，最终以 Runtime 的状态和证据检查为准。

## 不可变的 baseline

每个新 change 在创建时都要拿到一份完整的 baseline（项目初始状态的快照）。这是不可变事实——Runtime 不靠猜补全，比如不会把缺失的路径当成删除。

对于已经在用的 change，baseline 缺失或损坏不是 `doctor` 能自动修的问题，因为用当前文件重建会抹掉从创建以来的历史差异。这时只能从可信备份恢复原 baseline，或者保留需求文档和实现事实后新建 change。

唯一的例外是从旧版 schema 升级：`doctor --repair` 会在任何状态写入前先抓一份完整的迁移时点 baseline，抓不全就保持原状不动。迁移后的证据只覆盖升级之后的变化，不能继承升级前的 scope 或 pass。

## 证据与修复的边界

这两个主题在 [验证证据与自主修复](/zh/native/verification-and-repair) 有完整说明，这里只点出安全相关的结论：

- **验证证据会失效**：结论绑定 brief、spec、实现范围和 revision，任一变化旧证据作废。
- **修复有上限**：同一语义缺口第三次出现且无进展就停下，同一契约默认最多 5 次 Verify 失败。用完预算，Runtime 把决定权交还用户。
- **fail-closed**：任何完整性失败都不能靠手改 evidence 绕过。

## 环境感知恢复

`comet resume-probe` 是个只读探针：会话中断后，它读配置里的默认工作流，只查那一侧有没有可恢复的 change。

| 结果           | 含义                                                |
| -------------- | --------------------------------------------------- |
| `auto_resume`  | 目标唯一且请求确实要继续工作，按 `nextCommand` 恢复 |
| `ask_user`     | 多个候选或请求归属不明确，需要一个简短选择          |
| `out_of_scope` | 当前请求不是要进入可恢复工作流                      |
| `none`         | 没有可恢复 change                                   |

配置或状态损坏时，探针会停下并给出原因，不会扫另一套目录去猜。`ambient_resume: false` 可以关掉对普通请求的自动探测；显式调 `/comet` 不受影响。

## Dashboard 的职责

Dashboard 只读展示：阶段、证据是否有效、当前 continuation、结构化 finding、冲突摘要和归档就绪状态。它不重新推导事实，也不提供推进、修复或归档的写入按钮——所有写入都只能通过 CLI/Runtime 完成。
