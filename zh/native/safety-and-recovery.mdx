Native 的安全边界由两层组成：Skill 负责让模型遵循需求与阶段协议，Runtime 负责可确定检查的状态、证据和事务不变量。两者互补；文案 Rule 本身不等于不可绕过的状态机。

## 一次写入只属于一个 change

项目初始化会在每个平台安装一份 Comet 工作流 Rule；支持 Hook 的平台只安装一个 `comet-hook-router.mjs`。Hook Router 读取 `.comet/config.yaml` 与 `.comet/current-change.json`，把一次原子多文件写入最多路由到一个工作流 Guard。

Native 与 Classic 的 Guard 保持独立：

- Native 只按 Shape、Build、Verify、Archive 和 Native 路径检查；
- Classic 只按自己的五阶段与 OpenSpec/Superpowers 路径检查；
- 当前选择无效、陈旧或歧义时，可能写入会失败关闭；
- 明确认定的只读工具不会触发写入 Guard。

这个边界用于减少误写和双重阻塞。对于 shell、外部进程或平台未暴露给 Hook 的写入，最终仍以 Native Runtime 的状态和证据检查为准。

## 验证证据为什么会失效

Runtime 把验证结论绑定到：

- 需求简述与完整目标规格；
- 实现范围中的项目产物；
- 验收项 ID 与验证报告快照；
- 当前 change 修订版本；
- 可选的内置检查凭据。

这些输入变化后，旧证据会标记为失效。若变化发生在 Verify，状态命令会返回只含摘要的受控 `next`：先运行它退回 Build、生成新范围并验证。只有需求简述或规格的需求契约哈希也变化时才重新取得用户确认；仅项目快照或实现变化时保留原批准。Archive 中报告、凭据或其他绑定事实漂移时也使用同一回退协议；不能删除诊断项、手改证据引用或复用旧的通过结论。

Native Runtime 仅在 Git 项目中调用 Git 枚举项目文件和识别 gitlink 边界；普通文件的内容身份始终来自流式 SHA-256，不依赖 Git 对象哈希。新 change 会把规范化的 `native.snapshot.include`/`exclude` 策略绑定到基线快照，后续当前快照复用该范围；资源预算可以提高，但中途修改范围不能隐藏变化。`comet native check` 是独立的内置、有界、只读文本卫生检查，不调用 Git、shell、测试命令、外部 Skill 或任何外部进程，也不替代项目测试。

## 基线快照与数据结构迁移

新 change 必须在创建状态前取得完整基线快照。Git 快照只纳入已跟踪与未被忽略的未跟踪文件，子模块和 gitlink 作为原子条目；被忽略的缓存和未登记嵌套仓库的内容不会制造遗漏。当前快照不完整时不会把缺失路径推断成删除。

对已经使用 v3 数据结构的 change，基线快照缺失或不完整不是诊断命令可自动修复的问题。用当前文件重建会抹掉从创建以来的历史差异；只能从可信备份恢复原基线快照，或保留需求简述、规格和实现事实后新建 change。

v1/v2 数据结构迁移是唯一的切换例外。`doctor --repair` 会在任何状态写入前捕获完整的迁移时点基线快照；捕获不完整时旧状态保持不变。迁移后的证据只证明切换之后的变化，不能继承迁移前的范围或通过结论。旧 Verify/Archive 会受控退回 Build 重新建立 v3 证据。

## 自主修复不会无限循环

Verify 失败会回到 Build。Runtime 根据需求契约、未通过或缺失的验收项 ID 与失败检查 ID 形成语义签名：

- 相同语义缺口第二次出现时告警，第三次出现且没有进展时转为人工停止；
- 只有缺口减少、检查转绿或缺失证据恢复有效才算进展；普通实现范围变化不会重置计数；
- 无进展的显式越过只允许一次，并与当前签名绑定；
- 同一需求契约的 Verify 失败默认最多 5 次，可通过 `native.max_verify_failures` 配置正整数。

重复缺口停止与总失败预算独立生效。只有用户确认后的需求契约变化会开始新的目标周期；停止条件不按机械阶段往返次数计算。

## 并发规格冲突

多个 Native change 可以并行存在，但对同一正式规格的安全承诺有明确边界。Archive 会比较 Runtime 在 Shape 时冻结的 `base_hash` 与当前正式规格哈希；不一致时停止，不做最后写入覆盖。

处理步骤是：

1. 阅读最新正式规格；
2. 重写当前 change 的完整目标规格；
3. 运行 `comet native spec rebase <change> --summary <text>`；
4. 重新完成 Build 与 Verify；
5. 再次执行两步 Archive。

冲突雷达只报告当前 Native 产物根目录内可证明的能力重叠与范围信号，不声称理解任意外部分支或未纳入状态的并行工作。

## 事务与锁恢复

阶段推进、检查点、Archive 与产物根目录迁移都有明确的事务日志或恢复协议。普通写命令不会擅自接管陈旧锁；只有 `doctor --repair` 能在证明本机所有者已不存在、锁身份未变化且没有冲突事务时接管。

```bash
comet native doctor [<change-name>]
comet native doctor [<change-name>] --repair
comet native doctor [<change-name>] --repair --strategy continue
comet native doctor [<change-name>] --repair --strategy rollback
```

- 普通阶段转换只允许继续；
- Archive 与产物根目录迁移只有在事务日志所处阶段仍可逆时才能回滚；
- Archive 最终标记写入后只允许仅一次地继续；
- 诊断命令不会重写用户的需求简述、规格、验证报告或项目源码。

## 环境感知恢复

`comet resume-probe` 是只读探针。它先解析 `.comet/config.yaml` 的默认工作流，再只检查该侧状态：

| 结果           | 含义                                                |
| -------------- | --------------------------------------------------- |
| `auto_resume`  | 目标唯一且请求确实要继续工作，按 `nextCommand` 恢复 |
| `ask_user`     | 多个候选或请求归属不明确，需要一个简短选择          |
| `out_of_scope` | 当前请求不是要进入可恢复工作流                      |
| `none`         | 没有可恢复 change                                   |

配置或工作流状态损坏时，探针停止并给出原因，不扫描另一套目录猜测回退。`ambient_resume: false` 可以关闭普通请求触发的自动探针；显式调用 `/comet` 不受影响。

## Dashboard 的职责

Dashboard 只读取 Runtime 投影，展示阶段、证据有效性、后续动作、结构化诊断项、冲突摘要与归档就绪状态。它不重新推导事实，也不提供推进、修复或归档写按钮。CLI 和 Runtime 是唯一写入方。

需要处理并行需求时，查看 [多 change 与规格冲突](/zh/native/multi-change-and-conflicts)；遇到中断、跨设备发现或事务问题时，查看 [恢复与故障处理](/zh/native/recovery-playbook)。逐项命令和退出语义见 [Native CLI](/zh/cli/native)。
