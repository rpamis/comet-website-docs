长任务开发最怕两件事：一是会话窗口关了、上下文被压缩后，Agent 忘了之前确认过什么，把需求重新问一遍甚至把改过的代码覆盖掉；二是后台任务还在跑，新会话以为挂了又重派一份，造成重复提交或重复修改。

Native 把任务的完整执行历史保存在本机 SDK 运行记录（Run）中，同时在项目仓库的 `comet-state.yaml` 中写入恢复检查点（`run_checkpoint`）。**日常使用中，你只需回到原项目对话说“继续”或直接提要求**；Agent 会在后台自动读取 Runtime 返回的最新 `continuation` 指令推进，不靠聊天记忆猜进度。

## Runtime 如何告诉 Agent 下一步做什么

每次进入工作区或恢复会话时，Agent 会先在后台只读查询当前任务状态（不会修改任何文件或恢复丢失的 Run）。默认查询会完整返回所有待执行（`pending`）、运行中（`running`）和结果未知（`unknown`）的动作，同时每类已结束的历史集合只附带最近 12 条——既控制上下文开销，又不遗漏当前要处理的事情；需要追查更早轮次时再按需读取完整历史（`--details`），长任务还支持用 `--compact` 压缩重复结构。

Runtime 通过响应中的 `continuation.mode` 明确指示下一步动作，不需要 Agent 自己猜阶段：

| `continuation.mode` | 当前状态 | 接下来会发生什么 |
| --- | --- | --- |
| `execute` | 下一步明确，可直接推进。 | Agent 在指定工作区自动执行下一项工作并回报结果。 |
| `ask` | 停在人工决策点（如 Shape 确认、验收接受或失败恢复）。 | Agent 向你展示当前方案或结论，等你明确回复后再推进。 |
| `wait` | 任务已被某个执行者领取，正在执行中。 | Agent 继续跟踪原执行会话，等它完成后由原领取者回传结果。 |
| `reconcile` | 出现结果未知的动作、分支偏离或未完成事务。 | Agent 先核对原执行、目录或事务状态，再按返回的恢复指引处理。 |
| `done` | 流程已结束（已归档或已取消）。 | 核对最终状态；若已归档，单独核对约定的 Git 交付是否完成。 |

例如，之前处理 `login-error-message` 时关掉了窗口，重新打开 Agent 后你可以直接说“继续 `login-error-message`，先告诉我现在停在哪一步”。如果后台状态显示 `phase: "verify"` 且 `continuation.mode: "wait"`，Agent 会先去查原验收会话的进度，而不会直接重派一个新的 Verifier。

## 后台推进协议与防过期保护

普通任务和 Supervisor 任务的后台推进都通过统一的任务协议（`comet native next`）领取并回报：Shape 确认前用于提交结构化验收条目，Shape 确认后则统一覆盖开发实现、独立验收、子任务开发与验收、集成修复和父级修复。这套设计在底层提供了四项保障：

1. **一次提交串联内部步骤**：Agent 提交一轮业务结果后，Runtime 会严格校验格式（只接受合法状态和约定字段，拒绝拼写错误或多余字段），自动依次执行所有已获批准的内部步骤，直接返回下一个待办任务或人工确认点。
2. **自动附带适用上下文**：领取任务时，Runtime 会按当前阶段和任务自动注入相关的个人偏好与项目知识，避免每个阶段反复交代团队规范。
3. **幂等重传防重复记账**：如果网络抖动导致 Agent 没收到回执，原领取者携带相同任务标识、会话和结果再次提交时，Runtime 会识别为幂等确认，不会把同一轮结果重复记两次；但不同会话或不同内容会被拒绝。
4. **三类并发保护参数防旧确认覆盖**：当你确认 Shape、接受验收结果或发起修订时，Agent 在后台提交的命令会自动携带三类校验参数：
   - `--expected-state-version <n>`：校验状态版本号，如果期间状态已被其他会话推进，旧命令立即被拒；
   - `--expected-action <action>`：绑定当前预期动作，防止把确认提交到错误的动作上；
   - `--proposal-hash <hash>`：绑定当前等待确认的具体方案或验收结论摘要，一旦方案被修改，旧批准立刻失效。

## 工具超时、正在运行的任务与监控暂停

Agent 平台的等待工具超时，或者本地终端意外断开，**都不代表后台正在跑的测试、构建或 Verifier 已经失败**。Native 不使用操作系统 PID 来追踪或强杀任务，处理原则如下：

| 遇到的情况 | Agent 会怎么处理 |
| --- | --- |
| 会话关闭，Runtime 停在 `ask` 等待你批准 Shape 或验收结果。 | 重新向你展示当前方案或验收报告；此前已确认的决定继续有效，只处理当前待确认项。 |
| 等待工具超时，原 Verifier 或子任务仍在平台里执行。 | 到原平台查该会话进度；仍在跑就继续等，不会重新领取或另起一个相同任务。 |
| 平台明确回报任务未启动、执行出错或超时终止且无结果。 | 保留已完成的有效检查，按 Runtime 返回的恢复路径处理，只有在允许重试时才发起新执行。 |
| 原任务可能已改文件或调用外部接口，但结果未回传（`unknown`）。 | 先核对原会话、本地改动和外部系统状态；无法确认前保留现场，不重放可能有外部副作用的操作。 |

### 等待外部输入时如何处理定期监控

当任务仅仅在等你回复或等外部资料，且当前**没有**可执行子任务、**没有**仍在运行的后台任务、也**没有**需要定期轮询的外部作业（如 CI）时，Agent 可以暂停当前工作的定期监控，但保留其他独立任务的监控。首次进入等待时，Agent 会一次说明阻塞原因、缺少什么资料、暂停了哪些监控以及满足什么条件后恢复；收到新输入后再重读 Runtime 状态继续推进。

## 检查点写入边界与安全机制

理解“本机 Run”和“仓库检查点”的分工，就能清楚换机或恢复时哪些状态会自动保留：

- **本机 Run**：存放在用户主目录的 Comet 数据目录中（按工作区隔离），实时记录每一次推进、领取回执和内部事件。
- **仓库检查点（`run_checkpoint`）**：保存在项目仓库的 `comet-state.yaml` 中，随代码一起提交和同步。

### 检查点什么时候写入

Runtime 只在稳定边界写入 `run_checkpoint`——包括**等待用户确认前**、**Agent 任务交接时**、**外部命令执行前**以及**流程结束时**。纯内部、无副作用的中间步骤不会频繁改写 `comet-state.yaml`，避免制造无意义的 Git diff。不要手动编辑检查点来试图推进流程。

### 检查点的三层防错保护

1. **会话令牌单向脱敏**：写入仓库检查点前，本机 `claimToken` 会被哈希成 `portable-<sha256>`，避免把本机执行令牌提交到 Git。
2. **进行中的任务自动转为 `unknown`**：写入检查点时，处于 `running` 状态的动作会自动降级为 `unknown`。这样在另一台机器上恢复时，不会把旧机器上还在跑的任务当成可以直接重放的空闲动作。
3. **防篡改哈希与历史压缩**：检查点同时校验整体内容哈希（`hash`）以及与原本地版本号绑定的 `sourceHash`；长任务的 `v2` 检查点还会用共享值池压缩重复历史并附加 `storageHash`，任何手工篡改或文件截断都会在恢复时被拦截。

日常推进时，Agent 会在后台自动查询任务状态，你不需要手动运行。想自己查看时，你可以在终端运行下面的只读查询，查看 change 的当前状态和下一步。

<Accordion title="终端只读查看命令（可选）">

如果 change 位于独立 Git worktree 中，先进入对应 worktree 目录再运行：

```bash
# 查看当前工作区的活跃 change 列表
comet native status --json

# 查看指定 change 的阶段与下一步（默认附带最近 12 条历史记录）
comet native status <change-name> --json

# 查看完整业务状态、全部 Action 和 Wait 历史
comet native status <change-name> --details --json

# 压缩重复结构以减少 JSON 体积（请求模板保持完整）
comet native status <change-name> --json --compact
```

</Accordion>

Agent 在后台通过 `comet native next` 领取任务并回报结果，你不需要手动运行。

<Accordion title="命令参考（由 Agent 执行，仅供终端排障时查阅）">

```bash
comet native next <change-name> --session <会话标识> --json
comet native next <change-name> --session <会话标识> --action <action-id> --result <json-file|-> --json
```

</Accordion>
