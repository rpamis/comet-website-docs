---

Native 的自动推进不是后台任务，也不是无条件连跑。每次真实阶段转换都会返回下一阶段、是否自动衔接以及结构化后续动作；Skill 只在状态允许时继续。

## 后续动作结果

| disposition  | 含义                             | 后续动作                       |
| ------------ | -------------------------------- | ------------------------------ |
| `continue`   | 阶段转换已完成且下一动作明确     | 重新读取新阶段与必要产物后继续 |
| `await-user` | 仍有用户决定                     | 提出一个最上游问题并结束本轮   |
| `blocked`    | 状态、证据、冲突或恢复条件不满足 | 按诊断项修复，不猜测绕过       |
| `done`       | 归档已完成                       | 结束工作流                     |

`next: auto` 只表示 Runtime 允许继续，不代表后台守护进程已启动。调用方若明确要求在某次阶段转换后停下，Skill 完成该转换后不会再调用工具；下一会话从磁盘恢复。

## 检查点保存什么

长任务在同一阶段内中断时，可以保存：

```bash
comet native checkpoint <change-name> \
  --summary <已完成事实> \
  --next-action <下一动作> \
  --artifact <项目相对路径> \
  --expect-revision <n>
```

检查点包含简短事实摘要、下一动作和内容寻址产物清单。它不会推进阶段，也不替代需求简述、完整目标规格或 `verification.md`。

恢复时 Runtime 会检查检查点对应的阶段、修订版本和清单。任何一项变化都会使检查点失效；旧摘要仍可作为历史提示，但不能覆盖当前状态。

## 为什么不需要独立交接文档

Classic 需要在多个阶段 Skill 与外部方法之间交接，因此有设计上下文、计划和压缩投影。Native 始终由一个 Skill 重新读取正式产物：

- 需求简述和目标规格保存需求；
- 状态和后续动作保存阶段；
- 检查点保存阶段内进度；
- 验证报告与凭据保存证据。

因此 Native 没有 `context_compression` 模式，也不会生成只为阶段 Skill 传递上下文的交接文档。必要信息通过正式产物和哈希绑定，减少摘要漂移。
