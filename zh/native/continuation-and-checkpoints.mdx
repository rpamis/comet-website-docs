Native 的自动推进不是后台任务，也不是无条件连跑。每次真实 transition 都返回下一阶段、是否自动衔接以及结构化 continuation；Skill 只在状态允许时继续。

## Continuation 结果

| disposition | 含义 | 后续动作 |
| --- | --- | --- |
| `continue` | transition 已完成且下一动作明确 | 重新读取新 phase 与必要产物后继续 |
| `await-user` | 仍有用户决定 | 提出一个最上游问题并结束本轮 |
| `blocked` | 状态、证据、冲突或恢复条件不满足 | 按 finding 修复，不猜测绕过 |
| `done` | 归档已完成 | 结束工作流 |

`next: auto` 只表示 Runtime 允许继续，不代表后台 daemon 已启动。调用方若明确要求在某个 transition 后停下，Skill 完成该 transition 后不会再调用工具；下一会话从磁盘恢复。

## Checkpoint 保存什么

长任务在同一 phase 内中断时，可以保存：

```bash
comet native checkpoint <change-name> \
  --summary <已完成事实> \
  --next-action <下一动作> \
  --artifact <项目相对路径> \
  --expect-revision <n>
```

Checkpoint 包含简短事实摘要、下一动作和内容寻址 artifact manifest。它不会推进 phase，也不替代 brief、完整目标规格或 `verification.md`。

恢复时 Runtime 会检查 checkpoint 对应的 phase、revision 和 manifest。任何一项变化都会把 checkpoint 标为 stale；旧摘要仍可作为历史提示，但不能覆盖当前状态。

## 为什么不需要独立 handoff 文档

Classic 需要在多个阶段 Skill 与外部方法之间交接，因此有 design context、计划和压缩投影。Native 始终由一个 Skill 重新读取正式产物：

- brief 和目标规格保存需求；
- state 和 continuation 保存阶段；
- checkpoint 保存阶段内进度；
- verification 与 receipt 保存证据。

因此 Native 没有 `context_compression` 模式，也不会生成只为阶段 Skill 传递上下文的 handoff。必要信息通过正式产物和 hash 绑定，减少摘要漂移。
