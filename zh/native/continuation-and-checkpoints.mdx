title: '连续推进与恢复'
description: '理解 Native 如何用 Runtime continuation 推进 Build、Verify、Archive，并从稳定文件状态恢复。'
---

Native 不要求 Agent 记住上一轮对话，也不要求用户手动切换阶段。每次 Runtime 操作都会返回下一步；Skill 只执行当前 continuation 允许的动作，遇到用户决定或异常就停下来。

## Continuation 结果

| `status` / `stage` | 含义                               | Skill 的动作                                       |
| ------------------ | ---------------------------------- | -------------------------------------------------- |
| `continue`         | 当前动作完成，下一步明确           | 读取 `continuation`，执行给出的命令或 handoff      |
| `await-user`       | 需要用户决定、确认或解决外部阻塞   | 展示原因和选项，等待用户，不猜测                   |
| `blocked`          | 状态损坏、并发冲突或错误预算已用尽 | 读取恢复动作，必要时运行 doctor 或回到 Shape/Build |
| `done`             | 已完成归档                         | 结束当前 change                                    |

正常的 Native Loop 是：

```text
Shape → Build → Runtime checks → 新 Verifier →
  通过 → Archive
  失败 → Build（iteration + 1）
```

Verify 期间的额外检查通过当前 attempt 的 `request-checks` 请求。相同且已完成的检查会复用；Archive 正常路径不重复执行验收。

## 稳定边界是什么

跨会话、跨设备真正需要同步的是：

- `.comet/config.yaml`；
- change 的 `brief.md`、完整 Specs 和 `comet-state.yaml`；
- 已生成的 `verification.md`（缺失或落后时可由 YAML 重建）。

`.comet/runtime/native/` 的 `state.json`、日志、锁和事务是本机 overlay。它缺失、版本落后或属于另一个 change 时，Runtime 会丢弃并重建，不会把它当成 portable 事实。正在执行的检查按中断处理；旧 Verify pass 在新设备上按恢复策略重新确认。

## Skill 如何继续

先运行：

```bash
comet native status <change-name> --details --json
```

然后只使用输出中的 `continuation.commandArgs` 或 `inputOptions.template`。如果命令被拒绝、Verifier 不可用、执行错误、语义结果被阻塞或发生迁移/损坏，先查看 [Native status 命令](/zh/cli/status) 和 [恢复手册](/zh/native/recovery-playbook)，不要自行拼接内部 JSON。

`await-user` 不是失败，也不是可以跳过的提示。用户确认后，Runtime 会创建新的状态版本；如果实现已改变，则必须回 Build，由新的 Builder 和新的 Verifier 重新开始。

## 跨设备恢复

换设备后先确认代码、artifact root 和 branch/worktree 一致，再运行 `status`。如果目标不明确、代码未同步、active/archive 同名或 capability 有并行归档冲突，Runtime 会返回 `await-user`/`blocked`，而不是自动修改目录。没有 `verification.md` 的 Shape/Build 仍可恢复；Verify 和 `archive-ready` 会先重建必要的本机执行状态并重新确认。
