本文集中解答关于 Classic 五阶段工作流、断点状态恢复、阶段守卫拦截与轻量预设的常见疑问。

## 基础概念

<AccordionGroup>
  <Accordion title="Comet 与 OpenSpec、Superpowers 是什么关系？">
    Comet 并非两者的替代品，而是整合二者的工程框架。OpenSpec 负责 **WHAT**（梳理需求、生成技术提案、维护 Spec 生命周期与版本归档），Superpowers 负责 **HOW**（脑暴探索、技术方案设计、拆解计划、编码执行与功能验证）。Comet 则负责把二者串联为一条具备质量门禁、支持中断恢复的五阶段开发工作流，确保每个环节都有据可查。详见 [工作流核心概念](/zh/concepts/workflow)。
  </Accordion>

  <Accordion title="/comet 与 /comet-any 有什么区别？">
    在日常编码中，统一调用 `/comet` 即可。当项目配置为 Classic 时，系统会自动交由内部路由 `/comet-classic` 驱动 open、design、build、verify、archive 五阶段流程；若配置为 Native 则进入轻量工作流。而 `/comet-any` 是专门的 Skill Creator 创作工具，用于创建、优化和组合可复用的 Skill Bundle。两者的分工与职责截然不同。
  </Accordion>

  <Accordion title="我必须同时使用 OpenSpec 与 Superpowers 吗？">
    Classic 模式依赖这两者：OpenSpec 负责生成并维护规格文档，Superpowers 提供架构设计与任务拆解方法论。在执行 `comet init --workflow classic` 时系统会自动安装二者；而全新的项目初始化默认推荐使用不依赖外部框架的 Native 工作流。如果你只是想利用 Comet 创作与发布可复用的自定义 Skill，可以直接阅读 [组合任意 Skill 快速上手](/zh/skill-creator/getting-started)。
  </Accordion>
</AccordionGroup>

## 与相似产品的区别

<AccordionGroup>
  <Accordion title="Comet 与 superpowers-bridge 有什么本质区别？">
    两者都致力于把 OpenSpec 与 Superpowers 串联起来，但实现路径与保障机制存在本质差异：

    **superpowers-bridge** 是一个 [OpenSpec 原生 schema bundle](https://github.com/JiangWay/openspec-schemas)：需要将其拷入项目的 `schemas/` 目录中，通过 `--schema superpowers-bridge` 参数逐任务调用。它属于**纯 Prompt 层的松散集成**——不触及底层源码，依赖 `schema.yaml` 中的任务 DAG 规则和纯文本形式的 `PRECHECK` 提示词来约束模型顺序。

    **Comet** 则是工程化的 CLI 工具包（`@rpamis/comet`），内置跨平台 Node 运行时、`.comet.yaml` 状态机、PreToolUse hook 拦截、自动化诊断与零依赖断点恢复。二者的核心差异如下：

    | 维度 | superpowers-bridge | Comet |
    | ---- | ------------------ | ----- |
    | **产品形态** | 静态 OpenSpec schema 模板包 | 独立 npm CLI 工具包 + Node 跨平台运行时 |
    | **集成深度** | 纯 Prompt 提示词级约束 | Prompt + 工程运行时（状态机、Hook 守卫、阶段拦截） |
    | **流程编排** | 依赖纯文本说明，靠人工或模型自觉调用 `/opsx:*` | 五阶段状态机，支持脚本驱动的 [自动推进机制](/zh/concepts/auto-transition) |
    | **断点恢复** | 仅依赖散落的 Markdown 文件，无显式状态机 | 完备的 [`.comet.yaml` 状态机](/zh/concepts/state-management) 与检查点恢复 |
    | **约束强度** | 纯文本 `PRECHECK`（模型可读到却常忽视） | 阶段规则注入 + PreToolUse Hook 强制阻断，违规写入直接拦截 |
    | **平台门槛** | 强依赖具备子代理能力的平台 | 跨 39 个主流平台，无论是否支持 Subagent 均有完善的降级支持 |
    | **交互入口** | 仅能在 `/opsx:*` 系列命令下起效 | 基于 [智能意图识别](/zh/concepts/intent-routing)，自然语言需求直接精准分发 |
    | **流程分级** | 需人工判断“是否值得新建完整 change” | 内置开箱即用的 [hotfix](/zh/presets/hotfix) 与 [tweak](/zh/presets/tweak) 轻量预设 |
    | **生态延展** | 仅限单一开发工作流 schema | 全流程工作流 + Skill 创作与评测平台（[组合](/zh/skill-creator/getting-started) / [评测](/zh/cli/eval) / [可视化看板](/zh/cli/dashboard)） |
  </Accordion>

  <Accordion title="既然底层都是 OpenSpec + Superpowers，Comet 的优势体现在哪里？">
    相比单纯的 Prompt 模板堆砌，Comet 的优势集中体现在四个工程维度：

    1. **确定性状态机与零丢失恢复**：`.comet.yaml` 严格维护 `phase`、`build_mode`、`tdd_mode`、`review_mode` 等元数据。即使在遭遇超长任务或对话上下文被强行压缩后，也能基于检查点恢复到中断前的状态。
    2. **强制拦截违规操作**：Comet 具备底层 PreToolUse hook 守卫（如 `comet-hook-guard.mjs`），配合阶段守卫规则，在 design 阶段拦截业务代码编辑，跳步时抛出错误。纯文本提示词难以约束模型幻觉，Hook 则能实施硬性阻断。
    3. **稳定且全自动的意图路由**：系统能够直接从你的自然语言输入中推断真实意图并路由到对应流程，无需开发者死记硬背各类底层参数。
    4. **完善的生态工具链**：集成 `/comet-any`（可视化创建组合 Skill）、`comet eval`（沙箱化测试与量化打分）以及 `comet dashboard`（全景只读看板）。

    如果你只需要在 OpenSpec 中简单引入 Superpowers 的设计模板，且不介意手动运行各阶段的命令，superpowers-bridge 相对轻巧；但若追求复杂任务的稳定性、限制 Agent 执行范围的机制、多平台兼容以及完善的评测体系，Comet 能够提供更专业的工程保障。了解更多背景请查阅 [Comet 与业界实践对照](/zh/concepts/comet-vs-industry)。
  </Accordion>
</AccordionGroup>

## 状态与断点恢复

<AccordionGroup>
  <Accordion title="对话中断后再回来，Agent 如何知道进度停在哪了？">
    Comet 从不依赖脆弱的聊天历史。重新在项目中输入 `/comet` 时，系统底层会自动扫描当前活跃 change 的 `.comet.yaml` 状态机以及磁盘中的真实产物，核对无误后准确切回对应的阶段 Skill 继续执行。
  </Accordion>

  <Accordion title="运行 comet status 为何看不到刚刚创建的 change？">
    该变更可能是在外部直接通过原始命令（如 `/opsx:new`）创建的，缺少必要的 `.comet.yaml` 状态机，因此会被系统作为非受控目录跳过。此时只需在 Agent 中输入 `/comet`，系统会自动识别该目录并为你补齐状态文件完成接管。详见 [存量项目接入](/zh/guides/existing-project) 中的“孤儿 change”处置说明。
  </Accordion>

  <Accordion title=".comet.yaml 可以手动直接修改吗？">
    用户可见字段（如 `workflow`、`build_mode` 等）建议通过正常的流程流转更新，尽量不要手动修改 `phase`，避免造成状态机与文件不一致。而存储在本地缓存中的运行时底层文件（如 `.comet/run-state.json`），禁止手动篡改。若需排查或修复异常状态，请使用标准的 `comet-state` 工具，详见 [状态管理](/zh/concepts/state-management)。
  </Accordion>

  <Accordion title="窗口历史记录被意外清空或压缩，会不会导致开发进度丢失？">
    完全不会。在方案设计阶段系统会自动保存设计摘要，在编码阶段每个子任务也都有持久化的检查点。恢复时只需在对话中输入 `/comet`，系统会直接读取文件重新定位，代码与进度不受影响。详见 [恢复中断的工作](/zh/guides/resuming-workflow)。
  </Accordion>
</AccordionGroup>

## 阶段守卫与质量门禁

<AccordionGroup>
  <Accordion title="为什么不能跳过 design 阶段，直接开始写代码（build）？">
    Comet 的核心底线是“方案未敲定前不写代码”（hotfix 和 tweak 轻量预设除外）。完整流程的守卫在放行进入 build 之前，会强制校验 `design_doc` 是否存在。跳过方案推敲往往会导致后续开发频繁返工，因此守卫会明确拦截。
  </Accordion>

  <Accordion title="verify 阶段验收报错未通过该怎么处理？">
    切勿强行归档。对于常规的技术报错或测试失败，系统会在重试预算内自动退回 build 阶段修复，无需人工介入；只有当连续尝试 4 次依然未通过、或者报错涉及功能范围取舍时，系统才会主动暂停等待你做决策。在验收结果为 fail 的情况下，归档守卫会直接阻断归档，避免未经完整验收的变更被交付。
  </Accordion>

  <Accordion title="阶段是如何向前推进的，需要我手动输入下一阶段命令吗？">
    阶段的推进由守卫命令 `comet-guard.mjs --apply` 自动完成。在默认配置（`auto_transition: true`）下，当前阶段检查通过后会自动唤起下一个阶段的 Skill；若配置为 `false`，则会在达标后暂停并输出提示，等待你手动触发下一步。
  </Accordion>

  <Accordion title="修改了方案后，需要手动重新生成交接材料吗？">
    当前 Classic 采用直接读取正式文档的机制，无需手动重新计算 Handoff Hash。Agent 会先行评估方案调整带来的代码影响，并按需修正后续计划；若架构方案产生重大转向，只需重新确认即可。日常开发无需手动运行打包脚本。
  </Accordion>
</AccordionGroup>

## 预设模式与复杂需求

<AccordionGroup>
  <Accordion title="hotfix 与 tweak 预设有什么区别？">
    两套预设均跳过了繁重的独立设计文档流程，但依然完整保留了状态跟踪、自动化验证与规范归档。hotfix 专用于复现路径明确的 Bug 修复；tweak 适用于目标明确的配置微调、文案更新或小范围能力改动。一旦在开发中发现改动涉及核心架构或公开 API 变更，系统会自动提示你升级为完整流程。详见 [hotfix 预设](/zh/presets/hotfix)。
  </Accordion>

  <Accordion title="遇到复杂庞大的业务需求时该如何拆解？">
    在 open 阶段初期，`/comet-open` 会自动触发 PRD 拆分预检查。如果需求体量过大，系统会建议将其拆解为多个彼此独立、可单独测试与交付的子任务，并为你规划清晰的批次关系。详见 [大型 PRD 拆分](/zh/guides/prd-splitting)。
  </Accordion>

  <Accordion title="review_mode 参数有什么作用？">
    `review_mode`（可选 `off`、`standard`、`thorough`）用于控制 build 与 verify 阶段自动化代码审查的严格程度。完整工作流在开始编写代码前会提示你选定；hotfix 模式下默认关闭。你可以在 `.comet/config.yaml` 中设置全局默认值。
  </Accordion>
</AccordionGroup>

## 常见困惑与日常贴士

<AccordionGroup>
  <Accordion title="如何阻止 Agent 自动提交 Git commit？">
    自动提交属于部分底层工具（如 Superpowers 原生脚本）的固有行为。如果你不希望频繁自动提交，可以在配置中引入拦截 Git Commit 的针对性规则。
  </Accordion>

  <Accordion title="代码写到一半，我对实现方案不满意想重来怎么办？">
    首先明确让 Agent 暂停编写代码。随后根据实际情况处理：
    - **如果你手动修改了规格文档或计划**：直接在对话中再次输入 `/comet`，系统会自动重新加载变更文档，恢复到对应阶段；
    - **如果你手动修改了源码**：同样输入 `/comet` 并说明“我已手动调整了代码，请基于当前工作区评估进度”，系统会核对未提交的代码变动并重新校准状态。
  </Accordion>

  <Accordion title="使用 Comet 之后，Token 消耗增加、响应变慢了？">
    Comet 的完整流程面向的是复杂、高可靠性要求的业务需求：前期的多轮澄清、方案设计、测试驱动与代码审查，每一步都设立了严格的质量门槛，因此在复杂任务中的 Token 消耗会相对较高。对于日常的小改动或改动极小的需求，强烈建议优先使用 `comet-hotfix` 或 `comet-tweak` 轻量预设，或者采用 Native 工作流快速推进。
  </Accordion>
</AccordionGroup>
