Comet 能够自动流畅推进无歧义的执行步骤，但始终将核心产品走向与技术风险决策权留给你。每一个需要你参与确认的节点，都被定义为一个**停顿点（blocking decision point）**：Comet 会主动暂停并等待你做出选择，收到明确答复后才继续推进。

本文完整汇总了五阶段工作流中所有的停顿点，帮助你在使用前清楚了解在哪些关键节点需要人工把关。

## 交互形式与提问体验

在支持交互式卡片的平台（如 Claude Code 等）上，Comet 会优先将停顿点渲染为直观的可点击单选或多选控件。你会清晰看到各个选项的标签与其技术影响；系统提供的推荐项仅供辅助参考，最终抉择始终由你拍板。

| 交互场景                                   | 你将看到的界面体验                                               | Comet 的后续行为                                              |
| ------------------------------------------ | ---------------------------------------------------------------- | ------------------------------------------------------------- |
| 单选停顿点                                 | 一个单选问题卡片，例如是否继续执行、选择哪种 Git 分支处理方式    | 仅在你点选确认后，Comet 才会更新状态机或执行对应分支操作      |
| 多选停顿点                                 | 一个多选问题卡片，例如一次性选定工作区隔离方式、执行模式、TDD 策略与审查模式 | 提交选择后，Comet 一次性将这些参数固化写入状态机              |
| 平台不支持卡片交互，或首次卡片调用失败     | 清晰的编号文本选项，明确标注“单选”或“多选”、每项的具体影响，并提示你回复编号 | 当前会话后续所有停顿点均平滑退回文本编号模式，不再反复尝试失败的卡片调用 |

<Note>
  若在某个平台上看到的是纯文本编号列表，这并不意味着工作流功能被降级。这仅仅是输入控件的呈现形式差异；所有的阶段阻断规则、选项含义和安全门禁完全保持一致。
</Note>

## 停顿点全景速查

以下按五阶段推进顺序，依次列出全部停顿点。每个阶段的停顿点按触发时间先后排列，前一阶段通过后方可解锁下一阶段。

<Note>
  从 0.4.0-beta.5 起，Comet 仅在<strong>真正需要人工抉择的核心节点</strong>主动暂停。
  前 3 次可自动化修复的报错、唯一明确的下一步动作、以及完全遵从既有配置的操作均会自动执行，不再反复弹出琐碎确认。
  当 <code>auto_transition: false</code> 输出 <code>NEXT: manual</code> 时，仅表示交还终端控制权，<strong>并非新的决策停顿点</strong>，不会弹出“是否继续”的无效打扰。
</Note>

| 4    | 规格文档终审（名称与范围） | 最终审阅并确认变更名称、业务范围以及 proposal / design / tasks 文档是否达标 |

| ---- | -------------- | ----------------------------------------------------------------- |

| ---- | ------------ | ---------------------------------------------------------------------- |

| 编号 | 停顿点名称 | 核心决策内容                                         |
| ---- | ---------- | ---------------------------------------------------- |

## 各阶段停顿点详解

### 1 — 工作流目标选择（路由阶段）

| 属性         | 具体说明                                                            |
| ------------ | ------------------------------------------------------------------- |
| **触发时机** | 存在多个未结变更、新建与继续意图并存、或大需求批次拆分后选择起始项   |
| **决策内容** | 明确继续哪一个活跃变更、是否创建新变更、或者在拆分批次中优先做哪一项 |
| **呈现信息** | 当前所有活跃变更列表、批次任务清单及各自分支状态                    |

Comet 仅在存在真正歧义时才会暂停；如果当前只有一个清晰关联的活跃变更，系统会直接建议恢复。

### 2 — PRD 拆分预检查（open 阶段）

| 属性         | 具体说明                                          |
| ------------ | ------------------------------------------------- |
| **触发时机** | 需求描述为大型 PRD / 版本路线图，或包含多项互不依赖的独立能力 |
| **决策内容** | 评估是否将大需求科学拆分为多个更小、更安全的 change |
| **呈现信息** | 建议的拆分方案清单（包含各子任务的名称、目标、边界与依赖关系） |

可选方案：

| 选项                      | 实际效果                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------ |
| 创建多个 OpenSpec changes | 为每个子需求独立调用 `/comet-open`，并将批次关系持久化至 `.comet/batches/<batch-id>.json`  |
| 保持为一个 change 继续    | 放弃拆分，以单一完整任务继续推进，并记录不拆分的原因                                       |
| 调整拆分方案              | 重新微调拆分维度与范围，刷新清单后再次供你确认                                             |

在确认拆分方案之前，系统不会向磁盘写入任何正式产物。每个子需求完工后均需通过严格双重校验。详见 [大型 PRD 拆分](/zh/guides/prd-splitting)。

### 3 — 工作区隔离决策（open 阶段）

| 属性         | 具体说明                                                                                     |
| ------------ | -------------------------------------------------------------------------------------------- |
| **触发时机** | 创建 Classic change 之后、正式生成 OpenSpec 产物与 `.comet.yaml` 之前（严禁推迟至 build 阶段） |
| **决策内容** | 选择环境隔离模式：当前工作区（current）、新建 Git 分支（branch）还是独立的 Git worktree      |
| **呈现信息** | 三种隔离方式的优缺点对比与适用场景说明                                                       |

若你在初始需求中已明确表达了多任务并行意图，系统会直接选用 worktree 隔离，不再重复打扰；未明确时则一次性提供三种选项供你挑选。

### 4 — 规格文档终审（open 阶段）

| 属性         | 具体说明                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------- |
| **触发时机** | proposal / design / tasks 三份核心规格文档起草完毕且通过了完整性自检                              |
| **决策内容** | 最终审核并确认变更名称、业务边界以及三个文档的具体约定是否符合预期                                |
| **呈现信息** | proposal（背景与目标）、design（技术选型）、tasks（任务项与关键点）、系统推导的标准英文标识         |

| 选项               | 实际效果                           |
| ------------------ | ---------------------------------- |
| 确认无误，进入下一阶段 | 阶段守卫检查放行，正式推进到 design |
| 需要进一步调整     | 根据你的反馈修改文档，重新呈现确认 |

<Note>
  从 0.4.0-beta.5 起，open 阶段初期的需求澄清与命名过程默认<strong>不阻断流程</strong>。在业务目标与命名清晰的前提下，流程会自动流转，无需反复确认中间草稿；最终通过本停顿点 4 完成一次性全局终审。
</Note>

### 5 — 设计方案确认（design 阶段）

| 属性         | 具体说明                                                     |
| ------------ | ------------------------------------------------------------ |
| **触发时机** | 头脑风暴研讨结束、产出初步技术方案，在正式落盘 Design Doc 之前 |
| **决策内容** | 拍板确定采用的技术架构方案                                   |
| **呈现信息** | 建议的技术方案、关键架构权衡、潜在技术风险、测试策略及增量 Spec |

| 选项       | 实际效果                               |
| ---------- | -------------------------------------- |
| 确认采用   | 定稿并创建正式的 Design Doc 文档       |
| 需要调整   | 继续围绕具体架构分歧展开探讨，直至达成共识 |

在方案获得确认前，系统严禁擅自落盘 Design Doc、严禁写入状态机，更不允许放行进入编码阶段。

### 6 — build 联合决策（build 阶段）

在实施计划起草完毕后，系统通过一次联合决策面板，让你一次性定夺后续所有执行参数：

| 属性         | 具体说明                                                     |
| ------------ | ------------------------------------------------------------ |
| **触发时机** | 落地执行计划（writing-plans）起草完毕并保存至文件后           |
| **决策内容** | 选择立即继续执行还是暂停切换更高级的模型，同时选定执行模式、TDD 策略与代码审查严格度 |
| **呈现信息** | 计划已生成的就绪提示、各项参数的系统推荐值与说明             |

#### 计划就绪（plan-ready）动作

| 选项            | 实际效果                                               |
| --------------- | ------------------------------------------------------ |
| A：立即继续执行 | 设定 `build_pause: null`，直接进入代码实现阶段         |
| B：暂停切换模型 | 设定 `build_pause: plan-ready` 并停止会话，稍后唤起恢复 |

Comet **原生支持“高阶模型做方案规划、性价比模型做具体编码”的协同范式**；规划完成后你可以直接暂停，更换模型或切换开发机后再继续。

#### 执行模式选择

| 选项名称                      | 模式特点                                                              |
| ----------------------------- | --------------------------------------------------------------------- |
| `subagent-driven-development` | 启动独立的后台只读子 Agent 逐项编写代码，并引入双阶段代码审查机制      |
| `executing-plans`             | 轻量模式，直接在当前主会话中按序编码                                  |
| `direct`                      | 极速直接实现（主要用于 hotfix / tweak；full 流程需显式开启覆盖配置）  |

#### TDD 测试策略

| 选项名称 | 策略特点                                            |
| -------- | --------------------------------------------------- |
| `tdd`    | 严格的测试驱动开发：必须先写失败测试，再编写实现代码 |
| `direct` | 不强制红绿重构流程，但仍要求补齐关联测试与回归证据  |

#### 代码审查严格度

| 选项名称                      | 详细机制                                   |
| ----------------------------- | ------------------------------------------ |
| `off` / `standard` / `thorough` | 详见 [代码审查机制](/zh/concepts/review-mode) |

### 7 — Spec 漂移拆分决策（build 阶段）

如果在编码实现的过程中，发现需要临时新增的任务项已经超过了初始 `tasks.md` 的 50%，系统会强制暂停，提示你做范围评估：

| 选项              | 实际效果                                  |
| ----------------- | ----------------------------------------- |
| 拆分为新 change   | 保持当前变更纯粹，通过 `/comet-open` 为超范围需求另起新任务 |
| 继续在当前 change | 确认扩大本次变更范围，同步更新 tasks.md 与增量 Spec 文档 |

### 8 — 验证例外裁决（verify 阶段）

| 属性         | 具体说明                                                            |
| ------------ | ------------------------------------------------------------------- |
| **触发时机** | 质量检查未通过，且该问题无法全自动修复、需要人工权衡时              |
| **决策内容** | 决定是否接受特定非致命偏差、裁决 Spec 漂移、或在多次修复失败后调整策略 |
| **呈现信息** | 失败用例明细、严重度评级（CRITICAL / IMPORTANT / WARNING / SUGGESTION）及修复建议 |

系统针对不同评级实施差异化处理：

| 故障严重度与场景                                | 系统的处置规则                                         |
| ----------------------------------------------- | ------------------------------------------------------ |
| CRITICAL / IMPORTANT 致命报错或可客观修复的问题 | 自动触发 `verify-fail` 打回 build 重修（在重试预算内），不打扰你 |
| WARNING / SUGGESTION 且修复会带来新的行为或范围权衡 | 主动暂停，交由你选择是重修还是接受偏差；接受时必须记录原因与影响 |
| WARNING / SUGGESTION 且修复安全、无副作用       | 系统自动修正并重新测试，不暂停                         |
| 连续自动修复 3 次仍未解决（进入第 4 次失败）    | 强制暂停，仅提供“继续尝试修复”或“停止并寻求外部决策”两个选项 |

请注意：**CRITICAL 与 IMPORTANT 级别的严重错误绝不可豁免**，任何情况下都不允许带病上线。

#### Spec 漂移的三种处置通道（仅限 full 流程检查 6）

当检测到增量 Spec 与最初的 Design Doc 存在逻辑冲突时，提供三种解决路径：
- **路径 A**：在 Design Doc 中追加“Implementation Divergence（实现偏差说明）”，记录合理的实现调整；
- **路径 B**：触发 `transition verify-fail` 打回 build 阶段，并重新唤起方案脑暴重新对齐；
- **路径 C**：直接接受该技术偏差并继续验收，原因将记录在验证报告中备查。

### 9 — 归档与交付最终确认（archive 阶段）

| 属性         | 具体说明                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------- |
| **触发时机** | 所有测试验收全部亮起绿灯、即将执行底层归档合并之前                                                |
| **决策内容** | 最终确认是否归档，以及归档提交的远端交付形式（仅本地保留 / 推送远程 / 推送并创建 PR）             |
| **呈现信息** | 变更名称、最终验证报告摘要、当前绑定的分支与目录、未提交改动明细以及预定执行的远端操作            |

| 选项名称                    | 执行效果                                                                                      |
| --------------------------- | --------------------------------------------------------------------------------------------- |
| 仅本地归档（不推送到远端）  | 完成归档并生成规范的归档 Git 提交，停留在当前分支，不执行 push、不创建 PR                      |
| 确认归档并立即推送          | 完成归档、生成唯一归档提交，并一次性推送到远端关联分支                                         |
| 确认归档、推送并自动创建 PR | 完成归档并推送到远端，随后调用接口自动创建针对主干的 Pull Request                             |
| 需要调整或重新验证          | 触发 `archive-reopen` 回退至 `phase: verify`，唤起 `/comet-verify` 重新核验                    |
| 暂不归档                    | 保持活跃状态，停留在 archive 阶段，不写任何归档终结标记                                       |

<Note>
  无论 <code>auto_transition</code> 设置为自动还是手动，进入归档阶段前<strong>均必须经过停顿点 9 的人工确认</strong>。测试通过绝不会绕过你偷偷执行自动归档。
</Note>

### 10 — 预设升级评估（仅限 hotfix / tweak）

| 属性         | 具体说明                                                                     |
| ------------ | ---------------------------------------------------------------------------- |
| **触发时机** | 轻量预设在执行中检测到超出预期的重大信号（涉及跨模块、新 API、Schema 变动等） |
| **决策内容** | 确认是继续留在轻量预设中执行，还是平滑升级到完整的五阶段流程                 |
| **呈现信息** | 触发升级的信号来源以及升级为完整流程后的阶段变化                             |

| 选项名称             | 实际效果                                                          |
| -------------------- | ----------------------------------------------------------------- |
| 继续按轻量预设推进   | 确认当前变动范围完全可控，继续走 hotfix 或 tweak 流程             |
| 升级为完整全流程     | 调用 `comet state transition <name> preset-escalate` 合法回退至 design 补充架构设计 |

## 停顿点的通用执行准则

所有停顿点均严格遵循统一的协议规范：

- **该停则停，严禁越俎代庖**：遇到有两个及以上有效选项会改变代码范围、行为、风险或不可逆结果时，必须暂停等待用户确认，严禁基于默认值擅自替用户做主。
- **能自动则自动，杜绝琐碎打扰**：如果当前状态下仅存在唯一安全的下一步（例如客观报错修复、检查重试等），系统会自动执行并汇报，不再多此一举弹窗确认。
- **异常清晰阻断**：若遇到物理依赖缺失、路径越界或环境损坏，系统会清晰汇报阻塞原因与恢复指引，绝不假装成功。
- **卡片交互优先与优雅降级**：平台支持时展示直观卡片；不支持或调用失败时，会话平滑降级为标准的文本选项，不反复尝试无效 UI。
- **未获确认前严禁偷跑**：在收到你的明确指令前，绝不预先创建正式产物、绝不推进阶段状态机。
