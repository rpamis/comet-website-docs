title: '代码审查机制'

---

`review_mode` 用于控制 Classic 工作流在编码（build）阶段何时派发任务级代码审查、允许多少轮自动修复，并决定验收（verify）阶段最终综合审查的严格度。在 build 阶段内：`off` 不派发审查员；`standard` 仅针对高风险任务触发即时审查；`thorough` 则对每一个子任务逐一审查。整个变更的**最终全局综合代码审查只在 verify 阶段执行**，在所有子任务全部编码完成后，build 阶段不会再追加多余的全局审查。

<Note>
  <code>review_mode</code> 仅管控工作流内部的<strong>自动化</strong>审查行为。你在任何时候均可手动调用 <code>/comet-review</code>，对当前变更执行一次只读的按需审查。该独立命令不会推进工作流状态，仅负责客观报告代码 Diff 中的正确性、安全漏洞、边界条件与测试覆盖问题，绝不会擅自篡改文件或替代 Verify 验收。
</Note>

## 如何选择 review_mode

选择何种审查模式，主要权衡代码改动的风险面以及你能接受的时间与 Token 预算。hotfix / tweak 预设默认关闭审查（`off`），新建的完整全流程变更默认使用 `standard`：

| 实际研发场景          | 推荐审查模式        | 时间与 Token 开销 | 选型理由                                     |
| --------------------- | ------------------- | ----------------- | -------------------------------------------- |
| hotfix / tweak、文档等低风险改动 | `off`（默认） | 最低 / 最快       | 目标单纯、改动极小，无须重型审查             |
| 日常大部分全流程变更  | `standard`（默认）  | 中等              | 低风险任务直接放行，高风险任务即时审查，开销完全可控 |
| 涉及安全、鉴权、数据迁移 | `thorough`        | 最高 / 最慢       | 每个子任务均独立审查，严密筑牢安全防线       |
| 跨子系统 / 核心架构重构 | `thorough`        | 最高 / 最慢       | 逐任务深入审查，杜绝跨模块隐蔽缺陷           |

### 三档模式全面对比

| 核心维度         | `off`                        | `standard`                                   | `thorough`                                  |
| ---------------- | ---------------------------- | -------------------------------------------- | ------------------------------------------- |
| **任务级 Reviewer** | 0 个                         | 仅在命中风险信号时派发                       | **每个任务**均独立派发                      |
| **审查触发时机** | 不触发                       | 检测到风险信号时即时介入                     | 每个子任务完成后即刻介入                    |
| **审查关注范围** | —                            | 风险任务：Spec 规格契约 + 代码工程质量       | 每个任务：Spec 规格契约 + 代码工程质量      |
| **自动修复预算** | 0 轮                         | 单任务单次审查**最多 1 轮**修复 + 复审       | 单任务单次审查**最多 2 轮**修复 + 复审      |
| **阻断暂停条件** | —                            | 自动修复 1 轮后复审仍未通过 → 标记为 BLOCKED | 自动修复 2 轮后复审仍未通过 → 标记为 BLOCKED |
| **最终全局审查** | verify 阶段跳过              | 在 verify 阶段统一执行                       | 在 verify 阶段统一执行                      |
| **执行速度**     | 最快                         | 适中（安全跳过低风险任务）                   | 最慢（逐任务严格串行审查）                  |
| **Token 消耗**   | 最低                         | 适中可控                                     | 相对较高                                    |
| **适用场景**     | hotfix / tweak、轻量小改动   | 日常绝大多数全流程变更                       | 核心底层、架构重构、安全敏感型重大变更      |
| **默认设置**     | hotfix / tweak 默认          | full 完整流程默认                            | 需要显式指定开启                            |

### 三档模式的成本与耗时差异

成本的差异主要源于派发审查员（Reviewer）的频次。`off` 模式下 N 个任务完全不启动审查 Agent，速度最快且最节省 Token。`standard` 模式仅对触碰敏感边界的任务派发 Reviewer，且单任务最多自动重修 1 轮。而 `thorough` 的开销会随任务数量线性递增：N 个任务就会依次启动 N 次后台审查，且每次都有可能触发最多 2 轮修复。对于一个包含 12 个子任务的大型变更，`standard` 可能仅介入两三次，而 `thorough` 会执行整整 12 次深度审查，其 Agent 交互轮次会成倍增加。

## 单个任务的审查执行链路

`review_mode` 决定了 build 阶段的每个子任务是否需要、以及何时引入后台 Reviewer，并在发现缺陷后允许自动修复几轮。所有模式均具备扎实的基础质量底线：实现者先自测、提交代码、上报测试证据与风险信号，主调度会话核验达标后打勾并分派下一个任务。在 `subagent-driven-development` 模式下的运转机制如下：

### standard：仅对高风险任务触发审查

在 `standard` 模式下，子任务默认**不派发 Reviewer**。主协调会话在阅读完实现者的报告并快速检视 Diff 后：
- **若未命中任何风险信号**：直接在 `tasks.md` 中打勾，立即派发下一个任务；
- **若发现改动触碰了敏感边界**：系统立刻为该任务启动 1 位独立的只读 Reviewer，从“Spec 规格契约”与“代码实现质量”两个维度严格审查。若审查未发现致命或严重问题，任务放行；若检测到 CRITICAL / IMPORTANT 缺陷，则触发自动修复，**最多允许修复 1 轮**并复审。若复审仍未解决，流程标记为 **BLOCKED**，暂停交由人工处理。

### thorough：对每个任务均执行严格审查

在 `thorough` 模式下，每个子任务完成后，系统均会自动拉起全新的独立后台 Reviewer 执行全量审查，绝不采取批量合并的方式草草了事。高风险或核心架构变动必须在每个环节步步为营，避免把隐患累积到集成阶段。若审查发现严重问题，**最多允许自动修复 2 轮**；若 2 轮修复后仍未达标，立即标记为 **BLOCKED** 并暂停请示。

### off：免除自动化审查，以客观测试为据

在 `off` 模式下，系统在 build 阶段**完全不派发**任何后台审查或自动重修 Agent。任务是否完成，完全基于实现者的自测结果、构建命令输出以及测试用例的真实执行证据。系统会在中间产物中如实记录跳过自动审查的原因备查。

<Warning>
  <code>off</code> 模式仅仅跳过了<strong>大模型扮演的代码审查员</strong>，<strong>绝不等于跳过客观测试与构建验证</strong>。如果在编码执行中遭遇测试报错、构建失败或运行时崩溃，系统依然会无条件强制阻断并启动规范排错流程，绝不允许带着物理报错浑水摸鱼。
</Warning>

## 最终全局审查（verify 阶段）

需要再次强调：**整个变更的最终全局综合代码审查只在 verify 阶段执行**。
在 build 阶段把全部子任务都写完之后，不会再画蛇添足地追加全量审查员，而是直接平滑流转到 verify。`review_mode` 仅决定 verify 阶段是否开启这次自动化审查：`off` 模式跳过并记录原因，`standard` 与 `thorough` 均会严密执行。

## 风险信号识别清单

在任务执行中，一旦命中以下**任意一项**，系统便会将其标记为风险任务，进而在 `standard` 模式下自动触发 Reviewer 介入：

- 跨子系统 / 跨底层模块的联动修改；
- 安全敏感领域：身份认证、权限校验、加解密算法、SQL 查询构建、外部不可信输入处理、密钥及凭据处理；
- 并发控制、线程锁、跨进程共享状态；
- 数据表结构定义变更或数据库迁移脚本；
- 公共 API 接口或对外命令行参数契约变动；
- 实现者在任务总结中明确返回了带风险警告的结论（`DONE_WITH_CONCERNS`）；
- 单个子任务的代码变更量超过 200 行。

## 审查模型的分配策略（强制规范）

为避免成本失控，每次派发实现者、修复者或审查员时，**均应明确指定适用的模型档位**。若未指定模型，系统可能会默认沿用会话中最昂贵的顶配模型，不仅响应迟缓还会急剧消耗额度：

| 承担角色                | 推荐模型选择策略                                                                                                               |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **代码实现 / 错误修复** | 仅修改 1–2 个文件且 Spec 详尽 → 使用轻量模型；多文件协同/复杂逻辑/常规调试 → 使用标准模型；深层重构或全局架构推敲 → 使用顶配模型 |
| **子任务审查员**        | 根据该任务 Diff 的规模与复杂度按需指定。常规语法修改使用标准模型即可；复杂的并发与安全性改动建议指定强模型                    |
| **最终全局综合审查**    | verify 阶段的全局把关，建议使用可调用的最强模型，确保全貌审查万无一失                                                           |

## 配置方法与生效优先级

`review_mode` 遵从以下严格优先级：

```text
当前变更的 .comet.yaml  >  COMET_REVIEW_MODE 环境变量  >  .comet/config.yaml 中的 classic.review_mode  >  standard
```

### 全局配置默认值

直接在 `.comet/config.yaml` 中指定：

```yaml
classic:
  review_mode: thorough
```

项目内新建的变更会自动沿用该默认值。

### 针对当前变更单独指定

在完整全流程进入 build 阶段的联合决策时，你可以直接在交互面板中选定，或由命令写入状态机：

```bash
node "$COMET_STATE" set <change-name> review_mode standard
```

## 离开 build 阶段的硬性门禁

`review_mode` 是完整流程离开 build 阶段的**硬性准入门禁**：
1. 阶段守卫检查必须通过 `review_mode selected`；
2. 状态流转命令 `comet-state transition build-complete` 会核验该字段。

两道防线全部放行后，任务方可正式迈入 verify 阶段，确保质量策略严谨落地。
