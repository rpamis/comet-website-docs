这次复测回答一个具体问题：加强 Native 的 Sequential 澄清协议和 Build 前确认锁后，16 个既有业务任务的广度基线是否回归？

我们对当前 Native 运行相同的 16 个任务，每个任务重复 3 次，共 48 次；再与历史 0.4.0 Classic 的 48 次运行按 `task + repetition` 严格对齐。

<Note>
  Native 与 Classic 是两套面向不同模型能力的 workflow，不存在 Native 升级到 Classic
  的关系。对齐的是业务任务和 repetition；workflow 产物仍分别按各自契约验证。
</Note>

## 对齐口径

| 观察项        | 当前 Native                                    | 历史 0.4.0 Classic                                         |
| ------------- | ---------------------------------------------- | ---------------------------------------------------------- |
| 业务任务      | 相同的 16 个任务                               | 相同的 16 个任务                                           |
| 重复次数      | 每任务 3 次，共 48 次                          | 每任务 3 次，共 48 次                                      |
| Treatment     | `COMET_NATIVE_PHASE1`                          | `COMET_FULL_040_BETA`                                      |
| 实验标识      | `experiment_20260723_195551`                   | `combined_comet_workflow_full_k3_20260705_v3_rerun_failed` |
| 严格配对      | 48/48                                          | 48/48                                                      |
| Workflow 验证 | Native brief、spec、状态、轨迹、验证和归档证据 | Classic Skill、OpenSpec、阶段和依赖 Skill 契约             |

历史 Classic 记录早于完整 execution-identity manifest。对齐脚本只能用当前 canonical task tree 重建其 task-core hash，因此它证明比较时的任务结构一致，不能证明历史 checkout 的完整执行身份与当前完全相同。

## 核心结果

| 指标              | 当前 Native | 0.4.0 Classic |         差异 |
| ----------------- | ----------: | ------------: | -----------: |
| 严格运行通过      |       47/48 |         43/48 | Native +4 次 |
| task-macro pass@1 |        0.98 |          0.90 | Native +0.08 |
| task-macro pass@3 |        1.00 |          1.00 |         持平 |
| task-macro pass^3 |        0.94 |          0.75 | Native +0.19 |

两种 workflow 的 `pass@3` 都是 1.00，表示 16 个任务都至少在三次中成功一次。Native 的 `pass^3` 为 0.94：15 个任务三次全过；Classic 为 0.75：12 个任务三次全过。

本次 Native 唯一失败是 `comet-cross-file-refactor#r3`，业务实现完成，但 Native 终态的 brief、specification 或 verification 证据不完整。其他 15 个任务均为 3/3。

## 双方都通过时的执行效率

主效率视图只统计双方在同一 task repetition 上都严格通过的 42 组：

| 指标                     | 当前 Native | 0.4.0 Classic | Native 差异 |
| ------------------------ | ----------: | ------------: | ----------: |
| 模型启动/恢复次数        |        1.17 |          2.98 |      -60.8% |
| Agent 轮次               |       57.93 |         92.52 |      -37.4% |
| 工具调用                 |       55.76 |         82.95 |      -32.8% |
| 非缓存输入 Token         |      39,498 |        82,315 |      -52.0% |
| 输出 Token               |      10,662 |        14,012 |      -23.9% |
| 总 Token（包含缓存读取） |   2,077,084 |     3,928,545 |      -47.1% |
| 模型成本                 |      $1.480 |        $2.738 |      -45.9% |
| 累计模型耗时             |      429 秒 |        353 秒 |      +21.4% |

这次 Native 的 Agent 轮次、工具调用、Token 和成本仍明显更低，但 wall duration 反而高 21.4%。因此新数据不再支持旧报告“Native 耗时下降约 47%”的结论。

<Warning>
  Classic 来自历史运行，Native
  来自当前运行；机器负载、服务时段和历史遥测完整度不同。Token、轮次和工具调用具有较强结构解释力，wall
  duration 只能作为方向性观察，不能写成受控因果结论。
</Warning>

## 与 2026-07-16 Native 报告相比

旧 Native 基线为 46/48、`pass^3 = 14/16`。本次为 47/48、`pass^3 = 15/16`。失败任务也从两个终态证据缺口收敛为一个。

这支持“澄清与 Runtime 加强没有造成广度回归”：canonical 业务任务广度保持稳定，达到 47/48。
