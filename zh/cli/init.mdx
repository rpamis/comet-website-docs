---
title: 'comet init'
description: '初始化项目或全局的 Comet 环境：选择 Native 或 Classic 工作流，安装对应的 Skill 和运行资产。'
---

`comet init` 用来在项目里安装 Comet，或在全局安装一份供所有项目使用的环境。它会检测当前项目、选择工作流、部署对应的 Skill 和运行资产，并写好 `/comet` 入口的配置。

## 基本用法

```bash
cd your-project
comet init
```

常用选项参数：

| 选项 | 说明 |
| --- | --- |
| `--yes` | 不询问，自动补齐缺失的资产并跳过已有文件 |
| `--scope <scope>` | 安装范围：`project`（当前项目）或 `global`（全局用户目录） |
| `--language <lang>` | Skill 语言：`zh`（中文）或 `en`（英文） |
| `--workflow <mode>` | 启用的工作流：`native`、`classic` 或 `both`（两套同时启用） |
| `--platform <id>` | 只初始化指定的平台，或项目自定义的平台 |
| `--codegraph <op>` | 非交互模式下处理 CodeGraph 索引：`init`（创建）或 `skip`（跳过） |
| `--root <path>` | Native 产物根目录的相对路径，例如 `docs` |
| `--skip-existing` | 跳过已存在的资产文件 |
| `--overwrite` | 覆盖清单（Manifest）里列出的已有文件 |
| `--json` | 输出 JSON，供脚本解析 |

## Native 与 Classic 工作流的初始化

交互式初始化在 `project` 和 `global` 两种范围下都可以选择 Native、Classic 或两者同时启用。非交互模式下，系统按下面的顺序确定默认工作流：

1. **配置优先**：先读已有的 `.comet/config.yaml`，这是唯一依据；
2. **显式参数**：传了 `--workflow native|classic|both` 就按参数执行（`both` 模式下 `/comet` 默认进入 Native）；
3. **历史痕迹**：没有有效配置，但工程里有 Classic 的 `.comet.yaml` 或旧版 Ambient Resume 记录时，保持 Classic；
4. **默认 Native**：其余新环境默认用 Native。工程里存在业务源码、普通的 `openspec/` 或 `docs/superpowers/` 目录，都不会改变这个默认值。

Native 初始化会部署 Comet 自带的 Skill 和 Runtime、统一的工作流 Rule，并在平台支持时注册一个 Hook Router。生成的结构如下：

```text
.comet/config.yaml
<artifact-root>/comet/
```

Native 模式不安装 OpenSpec、Superpowers 或 CodeGraph，也不会生成 Classic 的变更文档或 `docs/superpowers/`。Rule 和 Router 按 `.comet/current-change.json` 把写入交给对应工作流的守卫，不会同时做两套校验。Classic 初始化则保留原有的多阶段流程。

只有当**所有勾选平台的必需资产都部署成功**，并且已有的 `/comet` 入口与最新路由规则兼容时，Comet 才会激活并写入 `.comet/config.yaml`。如果检测到你自己写的非标准 `/comet` 文件，系统会保留原文件，并把本次初始化标记为 `incomplete`；确认要整个覆盖时，加上 `--overwrite` 重新运行：

```bash
comet init --workflow native --root docs
comet init --workflow classic
comet init --workflow both
comet init --scope global --workflow native
comet init --scope global --workflow classic
comet init --scope global --workflow both
```

`global` 模式下，`--workflow` 决定全局安装包含哪些工作流。新项目首次调用 `/comet` 时，系统会把全局设置写进该项目的 `.comet/config.yaml`；之后修改全局配置不会影响已经激活的项目。`--root` 只用于项目级的 Native 初始化。

## 只初始化一个平台

工程适配了多个 Agent 平台，但这次只想装某一个或修复某一个时，用 `--platform`：

```bash
comet init --platform claude --workflow native
comet init --platform my-team-platform --workflow classic
```

参数可以是 Comet 内置的平台标识，也可以是项目自定义的平台。指定后只处理这个平台；不指定时继续沿用自动平台探测与既有回退规则。

非交互初始化时，可以用 `--codegraph init` 显式创建或刷新代码索引，或用 `--codegraph skip` 跳过。常规检查不会改动已有索引；需要诊断和修复时，先运行 `comet doctor` 看当前状态。

## 项目登记

自 0.4.0-beta.4 起，每个成功完成的项目级安装都会登记到本机的全局索引中。索引只记录项目路径和平台类型，供后续批量升级和卸载使用，不备份业务代码，也不上传任何数据。

登记后，交互式的 `comet update` 和 `comet uninstall` 会让你选择只处理当前项目，还是处理所有已登记的项目。加 `--json` 或 `--current-project` 可以限定在当前目录；批量操作必须显式加 `--all-projects`。写 CI 脚本时务必指明范围，不要依赖终端环境去推断。

## 部署方式：复制还是软链接

选择 Classic 或 both 工作流时，选定平台后系统会让你选**部署方式**（全局安装也一样）：

- **Copy（独立复制）**：为每个 Agent 平台各复制一份完整的 Skill 代码包，兼容性最广。
- **Symlink（符号链接）**：在各平台目录下建软链接，指向 `.comet/skills/`，所有平台共用同一份文件，省磁盘空间，升级一次即刻生效。

如果目标平台原本就有 `skills/` 目录，Comet 会保留该目录，只在其中创建自己管理的链接。你原有的自定义 Skill 或第三方插件不会因为选 Symlink 而被删除或覆盖。

两种方式的详细对比见 [支持的平台 · 安装模式](/zh/platforms#安装模式-复制-vs-符号链接)。

## 项目配置的合并方式

Native 与 Classic 共用 `.comet/config.yaml`。初始化会按当前启用的工作流合并配置：

- **保留**你已有的自定义参数（如 `native.artifact_root`、`classic.review_mode`）；
- **补齐**新版本新增配置项的默认值；
- **刷新**配置项上方的注释，使其与当前版本一致；
- **保留**你自己加的键值对；
- `default_workflow`、`workflows`、`ambient_resume` 以及两套工作流各自的参数互不影响；
- 配置损坏、无法安全解析时，Comet 直接停止，不改原文件。

合并成功后，终端会打印 `项目配置已合并 (.comet/config.yaml)`。

## OpenSpec CLI 的依赖范围

OpenSpec CLI 是 Classic 工作流使用的命令行工具。在 Classic 模式下，即使你选的是项目级安装，Comet 也会把它装成全局 CLI，不会为此在项目根目录生成多余的 `node_modules/`。Native 模式不检查也不安装它。

在 Comet 0.5.5 中，如果 OpenSpec 2 为所选平台生成共享的 `.agents/skills`，Comet 会把 Skills 装到该平台自己的目录。共享输出必须包含有效的 Skills，并在 `.openspec-target` 中写明所选平台。

## 安装后检查

```bash
comet doctor
```

如果检查提示缺少平台目录、Skill 脚本或权限，先按提示修复，再到对话里输入 `/comet`。

## 安装报告

`comet init`（以及 `comet update`）会按平台输出安装结果：

```text
Comet -> claude: installed (12 files) -> .claude/skills/
Comet -> claude: skipped (alreadyExists)
Comet -> opencode: failed (12 files, 1 failed) -> .opencode/skills/comet
```

| 状态 | 含义 |
| --- | --- |
| `installed` | 该模块声明的文件全部写入或链接成功 |
| `skipped` | 文件已存在且没加 `--overwrite`，系统跳过 |
| `failed` | 写入或权限出错，安装没有完成 |

<Warning>
  <strong>只要有文件写入失败，该平台的结果就会标记为 <code>failed</code></strong>，并显示失败的文件数。Classic 缺少 <code>comet-hook-guard.mjs</code> 会导致阶段守卫失效；Native 缺少核心 Runtime 则无法写入项目配置。遇到报错时重新执行 <code>comet init</code> 或 <code>comet update</code> 补齐缺失文件。
</Warning>
