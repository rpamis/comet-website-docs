---
title: 'comet init'
description: '初始化本地项目或全局 Comet 环境，科学选配 Native 或 Classic 工作流，一键安装配套 Skill 与运行资产。'
---

`comet init` 是 Comet 的标准化安装与工程接入入口。它能够智能探查当前项目环境，一键部署所需的 Skill 与运行态资产，并自动写入 `/comet` 统一入口的工作流配置。

## 基本用法

```bash
cd your-project
comet init
```

常用选项参数：

| 参数选项 | 说明 |
| --- | --- |
| `--yes` | 非交互式免确认模式，自动补全缺失资产并跳过已有文件 |
| `--scope <scope>` | 安装生效范围：支持 `project`（当前项目）或 `global`（全局用户目录） |
| `--language <lang>` | 目标 Skill 语言：支持 `zh`（中文）或 `en`（英文） |
| `--workflow <mode>` | 激活的工作流模式：支持 `native`、`classic` 或 `both`（双流并存） |
| `--platform <id>` | 仅初始化特定受支持平台或项目自定义平台 |
| `--codegraph <op>` | 非交互模式下处理 CodeGraph 索引：`init`（创建）或 `skip`（跳过） |
| `--root <path>` | Native 工作流产物根目录相对路径，例如 `docs` |
| `--skip-existing` | 安全跳过已存在的资产文件 |
| `--overwrite` | 强制覆写由清单（Manifest）纳管的既有文件 |
| `--json` | 输出标准机器可读 JSON 数据 |

## Native 与 Classic 工作流初始化

交互式初始化无论在 `project` 还是 `global` 作用域下，均支持选择 Native、Classic 或同时激活双流。在非交互模式下，系统严格依循以下优先级确定默认工作流：

1. **配置优先**：率先读取当前合规的 `.comet/config.yaml`，此为系统的唯一权威可信来源；
2. **显式参数**：若传入了 `--workflow native|classic|both`，严格按入参执行（在 `both` 模式下 `/comet` 默认进入 Native）；
3. **历史证据**：若无有效工作流配置，但在工程中检测到 Classic 模式的 `.comet.yaml` 或旧版 Ambient Resume 痕迹，自动维持 Classic；
4. **开箱默认**：其余全新环境默认选用 Native；业务源码、普通的 `openspec/` 目录或 `docs/superpowers/` 的存在绝不会强行扭转该默认值。

Native 初始化会部署 Comet 原生 Skill/Runtime 资产、统一工作流规范 Rule，并在 Agent 平台支持时注册单一的 Hook Router 路由钩子，生成如下文件结构：

```text
.comet/config.yaml
<artifact-root>/comet/
```

Native 模式绝不滥装 OpenSpec、Superpowers 或 CodeGraph，亦不会生成 Classic 的变更文档或 `docs/superpowers/`。统一的规则（Rule）与路由中枢（Router）将严格依照 `.comet/current-change.json` 把写入操作分发给对应的工作流守卫，绝不可能同时执行双重校验。而 Classic 初始化则会完整保留原有的多阶段工程治理体系。

Comet 具备强确定性保证：唯有当**所有勾选平台的必需资产均部署成功**、且既有的 `/comet` 入口与最新路由契约完全兼容时，才会正式激活并写入 `.comet/config.yaml`。若检测到用户先前自定义的非标准 `/comet` 文件，系统会完整保留原文件并明确标记本次初始化为 `incomplete`（未完成）；若确认需要全量覆写，请显式追加 `--overwrite` 重跑：

```bash
comet init --workflow native --root docs
comet init --workflow classic
comet init --workflow both
comet init --scope global --workflow native
comet init --scope global --workflow classic
comet init --scope global --workflow both
```

在 `global` 全局模式下，`--workflow` 用于指定全局安装的能力集合。未初始化的新项目在首次明确调用 `/comet` 时，系统会自动将全局偏好固化至该项目的 `.comet/config.yaml` 中，后续全局配置的变动绝不会破坏已激活工程的一致性。`--root` 依然严格限定仅用于项目级的 Native 初始化。

## 定向初始化单一平台

当工程同时适配了多个 Agent 平台，但本次仅需要针对其中某一个平台进行安装或修复时，可使用 `--platform`：

```bash
comet init --platform claude --workflow native
comet init --platform my-team-platform --workflow classic
```

参数既可以是 Comet 官方内置的平台标识符，亦可为项目自定义平台。指定后系统将仅针对该目标进行操作；若未指定，则继续走全局平台的自动探测与回退机制。

在非交互式初始化中，可通过 `--codegraph init` 显式创建或刷新代码知识图谱索引，或通过 `--codegraph skip` 显式跳过。常规的健康检查绝不会暗中篡改已有索引；若需诊断修复，推荐先执行 `comet doctor` 评估现状。

## 项目级全局登记索引

自 0.4.0-beta.4 起，所有执行成功的项目级安装均会自动登记至用户本机的全局索引账本中。该索引严格仅记录后续批量升级与卸载所需的工程物理路径与平台类型，绝不备份任何业务代码，亦绝不上传任何隐私遥测数据。

完成登记后，交互式的 `comet update` 与 `comet uninstall` 支持自由选择“仅操作当前项目”还是“批量处理所有已登记项目”。追加 `--json` 或 `--current-project` 即可安全限定在当前目录；批量全局操作必须显式追加 `--all-projects`。在编写 CI 自动化脚本时，务必显式传入作用域，切勿依赖终端环境的被动推断。

## 部署模式抉择：独立复制 vs 软链接共享

在选择 Classic 或 both 工作流时，系统在选定平台后会引导你选择**部署模式**（在 `global` 全局安装下同样适用）：

- **Copy（独立复制）**：为每个 Agent 平台独立拷贝一份完整的 Skill 代码包（兼容性最广的传统模式）。
- **Symlink（符号链接）**：在各平台目录下建立指向 `.comet/skills/` 的软链接，全平台共享同一份物理文件，极度节省磁盘空间且单点升级全量即刻生效。

若目标平台此前已存在原生的 `skills/` 目录，Comet 会安全尊重既有目录，仅在其内部建立受 Comet 纳管的链接。开发者原有的自定义 Skill 或第三方插件绝不会因选择 Symlink 而被误删或覆写。

两种模式的深入权衡请参阅 [支持的平台 · 安装模式](/zh/platforms#安装模式-复制-vs-符号链接)。

## 共享项目配置的平滑智能合并

Native 与 Classic 统一共享 `.comet/config.yaml`。初始化机制会依据当前激活的工作流对配置进行智能合并：

- **完好保留**你已有的自定义参数（如 `native.artifact_root`、`classic.review_mode`）；
- **按需补齐**最新版本中新增的受控配置项默认值；
- **同步刷新**配置项上方的注释文档，与最新版本规范对齐；
- **完好保留**你在配置文件中扩展编写的自定义键值对；
- 共享的 `default_workflow`、`workflows`、`ambient_resume` 与两套流的专属参数保持语义隔离；
- 若检测到损坏无法安全解析的非法配置，系统会执行失败关闭（Fail Closed），绝不凭空瞎猜默认值进行覆盖。

合并成功后，终端会打印 `项目配置已合并 (.comet/config.yaml)` 明确提示。

## OpenSpec CLI 的依赖范围

OpenSpec CLI 是 Classic 工作流跨工程调度的标准命令行。在 Classic 模式下，即便你选择的是项目级局部安装，系统亦会将 OpenSpec CLI 作为全局 CLI 进行安装或升级；绝不会为了该依赖在业务项目根目录创建冗余的 `node_modules/`。Native 模式则完全不检查亦不安装该依赖。

在 Comet 0.5.5 中，如果 OpenSpec 2 为所选平台生成共享 `.agents/skills`，Comet 会将 Skills 安装到该平台自己的目录。共享输出须包含有效的 Skills，并在 `.openspec-target` 中标明所选平台。

## 安装完成后的健康自检

```bash
comet doctor
```

若自检提示缺少平台目录、Skill 脚本或权限缺失，请先依循提示排查修复，再在对话框中唤起 `/comet`。

## 安装报告解读

`comet init`（及 `comet update`）在终端中会分平台回显详细的组件安装结果：

```text
Comet -> claude: installed (12 files) -> .claude/skills/
Comet -> claude: skipped (alreadyExists)
Comet -> opencode: failed (12 files, 1 failed) -> .opencode/skills/comet
```

| 状态标记 | 实际工程语义 |
| --- | --- |
| `installed` | 该模块声明的全部文件均成功拷贝或链接完成 |
| `skipped` | 文件已存在且未指定 `--overwrite`，系统安全跳过 |
| `failed` | 存在文件写入或权限异常，安装未能完整落地 |

<Warning>
  系统对安装结果采取零容忍度：<strong>只要存在局部文件写入失败，绝不会虚假粉饰为成功</strong>。若某个平台出现异常，会明确标记为 <code>failed</code> 并展示失败文件数。Classic 若缺少 <code>comet-hook-guard.mjs</code> 将导致阶段守卫失效；Native 若缺少核心 Runtime 同样无法写入项目配置。遇到报错请重新执行 <code>comet init</code> 或 <code>comet update</code> 补齐缺失资产。
</Warning>
