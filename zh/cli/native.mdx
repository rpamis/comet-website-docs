---
title: 'Native CLI'
description: '初始化 Native、管理 change、保存阶段内进度、推进状态、验证证据以及安全恢复和归档。'
---

`comet native` 是 Native 工作流的确定性 Runtime 入口。它的状态与工作流产物只归属共享项目配置 `.comet/config.yaml` 和配置指定的 `<artifact-root>/comet/`，不会读取或转换 Classic/OpenSpec change。为生成基线与实现范围，Runtime 会有界读取项目所有范围内的文件内容；项目存在 Git 元数据时，仅在构建 Git 感知快照时调用 Git。它不会调用外部 Skill、shell 或项目命令；内置 `comet native check` 仍不调用 Git 或任何外部进程。

## 初始化与根目录

```bash
comet native init [--root <artifact-root>] [--language en|zh-CN]
comet native root show
comet native root move <artifact-root>
```

示例：

```bash
# 默认：<project>/docs/comet/
comet native init --language zh-CN

# 可选：<project>/comet/
comet native init --root . --language zh-CN

# 事务化迁移到 <project>/artifacts/comet/
comet native root move artifacts
```

`artifact-root` 必须是项目内相对路径，默认为 `docs`。`.` 表示 `<project>/comet/`，`docs` 表示 `<project>/docs/comet/`。

`init --language` 会把以后新建 Native change 的默认语言写入 `.comet/config.yaml`。`new --language` 可以覆盖单个 change；再次运行 `init --language` 只改变以后新建 change 的默认值，不改写已有 change。

已有配置会拒绝冲突的 `init --root`。改变目录必须使用产物根目录迁移命令，不能直接编辑配置。迁移具有 `copying`、`ready`、`switched` 状态；存在 `pending_root_move` 时，普通写命令会失败关闭，避免两棵目录同时可写。

## change 管理

```bash
comet native new <change-name> --creation-authorization <path> [--language en|zh-CN]
comet native spec remove <change-name> <capability>
comet native spec rebase <change-name> --summary <text>
comet native list [--cursor <token>]
comet native show <change-name>
comet native status [--cursor <token>]
comet native status <change-name> [--details [--acceptance-cursor <token>]]
comet native select <change-name>
```

`change-name` 和 capability 使用字母开头的 lowercase kebab-case。`new` 在配置缺失时创建默认配置和 `<project>/docs/comet/`。`--creation-authorization` 必须引用由项目外 controller 签发、与当前 change 绑定的授权文件；实现者不能用项目内密钥为自己授权。

新增或替换长期行为时，把完整目标规格写入：

```text
changes/<change-name>/specs/<capability>/spec.md
```

Runtime 根据正式规格是否存在推导 `create` 或 `replace`，并冻结 `base_hash`。删除能力使用 `spec remove`，不要手工维护 `comet-state.yaml` 的 `spec_changes`。若并行 change 已改变同一正式规格，先重读并改写完整目标规格，再使用 `spec rebase` 刷新基线、重开 Build 并清除旧验证结论。

### 基线与 Git 感知快照

`new` 在提交 change 状态前捕获完整基线。Git 项目只纳入已跟踪和未被忽略的未跟踪文件；被忽略的缓存与未登记的嵌套仓库内容不属于项目所有范围，子模块和 gitlink 作为一个原子条目。非 Git 项目使用有界物理树提供器。任何项目所有项被省略都会返回结构化 `baseline-incomplete`，并清理未完成的 change，而不是把问题拖到 Build。

Git 选择需要一次稳定且有界的枚举：

- `git-selection-changed` 表示枚举期间 Git 索引变化。等待 `git add` 等 Git 写入结束后重新运行命令；不能用部分范围授权越过。
- `git-enumeration-limit` 表示已跟踪与未被忽略的未跟踪项目所有范围超过 Git 枚举安全预算。这是结构化不完整；应优先缩小或清理项目所有范围，或使用后续调整该产品预算的 Comet 版本，不能直接或默认越过。若确实无法恢复，只有 Runtime 返回带计数和内容哈希的可授权范围、且用户理解未知尾部风险时，才可按普通部分范围协议提交精确哈希、理由与 `--confirmed`。不能手改快照或证据，也不能猜测未枚举路径。

非 Git 项目的物理树选择使用有界、顺序无关的前后枚举围栏：

- `physical-selection-changed` 表示项目树在捕获期间发生变化。等待并发文件操作结束后重试。
- `physical-enumeration-limit` 表示节点、路径、字节或协作式执行预算耗尽。缩小项目树或把非项目内容移出项目所有范围后重试。

这两种物理树完整性失败都无法为未知尾部建立稳定范围，因此在当前快照中也不能通过部分范围授权。

普通遗漏会带原因、计数和有界样本路径。基线创建与迁移切换必须完整，两种 Git 选择遗漏都不能在这里授权。之后的当前快照只有在 Runtime 明确返回可授权部分范围时才可按精确哈希进入确认：`git-selection-changed` 仍必须先消除，`git-enumeration-limit` 仅能使用上一段所述的最终兜底。

### 有界状态视图

`list` 与不带 change 的 `status` 返回同一种只读分页投影：

- 每页最多 24 个活跃 change；
- 最多接受 4096 个可见 change；
- `nextCursor` 非空时原样传入下一次 `--cursor`；
- 游标绑定完整 change 名称集合，增删 change 后旧游标会明确失效。

`status <change-name>` 返回阶段、证据有效性、诊断项摘要、检查点、修复状态和结构化后续动作。使用 `--details` 可以取得最多 50 条详细诊断项、恢复信息以及首个验收项页面。若 `findingsTruncated` 为 `true`，不能把未展示项当作不存在。

当 `acceptancePage.nextCursor` 非空时，用 `--acceptance-cursor` 逐页读取；每页最多 16 条，游标同时绑定 change 与当前验收项哈希。`show` 对规格数量、单文件、累计读取和最终输出都有硬预算；超限时拒绝，不会通过截断需求正文伪装成功。

## 阶段内检查点

```bash
comet native checkpoint <change-name> \
  --summary <text> \
  --next-action <text> \
  [--artifact <project-relative-path>]... \
  [--expect-revision <n>]
```

检查点保存同阶段摘要、下一动作和内容寻址的产物清单，不改变阶段。`--expect-revision` 使用 CAS 防止旧会话覆盖更新后的状态。恢复会话应从 `status` 返回的检查点继续，而不是依赖聊天记忆。

## 内置只读检查

```bash
comet native check <change-name>
```

`check` 只允许在 Verify 且已有实现范围时运行。它执行 Comet 内置的有界只读文本策略，并把结果写入独立、内容寻址的凭据。

它不会：

- 调用 Git、shell、项目脚本、测试命令或外部 Skill；
- 接受任意命令、环境变量、路径或超时参数；
- 修改项目源码、change 阶段、运行状态或执行轨迹。

检查发现问题或范围已失效时返回退出码 `1`，但凭据仍会保存。模型仍应按任务风险自行运行真实项目测试；内置检查是可复核的补充证据，不是通用测试执行器。

## 阶段推进

```bash
comet native next <change-name> --summary <text> \
  [--confirmed] \
  [--artifact <project-relative-path>]... \
  [--no-code-reason <text>] \
  [--allow-partial-scope <sha256> --partial-reason <text> --confirmed] \
  [--result pass|fail] \
  [--report <change-relative-path>] \
  [--receipt <runtime/evidence/check-receipts/...json>] \
  [--failure-category <token>]... \
  [--failed-check <token>]... \
  [--override-repair <sha256> --override-summary <text>]
```

| 当前阶段 | Runtime 要求                                             | 推进结果                             |
| -------- | -------------------------------------------------------- | ------------------------------------ |
| Shape    | 完整需求简述、合法目标规格、无 `[blocking]` 问题         | 进入 Build                           |
| Build    | 需求简述与规格仍有效；真实产物或无代码原因；完整实现范围 | 进入 Verify                          |
| Verify   | 结构完整且绑定当前验收项、需求契约和范围的报告           | 通过则进入 Archive；失败则返回 Build |
| Archive  | 使用独立两步归档命令                                     | 更新正式规格并归档                   |

Shape 只有在用户刚确认当前共享理解后才传 `--confirmed`；Sequential 与 Batch 的正常 Skill 流程都会先保存这次最终确认，任何确认都不能绕过其他 `[blocking]` 问题。Sequential 缺少显式确认时 Runtime 会拒绝进入 Build；Batch 的既有 Runtime 兼容路径保持不变。进入 Build 时，Runtime 把批准状态绑定到当时的 `approved_contract_hash`。之后若需求简述或完整目标规格变化，Build 会保持阻塞并返回 `re-confirm-contract`；只有用户重新确认当前需求契约后才能再次传 `--confirmed`，不能复用旧确认或手改哈希。

Build 无法证明完整范围时，第一次调用只返回范围哈希和未归属项，不推进。当前快照不完整时，Runtime 不会把未观察到的路径推断成删除；变化明细超过预算时，保留有界明细，并用带计数和内容哈希的 `scope-detail-overflow` 表示其余变化。用户明确接受一组 Runtime 允许授权的具体风险后，使用完全匹配的 `--allow-partial-scope`、非空理由和 `--confirmed` 重试。授权与范围哈希绑定；实现变化后不能沿用旧授权。`git-selection-changed`、`physical-selection-changed` 与 `physical-enumeration-limit` 绝不可授权；`git-enumeration-limit` 只有在优先恢复无效、Runtime 返回可授权范围且用户理解未知尾部风险后，才能使用同一普通部分范围协议。

Verify 报告必须包含 Runtime 可解析的验收机器块，并逐项绑定当前验收项 ID。旧报告、旧凭据、变化后的需求简述或规格、变化后的实现范围或不同修订版本的证据都会被判定失效。

进入 Verify 后，若需求契约或项目快照变化，状态命令会返回只含摘要的受控 `next`。先运行该命令退回 Build 并生成新范围；只有需求简述或规格的需求契约哈希也变化时才让用户重新确认。若只是项目快照或实现变化，保留原 `approved_contract_hash`，不要制造无意义确认。不要在失效范围上提交通过或失败结论；Archive 中任一绑定事实变化时使用同一回退协议，不能沿用旧的通过结论。

## 自主修复与停止语义

Verify 失败会自动返回 Build，并把已校验的未通过或缺失验收项 ID 与失败检查 ID 投影到详细状态。模型先修复这些缺口，再重新运行完整验证；中间轮次不会进入 Archive。

- Runtime 使用需求契约、未通过或缺失验收项 ID 和失败检查 ID 形成重复失败签名；
- 缺口减少、检查转绿或缺失证据恢复为当前有效证据才算语义进展；只修改代码或实现范围不会重置计数；
- 相同语义缺口第二次出现时告警，第三次出现且没有进展时后续动作变为人工停止；
- 有明确新假设时，只允许使用 `status` 返回的签名和非空摘要 override 一次；
- 同一需求契约的 Verify 失败默认上限为 5，可通过 `native.max_verify_failures` 配置正整数；达到上限后停止。

只有用户确认后的需求契约变化会开始新的目标周期。达到停止条件时，应让用户决定是否调整目标、约束或终止，不应反复调用 `next`、弱化检查或提前归档。

## 两步 Archive

```bash
comet native archive <change-name> --dry-run
comet native archive <change-name> --expect-preflight <sha256>
```

Archive 不能用 `next` 代替，也不能单步提交：

1. 先运行 `--dry-run`，检查证据、正式规格哈希、目标路径和冲突，取得 `preflightHash`。
2. 把该哈希原样传入 `--expect-preflight`。
3. Runtime 在锁内重算全部事实；只有完全一致时才提交。

Archive 对源树、正式规格文件和事务日志使用有界、身份绑定的读取。目录移动先进入事务绑定的隔离区，再完成不可逆提交。若在最终标记前中断，可以按事务日志继续或回滚；标记写入后只能仅一次地继续，避免已经公开为归档的结果被反向撤销。

## 诊断与恢复

```bash
comet native doctor [<change-name>]
comet native doctor [<change-name>] --repair
comet native doctor [<change-name>] --repair [--strategy continue|rollback]
```

只读诊断命令不改文件。`--repair` 只处理 Runtime 能证明安全的事项：

- 陈旧的当前选择和锁；
- schema / workspace identity 迁移；
- 阶段转换、Archive 和产物根目录迁移事务恢复；
- 未引用且超过保留窗口的派生证据与凭据；
- 中断的 retention quarantine。

诊断命令不会自动重写用户的需求简述、规格、验证报告或项目源码。普通阶段转换只支持 `continue`；`rollback` 只适用于事务日志仍允许回滚的 Archive 或产物根目录迁移。

新 change 和当前数据结构的 v3 change 都必须保留创建时的完整基线。v3 基线缺失或不完整时，诊断命令不会用当前文件重新生成，因为那会抹掉 change 创建以来的差异；应从可信备份恢复，或保留用户产物和实现事实后新建 change。

显式 v1/v2 数据结构迁移是唯一的切换例外。`doctor --repair` 会在任何状态写入前捕获完整的迁移时点基线；捕获不完整时保持旧状态并停止。迁移后的实现证据只证明切换之后的变化，不能把迁移前聊天、旧范围或旧通过结论当作当前证据。v2 位于 Verify/Archive 时会受控退回 Build 重新建立证据。

普通写命令不会自动接管陈旧锁。只有显式 `doctor --repair` 能在证明本机 owner 已不存在、锁身份未变化且没有冲突事务时接管；活动锁和无法证明陈旧的锁始终保留。

证据保留机制只清理活跃 change 中至少 30 天、每种证据类型最新 32 份之外、且依赖闭包证明未引用的派生证据。当前状态引用、归档证据、依赖项、较新文件和每类最新 32 份始终保留。

## 后续动作与退出码

`status` 和写命令会返回结构化后续动作，常见处置方式包括：

- `continue-same-skill`：当前 Skill 可以按下一动作继续；
- `await-user`：需要真实用户决定或部分范围授权；
- `repair-runtime`：先执行 doctor/recovery；
- `stop`：已完成、手动停止或达到强制停止条件。

`next: auto` 表示调用方可以继续同一个 Native Skill，不表示后台守护进程会自行调用模型。

所有命令支持 `--json`。JSON 模式只输出一个对象，包含 `command`、`exitCode`、`data`，失败时增加结构化 `error`。

| 退出码 | 含义                                    |
| ------ | --------------------------------------- |
| `0`    | 成功                                    |
| `1`    | 内置 `check` 完成，但发现问题或结果失效 |
| `64`   | 参数或用法错误                          |
| `65`   | 配置、状态或产物无效                    |
| `70`   | 未预期的内部失败                        |
| `73`   | 锁、事务、并发哈希或根目录冲突          |
| `75`   | 修复停滞或强制停止条件阻塞继续          |

## 只提供 Skill 文件的环境

若宿主没有安装 `comet` CLI，可直接使用 `/comet-native` 随包发布的 Runtime：

```bash
node <comet-native-skill-root>/scripts/comet-native-runtime.mjs <command> [options]
```

它与 `comet native` 使用相同参数、输出和退出码。Runtime 与 Skill 一起发布，不依赖 OpenSpec、Superpowers、grill-me 或其他外部 Skill。
