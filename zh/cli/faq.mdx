本页汇总 CLI 的常见问题，按安装与初始化、状态查看与排查、升级与卸载、Skill 与评测、CI/CD 五类分开。

## 安装与初始化

<AccordionGroup>
  <Accordion title="comet init 会覆盖项目里现有的配置文件吗">
    不会。发现组件已存在时，`comet init` 会问你覆盖还是跳过。平台 Hook 采用非破坏性合并，你本地写的其他 Hook 脚本会保留。非交互的 `--yes` 模式下，已存在的文件默认跳过；要强制刷新就加 `--overwrite`。
  </Accordion>

  <Accordion title="安装摘要里某个平台显示 failed (12 files, 1 failed) 是什么意思">
    表示这个平台写文件时出错了，例如权限不足或目标路径被占用。只要有文件写入失败，该平台的结果就标记为 `failed`，并显示失败的文件数。如果缺的是 `comet-hook-guard.mjs` 这类核心文件，阶段守卫会失效，必须修复。重新执行 `comet init` 或 `comet update` 补齐文件，详见 [comet init · 安装报告解读](/zh/cli/init#安装报告)。
  </Accordion>

  <Accordion title="写文件时 Hook 报 [COMET-HOOK] crash 并以退出码 2 终止怎么办">
    `comet-hook-guard.mjs` 自己崩溃时（例如运行时脚本残缺、模块 import 失败或语法错误），会按**失败关闭（fail closed）**处理：打印 `[COMET-HOOK] crash: ...`，以退出码 2 终止并阻止写入。这说明阶段守卫不正常，最常见的原因是安装不完整、缺少关键脚本。

    处理分三步：先运行 `comet doctor` 找出缺了什么，再运行 `comet init` 或 `comet update` 补齐，最后重新执行原来的操作。
  </Accordion>

  <Accordion title="Windows 上可以直接运行吗，需要 Git Bash 吗">
    可以直接运行。自 0.4.0-beta.1 起，内部脚本和运行时守卫都由 Node.js 执行，Windows 不再需要 Bash、Git Bash 或 WSL。macOS、Linux 和 Windows 的命令用法完全一致。
  </Accordion>

  <Accordion title="项目级安装和全局安装怎么选">
    `project` 装在当前项目里，配置文件随 Git 仓库提交，保证团队用同一套规则；`global` 装在用户主目录，对你本机所有项目生效。不确定时选项目级。详见 [comet init](/zh/cli/init)。
  </Accordion>

  <Accordion title="comet init 支持哪些 Agent 平台">
    目前支持 39 个 AI 编程平台，包括 Claude Code、Codex、Cursor、Windsurf、GitHub Copilot、Oh My Pi 和 DeepSeek Harness 等。`comet init` 会扫描项目根目录，自动勾选已存在的平台。各平台对 Skill、Rule 和 Hook 的支持程度不同，详见 [受支持的平台](/zh/platforms)。
  </Accordion>
</AccordionGroup>

## 状态查看与排查

<AccordionGroup>
  <Accordion title="没有输入 /comet，只在对话里说“继续”会怎么样">
    在新会话里只发“继续”，或说的话只和已有 change 沾一点边时，Agent 会先问你这次是不是要继续那个任务；即使只有一个进行中的任务，或本地有 selection 索引，也会先确认。如果你说“继续 cache-controls”这样点明了变更，且状态允许，Agent 会直接恢复。当前会话本来就在流程中时，不会重复确认。详见 [comet resume-probe](/zh/cli/resume-probe)。
  </Accordion>

  <Accordion title="comet status 和 comet doctor 有什么区别">
    `comet status` 回答“当前变更推进到哪一步，下一步该做什么”。
    `comet doctor` 回答“环境哪里出了问题，哪个依赖或文件损坏了”。

    日常看 `status`；出现报错或恢复不了时，再用 `doctor` 做完整检查。
  </Accordion>

  <Accordion title="doctor 报告里的 warn 需要马上处理吗">
    `warn` 一般不影响使用，例如某个可选的三方依赖没配置；`fail` 是必须先解决的问题，例如核心 Skill 缺失或状态文件损坏。

    排查时先清掉所有 `fail`，再按实际影响处理 `warn`。详见 [comet doctor](/zh/cli/doctor)。
  </Accordion>

  <Accordion title="CodeGraph 索引正常，为什么 Agent 还是提示不可用">
    CodeGraph 的 CLI 是否可用、项目索引是否最新、平台的 MCP 是否注册、Agent 是否真正生效（effective），这四项彼此独立。CLI 可用且索引最新，只说明本地数据就绪；目标 Agent 还需要有正确指向 CodeGraph 服务的 MCP 连接，才会生效。

    运行 `comet doctor --json`，检查 `codegraph.cliStatus`、`indexStatus`、`mcpStatus`、`agents` 和 `effectiveForAgent`，按结果逐项补齐。索引正常不代表 MCP 连接没问题。
  </Accordion>

  <Accordion title="comet status 显示的阶段不对怎么办">
    先运行 `comet doctor`，检查是不是 `.comet.yaml` 有语法错误，或缺少某个阶段需要的证据文件。按诊断结果修复后重新运行 `comet status`。详细步骤见 [状态异常排查与恢复](/zh/guides/state-recovery)。
  </Accordion>

  <Accordion title="后台为什么常驻一个 Comet 的 Node.js 进程">
    自 0.4.2 起，Classic 与 Native 的只读状态查询会复用同一个项目级的守护进程（Daemon），避免每次查询都重新启动 Node、等它冷启动。该进程只在当前工程范围内工作，空闲一段时间后自动退出；环境不支持守护进程时，Comet 改为单次直接执行，不影响结果。

    你可以用下面的命令管理它：

    ```bash
    comet daemon status
    comet daemon start
    comet daemon stop
    ```
  </Accordion>
</AccordionGroup>

## 升级与卸载

<AccordionGroup>
  <Accordion title="怎么升级到 RC1 规范">
    交互式升级会把全局或本地的 npm 包更新到最新版本，并刷新所有已登记项目里的 Skill、Rule、Hook、Runtime 和配置。升级后建议运行 `comet doctor` 检查一遍：

    ```bash
    comet update
    comet doctor
    ```

    使用 `--current-project`、`--scope global` 或 `--json` 时，同样会默认先更新对应的 Comet npm 包，再刷新资产文件（`--self-update` 默认已开启）；如果只想刷新本地资产、不更新 npm 包，请加上 `--skip-self-update`：

    ```bash
    comet update --current-project
    comet update --current-project --skip-self-update
    comet doctor
    ```

    RC1 的 Native Portable State、Supervisor 架构、个人记忆、项目知识库和平台适配都依赖随包发布的最新 Runtime。只升级 npm 包、不执行 `comet update`，项目会继续用旧资产。
  </Accordion>

  <Accordion title="卸载会删掉我的业务代码或 OpenSpec 文档吗">
    不会。`comet uninstall` 只移除 Comet 清单里的 Skill 文件、规则和 Hook，保留你的业务代码、OpenSpec change 文档、设计文档和实施计划。详见 [comet uninstall](/zh/cli/uninstall)。
  </Accordion>

  <Accordion title="update 和 init 该用哪个">
    `comet init` 用于首次安装，或给已有项目加上新的 Agent 平台。
    `comet update` 用于 CLI 升级后刷新已有的资产和规则。

    两者都是非破坏性合并，覆盖文件前会先问你。
  </Accordion>
</AccordionGroup>

## Skill、评测与发布

<AccordionGroup>
  <Accordion title="comet skill 和 /comet-any 怎么选">
    要从零创作可复用的 Skill，在对话里用 `/comet-any`，它会自动调用编译器和沙盒。`comet skill` 是底层工具，适合单步调试、查看 Engine Run 和管理本地包。详见 [comet skill](/zh/cli/skill)。
  </Accordion>

  <Accordion title="comet eval 和 comet skill check 有什么区别">
    `comet eval` 评估 Skill 端到端解决问题的能力，用自动化测试集产出可供发布审计的证据；`comet skill check` 只检查某一次运行有没有缺少产物或状态字段，不产出发布用的证据。发布就绪状态必须以 `comet eval` 的结果为准。详见 [comet eval](/zh/cli/eval)。
  </Accordion>

  <Accordion title="comet bundle 和 comet publish 怎么选">
    日常发布用 `comet publish`。`comet bundle` 是底层的编译命令，只在排查深层编译问题、做数据审计或写 CI/CD 脚本时直接调用。详见 [comet publish](/zh/cli/publish)。
  </Accordion>
</AccordionGroup>

## 持续集成（CI/CD）

<AccordionGroup>
  <Accordion title="CI/CD 里怎么做完全不交互的初始化">
    加 `--yes --json`，跳过所有交互提示：

    ```bash
    comet init --yes --scope project --language zh --json
    ```
  </Accordion>

  <Accordion title="--json 输出的结构会保持稳定吗">
    会。`status` 和 `doctor` 的 JSON 结构属于 CLI 的稳定接口。在流水线里做质量检查时，建议只在 `doctor` 出现 `fail` 级问题时让构建失败。详见 [CI/CD 集成](/zh/guides/cicd-integration)。
  </Accordion>
</AccordionGroup>
