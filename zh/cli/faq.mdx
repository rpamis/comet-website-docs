本文精选汇总了关于初始化安装、状态机诊断、版本平滑升级与卸载、以及 Skill 评测发布的四大高频问题。

## 安装与初始化

<AccordionGroup>
  <Accordion title="comet init 会覆写我工程中现有的配置文件吗">
    绝不会强行覆写。在探测到已存在的物理组件时，`comet init` 会主动提示你确认是覆写还是跳过。针对平台 Hook 采取非破坏性智能合并策略，完好保留你在本地编写的其他自定义 Hook 脚本。在非交互 `--yes` 模式下，已存在的文件默认自动跳过；若需强制刷新请显式追加 `--overwrite`。
  </Accordion>

  <Accordion title="安装摘要中某个平台回显 failed (12 files, 1 failed) 代表什么">
    表明该 Agent 平台在物理写入文件时遭遇了异常（例如权限不足或目标路径被占用）。系统对安装采取严格的零容忍策略：只要存在局部文件写入失败，绝不虚假粉饰为成功，而是明确标记为 `failed` 并展示失败文件数。若缺失类似 `comet-hook-guard.mjs` 等核心组件，会导致阶段守卫在暗中失效，必须先予修复。建议重新执行 `comet init` 或 `comet update` 补齐缺失文件，详见 [comet init · 安装摘要解读](/zh/cli/init#安装摘要怎么看)。
  </Accordion>

  <Accordion title="写入文件时 Hook 抛出 [COMET-HOOK] crash 并以退出码 2 终止怎么办">
    `comet-hook-guard.mjs` 在自身崩溃（如核心运行时脚本残缺、模块 import 失败或语法异常）时会坚决贯彻**失败关闭（Fail Closed）**原则：打印 `[COMET-HOOK] crash: ...` 诊断信息，并抛出非零退出码 2 强行阻断写入。这表明阶段守卫处于非健康状态，最典型的根因在于安装不完整（遗漏了关键脚本）。

    标准处置建议遵循三步闭环：首先运行 `comet doctor` 揪出具体缺项，随后执行 `comet init` 或 `comet update` 补齐资产，最后重新执行原业务操作。
  </Accordion>

  <Accordion title="Windows 环境下支持顺畅运行吗，还需要依赖 Git Bash 吗">
    原生完美支持。自 0.4.0-beta.1 起，所有内部脚本与运行时守卫均原生通过 Node.js 执行，Windows 平台彻底摆脱对 Bash、Git Bash 或 WSL 的外部依赖。macOS、Linux 与 Windows 享受完全一致的跨平台命令心智。
  </Accordion>

  <Accordion title="项目级局部安装与全局用户安装应该如何抉择">
    `project` 项目级模式专为团队工程优化（配置文件与规则规范随 Git 仓库提交纳管，确保全团队统一行为）；`global` 全局模式则契合个人本地开发环境（写入用户主目录，跨工程一键共享）。若拿不准主意，推荐优先采用项目级模式。详见 [comet init 详尽参考](/zh/cli/init)。
  </Accordion>

  <Accordion title="comet init 官方支持哪些 Agent 平台">
    目前已深度适配 39 款主流 AI 编程平台，包括 Claude Code、Codex、Cursor、Windsurf、GitHub Copilot、Oh My Pi 以及 DeepSeek Harness 等。`comet init` 会自动扫描当前项目根目录已存在的平台目录并完成智能预选。各平台在 Skill、Rule 与 Hook 的支持度上略有差异，详情请参考 [受支持的平台矩阵](/zh/platforms)。
  </Accordion>
</AccordionGroup>

## 状态透视与排障诊断

<AccordionGroup>
  <Accordion title="没有键入 /comet，仅在对话中发送“继续”会触发什么">
    在全新的对话会话中，若仅发送“继续”、或意图仅与历史已有的 change 存在语义弱相关时，Agent 会率先主动向你确认本次是否确定要接续该流程；即使在途任务唯一或本地存在 selection 索引，亦绝不跳过确认。唯有当你明确发出“继续 cache-controls”等指名道姓的指令且状态允许时，方可直接恢复现场。若当前会话此前已在流程中，则无需重复确认。详情请参考 [恢复探测命令](/zh/cli/resume-probe)。
  </Accordion>

  <Accordion title="comet status 与 comet doctor 的核心定位有何区别">
    `comet status` 专职解答“当前变更推进到了哪个阶段，下一步建议执行什么命令”。
    `comet doctor` 专职解答“底层环境因何抛锚，哪项依赖或文件被损坏了”。

    日常开发建议优先查阅 `status`，唯有在观察到异常报错或断点接续受阻时，再执行 `doctor` 展开全方位深度体检。
  </Accordion>

  <Accordion title="doctor 报告中打印的 warn 警告项需要立即处理吗">
    `warn` 绝大多数属于非阻塞的优化提示（例如某个可选的三方依赖尚未配置），而 `fail` 则是致命的硬伤阻塞项（例如核心 Skill 缺失、状态机文件损坏）。

    在自愈排障时，优先全力消除所有的 `fail` 项，随后再结合业务实际影响按需处理 `warn`。详情请参考 [comet doctor 环境诊断](/zh/cli/doctor)。
  </Accordion>

  <Accordion title="CodeGraph 图谱索引显示正常，为什么 Agent 依然提示不可用">
    CodeGraph 底层 CLI、项目图谱索引、平台 MCP 协议注册与 Agent 实际生效（effective）属于四个正交的解耦状态。CLI 已就绪且索引新鲜，仅能证明本地工程的数据资产已准备就绪；目标 Agent 还必须合规配置指向 CodeGraph 服务的有效 MCP 连接，方能正式激活生效。

    建议运行 `comet doctor --json`，细致核验 `codegraph.cliStatus`、`indexStatus`、`mcpStatus`、`agents` 以及 `effectiveForAgent`。依据诊断报告逐项补齐缺失环节，切忌单纯因为索引显示正常就忽略了 MCP 连接层的排查。
  </Accordion>

  <Accordion title="comet status 回显的所处阶段不符合预期该如何处理">
    优先执行 `comet doctor`，排查是否存在语法残缺的 `.comet.yaml` 状态机文件或丢失了关键的阶段客观证据链。依照诊断建议修复现场后，重新执行 `status` 复核。深层排障指引详见 [状态异常排查与恢复](/zh/guides/state-recovery)。
  </Accordion>

  <Accordion title="操作系统后台为什么会常驻 Comet 的 Node.js 进程">
    自 0.4.2 版本起，面向只读的 Classic 与 Native 状态查询，系统会自动复用一个按需唤起的项目级轻量守护进程（Daemon），彻底避免每次命令行查询都需重复经历缓慢的 Node 虚拟机冷启动。该进程严格限定在当前工程作用域内，在空闲一段时间后会自动平稳退出；若环境不支持守护进程，Comet 会自动降级为原生单次直接执行，绝不影响结果的准确性。

    支持通过以下命令随时管理该守护进程：

    ```bash
    comet daemon status
    comet daemon start
    comet daemon stop
    ```
  </Accordion>
</AccordionGroup>

## 版本升级与卸载

<AccordionGroup>
  <Accordion title="如何平滑无损升级至 RC1 规范">
    交互式升级会自动将相关的全局/本地 npm 包更新至最新版本，并同步刷新所有已在册工程内的 Skill、Rule、Hook、Runtime 与托管配置。升级完成后推荐运行 Doctor 核验整体健康态：

    ```bash
    comet update
    comet doctor
    ```

    若使用了 `--current-project`、`--scope global` 或追加了 `--json`，系统默认仅刷新物理资产，不自动拉取 npm 更新。若在上述受限模式下需要同步升级底层 CLI，请显式追加 `--self-update`：

    ```bash
    comet update --current-project --self-update
    comet doctor
    ```

    RC1 规范中的 Native Portable State、Supervisor 复合架构、个人记忆、项目知识库及 Agent 平台适配均深度绑定随包发布的最新 Runtime 资产，仅更新 npm 包而不执行 `comet update` 会导致项目工程继续沿用陈旧的历史资产。
  </Accordion>

  <Accordion title="执行卸载会误删我的业务代码或 OpenSpec 产物吗">
    绝对不会。`comet uninstall` 严格且仅移除受 Comet 清单管辖的 Skill 文件、规则规约与 Hook 钩子，完好捍卫你的业务源码、OpenSpec change 文档、架构设计方案及实施拆解计划。详情请参考 [comet uninstall 卸载指南](/zh/cli/uninstall)。
  </Accordion>

  <Accordion title="update 与 init 命令到底该用哪一个">
    `comet init` 专职用于“首次接入安装”或“为已有项目增补全新的 Agent 平台”。
    `comet update` 专职用于“CLI 版本升级后无损刷新既有资产与规则”。

    两条命令均贯彻非破坏性合并策略，物理文件是否覆写完全由人类开发者显式拍板。
  </Accordion>
</AccordionGroup>

## Skill 编排、自动化评测与发版

<AccordionGroup>
  <Accordion title="comet skill 与 /comet-any 应该如何选用">
    若需从零创作并沉淀可复用的标准化 Skill，强烈推荐优先在对话框中使用交互式的 `/comet-any`，它会在底层自动串联各编译器与沙盒。`comet skill` 属于底层技术工具，更适合本地开发单步调试、高级 Engine Run 实例透视及底层包管理。详见 [comet skill 详尽参考](/zh/cli/skill)。
  </Accordion>

  <Accordion title="comet eval 与 comet skill check 的本质区别是什么">
    `comet eval` 属于端到端的能力综合评测框架，通过自动化测试集产出面向发版审计的权威证据链；而 `comet skill check` 严格仅校验某单次具体运行是否缺少特定的 artifact 或状态机字段，不产出端到端的发版凭据。发版就绪度（Readiness）必须完全依托 `comet eval`。详情请参阅 [comet eval 评测指南](/zh/cli/eval)。
  </Accordion>

  <Accordion title="comet bundle 与 comet publish 应该如何选用">
    日常开发者与团队发版责任人推荐首选 `comet publish`（人类友好的交互式发布主通道）。`comet bundle` 纯属底层引擎的裸机控制台，仅在深层编译排障、数据审计或编写高阶 CI/CD 自动化编排时直接调用。详情请参阅 [comet publish 交互发布指南](/zh/cli/publish)。
  </Accordion>
</AccordionGroup>

## 持续集成（CI/CD）实践

<AccordionGroup>
  <Accordion title="如何在 CI/CD 流水线中实现完全非交互式初始化">
    追加 `--yes --json` 组合参数即可彻底跳过全部终端交互提示：

    ```bash
    comet init --yes --scope project --language zh --json
    ```
  </Accordion>

  <Accordion title="CLI 的 --json 报文结构能够保持长期稳定解析吗">
    具备绝对的确定性保障。`status` 与 `doctor` 的 JSON Schema 是 CLI 稳定发布契约的核心组成部分。在配置流水线质量门禁时，强烈建议仅在 `doctor` 的诊断结论中存在 `fail` 级别硬伤时使构建步骤退出非零。详情请参考 [CI/CD 持续集成实践](/zh/guides/cicd-integration)。
  </Accordion>
</AccordionGroup>
