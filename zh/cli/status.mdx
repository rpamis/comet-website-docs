---
title: "comet status"
description: "查看 Native、Classic 及普通 OpenSpec change 的当前进度，以及下一步建议。"
---

`comet status` 用来查看项目当前的工作流入口、所有进行中的 change，以及每个 change 的下一步建议命令。无论是刚接手项目想了解进度，还是中断后不确定下一步做什么，都可以随时运行它。

`comet status` 只读取状态：它不切换当前 change，不修改文件，也不会触发构建或测试。

## 文本输出

```bash
comet status
```

若当前项目没有任何进行中的变更，终端会输出：

```text
Default Entry: native -> /comet-native [project-config]

Native Changes:

  No active changes.

Classic Changes:

  No active changes.

Unmanaged OpenSpec Changes:

  No active changes.
```

输出内容解读：

- `Default Entry`：`/comet` 默认进入哪套工作流。示例中是 Native，入口为 `/comet-native`，依据是当前项目配置。
- `Native Changes`：当前进行中的 Native change。
- `Classic Changes`：由 Comet 状态机管理、按五阶段推进的 Classic change。
- `Unmanaged OpenSpec Changes`：不受 Comet 状态机管理的原始 OpenSpec change，需要用 OpenSpec 自己的命令维护。
- `No active changes.`：该分类下当前没有任务。它不代表 Comet 安装失败，也不代表项目配置有问题。

## 有进行中的变更时的输出

Classic change 的输出会把当前阶段、任务进度和下一步合并显示：

```text
Classic Changes:

  1. next-build [Comet] [phase: build [1/2 tasks]]
     workflow: classic | build_mode: executing-plans
     isolation: branch
     run_step: full.build.plan
     next: /comet-build
```

这段输出表示：`next-build` 处于 Classic 的 `build` 阶段，2 个任务已完成 1 个；当前在独立 Git 分支上开发，下一步由 Agent 调用 `/comet-build`。

如果进入下一阶段需要的证据文件缺失，终端会列出缺了哪些文件，以及怎么补：

```text
runtime_check: fail (full.open; missing: openspec.proposal, openspec.tasks)
next: run /comet-open or restore missing evidence (openspec.proposal, openspec.tasks), then rerun comet doctor
```

看到这个提示时，不要跳过检查直接进入 Build。按提示补上缺失的 `openspec.proposal` 和 `openspec.tasks`：可以让 Agent 回到 `/comet-open` 重新生成，也可以从 Git 历史中找回原文件，然后重跑 `comet doctor` 检查。

Native change 单独列在 `Native Changes` 下：

```text
Native Changes:

  1. native-text [Native] [phase: shape]
```

`phase` 是当前实际所处的阶段。想看这个 Native change 的完整状态细节，你可以在终端运行：

```bash
comet native status <change-name> --details --json
```

## JSON 输出

需要写自动化脚本，或让 Dashboard 解析状态时，加上 `--json`：

```bash
comet status --json
```

JSON 输出的顶层按工作流分开：

```json
{
  "schema": "comet.status.v2",
  "defaultEntry": {
    "workflow": "native",
    "skill": "comet-native",
    "source": "project-config"
  },
  "workflows": {
    "native": { "changes": [] },
    "classic": { "changes": [] }
  },
  "unmanagedOpenSpec": [],
  "changes": []
}
```

`changes` 是 Classic 和原始 OpenSpec change 合并后的列表，方便上层工具统一遍历；Native change 单独放在 `workflows.native.changes` 里。

Native 的状态详情命令返回的 JSON 包含 `loop` 迭代进度、验收项通过情况、Runtime 检查日志和 `continuation` 指令：

```json
{
  "schema": "comet.native.v4",
  "name": "avatar-upload",
  "status": "verify",
  "phase": "verify",
  "loop": { "stage": "verify", "iteration": 1, "attempt": 2 },
  "acceptance": { "passed": 3, "failed": 0, "blocked": 0, "pending": 0 },
  "continuation": { "action": "dispatch-verifier" }
}
```

推进 Native 任务时，以响应里的 `continuation.commandArgs` 与 `inputOptions.template` 为准。不要照着示例自己拼内部调试参数。

## 多个 Change 并行时

同一个项目可以有多个进行中的 Native change。`.comet/current-change.json` 记录当前工作区选中的是哪一个：同一目录下的会话共用这个选择，独立的 worktree 各自记录自己的。

Agent 用下面的命令在当前工作区切换选中的 change，你也可以在终端自己运行：

```bash
comet native select <change-name>
```

在 0.5.5 中，如果想在 Shape 等待确认期间处理无关的修改，可以先让 Agent 执行 `comet native select --none`。原 change 和批准记录都会保留，恢复探测也会遵循当前工作区的取消选择。工作流材料仍受写入保护；继续原任务时重新选中它即可。

遇到分支或 worktree 不匹配、任务归属不清、代码还没同步或目录重名时，Runtime 会返回 `await-user` 或 `blocked` 让你先处理，不会切换到其他无关任务。

## 可以归档时的提示

当某个变更已经满足归档条件，`status` 会在输出末尾打印归档建议：

```text
recommended archive: comet archive comet-ready
recommended archive: comet classic openspec -- archive open-ready -y
```

- 第一条用于由 Comet 管理的 Classic change；
- 第二条用于不受状态机管理的原始 OpenSpec change；
- 如果输出里没有 `recommended archive`，说明还有验收项没通过或阶段没走完，不要强行归档。

Native change 的归档由 Agent 调用 `comet native archive <change-name> --confirmed` 完成，不需要你自己运行。

如果输出里有状态异常提示，按 `next` 的提示或 Native JSON 中的 `continuation` 处理，之后可以运行 `comet doctor` 做一次完整检查。
