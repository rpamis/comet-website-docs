---
title: "comet status"
description: "全局查看 Native、Classic 及普通 OpenSpec change 的实时推进水位，获取精准的下一步操作建议与状态诊断。"
---

无论是新接手项目需要摸清当前进度，还是在开发中途中断后不确定下一步该做什么，都可以随时运行 `comet status`。它会直观呈现默认工作流入口、当前所有在途的 change 列表，以及每个变更的下一步建议指令。

`comet status` 为纯只读命令，绝无副作用：它不切换当前绑定的 change，不修改任何文件，亦不会擅自触发编译构建或测试验收。

## 文本输出总览

```bash
comet status
```

若当前项目没有任何活跃在途的变更，终端将清晰呈现：

```text
Default Entry: native -> /comet-native [project-config]

Native Changes:

  No active changes.

Classic Changes:

  No active changes.

Unmanaged OpenSpec Changes:

  No active changes.
```

输出内容解读：

- `Default Entry`：标明 `/comet` 统一入口默认分发至哪套工作流。示例中显示为 Native，入口为 `/comet-native`，判定依据为当前项目配置文件。
- `Native Changes`：陈列当前正在推进中的 Native change。
- `Classic Changes`：陈列由 Comet 状态机统一监管、遵循经典五阶段的 Classic change。
- `Unmanaged OpenSpec Changes`：陈列未纳管进 Comet 状态机的原生 OpenSpec change（需直接使用原生 OpenSpec 命令行维护）。
- `No active changes.`：明确指代该目录下当前无在途任务，既不代表 Comet 未正确安装，亦不代表项目配置存在异常。

## 存在活跃变更时的输出解读

针对 Classic change，输出会将当前阶段、任务完成进度与下一步建议紧凑聚合展示：

```text
Classic Changes:

  1. next-build [Comet] [phase: build [1/2 tasks]]
     workflow: classic | build_mode: executing-plans
     isolation: branch
     run_step: full.build.plan
     next: /comet-build
```

上述输出直观表明：`next-build` 正处于 Classic 的 `build` 编码阶段，共 2 个任务已完成 1 个；当前启用了独立 Git 分支隔离，当前阶段的下一步操作指引为唤起 `/comet-build`。

若 Runtime 检查发现缺失进入下一阶段所需的客观证据链，终端会明确指出具体缺项及对应的自愈手段：

```text
runtime_check: fail (full.open; missing: openspec.proposal, openspec.tasks)
next: run /comet-open or restore missing evidence (openspec.proposal, openspec.tasks), then rerun comet doctor
```

遇到此种提示时，不要强行越级跳到 Build 阶段。请遵循提示执行 `/comet-open` 补齐证据，或从 Git 历史中检出恢复缺失文件，随后重跑 `comet doctor` 核验。

Native change 则独立汇总在 `Native Changes` 分类下：

```text
Native Changes:

  1. native-text [Native] [phase: shape]
```

其中的 `phase` 如实呈现当前所处的实时阶段。若需要查阅该 Native change 的全量底层状态机细节，可执行：

```bash
comet native status <change-name> --details --json
```

## 结构化 JSON 输出规范

当需要编写自动化运维脚本或由 Dashboard 可视化面板解析状态时，追加 `--json` 参数即可：

```bash
comet status --json
```

顶层 JSON 数据包按工作流严格分层归属，遵循版本化的标准规范契约：

```json
{
  "schema": "comet.status.v2",
  "defaultEntry": {
    "workflow": "native",
    "skill": "comet-native",
    "source": "project-config"
  },
  "workflows": {
    "native": { "changes": [] },
    "classic": { "changes": [] }
  },
  "unmanagedOpenSpec": [],
  "changes": []
}
```

其中 `changes` 聚合了 Classic 与原生 OpenSpec 的合并列表，便于上层工具链统一遍历；Native change 则完整保留在 `workflows.native.changes` 专用对象中。

Native 详情命令返回的 JSON 包含 `loop` 迭代进度、验收用例达标率、Runtime 客观检查日志以及 `continuation` 指令：

```json
{
  "schema": "comet.native.v4",
  "name": "avatar-upload",
  "status": "verify",
  "phase": "verify",
  "loop": { "stage": "verify", "iteration": 1, "attempt": 2 },
  "acceptance": { "passed": 3, "failed": 0, "blocked": 0, "pending": 0 },
  "continuation": { "action": "dispatch-verifier" }
}
```

在继续推进 Native 任务时，必须严格以响应报文中的 `continuation.commandArgs` 与 `inputOptions.template` 为基准，切勿在终端手动拼凑非公开的内部调试参数。

## 多 Change 并行时的状态定位

同一个项目可以保留多个活跃的 Native change。`.comet/current-change.json` 记录当前工作区的选择。同一目录中的会话共享选择，独立 worktree 分别记录。

在当前工作区选择 Native change：

```bash
comet native select <change-name>
```

在 0.5.5 中，如果需要在待确认的 Shape 旁处理无关修改，可先执行 `comet native select --none`。原 change 和批准记录会保留，恢复探测也会尊重当前工作区的取消选择。正式工作流材料仍受写入保护；继续原任务时重新执行 `comet native select <change-name>`。

当检测到分支或 worktree 不匹配、任务归属模糊、代码尚未同步或目录命名冲突时，Runtime 会主动返回 `await-user` 或 `blocked` 提示排查，不会切换到其他无关任务中。

## 达成归档条件时的命令指引

当某个变更已全量满足归档准入规则时，`status` 命令会在末尾打印对应的归档建议指令：

```text
recommended archive: comet archive comet-ready
recommended archive: comet classic openspec -- archive open-ready -y
```

- 第一条专用于由 Comet 纳管的 Classic change；
- 第二条专用于未受状态机管辖的普通原生 OpenSpec change；
- 若终端未回显 `recommended archive`，表明当前任务尚有未达标的验收项或未走完的阶段，不要擅自强推归档。

针对 Native change，对应的标准归档命令为：

```bash
comet native archive <change-name> --confirmed
```

若在输出中观察到任何状态异常提示，优先遵循 `next` 文本指引或 Native JSON 中的 `continuation` 进行纠偏，随后可随时运行 `comet doctor` 展开全项目健康诊断。
