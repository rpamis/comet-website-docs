---

`comet resume-probe` 用于在未输入 `/comet` 的情况下识别自然语言恢复意图：当会话被压缩、新建对话窗口或更换开发机后，新启动的 Agent 没有历史对话记录。恢复探测会以只读方式比对你的输入与进行中的 change，判断是否需要恢复到对应的 Native 或 Classic 工作流，避免 Agent 将“继续刚才的用户系统重构”误判为全新任务。

<Note>
  本页命令由 Agent 在后台调用，你不需要手动运行。日常开发只需在对话中输入 <code>/comet</code> 提需求、回答 Agent 的提问，或说“继续”。本页供你在终端排查问题、编写脚本或接入其他 Agent 平台时查阅。
</Note>

探测先读项目根目录的 `.comet/config.yaml`，确认当前用的是 Native 还是 Classic，然后只查看这套工作流下进行中的 change、当前阶段和你的意图。配置文件损坏时，Comet 会停止探测并提示排查。

探测只输出判断结果和路由建议，不改任何 change 数据，也不推进阶段。新会话里如果只是语义上沾边，即使目标唯一或本地有 selection 索引，系统也会先问你要不要继续这个任务。你确认后，Agent 会加载返回的 `skill`；如果你已经点明了 change 名称且状态允许，就按 `nextCommand` 直接进入对应入口。

## 为什么需要恢复探测

长时间运行的项目很少一直待在同一个会话里。下面这些情况都会让 Agent 忘记当前工程正在用 Comet：

- 对话被平台压缩，或换了 IDE 窗口、新建了会话；
- 换了开发机，克隆同一个仓库继续做；
- 新启动的 Agent 只看到磁盘上的代码，和一句“继续之前的工作”；
- 习惯用自然语言下指令，没有再说 `/comet`。

`comet init` 会在项目里写入恢复说明，引导 Agent 在处理这类指令前先做一次只读探测。探测综合项目配置、进行中的变更、当前阶段、本地索引和你的话，给出最可能的候选和依据。如果只是弱相关，系统只会告诉你存在候选，仍需你确认；如果你点明了变更且状态允许，可以直接恢复。

## 自动探测怎么运行

日常你不用手动运行 `comet resume-probe`。照常说：

> 继续刚才的用户系统重构。

`comet init` 和 `comet update` 会把恢复说明写进项目的 Agent 规则文件。只要全局开关 `ambient_resume` 打开，Agent 在收到像长期任务的指令前，会在后台自动做一次只读探测：

1. 读项目配置，确认该检查 Native 还是 Classic；
2. 比较你的意图、进行中的 change、当前阶段和本地选择索引；
3. 只是弱相关，或本地只有索引记录时，把匹配到的名称和阶段告诉你，问这次是否继续；
4. 你确认后直接进入对应工作流，不再重新扫描全项目。如果只是普通问答，或你明确说不继续，就按一般对话处理，已有的 change、审批记录和阶段保护都不受影响。

已经在 Comet 流程里的会话会自动沿用之前的确认，推进任务、回答流程内问题、会话恢复时都不会反复追问。在新会话里只说“继续”，或只提到一个宽泛的测试要求时，系统仍会先向你确认；只有说“继续 cache-controls”“提交当前 change”这样具体的内容，才会直接定位到目标。

输入 `/comet` 时按项目配置直接进入对应工作流，不依赖探测。通过 Agent 平台调用的**非 Comet 原生**斜杠命令同样不触发探测，因为这条命令已经明确了任务。把 `ambient_resume` 设为 `false` 后，普通自然语言不再触发探测，`/comet` 入口照常可用。

## 供 Agent 和脚本调用

脚本或上层 Agent 可以直接传入要判断的文本：

```bash
comet resume-probe . --utterance "继续刚才的用户系统重构" --json
```

也可以从标准输入读取：

```bash
echo "继续刚才的用户系统重构" | comet resume-probe . --stdin --json
```

| 参数 | 作用 |
| --- | --- |
| `--utterance <text>` | 直接传入要判断的用户输入 |
| `--stdin` | 从标准输入读取用户输入 |
| `--json` | 输出结构化的 JSON，供 Agent、Hook 或流水线解析 |
| `--no-workflow-work` | 把这次请求当作只读查询，不触发工作流推进 |
| `--already-in-comet-flow` | 声明当前已在 Comet 流程中，返回 `out_of_scope`，避免重复路由 |

## 返回值怎么处理

| `action` | 含义 | 下一步 |
| --- | --- | --- |
| `auto_resume` | 用户明确要求恢复指定的 change，且当前状态允许 | Agent 按 `nextCommand` 进入对应入口：Native 用 `/comet-native`，Classic 用 `/comet-classic` |
| `ask_user` | 需要用户确认，或存在多个候选、状态异常、等待人工决策 | 向用户展示候选和依据并等待答复；用户确认后直接加载 `skill`，不再重新扫描 |
| `out_of_scope` | 用户明确不继续、当前已在流程中，或只是咨询 | 按普通会话回答，不启动 Comet 工作流 |
| `none` | 项目里没有进行中的 Comet change | 不做恢复；如果用户要提新需求，引导其输入 `/comet` |

输出遵循 `comet.resume_probe.v2`，包含 `workflow`、`skill`、`entrySource`、`reasonCode`、`candidates`、`changeName`、`phase`、`nextCommand` 和判断依据。Native 无论处于哪个阶段，都通过 `/comet-native` 恢复；`comet native next` 是内部推进指令，不能当作恢复入口。Classic 模式下顶层 CLI 同样返回 v2 格式。

## 哪些情况会返回 ask_user

- 新会话里只找到弱相关的变更，你还没指明要继续哪一个，即使目标唯一或选择索引有效；
- 有多个进行中的 change，你的话没点明是哪一个；
- 有多个进行中的 change，且本地没有有效的选择记录或指名指令；
- change 的核心状态文件缺失，或项目配置文件格式损坏；
- 任务正停在 plan-ready 确认、验证未通过、归档审批等需要你决定的节点；
- 你的请求和现有 change 完全无关，或只是普通咨询（此时返回 `out_of_scope`）。

Native 模式下，工作区有未提交改动只作为恢复时的提示，不会因此阻止强模型进入 `/comet-native` 查看实际情况；Classic 模式则继续严格校验工作树归属。

<Warning>
  <code>ask_user</code> 表示当前信息还不够，或状态机在等待用户决定，属于正常的停顿。调用方应说明原因并等待用户答复；重复探测无法补出缺少的信息。
</Warning>

## 几个命令的职责边界

| 命令 | 作用 |
| --- | --- |
| `/comet` | 统一入口，按项目配置进入 `/comet-native` 或 `/comet-classic` |
| `comet resume-probe` | 正式进入工作流前，只读地判断要不要恢复已有任务 |
| `comet status` | 查看进行中的 change、阶段进度、证据和下一步建议 |
| `comet doctor` | 检查 CLI 安装、平台环境和配置，并给出修复方法 |
