title: "comet eval"
description: "通过共享 eval harness 评估本地 Skill 或 comet/eval.yaml，并生成报告。"
---

`comet eval` 是通用 Skill 评估入口。它封装 eval harness，让你不需要手工切到 `eval/` 或拼 pytest 参数。

它为 Skill 提供发布前证据：能评估 `/comet-any` 的生成物，也能对本地 Skill 目录做早期冒烟。

## 命令形态

`comet eval` 是单入口命令。你把 Skill 目录、`SKILL.md` 或 `comet/eval.yaml` 作为 target 传入，再用选项决定是 collect 还是执行真实评估。

| 命令 | 用途 | 是否执行模型任务 |
| --- | --- | --- |
| `comet eval ./generated-skill/comet/eval.yaml --collect` | 只做发现和预检查，不执行模型或 Docker 任务 | 否 |
| `comet eval ./generated-skill/comet/eval.yaml --html` | 执行本地 eval，可生成 HTML 报告 | 是 |

<Note>
  还有一个名字相近的 <code>comet skill check</code>，它是<strong>完全不同的命令</strong>——检查某次 Skill 运行的 runtime checks，不是通用 Skill 评估。详见 <a href="/zh/eval/runtime">Runtime check</a>。
</Note>

## 运行前需要准备

这些依赖不属于核心 Comet 运行时。只有在运行 `comet eval` 时，eval harness 才需要它们来启动真实模型任务：

- **uv**（`comet eval` 内部用它驱动 pytest）
- **Python 3.11+**
- **Docker**（构建任务镜像、隔离运行）
- **`claude` CLI** 在 PATH 上
- **`ANTHROPIC_API_KEY`** 或 **`ANTHROPIC_AUTH_TOKEN`**

请先确认环境就绪；缺少 Docker、`claude` CLI 或模型凭证时，suite 通常会被**跳过**，而不是直接报错。完整准备步骤见[评估快速上手 · 运行前你需要准备什么](/zh/eval/quickstart#运行前你需要准备什么)。

<Note>
  <strong>用代理型凭证</strong>（BigModel / OpenRouter 等）：当 <code>ANTHROPIC_API_KEY</code> 未设置时，在 <code>eval/.env</code> 里配置 <code>ANTHROPIC_AUTH_TOKEN</code> + <code>ANTHROPIC_BASE_URL</code> 等变量即可，harness 会让 Docker 内的 <code>claude</code> 用代理认证。完整变量表见 <a href="/zh/eval/harness#环境变量参考">Eval harness · 环境变量参考</a>。
</Note>

## 推荐路径

有 `comet/eval.yaml` 时（发布前完整评估）：

```bash
comet eval ./generated-skill/comet/eval.yaml --collect
comet eval ./generated-skill/comet/eval.yaml --html
```

只有本地 Skill 目录时（早期冒烟）：

```bash
comet eval ./my-skill --skill-name my-skill --quick
```

<Tip>
  先加 <code>--collect</code> 做低成本发现预检查，再加 <code>--html</code> 执行真实评估。<code>--collect</code> 不消耗模型调用。
</Tip>

## 命令选项

```bash
comet eval [target] [options]
```

| 选项 | 说明 | 默认值 |
| --- | --- | --- |
| `[target]` | 本地 Skill 目录、`SKILL.md` 或 `comet/eval.yaml` | 无 |
| `--project <dir>` | 包含 `eval/` 的仓库根目录 | `.`（当前目录） |
| `--manifest <path>` | `comet/eval.yaml` 路径 | 无 |
| `--skill-path <path>` | 本地 Skill 目录或 `SKILL.md` | 无 |
| `--skill-name <name>` | `--skill-path` 的 Skill 名 | 无 |
| `--profile <name>` | 覆盖 eval profile | `generic` |
| `--task <task>` | 指定 eval task | 见下表 |
| `--report-config <path>` | 自定义 report config 路径 | `--html` 时自动生成临时文件 |
| `--html` | 生成 HTML 报告（同时产出 markdown） | 关闭 |
| `--quick` | 使用默认 quick smoke task | 关闭 |
| `--collect` | 只做发现和预检查，不执行模型或 Docker 任务 | 关闭 |

### `--manifest` 和 `--skill-path` 互斥

一次评估只能选一个入口：

- 只传 `--manifest`：评估 `comet/eval.yaml`。
- 只传 `--skill-path`：评估本地 Skill 目录。
- 传 `[target]`：CLI 会根据路径判断是 manifest 还是本地 Skill。
- 两个都传或都不传：报错。

### 默认 task 和 profile

| 模式 | 默认 profile | 默认 task |
| --- | --- | --- |
| `--manifest` | manifest 自带（通常 `authoring-skill`） | `recommended`（读 manifest 的 `recommendedTasks`） |
| `--skill-path --quick` | `generic` | `generic-skill-smoke` |
| `--skill-path`（无 `--quick`） | `generic` | `recommended` |

可以用 `--task` 和 `--profile` 覆盖默认值。

## 执行信息

`comet eval` 在运行前会先打印一组执行信息，便于定位报告：

- `Eval root`：实际从哪个 `eval/` 根目录启动
- `Mode`：`collect` 或 `run`
- `Target`：当前评估的是 manifest 还是本地 Skill 目录
- `Experiment`：本次实验 id
- `Profile`：本次评估使用的 profile
- `Task`：本次评估任务
- `Report path`：报告位置
- `Report config`：启用 `--html` 时使用的临时报告配置

`run` 模式还会额外提示失败归因会被记录到生成的 eval summary 里。

## 报告位置

`--html` 会要求报告同时产出 markdown 和 HTML。报告通常位于：

```text
eval/local/logs/experiments/<experiment-id>/summary.html
```

experiment id 格式是 `<task>_<YYYYMMDD_HHMMSS>`。详见[读取评估报告](/zh/eval/reports)。

## manifest 路径和 skill-path 路径怎么选

| 场景 | 推荐入口 |
| --- | --- |
| 有 `comet/eval.yaml` | `--manifest` |
| 只有本地目录、还在早期调试 | `--skill-path --quick` |
| 是 `/comet-any` 生成物 | `--manifest` |
| 要进入发布 readiness | `--manifest` |

<Warning>
  发布 readiness 优先使用 manifest 路径。<code>--skill-path --quick</code> 只适合早期冒烟，不要当成最终发布评估。
</Warning>

## 失败时怎么判断下一步

### collect 失败

优先检查：

- manifest 路径是否正确
- `comet/eval.yaml` 是否存在
- manifest 里推荐的 task 是否存在
- 当前是否在 Comet 仓库根目录或传了正确 `--project`

### run 失败

优先看报告里的 failure attribution：

| 归因 | 含义 | 下一步 |
| --- | --- | --- |
| `harness` | eval harness、依赖、Docker、路径或环境问题 | 检查依赖、Docker、网络或本地环境 |
| `workflow` | Skill 执行流程没有达到预期 | 回到 `/comet-any` 优化 Skill |
| `task` | 任务定义、验证条件或 fixture 问题 | 检查 eval 任务定义和 fixture |
| `model` | 模型行为、工具使用或不稳定输出问题 | 重跑或降低对非确定行为的依赖 |

### HTML 报告没找到

先看 CLI 输出的 `Experiment` 和 `Report path`。如果路径里有占位符，用实际 experiment id 到 `eval/local/logs/experiments/` 目录查。

## comet eval 和 comet skill check 不一样

这两个命令名字接近，但用途不同：

- `comet eval`：共享 eval harness 的用户入口，评估一个 Skill 包或 `comet/eval.yaml`。
- `comet skill check`：某次 Skill 运行的完成度检查，判断某个 run / change 是否满足 `comet/checks.yaml` 里的 runtime checks。

如果你的问题是"这个 Skill 作为产品能力能不能通过评估"，用 `comet eval`。如果你的问题是"这次 Skill 运行是否缺 artifact 或状态"，才用 `comet skill check`。详见 [Runtime check](/zh/eval/runtime)。

## 用户最少需要记什么

1. `/comet-any` 生成物优先用 `comet/eval.yaml`
2. 先 `--collect`，再 `--html`
3. eval 结果是 `/comet-any` 发布 readiness 的证据，不是发布动作本身

推荐命令：

```bash
comet eval ./generated-skill/comet/eval.yaml --collect
comet eval ./generated-skill/comet/eval.yaml --html
comet creator next <name> --json
```
