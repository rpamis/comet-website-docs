---
title: 'comet eval'
description: '评估本地 Skill、评测清单或完整 SDK 应用，生成可复查的评测报告。'
---

`comet eval` 是你在终端运行的评测命令，用来评估 Skill 或完整应用。可以直接评估现有的本地 Skill，不需要先运行 `/comet-any`，也不用提前写 `comet/eval.yaml`。

评估完整的 SDK 应用时，运行 `comet eval ./weekly-report/application.json --html`。Comet 会用真实的应用包、固定依赖和冻结的用例检查流程行为。详见 [评估 SDK 应用](/zh/eval/applications)。

## 内置基准数据集

可以选择固定版本的 WorkBuddy Code 或 SkillsBench 数据集，用原始题目和官方评分器评估 Comet Native 工作流。Claude Code Goal 可以作为对照组单独运行。Goal 模式只支持 Claude Code，它在没有 Comet CLI、Skill 和 Runtime 的干净工作区里运行。

建议先查看来源再下载。npm 包里只有元数据和适配代码，不含数据集。查看数据集信息或做静态采集不会启动 Docker 容器，也不消耗 Token。

例如，查看可用数据集、下载 SkillsBench 并做静态检查：

```bash
comet eval --list-datasets
comet eval --dataset skillsbench --fetch-dataset --dataset-root ./.comet/eval/cache/datasets/skillsbench
comet eval --dataset skillsbench --dataset-root ./.comet/eval/cache/datasets/skillsbench --collect
```

WorkBuddy 数据集的 ID 是 `workbuddy-code`。下载或运行前要先读它的开源协议，并在命令里加 `--accept-dataset-license`。下载时会校验版本号和内容哈希，都相同就复用本地缓存。静态预览会列出当前环境不支持的用例和原因。选了不支持的用例时，整次运行直接终止，不会换成别的用例。

确认任务、模型和重复次数后，再发起运行：

```bash
comet eval --dataset skillsbench --dataset-root ./.comet/eval/cache/datasets/skillsbench --task dialogue-parser --count 1 --agent claude-code --model <model-id> --project . --html
```

加 `--dataset-treatment goal` 可以单独运行 Goal 对照组，默认条件是 `native`。两组分开启动。运行时两组的题目、重复次数、Agent 平台、模型、请求端点和计算预算要保持一致；条件不一致时，结果只能并排看。原始用例得分、部分得分和流程异常分开统计。部分用例通过，不代表整个数据集都能跑，结果也不是对官方榜单的复现。

Dashboard 的 **Eval → 新建评估 → 内置数据集** 功能相同。首次打开或切换数据集时只显示元数据；点击下载后开始拉取，并显示进度和缓存状态。正式运行需要本机有 uv、Docker 和所选 Agent 的凭据。默认给每道题的运行时间和镜像构建时间都设了上限，可以手动调整，也可以随时终止。

## 最短运行路径

```bash
# 静态自检：检查 Skill 结构、manifest 配置和用例能否被识别
comet eval ./my-skill --collect

# 少量用例的冒烟评测
comet eval ./my-skill --quick --html

# 完整的本地评测
comet eval ./my-skill --html
```

`target` 可以是本地 Skill 目录、`SKILL.md` 文件，或 `comet/eval.yaml` 清单。传入目录时，Comet 会在目录里查找 manifest。没有 manifest 时，常规运行会基于当前代码快照在受限沙盒里生成 2–4 个测试任务，不改源文件。

三种指定目标的方式：

| 方式 | 适合什么情况 | 示例 |
| --- | --- | --- |
| 位置参数 target | 评测本地现成的 Skill 目录或 manifest，日常首选 | `comet eval ./my-skill --html` |
| `--manifest <path>` | 测试清单和 Skill 不在同一个目录 | `comet eval --manifest ./evals/smoke.yaml` |
| `--skill-path` + `--skill-name` | 写 CI 流水线时固定输入，不依赖当前路径 | `comet eval --skill-path ./skills --skill-name my-skill` |

- `--collect` 只做静态解析和配置检查，不启动 Agent、Docker 容器、插件，也不发网络请求；
- `--quick` 使用内置的 `generic-skill-smoke` 通用用例，快速检查语法和基本逻辑；
- `--html` 在输出终端日志和 Markdown 报告的同时，生成 HTML 离线报告；
- 报告和运行记录默认保存在 Skill 目录内，或 `--project` 指定的 `.comet/eval/runs/` 目录下。

Skill 在外部共享目录里时，可以指定包含 `eval/` 框架的项目根目录：

```bash
comet eval ./my-skill --project ./my-project --html
```

## 全局环境配置（.env）

通过 npm 全局安装的 CLI 不需要拉源码。把鉴权配置放到本机的全局 Eval 配置目录即可：

```text
Unix / macOS:  ~/.comet/eval/.env
Windows:       %USERPROFILE%\.comet\eval\.env
```

被测模型（Bench）和裁判模型（LLM-as-judge）使用各自独立的模型、端点和凭据：

```dotenv
BENCH_API_KEY=subject-key
BENCH_BASE_URL=https://subject.example/v1
BENCH_MODEL=subject-model

BENCH_JUDGE_API_KEY=judge-key
BENCH_JUDGE_BASE_URL=https://judge.example/v1
BENCH_JUDGE_MODEL=judge-model
```

优先级从高到低：CLI 显式参数和 manifest 配置 > 当前终端的系统环境变量 > `.env` 文件。Claude Code、Codex、CodeBuddy 会把通用环境变量映射成各自的配置。Codex 会加载独立的运行时 `config.toml`；Qoder 按官方的鉴权和代理接口使用。各平台自己的环境变量优先级高于通用变量。

Eval 不会把 API Key 写进分发包、manifest、测试报告或 Skill 源码。用 Docker 调度 Agent 时，Codex、Qoder、CodeBuddy 都会在容器内创建临时配置目录。Codex 的 `config.toml` 只引用环境变量，CodeBuddy 的 `settings.json` 通过 `apiKeyHelper` 取凭据；凭据只存在容器内存中，容器销毁后清除。

## 评测任务的选择顺序

选择任务时按这个顺序判断：命令行 `--task` > `--quick` 冒烟用例 > manifest 中的 `evaluation.tasks` > 声明的 `recommendedTasks` > 系统自动生成的任务。自动生成的用例会结合 Skill 快照、目标 Agent 和测试配置缓存，后续相同的运行直接复用。

要给团队建立稳定的质量检查，可以在 `comet/eval.yaml` 里写内联任务（Inline Tasks）：

```yaml
evaluation:
  tasks:
    - name: writes-summary
      prompt: 整理本次改动并生成 summary.md 文档。
      expect:
        files:
          - summary.md
        contains:
          summary.md:
            - '# Summary'
```

也可以用 `source` 引入 Skill 包里自带 `task.toml` 和 `instruction.md` 的任务包。内联任务支持检查文件是否存在、文本关键词、结构化 JSON 和断言命令。任务的工作区和产物必须限制在被测 Skill 包内或沙盒工作区内。

## 选择评测 Agent

默认用 `claude-code`，也可以指定 `codex`、`qoder` 或 `codebuddy`：

```bash
comet eval ./my-skill --agent codex --model subject-model
```

被测 Agent 和裁判 Agent 可以分别配置：

```yaml
execution:
  agent: codex
  model: subject-model
  baseUrl: https://subject.example/v1

judge:
  agent: claude-code
  model: judge-model
  baseUrl: https://judge.example/v1
```

命令行参数优先于 manifest 配置。启用裁判机制后，必须为裁判配置独立的模型和凭据，系统不会复用或借用被测 Agent 的身份凭据。

接入自研 Agent 需要先注册适配器；Comet 不会因为某个可执行文件在 PATH 里就直接调用。适配器配置放在：

```text
~/.comet/eval/adapters/<agent-id>/adapter.yaml
```

注册后就可以用 `--agent` 指定：

```bash
comet eval ./my-skill --agent my-agent
```

## 评测数据套件（Suite）

默认使用 `local` 本地套件，适合单机日常研发和离线查看 HTML 报告。需要把每次评测接入团队的监控面板时，可以使用 LangSmith：

```bash
comet eval ./my-skill --suite langsmith --html
```

需要把模型调用记录、用例得分和 A/B 实验数据同步到 Langfuse 时：

```bash
LANGFUSE_PUBLIC_KEY=pk-lf-... LANGFUSE_SECRET_KEY=sk-lf-... \
  comet eval ./my-skill --suite langfuse --html
```

Langfuse 套件同步云端数据的同时，本地仍保留完整的离线 HTML 报告。执行 `--collect --suite langfuse` 时不会初始化外部 SDK、不发起网络连接，也不下载插件。

## 构建超时设置

首次运行时拉取评测依赖可能因为网络较慢而超时。要取消本地 Docker 镜像构建的超时限制，可以在当前终端设置 `COMET_EVAL_BUILD_TIMEOUT_SECONDS=0`：

```powershell
$env:COMET_EVAL_BUILD_TIMEOUT_SECONDS = "0"
```

这个设置只放宽镜像构建和工作区挂载阶段，不影响用例执行和评分的时限。底层确实有语法或构建错误时仍会报错。配置检查、任务选择和静态预览不会调用模型；真正的评测只在你运行评测命令后才开始。

## 常用参数

```text
comet eval [target] [options]
```

| 选项 | 说明 |
| --- | --- |
| `--project <dir>` | 指定包含 `eval/` 框架的项目根目录 |
| `--manifest <path>` | 直接指定 `comet/eval.yaml` 清单 |
| `--skill-path <path>` | 指定待测 Skill 目录或 `SKILL.md` 的路径 |
| `--skill-name <name>` | 指定待测 Skill 的名称 |
| `--agent <agent>` | 选择被测 Agent，如 `claude-code`、`codex` |
| `--model <model>` | 指定被测模型 |
| `--base-url <url>` | 指定被测模型的 API 地址 |
| `--judge-agent <agent>` | 选择裁判 Agent |
| `--judge-model <model>` | 指定裁判模型 |
| `--judge-base-url <url>` | 指定裁判模型的 API 地址 |
| `--profile <name>` | 指定评测 Profile |
| `--report-config <path>` | 指定自定义报告渲染配置 |
| `--suite <suite>` | 选择数据套件：`local`、`langsmith` 或 `langfuse` |
| `--task <task>` | 只运行指定的一个测试任务 |
| `--collect` | 静态检查配置和依赖，不发网络请求 |
| `--quick` | 使用冒烟用例，适合日常快速验证 |
| `--html` | 在终端日志之外生成离线 HTML 报告 |

## 报告与问题归因

开始评测前，CLI 会在终端打印本次的信息：目标、套件、用例集、实验标识 Experiment 和报告保存位置。报告把所有问题归为四类：

- `harness`（基础设施故障）：依赖缺失、Docker 守护进程崩溃、路径越权或环境配置缺失；
- `workflow`（工作流逻辑问题）：Skill 的状态机推进、步骤编排或命令组合不符合预期；
- `task`（测试用例设计缺陷）：用例的 Prompt 有歧义，或断言的预期不符合实际；
- `model`（模型不稳定）：模型出现幻觉、调用超时，或输出格式不符合预期。

`comet eval` 评估 Skill 端到端解决问题的能力；`comet skill check` 只检查某一次运行的单步是否健康。两者不能混用。
