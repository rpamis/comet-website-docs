开发过程中改需求、重构代码、修测试都是常事。除了按顺序往前推进，Comet 也提供了受状态机保护的修改和回退方式。本页讲每种情况该怎么处理。

## 改完文件后接着做

无论 Native 还是 Classic，在 Build、Verify 或归档之前，你在工作区里的改动都会被保留，Agent 核实改动范围后继续。常规的代码微调不需要重新创建变更：

- **改源码或测试**：保留仍然有效的成果，只重跑受影响或缺失的检查；
- **brief、Spec、Design Doc 只改文字、接口契约没变**：核对后保留原来的批准和阶段状态；
- **核心目标、验收标准或技术选型有实质变化**：说明影响，重新走一遍对应的确认流程；
- **验收已通过、还没交付时改文档**：核对影响、刷新相关检查后继续归档，不重复已经做过的事。

## 前提：不要手动改 phase

`.comet.yaml` 里的 `phase` 由状态机维护。直接运行 `set phase build` 会被拒绝。回退阶段必须通过**合法的状态流转事件**触发，每个事件都要通过阶段检查。

只有极端情况下需要手动修状态时，才用 `COMET_FORCE_PHASE=1` 强制覆盖（命令会给出安全警告）：

```bash
COMET_FORCE_PHASE=1 node "$COMET_STATE" set <name> phase verify
```

日常开发请用下面这些正常方式。

## 可以用的状态流转事件

| 事件          | 方向                | 触发场景                                           |
| --------------------- | ----------------------- | -------------------------------------------------- |
| `open-complete`       | 前进：open → design     | 需求探索完成，规格文档齐全                     |
| `design-complete`     | 前进：design → build    | 方案已确认，Design Doc 已写入                |
| `build-complete`      | 前进：build → verify    | 编码完成，构建和测试都通过                   |
| `verify-pass`         | 前进：verify → archive  | 验收全部通过，生成验证报告                     |
| **`verify-fail`**     | **回退：verify → build** | 验收没通过，或你要打回重写代码                   |
| **`preset-escalate`** | **回退：build → design** | hotfix / tweak 发现改动超出范围，升级到完整流程   |
| **`archive-reopen`**  | **回退：archive → verify** | 归档前想再验一遍或做最后调整                       |
| `archived`            | 完成归档                | 归档结束                                   |

## 场景一：build 过程中微调 Spec

编码时增量 Spec（delta spec）可以适度修改，按改动大小分别处理：

| 规模 | 原因                       | 处理方式                                                 | 阶段是否变化 |
| -------- | ------------------------------ | ------------------------------------------------------------ | ------------------ |
| **轻度** | 补边界用例、修正模糊的措辞     | 直接修改增量 Spec 并追加到 `tasks.md`，提交时写明原因 | 不变，仍在 build |
| **中度** | 涉及接口变动、组件调整或数据流 | 停下来确认 → 开始讨论，更新 Design Doc 和增量 Spec       | 不变，仍在 build |
| **重度** | 引入全新的业务 capability      | 停下来确认 → 用 `/comet-open` 为新模块另起一个变更        | 新任务从 open 开始 |

<Note>
  轻度和中度修改<strong>不需要回退阶段</strong>，直接在 build 里处理。只有出现超出当前变更范围的新能力时，才建议拆成新的任务。
</Note>

## 场景二：代码不满意，从验证阶段退回重写

进入 verify 阶段后，如果测试中发现重大逻辑问题，想重新写：

```bash
node "$COMET_STATE" transition <change-name> verify-fail
```

回退后的状态：
- `phase`：回到 `build`；
- `verify_result`：改为 `fail`；
- `verification_report` 和 `branch_status` 保留，分支状态仍是 `pending`。

改完代码并通过本地测试后，再次推进到 `build-complete`，重新验收。

## 场景三：验证通过了，归档前还想调

进入 archive 阶段后，最终确认时发现漏了测试或想微调：

```bash
node "$COMET_STATE" transition <change-name> archive-reopen
```

重新打开后的状态：
- `phase`：回到 `verify`；
- `verify_result`：重置为 `pending`；
- `branch_status`：保持 `pending`；
- `verified_at`：清空为 `null`。

随后重新核验，确认后再归档。

## 场景四：hotfix / tweak 升级为完整流程

用 hotfix 或 tweak 时发现改动超出预期，需要补正规的设计文档：

```bash
node "$COMET_STATE" transition <change-name> preset-escalate
```

这条命令一次把工作流类型改成 `full`、把 `phase` 退回 `design`，并清理临时标记。之后系统自动进入 `/comet-design` 补 Design Doc。已有的代码和测试可以继续用。

## 场景五：恢复时发现本地有未提交改动

重新输入 `/comet` 恢复任务时，如果工作区有未提交的改动：
- **确定属于当前变更**：并入当前任务，不重复编写；
- **是你的其他临时改动**：系统停下来问你——并入当前变更、另起新任务、先暂存，还是放弃；
- **不确定属于谁**：系统停下来列出文件清单，等你确认。

<Warning>
  未提交的改动只是代码现状，<strong>不会自动打勾或推进阶段</strong>。确认归属、测试通过并通过阶段检查后才会放行。
</Warning>
