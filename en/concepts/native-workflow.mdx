title: 'Native workflow'
description: 'A self-contained requirements workflow for strong coding models: detailed constraints, lightweight execution, recoverable state, and safe archive.'
---

Comet Native is designed for strong coding models that can investigate code, choose an implementation approach, and scale verification to risk. It preserves what matters from Spec workflows—requirements management, a change lifecycle, phase checks, automatic progression, verification evidence, concurrent conflicts, and recoverable archive—without prescribing a fixed design, planning, TDD, debugging, or review method.

Its principle is: **make requirements and acceptance conditions detailed, and keep the execution protocol light.** The model needs the outcome, boundaries, decisions, complete target behavior, and verification expectations. It decides how to implement from repository facts.

## Native and Classic are independent workflows

|                        | Native                                                     | Classic Spec mode                                              |
| ---------------------- | ---------------------------------------------------------- | -------------------------------------------------------------- |
| Intended model         | Strong models that can plan and verify autonomously        | Models that benefit from explicit step-by-step guidance        |
| Requirements artifacts | Comet-owned brief, complete target specs, and change state | OpenSpec change/delta specs plus Superpowers documents         |
| Execution constraints  | Constrains outcomes, evidence, and safety boundaries       | Five-phase Skills plus design, plan, TDD, and review protocols |
| Dependencies           | Only Comet's bundled Native runtime                        | The Classic, OpenSpec, and Superpowers composition             |
| Entry point            | `/comet-native`, `comet native ...`                        | `/comet-classic` and Classic phase Skills                      |

`/comet` is a configuration-driven shared alias: it reads only the project-root `comet.config.yaml`, then forwards to `/comet-native` or `/comet-classic`. It never switches modes based on task size, file count, or model judgment, and it provides no Native-to-Classic upgrade or conversion. The two workflows share no changes, state, or archive directories.

## Initialization and default entry point

A project-scope initialization defaults to Native for a new Comet project:

```bash
comet init
```

This path installs only Comet-owned Skills and runtime, creates `comet.config.yaml` and the default `comet/` directory, and does not install OpenSpec, Superpowers, or CodeGraph or write Classic rules, hooks, or `.comet/config.yaml`. Projects with clear existing Classic state remain Classic; an ordinary `openspec/` or `docs/superpowers/` directory alone is not misclassified as Classic.

Choose explicitly when needed:

```bash
comet init --workflow native
comet init --workflow native --root docs
comet init --workflow classic
```

Changing `default_workflow` explicitly changes only where `/comet` enters. It does not migrate, delete, or convert existing changes. `--root` applies only to project-scope Native initialization; a global installation still means installing global capabilities without writing project configuration.

## Layout and artifact root

Native uses only Comet-owned directories:

```text
<project>/comet.config.yaml
<artifact-root>/comet/
  specs/
  changes/
  archive/
  runtime/
```

The default artifact root is the project root, producing `<project>/comet/`. Initialize with `docs` to use `<project>/docs/comet/` instead:

```bash
comet init --workflow native --root docs
```

`artifact_root` must be a project-relative path. `comet native init --language en` also persists the default language for future changes, while an individual `new --language` can override it. Use `comet native root move` to change location instead of editing configuration. The move records transaction state and can continue or roll back after interruption.

## Four phases

```mermaid
flowchart LR
  A["Shape: clarify requirements"] --> B["Build: implement autonomously"]
  B --> C["Verify: record evidence"]
  C -->|pass| D["Archive: update specs and archive"]
  C -->|fail| B
```

### Shape: make the information sufficient

Shape captures the user goal in `brief.md` under Outcome, Scope, Non-goals, Acceptance examples, Constraints and invariants, Decisions, Open questions, and Verification expectations.

The model first investigates facts available from the repository. It asks the user only about decisions that materially affect scope, user-visible behavior, compatibility, risk, or irreversibility. When one exists, it asks the single most important question and includes a recommendation, rationale, and practical impact of each option. After the answer, it records the decision and advances with `next --confirmed`. With no high-impact unknown, it keeps going and the runtime records implicit approval. A `[blocking]` question must be resolved under either approval form.

When durable behavior changes, each capability also receives a **complete target specification** at `changes/<change>/specs/<capability>/spec.md`: the full behavior that should exist after archive, rather than an incremental patch meaningful only against old text. The runtime derives `create` / `replace` and freezes `base_hash` from canonical specs; deletion uses `comet native spec remove`. The model does not maintain this state metadata directly.

### Build: let the strong model choose the method

In Build, the model chooses the simplest reliable approach that satisfies the brief and target specs. Whether to write an implementation plan, which test granularity to use, and how deeply to debug or review all depend on task risk. Native neither requires process-only documents nor mandates TDD.

When implementation reveals a new high-impact decision, the model marks it `[blocking]` and asks only one question. After the answer, it updates Decisions, removes the blocker, and records the decision with `--confirmed` while leaving Build. Build rechecks the brief and target specifications, so artifact references cannot bypass a newly discovered question.

Progression cites real project artifacts. Documentation-only or no-code work records an explicit no-code reason instead.

### Verify: facts instead of assertions

Verify checks the Acceptance examples, complete target specs, and relevant risks. `verification.md` records actual commands and results, skipped checks, specification consistency, known limitations, and the conclusion, plus a Runtime-readable acceptance block. Every Acceptance ID binds either to evidence or to an explicit skip reason.

The Runtime binds the report to the current contract, implementation scope, and change revision. Changing the brief, target specifications, or implementation files makes the old pass and old check receipt stale, so they cannot be archived. Failure automatically returns to Build; an unrun check cannot be reported as passing.

The model may repair autonomously, but the Runtime prevents endless loops without evidence progress. Under the same scope, the third identical failure signature becomes a manual stop, and one repair episode records at most 12 failures. Real scope progress opens a new episode, while a no-progress override is available only once.

### Archive: converge without overwriting conflicts

Archive is allowed only after Verify passes. First run `archive --dry-run` to obtain a content-bound `preflightHash`, then submit it with `archive --expect-preflight <sha256>`. While holding a lock, the Runtime recomputes evidence, paths, and canonical-spec SHA-256 values:

- `create` requires the canonical spec not to exist;
- `replace` and `remove` require the current hash to equal the runtime-frozen `base_hash`;
- when a hash changed, archive stops and reports a conflict instead of overwriting another change.

A conflict is recoverable: re-read the latest canonical specification, rewrite the complete target specification, and run `comet native spec rebase`. The runtime refreshes operation/hash, reopens the change in Build, and clears the old verification conclusion before implementation, confirmation, and verification run again.

On success, complete target specs become canonical, the active change moves to `archive/YYYY-MM-DD-<change-name>/`, and the trajectory retains Shape, Build, Verify, and Archive summary evidence without hidden reasoning. Source trees and destination files use bounded, object-identity-bound reads, and directory deletion first enters transaction quarantine. Rollback remains safe before the final archive marker; after that marker, only exactly-once continue is allowed.

## Phase checks, automatic progression, and recovery

Resume from disk facts: read configuration, run `comet native status` and `show`, then inspect the target change, canonical specs, implementation, and tests. Do not guess the phase from chat history or edit phase, Run state, locks, or transaction journals manually.

Within a phase, `checkpoint` can preserve a summary, next action, and content-addressed artifact manifest. `status` returns the latest checkpoint and structured continuation: `continue-same-skill` continues the current Skill, `await-user` waits for a real decision, `repair-runtime` runs recovery first, and `stop` means done or stopped. This lets a new session recover work; it does not mean a background daemon invokes the model.

Change lists, project status, detailed findings, and Acceptance IDs all use bounded pagination. Cursors bind the current name set or acceptance hash and fail explicitly after input changes instead of silently shifting pages. The Runtime fails closed on input or output budget overflow rather than hiding omitted requirement text.

`comet native next` advances automatically when phase conditions pass. Otherwise it returns structured findings and stays in the current phase. An ordinary transition records deterministic before-and-after state in `runtime/transition.json` before writing Run state, `change.yaml`, trajectory, and checkpoint. After interruption, the next `next` or `archive` continues automatically; `doctor --repair --strategy continue` performs the same recovery explicitly.

`comet native doctor` is read-only by default. `--repair` is limited to provably safe stale selections, locks, and deterministic transaction recovery; it does not rewrite user-authored briefs, specs, or verification reports. Ordinary transitions do not support rollback. Archive and root-move journals still decide whether rollback remains safe for their own transactions.

Native also provides a narrow `comet native check`. In Verify it runs only a built-in bounded read-only text policy over the current implementation scope and produces a content-addressed receipt. It does not execute Git, a shell, project scripts, or external Skills. The strong model still selects and runs real project tests according to risk.

`comet status` presents Native, Classic, and unmanaged OpenSpec changes in separate sections. For natural-language recovery, `comet resume-probe` resolves the project's default workflow first and then inspects only that side. Native always resumes through `/comet-native`; it never treats `comet native next` as a resume command or scans Classic directories. If configuration is malformed, the probe stops and requests a repair instead of guessing a fallback.

See [Native CLI](/en/cli/native) for every command.

## Dashboard is an observation surface

Dashboard can show a Native change's phase, evidence freshness, continuation, checkpoint, archive readiness, and conflict summary, but it consumes only the Runtime's read-only projection. It neither re-derives state nor caches a second source of truth, and it provides no advance or repair controls. CLI/Runtime remains the only writer.
