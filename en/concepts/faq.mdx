Common questions about the five-stage workflow, status, guard, and presets of `/comet` after entering the classic Spec mode by project configuration.

## Basic concepts

<AccordionGroup>
  <Accordion title="What is the relationship between Comet, OpenSpec and Superpowers">
Comet does not replace either party. OpenSpec is responsible for WHAT (requirements, proposals, spec lifecycle, and archiving), while Superpowers is responsible for HOW (brainstorming, technical design, planning, execution, and verification). Comet links the two into a recoverable five-stage workflow and ensures reliable handover with state machines and guards. For details, please refer to [Workflow Concept ](/en/concepts/workflow)
  </Accordion>

<Accordion title="What's the difference between /comet and/Comet-any">
Users uniformly call `/comet`; After selecting Classic for the project configuration, the internal permanent entry `/comet-classic` driver is selected
The open/design/build/verify/archive five-phase process. `/comet` is the project-configured unified entry point and may enter Native or
Classic. `/comet-any` is Skill Creator, used to create, optimize, and compose reusable Skills. Each has a different responsibility.
</Accordion>

<Accordion title="Must I use OpenSpec and Superpowers">
Classic Spec mode relies on both: OpenSpec records requirement specifications, while Superpowers provides the design and execution methodology. `comet init
--workflow classic` installs both. New project-level `comet init` runs use Native by default, which does not depend on them.
If you only want Comet's Skill platform capabilities—using `/comet-any` to compose Skills into verifiable, reviewable, and distributable Skill Bundles—start with [Compose any Skill](/en/skill-creator/getting-started).
</Accordion>

</AccordionGroup>

## The differences from similar products

<AccordionGroup>
  <Accordion title="What are the differences between Comet and superpowers bridge">
Both aim to integrate OpenSpec and Superpowers into a single workflow, but their implementation forms and guarantee levels are completely different.

**superpowers-bridge** is an [OpenSpec native schema bundle](https://github.com/JiangWay/openspec-schemas) Copy it to the current OpenSpec root directory of the project's `schemas/` (the default for Classic new projects is `docs/openspec/schemas/`, and for projects that retain the old layout, it is `openspec/schemas/`), and select it by pressing change with `--schema superpowers-bridge`. It is a ** pure prompt layer integration ** - without modifying the source code of Superpowers or the OpenSpec CLI, the order is constrained by the artifact DAG (`brainstorm → proposal → design → specs → tasks → plan → verify → retrospective`) and prose `PRECHECK` in `schema.yaml`. It also fills in a `retrospective` artifact that was natively missing from Superpowers and prioritized evidence.

**Comet** is an independent npm package (`@rpamis/comet`), featuring cross-platform Node runtime, `.comet.yaml` state machine, hook hard interception, diagnosis and recovery. The core difference between the two:

    |"Dimension"| superpowers-bridge | Comet |
    |------|--------------------|-------|
    |"Form"|OpenSpec schema bundle, copied to `schemas/` in the current OpenSpec root directory|Independent npm package + CLI + Node runtime|
    |Integration layer|Pure prompt layer, without modifying the source code /CLI|prompt layer + Engineering runtime (state machine, hook, guard)|
    |"Arrangement|The DAG of the product + prose description is adjusted in sequence by model/manual|Five-stage state machine, scripted [auto-transition ](/en/concepts/auto-transition)|
    |Status/Recovery|There is only the artifact file itself, and no explicit stage status|[`.comet.yaml` state machine ](/en/concepts/state-management) + [Compression recovery ](/en/concepts/context-compression)|
    |Constraint strength|Prose `PRECHECK` (Read but not mandatory)|phase-guard rules inject each round + hook hard interception ](/en/concepts/decision-points)|
    |Platform requirements|The subagent platform must be used; otherwise, it will revert to spec-driven|Cross-platform, no mandatory subagent, with a degradation path|
    |Entrance|Only the `/opsx:*` command takes effect. Natural language triggering will cause air leakage|The intent route ](/en/concepts/intent-routing) is routed from any input to the stage|
    |Classification|Relying on manual judgment of "whether to build a change"|Built-in [hotfix](/en/presets/hotfix)/[tweak](/en/presets/tweak)] presets|
    |Scope|A development workflow schema|Workflow + Skill Platform ([Combination ](/en/skill-creator/getting-started)/[Evaluation ](/en/cli/eval)/[Visualization ](/en/cli/dashboard)|

  </Accordion>

  <Accordion title="Since both are OpenSpec and Superpowers, what are the advantages of Comet">
Compared with pure schema integrations like superpowers-bridge, Comet's advantages are concentrated in four points:

    1. ** Recoverable State Machine ** : `.comet.yaml` explicitly records `phase`, `build_mode`, `tdd_mode`, and `review_mode`. After compressing long tasks or contexts, breakpoints can be precisely restored directly from these states.
    2. ** Hard execution Defense line ** : Comet has `comet-hook-guard.mjs` (PreToolUse hook) for hard interception, along with phase-guard rules for each round of injection - for instance, source code writing is prohibited during the design phase, and illegal jump phases will be blocked. Pure schema `PRECHECK` is just prose, and the model can "read but not execute".
    3. ** Robust entry + Cross-platform ** : Intent routing can be routed from any user input to a stage, eliminating the front door problem of "only taking effect when `/opsx:*` is used and leaking when triggered by natural language". And the subagent platform is not mandatory.
    4. It's not just a workflow, but a Skill platform: `/comet-any` combines any Skill, `comet eval` assesses local Skill, `comet dashboard` visualizes each change, beyond a single development workflow.

If you only want to add a layer of superpowers in OpenSpec and don't mind manual driving, Superpowers-Bridge is lighter. Comet is more suitable for long-term task recoverability, strong anti-drift constraints, multi-platform and Skill platform capabilities. To understand which industry practices Comet's runtime, workflow, evaluation, and Skill creation correspond to respectively, you can further read [Comet vs. Industry Practices ](/en/tech-blog/comet-vs-industry)

  </Accordion>

</AccordionGroup>

## Status and Recovery

<AccordionGroup>
  <Accordion title="How does the Agent know where it has reached when it comes back after an interruption">
Comet does not rely on chat history. Each time `/comet` is called and the configuration enters Classic, the internal `/comet-classic` will re-read the `.comet.yaml` and OpenSpec artifacts of the active change, determine whether the current stage and evidence are consistent, and then route to the correct stage Skill.
  </Accordion>

<Accordion title="comet status can't see my change">
This change might have been created with the original `/opsx:new`. If `.comet.yaml` is missing, it will be silently skipped by `comet status`. in
The Agent platform calls `/comet` and enters Classic through configuration
Let it take over and fill in the status file. For details, please refer to the "Orphan change" of existing projects connected to ](/en/guides/existing-project).
</Accordion>

  <Accordion title="Can.comet.yaml be edited manually">
User-visible fields (workflow, phase, build_mode, etc.) should, in principle, flow through `/comet-classic` and phase guards. Do not manually modify `phase`. The machine-owned Run field (in `.comet/run-state.json` or `.comet/runs/<run-id>`) must never be modified manually. When troubleshooting, you can use the `comet-state` command. For more details, please refer to [Status Management ](/en/concepts/state-management)
  </Accordion>

  <Accordion title="What should I do if the context is lost after context compression">
In the design stage, `brainstorm-summary.md` was written as the recovery checkpoint. In the build stage, the sub-agent has a persistent checkpoint. When restoring, call `/comet`; After the configuration enters Classic, the internal route will directly read the file status and locate the breakpoint. For details, please refer to [Restoring Interrupted Work ](/en/guides/resuming-workflow)
  </Accordion>
</AccordionGroup>

## Stages and Guards

<AccordionGroup>
  <Accordion title="Why can't we skip design and build directly">
The core principle of Comet is that brainstorming cannot be skipped (except for hotfix/tweak presets). The guard of the complete workflow will check whether `design_doc` exists. If it is missing, it will be FATAL. Skipping the design will lead to a lack of technical basis in the subsequent stages.
  </Accordion>

<Accordion title="What should I do if the verification fails">
Don't file directly. Comet will allow you to choose: go back to build after fixing, accept the deviation (add a description in the design doc), or go back and restart
"brainstorming. When `verify_result: fail` is used, archiving will be blocked by guard.
</Accordion>

<Accordion title="How does the stage progress? Do I need to operate it manually">
The guard script `comet-guard.mjs --apply` advances phases. With `auto_transition: true` (the default), completing one phase automatically invokes the next phase Skill. With `auto_transition: false`, the workflow pauses and you run the HINT manually. Phase advancement still occurs; this setting only controls whether the next Skill is invoked automatically.
</Accordion>

  <Accordion title="What does a handoff hash mismatch mean?">
After the design stage to generate handoff, OpenSpec artifacts (proposal/design/tasks/spec) is modified. The solution is to re-run `comet-handoff` to enable Superpowers to obtain the current OpenSpec context. For details, please refer to "How to Hand Over Products" in the Workflow concept ](/en/concepts/workflow).
  </Accordion>
</AccordionGroup>

## Lightweight presets and high demand

<AccordionGroup>
  <Accordion title="What's the difference between hotfix and tweak">
Both skip the full brainstorming process and retain the OpenSpec status, verification, and archiving. hotfix is suitable for reproducing bug fixes with clear paths. tweak is suitable for minor changes with a clear scope. When cross-module coordination, new public apis, or schema changes occur, full should be upgraded. For details, please refer to [hotfix preset ](/en/presets/hotfix)
  </Accordion>

<Accordion title="How should large demands be handled">
`/comet-open` will trigger a PRD split pre-check before creating artifacts, breaking down large requirements into multiple independently designed, delivered, and archived ones
"change. For details, please refer to [Large PRD Split ](/en/guides/prd-splitting)
</Accordion>

  <Accordion title="What is the use of review_mode">
`review_mode` (off/standard/thorough) controls the intensity of automatic code review in the build and verify phases. The full workflow must be selected before leaving the build; hotfix is off by default. The default values of the project can be set in `classic.review_mode` of `.comet/config.yaml`.
  </Accordion>
</AccordionGroup>

## Q&A

<AccordionGroup>
  <Accordion title="What should I do if the code keeps submitting automatically">
Auto-commit is a source code behavior of Superpowers. You can have the AI generate hooks or rules to block git commits for you to prevent this behavior from happening.
  </Accordion>
  <Accordion title="I'm halfway through writing the code and I'm not satisfied with the solution. What should I do">
First, stop the Agent and don't continue writing the code. Then handle it according to what you have actually done:

    - ** You have changed the spec, design or tasks** : Directly call `/comet` again. After entering the Classic configuration, Comet will re-read `.comet.yaml` and OpenSpec artifacts and restore to the correct phase according to the current phase.
    - ** You have modified the code yourself ** : Call `/comet` again and tell the Agent: "I have modified the code. Please restore it to the current workspace." Comet will check and attribute uncommitted changes according to the dirty-worktree protocol.

If both the spec and the code have been modified, restore them first using `/comet`. You need to explain whether these changes represent the new plan; Do not manually modify the `phase` or `.comet/run-state.json` of `.comet.yaml`. Comet will recover from the current file state and persistent artifacts.

  </Accordion>
  <Accordion title="After using Comet, the Token consumption increases and the time becomes longer">
The Comet Full process is required for complex demands/functions. It will go through multiple rounds of clarification, as well as optional TDD execution and Review. The process is relatively strict, so the Token consumption is relatively fast. If you need lightweight and fast delivery, please use comet-tweak and comet-hotfix presets. For small requirements/functions, they can also be replaced by Plan or /loop.
  </Accordion>
</AccordionGroup>
