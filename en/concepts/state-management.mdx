Comet separates human-readable workflow state from machine-managed runtime evidence.

## Three state layers plus config

| File | Role | Who owns it |
| --- | --- | --- |
| `.comet.yaml` | Current workflow, phase, change id, mode, and user-visible metadata | Human-readable, Comet-updated |
| `.comet/run-state.json` | Runtime checkpoints and machine evidence | Machine-managed; written automatically by the runtime and not meant for manual editing |
| OpenSpec and Superpowers artifacts | Proposal, spec deltas, design docs, plans, and archive history | Workflow artifacts |
| `.comet/config.yaml` | Project defaults | User-configurable |

## Configuration precedence

Effective behavior is resolved in this order:

1. explicit command flags;
2. environment variables;
3. `.comet/config.yaml` project defaults;
4. package defaults.

## `auto_transition`

`auto_transition` controls whether Comet may advance phases automatically when the required evidence is present.

## `.comet.yaml` field groups

| Group | Examples |
| --- | --- |
| Workflow and phase | `workflow`, `phase`, `change_id` |
| Execution mode | classic workflow, hotfix, tweak |
| Verification and branch | expected checks and branch metadata |
| Paths | links to OpenSpec, Superpowers, and archive artifacts |
| Time and archive | timestamps and archive markers |
| Machine-managed hints | fields Comet updates and users should not hand-edit casually |

## State-machine constraints

Comet does not treat phase as a free-form note. Transitions must follow allowed events such as proposal approval, design approval, build completion, verify failure, or archive completion.

## Boundary between workflow state and run state

`.comet.yaml` should stay readable and useful to humans. Detailed checkpoint data belongs in run state, where the runtime can manage it without polluting the main workflow file.
