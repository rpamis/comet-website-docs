Comet exposes its core capabilities as **Skills**. A Skill is an independent directory: `SKILL.md` explains what it does and which steps it follows, while scripts, reference docs, and validation files can sit beside it. After installation, it either becomes a platform slash command such as `/comet-native`, or Comet Engine resolves it by name.

Normal use requires only `/comet`; you do not need to understand these mechanisms. This page answers three questions: where Skills come from, where they are installed, and who discovers them, so you can use it when customizing, installing, or troubleshooting.

## Three sources

Comet Skills fall into three groups based on how they are created and where they are installed:

| Source                 | Created by                     | Installed in                         | How it is used                              |
| ---------------------- | ------------------------------ | ------------------------------------ | ------------------------------------------- |
| Built-in workflow Skill | `comet init` / `comet update`   | Platform directory such as `.claude/skills/` | Discovered by the platform as a slash command |
| Project Skill           | `comet skill add`              | `.comet/skills/<name>`               | Resolved by Comet Engine by name, not exposed to the platform |
| Generated Skill         | Created and published by `/comet-any` | Bundle draft directory               | Distributed after evaluation as a project or platform Skill |

<Note>
  The first two are easiest to confuse: <strong>Platform Skills</strong> are installed by
  <code>comet init</code> into <code>.claude/skills/</code> and similar platform directories, then
  discovered by the AI platform as slash commands. <strong>Project Skills</strong> are installed by
  <code>comet skill add</code> into <code>.comet/skills/</code>; they belong to Comet Engine's own
  Skill pool, are not exposed directly to the platform, and are resolved by name at runtime.
</Note>

## Project Skills

A project Skill is a Skill package installed under `.comet/skills/<name>/`:

- **Location**: `.comet/skills/<name>/`, alongside `.comet/config.yaml`, as part of the repository and suitable for Git.
- **Discovery order**: when Engine resolves a Skill name, it searches **explicit path -> project Skill -> built-in Skill**, with project Skills taking precedence.
- **Not exposed to the platform**: project Skills do not automatically become slash commands.

| Use case             | Details                                                                                         |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| Override built-ins   | Put a same-named Skill in `.comet/skills/`; Engine uses it first. Useful for standardizing a team workflow. |
| Install extra Skills | Install a Skill generated by `/comet-any` or a community Skill so Engine can run it.            |
| Share inside a repo  | Commit it to Git so teammates get the same Skill pool when they clone the repository.            |

Install a Skill with:

```bash
comet skill add ./my-skill --project .
```

Comet validates `./my-skill`, computes its hash, and copies it to `.comet/skills/<metadata.name>/`. An existing Skill requires `--overwrite`. Symlinks are rejected so the package contains real files.

<Warning>
  If a project Skill shadows a built-in Skill but fails validation, Engine <strong>fails directly</strong>
  instead of falling back to the built-in. This avoids thinking a custom version is running when the
  built-in one was silently selected (fail-closed rather than silent downgrade).
</Warning>

## Local Skill commands

| Command                | Purpose                                                          |
| ---------------------- | ---------------------------------------------------------------- |
| `comet skill add`      | Install a Skill package into `.comet/skills/`.                   |
| `comet skill show`     | Inspect source, hash, structure, guardrails, and runtime checks. |
| `comet skill run`      | Start an advanced deterministic Engine Run.                      |
| `comet skill continue` | Resume a run or submit pending action output.                    |
| `comet skill check`    | Run Engine runtime checks.                                       |

## On-demand code review: /comet-review

`/comet-review` performs one **manually triggered, read-only code review** of the selected Comet change, Native or Classic. It compares the implementation diff with existing evidence and reports correctness, security, boundary, and coverage issues by priority.

It belongs to no phase and does not replace Build or Verify:

- The entire call is read-only: it does not modify files, advance phases, update state or verification reports, or fix findings.
- It is independent of `review_mode`: `review_mode` controls automatic in-workflow review, while `/comet-review` represents one manual review and neither reads nor changes the current change's `review_mode`.
- A review result is not a Verify pass; “no findings” does not mean tests have passed.

## Create a reusable Skill with /comet-any

`/comet-any` is the main entry for creating or improving a Skill. Describe the workflow you want and it will:

1. Read project preferences from `.comet/skill-preferences.yaml`.
2. Use `find-skill` to resolve **real local Skill content** instead of inferring capabilities from names.
3. Show a Skill Creator confirmation page with each Skill's source, hash, role, and invocation order.
4. After confirmation, generate a **stable composable Skill Bundle** containing skills, scripts, rules, hooks, and references instead of one `SKILL.md`.
5. Run validation and generate an install candidate through the CLI backend, with optional installation.

`.comet/skill-preferences.yaml` supports `prefer`, `require`, and `advisory` entries; confirmation computes a `preferenceHash` bound to the artifact.

<Note>
  Ordinary users do not need to understand the internal concepts of Bundle, Factory, composition, or
  Phase Recipe. From the user perspective there are three starts: <strong>customize
  /comet-classic</strong>, <strong>create a new Skill</strong>, or <strong>upgrade an existing
  Skill</strong>.
</Note>

```text
/comet-any -> comet eval -> comet creator status/next -> review/approve/run -> distribute
```

See [Skill Creator quickstart](/en/skill-creator/getting-started).

## Engine: advanced details

If you create a reusable Skill with `/comet-any`, or use `comet skill` for local debugging and Engine Runs, you need to understand Skill Engine, Comet's deterministic runtime. Engine covers package structure, pending-action/resume loops, immutable snapshots, guardrails, and runtime checks.

Users who only use built-in workflow Skills **do not need to understand Engine**. For deeper detail, see [Skill and Engine](/en/skill-creator/engine), which documents the complete Engine runtime on the Skill Creator tab.
