`comet dashboard` opens a local read-only browser interface for both Comet workflows. Use the switch in the upper-left corner to show either the detailed Classic workspace or the lightweight Native workspace; the two views are not mixed on one page.

## Start it

```bash
comet dashboard
```

Useful options:

| Option          | Purpose                                 |
| --------------- | --------------------------------------- |
| `--json`        | Print the same snapshot as JSON.        |
| `--port <port>` | Choose a port.                          |
| `--no-open`     | Start server without opening a browser. |

## Classic / Native switch

Dashboard provides a **Classic / Native** workflow switch in the upper-left corner. Both workspaces use the same project-summary, Changes Explorer, change-detail, and status-sidebar structure, but only the selected workflow is shown. The Native view consumes read-only projections produced by Native Runtime together with archive preflight and conflict-radar results; Dashboard does not re-derive workflow facts.

Each Native change shows:

- Current phase: Shape, Build, Verify, Archive, or invalid state
- Verification evidence freshness: missing, invalid, stale, complete, partial, or unknown
- Archive readiness
- Continuation disposition: continue, await user, blocked, or done, including whether a user decision is required
- Structured finding codes
- Definite conflicts or possible overlaps with other Native changes
- User-facing Markdown artifacts such as the brief, changed Specs, and verification report
- Latest checkpoint summary, next action, and progress timestamps
- Capability scope with create, replace, and remove counts
- Acceptance totals split into evidenced, skipped, and missing criteria
- Bounded implementation-scope, Repair, and project Git summaries

The Native view provides Active, Archived, and All filters and uses the same Markdown preview drawer as Classic. It remains bounded: one snapshot exposes at most 32 changes, with up to 8 finding codes, 8 conflict peers, and 8 user-facing artifacts per change. Use `comet native status --details` and the other Native CLI commands for complete diagnostics.

<Note>
  The Native view previews only the brief, changed Specs, and verification report, and projects
  bounded checkpoint and evidence summaries. It does not expose hashes, Runtime paths, raw evidence,
  or other internal state files, and it has no progression, repair, or archive controls. Native CLI
  and Runtime remain the only writers.
</Note>

| Capability    | Classic workspace                        | Native workspace                                                    |
| ------------- | ---------------------------------------- | ------------------------------------------------------------------- |
| Change scope  | Active and archived                      | Active and archived                                                 |
| Phases        | open → design → build → verify → archive | Shape → Build → Verify → Archive                                    |
| Primary view  | Artifacts, tasks, verify, risks, Git     | Progress, scope, acceptance, user artifacts, Repair, conflicts, Git |
| Write actions | None                                     | None                                                                |

## What the Classic workspace shows

- Active and archived changes.
- Phase and workflow state.
- Proposal, design, tasks, Design Doc, Plan, and verify reports.
- Runtime status, risk signals, and Git context.
- Markdown previews for artifacts, including tables, quotes, task lists, syntax highlighting, Mermaid diagrams, and structured YAML/JSON tables (`.comet.yaml` and handoff/checkpoint files render as tables instead of raw text).

The workspace remains within the viewport when the left explorer is open. Artifact previews remember the current scroll position and return to it when closed. Archived changes are shown as complete rather than being sent back to verify, and their project-root `docs/superpowers/` Design Docs, Plans, and verification reports remain available.

When Dashboard is launched from a nested repository directory, it first locates the project root. Classic data is collected from the root selected by `classic.artifact_layout`: `docs/openspec/changes/` for the default documentation layout or `openspec/changes/` for a retained legacy layout, including the corresponding `changes/archive/` directory. Native data is read from the configured Native artifact root. Both views are read-only and best effort. A collection failure is shown as an error instead of an empty workspace and does not prevent the other workflow snapshot from loading.
