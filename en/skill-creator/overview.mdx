Comet Any turns business workflows into complete SDK Skill applications. Each application contains a readable entry and business rules, plus a Runtime that manages execution, approvals, artifacts, and recovery.

## Who writes what

| Participant        | Responsibility                                                                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authoring Agent    | Investigate actual Skills; write the complete entry, business Rule, execution ports, business validators, and validation samples                  |
| SDK                | Assemble the actual workflow, pin content and dependencies, append the execution protocol, save Runs, and check Actions, approvals, and artifacts |
| Execution host     | Load actual Skills, hand off tasks, call tools, obtain user decisions, and reconcile external results                                             |
| Distribution entry | Preview and install platform Skills, shared Rule/Hook entries, and Runtime dependencies                                                           |

SDK's general execution protocol cannot replace business content. For example, “the report must include sources” belongs in both business requirements and actual validation conditions. A single instruction does not establish enforcement.

## Application contents

The complete package uses `application.json` as its entry and pins application identity, version, entry Skill, execution module, and actual Skill dependencies. The authoring plan must contain complete `SKILL.md` and `rules/workflow-guard.md` content. It may include Markdown resources that are actually referenced.

Platform installation entries refer to this pinned package. Successful file installation, Skill loading, Action completion, machine validation, and actual host validation are recorded separately.

## Three composition types

**Native extensions** add work at allowed candidate, parent, child, or integration checks. The original Builder, independent Verifier, user approvals, and archive constraints remain.

**Classic composition** uses the full, hotfix, and tweak domain factories to add or replace Skills within required-document and stage-authorization constraints.

**Standalone applications** declare their own workflow graphs, Schemas, state, branches, parallel work, and child workflows. Their contracts define acceptance. For example, a local report's rejection branch can end normally without publication.

## What confirmation pins

A proposal shows complete content, actual steps, dependencies, output conditions, failure paths, and capability limitations. Approval applies to the whole proposal; a content summary or old approval cannot replace it.

After compilation, execution uses pinned content. If files or dependencies drift, retain the current records and restore the original content, or revise the plan and obtain new confirmation.

## How stage files prevent progress

Applications declare required artifacts and content conditions for actual steps. Business validators check domain conditions. SDK checks actual files and digests. Missing files or failed conditions prevent stage results from becoming successful evidence, and downstream work cannot proceed on stale evidence.
