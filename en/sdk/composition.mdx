---
title: 'Compose Native, Classic, and standalone workflows'
description: 'Choose an application factory to extend or compose Skills within existing acceptance rules.'
---

An application's `base` determines which workflow it uses. Choose based on the business stages, validation, and recovery you need. Editing entry Skill text alone cannot change the workflow.

| Type            | Public factory                    | Suitable work                                                     |
| --------------- | --------------------------------- | ----------------------------------------------------------------- |
| Native          | `createNativeWorkflowApplication` | Add team work at candidate, parent, child, or integration checks  |
| Classic         | `createClassicApplication`        | Compose Skills and extension steps for full, hotfix, and tweak    |
| Standalone      | `createStandaloneApplication`     | Define steps, branches, parallel work, joins, and child workflows |
| Report template | `createReportApplication`         | Generate, approve, and publish local reports                      |

## Native extensions

Import the factory from `@rpamis/comet/applications/native`. Extensions declare their Skills, artifacts, validators, and scope: `candidate`, `parent`, `child`, or `integration`.

Extension work binds to the current candidate and actual inputs. After requirements, the formal Spec, original candidate, approval, or artifacts change, old results cannot serve as current checks.

Native continues to manage its Builder, independent Verifier, Supervisor, user decisions, and Archive conditions. Extensions add their own business checks without replacing these responsibilities.

## Classic composition

Import the factory from `@rpamis/comet/applications/classic` and select full, hotfix, or tweak. A replacement Skill receives the original stage's required inputs and must produce outputs that meet that stage's requirements. Place added steps at checks allowed by the domain.

Machine checks in Build, Verify, and Archive use actual commands and evidence from the current round. A missing check plan, failed command, or changed input prevents a successful result from advancing the workflow.

Classic's user approvals, required documents, and archive rules still apply. Git commits, pushes, and other external operations follow actual delivery authorization.

## Standalone workflows

Standalone applications can declare their own workflow graphs, output Schemas, state, transition handlers, executors, and validators. Declare every transition in the graph. When parallel work writes to the same scope, specify an order or use separate workspaces.

Validation follows the standalone application's own contracts. For example, `completed` in a report workflow may mean publication finished or a rejection branch ended. Read the actual business result.

## Assemble from a confirmed plan

`@rpamis/comet/applications/compiler` provides `prepareWorkflowApplicationPlan` and `compileWorkflowApplication`. Preparation assembles the actual graph and proposal. Compile the complete package after confirmation.

The plan pins Skill content, modules, inputs and outputs, and validation conditions. Prepare and confirm it again if documents, dependencies, or the workflow change. Do not substitute a different execution module for the confirmed graph.

If you prefer not to write the plan structure directly, [Comet Any](/en/skill-creator/overview) investigates actual Skills and prepares a proposal. [comet application](/en/cli/application) handles platform installation.
