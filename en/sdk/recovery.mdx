Read the original Run when recovering. Distinguish pending work, running work, user waits, known failures, and unknown results. Each state has its own recovery path.

## Continue the same Run

With a file Store, register the same workflow version, executors, and validators in the new process, then read the original Run ID. Do not create a new Run to repeat completed Actions.

Applications retain pinned packages by identity and version. Upgrades keep older versions needed by active Runs. If dependency content changes, restore the original dependency or confirm a new application version.

| Current situation               | What to do                                                                         |
| ------------------------------- | ---------------------------------------------------------------------------------- |
| pending Action                  | Claim and execute through the configured execution port                            |
| pending Wait                    | Show the current proposal and submit the actual user decision or required evidence |
| Known failure                   | Correct the cause and continue along an allowed retry path                         |
| running / unknown               | Check the original executor and external system first                              |
| Changed requirement or proposal | Revise and obtain new approval for the current proposal                            |

## Check unknown results first

An external operation may already have happened when a connection breaks after dispatch. For example, a report may have reached an external service before the host saved its result. Do not call publish again to find out.

The host's reconciliation API queries the original Action's actual result. If it ran, report an Outcome for the same Action. Retry with verifiable evidence only after confirming it did not run and that the original executor has stopped. Preserve the current records if the result cannot be established.

Complete applications can use `reconcileApplicationSkill` to invoke the configured host's reconciliation capability and report the original result. This API does not redispatch the operation.

SDK saves Runs and claims; it does not make local records and external services one atomic transaction. Business idempotency keys and query APIs belong to the host and external service.

## Where data is stored

The base Runtime's `createFileRuntimeStore` uses your chosen `rootDir`.

When you use Native, Classic, and SDK applications through Comet CLI, machine-local execution data is stored in the user Comet data directory, isolated by project checkout and Git worktree. The default root is `~/.comet`; override it with `COMET_DATA_DIR`. On Windows, the default is `.comet` under your user directory. The chosen user data root must be outside the current workspace, never inside the project.

Requirements, Specs, entry Skills, and readable state projections remain in the project. SDK changes with complete portable checkpoints can recover after copying. You do not need to manually copy or edit local locks, transactions, or Run JSON.

## Host and installation capabilities

Actual Skill execution requires the host's declared loading, handoff, and authorization capabilities. The platform installation preview lists missing capabilities and Hooks that need activation. Writing files to an installation directory does not establish host execution, active Hooks, or business acceptance.

See [comet application](/en/cli/application) for complete application installation and upgrades. Observe daily execution in [Dashboard](/en/dashboard/overview); progress and user decisions still use the original Run's execution entry.
