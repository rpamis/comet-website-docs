The Verify phase is the quality gate before archiving. `/comet-verify` runs your tests and build commands, checks that implementation matches design, and records a verification report saved to disk. The first 3 repairable failures return to build automatically; it pauses only when you accept a deviation, handle spec drift, or hit the retry limit.

Verify **no longer handles the branch**. Branch closeout moved to the archive phase: after the archive commit, archive handles the branch and writes `branch_status: handled`, so the final branch or PR includes merged specs and archive metadata.

## Trigger

Run `/comet-verify` directly, or let `/comet` auto-dispatch when all tasks in `tasks.md` are checked. Both OpenSpec and Superpowers contribute to this phase.

## Owner

**Both OpenSpec and Superpowers** — OpenSpec's `openspec-verify-change` skill handles full spec-coverage verification for larger changes. Lightweight verification (small changes) runs inline without loading an external skill. Branch handling no longer fires here; it fires in archive.

## What Happens

<Steps>
  <Step title="Scale assessment determines verification mode">
    The AI runs a scale assessment that counts tasks, delta specs, and changed files to determine whether this is a **lightweight** (small change) or **full** verification. The result is written to `.comet.yaml` as `verify_mode`. If every task was committed individually, the AI also checks the `base-ref` commit range for a more accurate picture of change scope.
  </Step>
  <Step title="Tests and build commands run">
    The AI executes your project's normal build and test entrypoints. Guard auto-detects the project build command where possible (`npm run build`, Maven, Cargo, etc.) and prints failed command output as evidence. `verify_command` and `build_command` are no longer valid `.comet.yaml` configuration fields.

    - **Lightweight verification** checks: all tasks complete, changed files match task descriptions, build passes, tests pass, no obvious security issues (hardcoded keys, unsafe operations).
    - **Full verification** additionally loads `openspec-verify-change` and checks: implementation vs. `design.md` high-level decisions, implementation vs. Design Doc (technical RFC), all delta spec acceptance scenarios pass, `proposal.md` goals satisfied, and consistency between delta spec and Design Doc.
  </Step>
  <Step title="Verification report is produced and saved">
    Verification conclusions are written to a report file at `docs/superpowers/reports/YYYY-MM-DD-<change-name>-verify.md`. The path is recorded in `.comet.yaml` as `verification_report`. This file must exist on disk — the guard checks the path, not just the field value.
  </Step>
  <Step title="Guard validates evidence and advances state">
    The phase guard checks the prerequisite before allowing the transition to archive:
    - `verification_report` points to an existing file

    When satisfied, the guard auto-transitions `.comet.yaml` to `phase: archive`, sets `verify_result: pass`, and records `verified_at`. `branch_status` stays `pending` — branch handling happens inside archive after the archive commit.
  </Step>
</Steps>

## Verify Result Values

The `verify_result` field in `.comet.yaml` reflects the current verification state:

| Value | Meaning |
|-------|---------|
| `pending` | Verification has not yet completed (initial state after build) |
| `pass` | All verification checks passed and the guard has confirmed evidence |
| `fail` | Verification failed; repairable failures return to `phase: build` automatically (within the retry limit), while real tradeoffs pause for your decision |

## Verification Failure Handling

Since 0.4.0-beta.5, failures are classified before pausing. The AI first reads `comet state get <change-name> verify_failures` for the persisted consecutive failure count:

| Situation | Handling |
| --- | --- |
| CRITICAL/IMPORTANT or objectively repairable in-scope issues | Automatically `comet state transition <change-name> verify-fail` back to build (within the retry limit), without asking you |
| WARNING/SUGGESTION whose fix introduces a behavior/scope/risk tradeoff | Pauses for you to choose fix or accept; records reason and impact scope when accepted |
| WARNING/SUGGESTION with a safe, local, tradeoff-free fix | Repaired automatically within the retry limit; no pause |
| 4th failure after 3 consecutive (`verify_failures >= 3`) | Pauses with only "Continue fixing" or "Stop and seek an external decision" |

**CRITICAL and IMPORTANT findings are never waivable.** Only accepting a WARNING/SUGGESTION deviation, spec drift, or the retry-limit strategy is a user pause. The consecutive failure count is persisted by the machine-owned `verify_failures` field across resumes; `verify-pass` or `archive-reopen` resets it to `0`.

## Required Evidence

The guard enforces this condition as a hard prerequisite before `verify-pass` can be recorded:

1. **`verification_report`** must point to a file that actually exists on disk at the recorded path

`branch_status` stays `pending` through verify; it is written `handled` only by archive after the branch decision. Do not handle, merge, or discard branches in verify.

## Spec Drift Handling

If full verification finds that the delta spec was modified during Phase 3 but the Design Doc doesn't reflect those changes, the AI pauses and asks you to choose one of three options. This is one of the few genuine verify pauses:

| Option | Action |
|--------|--------|
| **A — Document the divergence** | Append an "Implementation Divergence" section to the Design Doc explaining why the implementation drifted. This is a verify-phase artifact and does not re-trigger dirty-worktree checks. |
| **B — Fix the Design Doc** | Roll back to build phase; the Superpowers `brainstorming` skill updates the Design Doc and delta spec to reflect the actual implementation. |
| **C — Accept the deviation** | Confirm the drift is acceptable and continue. The Design Doc will be marked `superseded-by-main-spec` during archiving. |

The AI will not choose for you — the spec drift decision is always a user choice.

## Context Compaction Recovery

The verify phase may trigger context compaction, especially during full verification of large changes. To recover, run:

```bash
comet state check <change-name> verify --recover
```

The script outputs the current phase, verification status, and a recommended recovery action. Follow the recovery action to resume from the correct step — for example, if `verify_result` is already `pass`, the recovery action will direct you straight to the guard for transition.
