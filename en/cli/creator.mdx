---
title: 'comet creator'
description: 'Start, inspect, and recover Comet Any SDK authoring Runs, and report actual Actions and current user decisions.'
---

Start everyday authoring with [Comet Any](/en/skill-creator/getting-started). `comet creator` provides the CLI for the same process, including state inspection, recovery, and host integration.

## Subcommands

| Command           | Purpose                                                                |
| ----------------- | ---------------------------------------------------------------------- |
| `start <name>`    | Start recoverable authoring from a natural-language goal               |
| `list`            | List authoring records in the project                                  |
| `status <name>`   | Read the current Run, Actions, Waits, and evidence                     |
| `next <name>`     | Execute local steps until a host Action or user decision is needed     |
| `dispatch <name>` | Claim Actions, report actual results, or submit current user decisions |
| `guide`           | Read first-use, preference, and recovery guidance                      |
| `candidates`      | Investigate Skill candidates for authoring                             |

Subcommands support `--project <dir>` and `--json`.

## Start and inspect state

```bash
comet creator start weekly-report --project . --host codex --goal "Summarize accepted tasks, generate a weekly report, and check sources; publish a local file after user confirmation" --install-target .comet/creator/exports/weekly-report --json
comet creator status weekly-report --project . --json
comet creator next weekly-report --project . --json
```

`--host` accepts `codex` or `claude-code`. `--install-target` is the complete application package's export directory inside the project, rather than the platform Skill entry directory.

Optional `--eval-config <file>` points to an Eval configuration JSON file. Model credentials come from the execution environment and are not written to this configuration, the package, or reports.

## Host Actions and user decisions

Save requests in a JSON file:

```bash
comet creator dispatch weekly-report --project . --request request.json --json
```

| Operation        | Facts the host must retain                                                                      |
| ---------------- | ----------------------------------------------------------------------------------------------- |
| `claim`          | Current Run, Action, execution port, actual session, stable claimToken, and actual capabilities |
| `record-outcome` | The same Action and claim credentials, actual result, and actual artifacts                      |
| `resolve-wait`   | Current Wait ID, proposal hash, unique decision ID, and actual user choice                      |

Read the actual identities and current state returned by `status` first. Do not guess Action or Wait IDs from the authoring name. Analysis Actions use the configured `creator-host` port and require actual `skill-load` and `handoff` capabilities.

Submit only choices supported by the current pending Wait. After changing the plan, content, or dependencies, approval of the old proposal cannot be reused.

## Recovery

`next` does not execute unknown operations for the host or approve on the user's behalf. Follow the returned retry, revision, or rejection path when required artifacts are missing or business validation fails. Skipping model Eval does not bypass local checks.

For dispatched work with unknown results, check the original Action and actual files before reporting. See [authoring, validation, and installation](/en/skill-creator/workflow) for the complete process. Use [comet runtime](/en/cli/runtime) for application execution and [comet application](/en/cli/application) for distribution.
