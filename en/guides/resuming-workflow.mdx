---
title: "Resume interrupted work"
description: "After a session interruption, context compression, or device switch, usually call /comet again and Comet continues from file-backed state."
---

## Short path

Open the same repository in your AI coding tool and type:

```text
/comet continue
```

In most cases, that is enough. Comet reads the current project state and resumes the right phase.

## Why `/comet` can resume directly

Comet does not depend only on chat history. It reads `.comet.yaml`, `.comet/run-state.json`, OpenSpec changes, Superpowers artifacts, and archive history.

## Resume from any phase

| Current phase | What resume does |
| --- | --- |
| open | Continues proposal/spec/task preparation. |
| design | Reopens design work and checks whether the spec changed. |
| build | Continues implementation from the plan and current task evidence. |
| verify | Re-runs or interprets checks and decides whether to archive or return. |
| archive | Completes archive or confirms the change is already closed. |

## Uncommitted changes

Uncommitted changes are not automatically discarded. Comet should identify them and work with them unless you explicitly ask to revert.

## When you need to intervene

You may need to decide when the worktree has unrelated changes, the spec changed after design approval, verification failed in a way that changes scope, active changes overlap, or archive would overwrite existing spec history.

## When to use `comet status` or `comet doctor`

Use `comet status` for a quick local snapshot. Use `comet doctor` when install paths, platform files, or runtime assets look broken.
