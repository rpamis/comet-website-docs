Sequential asks the most-upstream questions step by step, and Batch asks every question whose prerequisites are settled in a round, so you are never forced to guess while information is missing. `native.clarification_mode` only decides how questions are split into rounds; it does not change Shape, Build, Verify, or Archive, and it does not lower the shared-understanding confirmation required before Build. New projects default to Batch.

## Choose a clarification mode

Configure it in `.comet/config.yaml`:

```yaml
native:
  artifact_root: docs
  language: en
  clarification_mode: batch
```

| Mode         | Behavior per round                                                         | Best suited for                                                                                    |
| ------------ | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `sequential` | Asks one most-upstream question, then recomputes the next after the answer | Requirements are still changing quickly, or each answer materially changes the following questions |
| `batch`      | Asks every question in the round whose prerequisites are already settled   | You want fewer round trips and the same round contains several mutually independent decisions      |

When the field is absent, `batch` is used. Switching modes does not clear `[blocking]` items already in the brief, nor does it auto-fill unanswered questions with the recommended option. Handle the current persisted question first, then organize the next round under the new mode.

## The currently answerable question set

Batch does not turn every unknown into a one-time questionnaire. Native checks, for each question, whether its prerequisites are ready:

1. The user decision it depends on is settled;
2. The repository or environment facts needed to answer it have been investigated;
3. Its answer does not depend on another unanswered question in the same round.

Native organizes the user-visible results as a decision tree. Questions for which all the above conditions hold are the questions that can be put to the user this round. Questions that still depend on another decision or investigation result wait for the next round. After the user answers, Native recomputes the whole decision tree rather than reusing the old question list.

When a candidate branch needs an environment fact, investigating it is still the Agent's responsibility. When the host supports sub-agents or other parallel capability, Native launches mutually independent fact investigations in parallel; a fact under investigation only defers the downstream questions that depend on it, while other questions that can be asked this round are still put in the current round. When the host does not support parallelism, the current Agent investigates directly and does not hand a discoverable fact to the user, so you are not asked to guess without prerequisites.

Each question should still provide separately:

- **Question**: the user-visible behavior that needs to be decided;
- **Recommendation**: the suggested option based on the current goals and tradeoffs;
- **Impact**: how each option changes scope, outcome, or risk.

## Structured questions in Claude Code

When the current tool list provides `AskUserQuestion`, Native prefers Claude Code's structured question interface. Sequential submits one question per round; Batch puts the whole round into a single call only when the entire round fits the current tool's limits on question count, option count, and fields.

One round is never split across multiple blocking tool calls. If the entire round cannot fit in one call, Native uniformly downgrades the whole round to numbered text, keeping the same questions, options, recommendations, and impact, then waits for the user to answer by number.

Single-select and multi-select follow the semantics of the decision itself:

- Use single-select when options are mutually exclusive;
- Use multi-select only when a single decision allows several compatible options to be selected together;
- Do not compress several independent decisions into one multi-select question.

If the first structured question call in a session fails, later rounds fall back to text directly and do not re-trigger the same host error. After a tool call succeeds, Native does not emit a duplicate set of text questions.

## How questions are saved and resumed

The conversation is not the recovery source. Sequential saves only the current most-upstream question in `brief.md`; Batch saves the round's questions with stable numbering:

```markdown
## Open questions

- [blocking] Q1: On an avatar upload failure, keep the existing avatar or clear it?
- [blocking] Q2: May users delete their existing avatar?
```

After the user answers, the settled content is written into Decisions and the target spec, and only then is the corresponding blocker removed. Unanswered or ambiguous items stay `[blocking]`.

When all questions are resolved, both modes recheck for any omitted or silently-defaulted user-visible branches, then produce a single shared-understanding summary covering the outcome, scope, key decisions, acceptance criteria, and non-goals, and persist the final confirmation:

```markdown
- [blocking] CONFIRM: Confirm entering Build under the current summary
```

That item is removed and Build entered only after explicit confirmation from the user. Each Sequential round still asks only one product decision; the final shared-understanding confirmation is a separate last step and does not compress unresolved decisions into one round. The normal flow records that confirmation in Runtime; without it, Runtime blocks both Sequential and Batch from entering Build. A migrated older change must pass through the same confirmation and cannot bypass it by editing state.

## Continue a clarification round across sessions

On resume, read the project configuration first, then the numbering already saved in the brief:

```bash
comet native show <change-name>
comet native status <change-name> --details
```

Do not reconstruct questions from chat memory, and do not renumber the current round because the configured mode has changed. First map the user's answers to the saved Q1 and Q2, then compute later questions.
