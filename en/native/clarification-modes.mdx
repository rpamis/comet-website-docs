Native runs a **Shape clarification phase** before Build to turn verbal requirements into well-bounded, verifiable behavior specifications and acceptance criteria, locking in edge cases, failure fallbacks, and scope constraints before coding begins.

The `native.clarification_mode` setting controls questioning cadence and supports `batch` (default) and `sequential`. Regardless of the mode you choose, both produce the same formal artifacts and require your explicit final confirmation before entering Build.

## Separate what to ask from what not to ask

Native does not turn every detail into a multiple-choice question. Instead, it sorts information into three categories (see [Which decisions need your confirmation](/en/native/decision-ownership) for full boundaries):

1. **Investigatable facts**: Current repository state, existing interfaces, tool capabilities, dependency defaults, and runtime environment. The Agent inspects the codebase directly or dispatches parallel read-only investigations without interrupting you.
2. **User decisions**: Choices that materially change outputs, default behavior, failure outcomes, delivery scope, or irreversible effects and cannot be reliably inferred from existing documentation or project rules. Only these are presented to you.
3. **Implementation choices**: Algorithms, internal structure, and code organization that do not affect user-visible outcomes. The Agent decides these on its own.

If you supply a PRD, local file, attachment, or external link as a requirements source, the Agent first inventories the full set of source items under the source-document coverage rules, then asks you about ambiguities, omissions, or unstated constraints. If a material is only provided for troubleshooting, evidence, or implementation reference, it does not trigger full source-document coverage.

## Batch vs. sequential mode

Switch modes in `.comet/config.yaml`:

```yaml
native:
  clarification_mode: batch # Options: batch (default) | sequential
```

| Clarification mode | How questions are asked | Best suited for |
| --- | --- | --- |
| **`batch` (default)** | Asks all independent questions in one round once their prerequisite facts and upstream decisions are settled. | Requirements whose overall direction is clear and decision points are loosely coupled, when you want fewer round trips. |
| **`sequential`** | Asks one high-impact question per round, updates dependencies from your answer, and then derives the next question. | Exploratory requirements where an earlier answer directly reshapes downstream options or eliminates later questions. |

Changing this setting mid-task only affects the next round of questions. Confirmed decisions already recorded in `brief.md` and unanswered `[blocking]` questions remain intact.

## Question ordering and dynamic dependency management

For straightforward requirements, the Agent lists pending items and necessary dependencies directly without forcing a complex node structure. When multiple decisions interact and earlier choices change downstream branches, the Agent maintains a dynamic dependency decision tree in working memory (without creating extra Runtime state files).

A question enters the current askable set only when all three conditions hold:

1. All upstream user decisions it depends on are settled;
2. All codebase facts needed to answer it have been investigated;
3. It does not depend on any other unanswered question in the current round.

While waiting on a codebase investigation, only branches that depend on that fact pause; independent questions and investigations continue normally. After each answer you provide, the Agent immediately recalculates affected downstream branches to avoid asking questions already ruled out by earlier choices.

## Question format and interactive tool fallback

To make trade-offs obvious at a glance, every question turns abstract requirements into concrete "input → output" or "trigger → outcome" cases with three elements: **the decision difference**, **a recommended option with rationale**, and **the practical impact of each option**.

- **Prefer structured questioning components**: When there are two or more clear options and your Agent platform provides a structured questioning tool such as `AskUserQuestion`, the Agent uses it first. Single-select options are strictly mutually exclusive; multi-select is used only when multiple compatible features can be combined. Once the component call succeeds, the Agent waits directly without repeating the questions as plain text.
- **Automatic fallback to numbered text**: For open-ended questions, platforms without a questioning component, component call errors, or `batch` rounds exceeding the component's item limit, the Agent **falls back as a whole batch to numbered text** instead of splitting one round into fragmented prompts to work around component limits.

Batch text questions use stable `Q1`, `Q2` labels (marked single-select, multi-select, or open-ended). If you answer only part of a round, unanswered items keep their original numbers in the next round instead of renumbering:

```markdown
💬 **Q1 | Page behavior when avatar upload fails (single-select)**

When the upload API returns an error, determine how the avatar area should behave.

| Option | Approach | Practical impact |
| --- | --- | --- |
| A | Keep the existing avatar and show an error | Users do not lose their current avatar and can retry right away. |
| B | Clear the avatar preview | Visually more direct, but users must pick a file again. |

💡 **Recommended answer: A (Keep the existing avatar and show an error)**

Rationale: Prevents temporary network hiccups from making users think their existing avatar was deleted.
```

For open-ended questions that lack sufficient facts, the Agent explains what information or format you need to provide rather than inventing a recommended option. For questions with fixed choices—such as Supervisor coordination mode or workspace isolation—the Agent keeps the original option identifiers and complete impact descriptions.

## Answers are written to formal artifacts immediately

Chat history is only for communication; files in the project are the basis for interruption recovery. As soon as you reply, the Agent writes confirmed conclusions into the **Decisions** section of `brief.md`, updates target Specs and acceptance criteria, and removes resolved items. Partially answered or still ambiguous items stay in **Open questions** (an answer only confirms what you explicitly specified).

`sequential` mode records the current pending item:

```markdown
## Open questions

- [blocking] When avatar upload fails, should the existing avatar be kept or cleared?
```

`batch` mode preserves stable question numbers:

```markdown
## Open questions

- [blocking] Q1: When avatar upload fails, should the existing avatar be kept or cleared?
- [blocking] Q2: Can users delete their existing avatar?
```

Even when the open-questions list is empty, clarification does not end automatically—the Agent still checks for missed implicit assumptions, edge cases, and failure branches before initiating final confirmation.

## Final confirmation before Build and re-review on requirement changes

Final confirmation begins once all decisions affecting visible outcomes are settled, implicit assumptions are verified, `brief.md` has no remaining `[blocking]` items, affected directory structures are documented, and acceptance criteria are concrete, verifiable, and non-duplicated.

1. **Submit acceptance criteria**: The Agent extracts acceptance criteria and a summary from the formal documents and submits them to the Runtime, where the CLI assigns stable acceptance IDs (for large requirements, it evaluates splitting into a [Supervisor Change](/en/native/supervisor-change) beforehand).
2. **Present the complete Shape for confirmation**: The Agent presents the full proposal—**goals and scope**, **key decisions**, **itemized acceptance criteria**, and **non-goals**—and waits for your explicit agreement. Final confirmation itself is never written as an ordinary `[blocking]` question.
3. **Advance to Build with guard parameters**: After you explicitly approve in conversation, the Agent automatically runs the confirmation command in the background (carrying state-version and expected-action guard parameters, plus the selected coordination mode for multi-child Supervisors) to advance into Build.

Your initial requirement prompt cannot substitute for this final confirmation. If you add details or overturn a decision at this final step, the Agent updates the documents and requests confirmation again, immediately invalidating the previous proposal.

### Re-confirming after mid-flight requirement changes

If a requirement change sends a task back to Shape from Build, Verify, or archive-ready, the Agent first compares against the last approved proposal and presents a **change summary**:

- Which behaviors were added, removed, or modified;
- Which acceptance criteria are affected;
- Which existing code and checks remain valid, and which steps must be redone.

After reviewing the change summary, you still confirm the **complete current Shape**. If no reliable previous proposal exists for comparison, the Agent states clearly that an item-by-item comparison is unavailable instead of fabricating differences or claiming "everything else is unchanged."

## Resuming clarification after an interruption

If you close the conversation or switch windows mid-clarification, reopen the project and simply continue the task in conversation. Native restores the current clarification mode, recorded decisions, and pending questions with their original numbers from `.comet/config.yaml` and `brief.md`. You do not need to enter commands manually in daily use; if you want to inspect the current documents and status offline in your terminal, run these two read-only commands:

```bash
comet native show <change-name>
comet native status <change-name> --details
```
