---
title: 'Verification and repair'
description: 'Learn how to evaluate every acceptance criterion, reuse check results that still apply, and handle implementation failures and verification blockers.'
---

Verify checks the current implementation against the original request, confirmed `brief.md`, relevant Specs, and all acceptance criteria. It looks for missing requirements and unapproved reductions in scope, and checks that required file locations, sections, and formats match what you agreed to.

## Choose the review session

Verify can run in the current session. The Agent decides whether to request independent review based on the remaining uncertainties and your requirements. If you explicitly require independent review, the Verifier must claim the task in a separate read-only session and submit its own verdict. The report records the review method used.

## Run necessary checks and evaluate each criterion

1. **Read the Builder handoff.** Review the implementation, change scope, checks already run, and known limitations. Use the current candidate as the basis for Verify.
2. **Collect missing evidence.** The Agent runs necessary tests, builds, or static checks with platform tools and records commands, working directories, results, and available log references. If an earlier result still applies to the current code and environment, cite the original execution. Run checks affected by the change or missing evidence. Record checks that were skipped, failed, or have an unknown outcome.
3. **Record a verdict for each criterion.** Mark every acceptance criterion as `passed`, `failed`, or `blocked` and explain the evidence. A passing test command establishes only the behavior it covers. Check the remaining criteria with the evidence each one requires.

For example, if the change affects a message shown after a failed sign-in, an earlier API test can still apply if its conditions are unchanged. The Verifier still needs to check the message the interface displays and cover the other confirmed criteria.

## Act on the result

| Verification outcome | What happens next |
| --- | --- |
| All criteria pass | Read the item-by-item verdicts, check evidence, and known limitations in `verification.md`. Accept the current result to enter Archive. |
| The implementation falls short | If failures are below the limit, return to Build and repair the failed items. Submit the revised implementation and verify every acceptance criterion again. |
| A prerequisite is missing | Identify the specific missing permission, input, or environment requirement. Once it is available, follow the current instructions to continue verification. |
| Requirements or acceptance criteria need to change | Update the Shape proposal and ask you to confirm the affected decisions before proceeding. |

If you explicitly delegated acceptance and archiving on a pass, the Agent can apply that decision when submitting a passing result. Otherwise, the Runtime waits for you to accept the current result. If the verification session is lost or exits unexpectedly, check the original task first and follow [Task progress and interruption recovery](/en/native/continuation-and-checkpoints).

## Decide which results still apply after edits

After a repair, the Agent reviews the actual edits to determine which checks still apply. Formatting or comment changes that leave requirements and behavior intact can retain the original approval and valid evidence. Changes to behavior, check inputs, or the execution environment require updated conclusions where affected. If a check later fails, use the newer result and keep a record of the failure.

Use `verification.md` to review the result. When verification passes, the Runtime generates or updates the report from the submitted results. Editing the report cannot change the verdict. See [Archive and delivery](/en/native/archive-and-delivery) for the archive workflow.
