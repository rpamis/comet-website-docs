---
title: 'Verification and repair'
description: 'Understand how Native runs necessary checks, dispatches an independent Verifier, and repairs failures through a bounded Loop.'
---

Native does not require a fixed TDD or review method, but it does not accept “I am done” as an acceptance result. **The Builder implements, the Runtime executes checks, a fresh read-only Verifier reviews each item, and the Runtime decides whether the change is complete.**

## What Verify actually does

1. The Builder submits a handoff describing the implementation, the relevant brief/Specs, and the candidate to review.
2. Runtime resolves the complete acceptance list and required-check plan, then records the attempt in a short state update.
3. Runtime executes the required checks. A matching completed check for the same candidate is reused instead of run again. Command output streams to local logs, while the report keeps a safe summary.
4. Runtime dispatches a fresh read-only Verifier. The Verifier must return exactly one result for every A1…An item; missing, duplicate, unknown, or Builder-self-reported results are rejected.
5. Runtime moves to `pass`, returns to Build, or waits for a user resolution. The normal Archive path does not run the checks again.

The Verifier cannot use the Builder's context as its own endorsement. Hosts that can provide an independent subagent dispatch a new execution; when only Skill coordination is available, Runtime clearly marks semantic verification as unavailable and requires one user confirmation before Archive.

## Checks and the report

Runtime resolves required checks from the project's formal content; an Agent's prose saying “passed” is not a substitute. Each result records command status, exit code, duration, and a readable summary. Full stdout/stderr stays in local logs; long output is preview-truncated and does not by itself invalidate a valid result.

When an additional check is genuinely needed, the Verifier requests it through `request-checks` in the current attempt. Runtime deduplicates equivalent plans, limits request rounds, and returns the results to the Verifier. The Agent must not fabricate a result or paste a third-party command's output into a pass field.

`verification.md` is a user report generated from `comet-state.yaml`. It contains checks, per-item acceptance results, limitations, and the conclusion. It can be rebuilt; a missing report is never a reason to bypass Verify.

## How failures return to Build

Any failed acceptance item, failed check, incomplete Verifier response, or invalid coverage writes a concrete gap into the next continuation and returns the change to Build. The next round repairs those gaps first, then submits a new Builder handoff and a new Verifier attempt. A stale attempt cannot be turned into a pass by resubmitting the same text.

The Loop counts substantive convergence as progress: unresolved acceptance items strictly shrink, a failed check becomes passing, or missing information is supplied. Rewriting explanations, rerunning the same command, or alternating between failure sets does not extend the Loop indefinitely.

After the Skill-coordinated Verifier passes, Runtime waits for one explicit user decision. The three options are mutually exclusive:

| Decision                   | Result                                                               |
| -------------------------- | -------------------------------------------------------------------- |
| `--accept-result`          | Accept the current Verify result and enter Archive.                  |
| `--revise-implementation` | Keep the confirmed requirements and return to Build.                 |
| `--revise-requirements`    | Return to Shape when the visible goal or acceptance criteria changed; update the formal artifacts and reconfirm. |

Decision commands carry the `--expected-state-version` and `--expected-action` guards issued by the continuation. Expired state or a mismatched action is rejected; starting a new goal cycle invalidates old Archive authorization.

The `--revise-requirements` option is also available when Archive is waiting at `archive-ready`, not only immediately after Verify. It returns the change to Shape, starts a new goal cycle, invalidates the previous verification and Archive authorization, and preserves the change workspace.

## Stagnation and error budgets

`comet-state.yaml` stores `iteration`, `attempt`, `no_progress_count`, `failed_iteration_count`, `execution_failure_count`, and bounded history. An unchanged or regressing unresolved set increases the stagnation count; repeated Runtime execution errors increase the execution count. Once a limit is reached, the state becomes `await-user` or `blocked` with a concrete `resolution_action` instead of consuming more time.

The user may return to Shape when the requirement changed, or explicitly retry a Verifier when the implementation is unchanged and an external blocker has been resolved. An ordinary “try again” does not clear the history or carry an old pass into a new candidate.

## Reliability boundary

Runtime can ensure that the command actually ran, a non-zero exit cannot be treated as a pass, the acceptance list is covered, and matching checks are not needlessly repeated. It cannot decide whether a test is meaningful, nor observe background or IDE writes that the host does not expose. When an independent Verifier is unavailable, the Dashboard and report show the degraded status explicitly instead of presenting it as independent semantic verification.
