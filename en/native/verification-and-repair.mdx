Native does not prescribe TDD or a fixed review method, but verification has deterministic requirements: conclusions must match the current requirements, specifications, and real implementation scope, and an unrun check cannot be reported as passed.

## Implementation scope

At the end of Build, the model submits real project-relative paths. The Runtime content-addresses those artifacts together with the current change contract, creation baseline, and current project snapshot to form an implementation scope and derive stable Acceptance IDs.

A Git project snapshot contains only tracked and non-ignored untracked files and treats each submodule/gitlink as one atomic entry. Non-Git projects use the bounded physical-tree provider. An incomplete current snapshot never turns a missing path into a guessed deletion. When change details exceed the budget, bounded items remain and `scope-detail-overflow` represents the rest with a count and content hash.

The current snapshot reuses the include/exclude policy stored in the baseline manifest when the change was created. This keeps baseline and current comparisons on the same boundary. Editing project configuration during implementation affects future changes only and cannot make current-change differences disappear. You may raise capture budgets without changing scope identity. If an excluded path later becomes a real implementation dependency, update the requirement boundary and establish a baseline that covers the complete scope instead of reusing the old scope.

If the Runtime cannot prove that the scope is complete, it remains in Build and returns a partial-scope hash with unowned items. Add the missing artifacts or remove the unexplained changes first. Proceeding with partial scope requires explicit user acceptance of a concrete gap that the Runtime permits for authorization, the same hash, a reason, and `--confirmed`. `git-selection-changed` requires a retry after the Git index settles and is never authorizable. For `git-enumeration-limit`, first decide whether affected files belong in scope: raise snapshot budgets or clean unrelated project content when they do, or configure an explicit exclude for a future change when they do not. A later current snapshot may use the ordinary partial protocol only when recovery is impossible, the Runtime returns an authorizable scope bound to a count and content hash, and the user understands the unknown-tail risk. In non-Git projects, `physical-selection-changed` requires a stable project tree and `physical-enumeration-limit` requires reducing that tree; neither can bind its unknown tail and neither is authorizable. No integrity failure may be bypassed through edited evidence.

## Verification report

`verification.md` records at least:

- commands actually run and their results;
- skipped checks and reasons;
- known limitations and the overall conclusion;
- a current manual or automated receipt reference, or an honest `skipped_reason`, for every Runtime Acceptance ID.

`comet native receipt manual` records reviewable steps and observations. `receipt automated` runs an explicit check command from the project root and stores its exit status, timeout, worktree identity, and a bounded credential-redacted output summary in a content-addressed receipt. A failed acceptance item may cite a non-passing receipt; Runtime derives repair gaps from that evidence without separate caller-supplied failure classifications.

`comet native check` performs only a bounded read-only text hygiene scan. It does not call Git, a shell, test scripts, or an external Skill, and it does not replace project tests. Runtime runs and binds this required check automatically when a passing conclusion is submitted, so the caller does not provide its receipt.

## Why evidence becomes stale

Verification binds the brief, complete target specifications, implementation scope, revision, report snapshot, built-in required check, and acceptance receipts referenced by the report. Changing any input makes the old evidence stale.

If the contract or project snapshot changes during Verify, status returns a summary-only `next`. Run it to retreat to Build and seal a new scope. Reconfirm only when the brief/spec contract hash also changed. If only the project snapshot or implementation changed, retain the existing approval instead of introducing another confirmation. Never submit a conclusion against the old scope. A changed report, receipt, or other bound fact in Archive uses the same retreat protocol; never reuse the old pass.

## Why repair is bounded

A Verify failure returns to Build. Runtime returns failed or missing acceptance items and failed checks from the validated acceptance matrix. The next iteration addresses those gaps instead of retrying Verify immediately.

The repeated-failure signature contains the current contract, sorted failed or missing Acceptance IDs, and failed check IDs:

- the second recurrence of the same semantic gap warns;
- on the third recurrence without semantic progress, continuation remains Agent-owned while one override remains and requires a concrete new repair hypothesis;
- only fewer gaps, passing checks, or missing evidence restored as current valid evidence count as semantic progress;
- changing files, changing implementation scope, or rewriting an explanation without changing the failure set does not reset stagnation;
- the exact failure signature from `status` and a non-empty hypothesis summary may be used for one override; this step is not delegated to the user;
- one contract accepts at most five Verify failures by default; set `native.max_verify_failures` to an integer of at least one to change the budget.

Repeated-gap stopping and the total failure budget are independent. Only after the override is used or the total failure budget is exhausted does Runtime return one explicit user decision: increase the budget, change the confirmed contract, or stop. Only a user-confirmed contract change starts a new goal cycle; ordinary implementation changes do not clear accumulated failures.

This permits continuous repair without treating code activity as completion progress. When a user decision is required, present the current evidence and those three directions once. The model must not weaken checks, enter Archive early, or invent a pass.
