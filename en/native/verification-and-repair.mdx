---
title: 'Verification evidence and autonomous repair'
description: 'Understand how Native forms an implementation scope, acceptance evidence, stale evidence, and bounded repair.'
---

Native does not prescribe a fixed TDD or review method, but it does have one hard rule: the verification conclusion must correspond to the current requirements and the real implementation, and a check that has not actually been run cannot be written as passed. **The Agent finds and repairs gaps; the Runtime judges whether it is done.**

## Implementation scope

At the end of Build, the model submits the files it actually changed. Based on those artifacts and the current project state, the Runtime confirms exactly which scope this implementation covered (the implementation scope).

This scope is fixed when the change is created — it is the scope circumscribed by `snapshot.include`/`exclude` in the configuration. Changing the configuration during implementation can only affect future new changes; it cannot make the current change's differences disappear into thin air. If you find that an excluded path is in fact an implementation dependency, the correct move is to update the requirement and create a new change with a complete scope, rather than reusing the old scope.

If the scope contains changes that cannot be accounted for, the Runtime stops at Build and tells you what is missing. Fill it in first; if it genuinely cannot be filled in, you must explicitly accept the residual risk before you can continue. But there is a bottom line: an incomplete scope cannot be bypassed by hand-editing the evidence.

## Verification report

A verification report records at least:

- the commands actually run and their results;
- which checks were skipped, and why;
- known limitations and the overall conclusion;
- the evidence for each acceptance item; anything that could not be run is marked honestly, never written as passed.

Use these two commands to record evidence:

- `comet native receipt manual` — records reviewable manual steps and observations;
- `comet native receipt automated` — runs one explicit check command and stores the result as reviewable evidence.

A failed acceptance may also cite a non-passing receipt; the Runtime derives what is still missing from it, so you do not need to submit a separate failure classification.

In addition, when you submit a passing conclusion the Runtime automatically runs one built-in `comet native check` — a read-only text hygiene scan that does not call Git, a shell, or test scripts, does not replace project tests, and is simply a required check bound to a passing conclusion.

## Evidence goes stale

A verification conclusion is not once-and-for-all. It binds to the requirements, the implementation scope, and the project state at that moment — change any of those and the old evidence is void.

There are two sources of change:

- **The requirements or spec changed**: you must be asked to confirm again, because the requirement itself changed.
- **Only the project files changed** (the requirements did not move): keep the existing confirmation. The Runtime retreats to Build, rebuilds the scope, and re-verifies, without bothering you further.

So never submit a conclusion against the old scope. After entering Archive, if the report or evidence changes again, the same applies: start over, do not reuse the old pass.

## Bounds on repair

A Verify failure returns to Build. The Runtime hands the unpassed acceptance items to the next round so you close those gaps first, rather than retrying directly.

But repair cannot loop forever. The bar for "progress" is substantive: fewer gaps, a check turning green, or missing evidence restored count as progress; merely changing files or rewriting explanations while the failure set stays unchanged does not. The rules are roughly:

- the second occurrence of the same issue warns;
- the third occurrence without progress gives one last chance and requires you to propose a new repair hypothesis;
- the same contract accepts at most five Verify failures by default, adjustable in the configuration with `native.max_verify_failures`.

When the count is spent, the Runtime stops and hands it to you, laying out the current evidence and three directions: raise the limit, change the confirmed requirement, or stop. Only a requirement change you have confirmed resets the count; ordinary implementation changes do not.

A strong model may repair for several rounds in a row, but the basis for judging completion is whether the gaps are shrinking, not how much code changed.
