---
title: 'How to choose between Native and Classic'
description: 'Compare Native and Classic on completion verdicts, execution overhead, phase trade-offs, and use cases.'
---

Native and Classic are not light and heavy tiers, nor two versions of one workflow. Native targets strong models that can plan, implement, and repair autonomously; Classic targets tasks that benefit from finer phases and explicit methods.

## The one-line distinction

- **Native**: the model chooses planning, implementation, testing, and review methods; Runtime enforces Shape, necessary checks, a fresh Verifier, the bounded Loop, and safe Archive. Portable state and user documents can recover across devices.
- **Classic**: OpenSpec and Superpowers provide open → design → build → verify → archive governance, explicitly organizing design, plans, TDD, debugging, and review.

## Who owns the completion verdict

Native does not trust a Builder's “done” claim. Build submits a handoff; Runtime runs necessary checks and dispatches a fresh read-only Verifier over every acceptance item. Failure returns to Build, and limits return control to the user. Classic advances through its phase Guards and formal task/report artifacts.

## Execution overhead

Native does not scan or fingerprint the whole project during Verify, and the normal Archive path does not rerun checks. Completed matching checks are reused for the same candidate, while long command output streams to local logs. Classic's advantage is stronger method guidance, at the cost of more phase context and process artifacts.

## Artifacts and recovery

A Native change's user-facing artifacts are the brief, complete Specs, `comet-state.yaml`, and `verification.md`. Local execution state, logs, locks, and transactions live under `.comet/runtime/native/`. On another device, Runtime recovers from portable YAML and rebuilds a missing local overlay.

Classic continues to use its `.comet.yaml`, OpenSpec directories, Superpowers plans, and Classic Runtime. The workflows do not share changes, Guards, or directories.

## Recommendation

| Scenario                                                                | Recommended workflow                                                          |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| A strong model can investigate, implement, and judge proportional tests | Native                                                                        |
| The task needs step-by-step guidance, TDD, plans, and review            | Classic                                                                       |
| One project has both types of work                                      | `comet init --workflow both`, then choose the default in `.comet/config.yaml` |
