title: 'Native artifacts and state'
description: 'Locate requirements, Specs, progress, and verification reports for a Native change, and see which files to sync and which Comet maintains.'
---

Native stores requirements, target Specs, state files, and verification reports in the project. The local Run keeps the current stage, approvals, and execution results. To understand a change, read `brief.md` for the agreement, `verification.md` for the acceptance evidence, and the CLI response for available actions.

## Locate the change directory

This example uses `login-error-message`. The default artifact root is `docs`. You can set `native.artifact_root` in `.comet/config.yaml`. Use the paths returned by `show` for your project.

```text
docs/comet/
  changes/login-error-message/
    brief.md
    specs/authentication/spec.md
    specs/authentication/delta.yaml
    comet-state.yaml
    verification.md
  specs/authentication/spec.md
  archive/
```

Here, `delta.yaml` applies to a change associated with an existing capability. `verification.md` might not exist until verification passes. A Supervisor Change can also have `children.yaml`.

```bash
comet native show login-error-message --json
```

Find the change directory, brief, Specs, state file, and report in the returned `artifacts` object. If a path differs from what you expect, check the current workspace and project configuration first. For archived artifacts, use the directory returned by Archive.

## Maintain requirements and target Specs in Shape

<span id="briefmd" />

### `brief.md`

`brief.md` records goals, scope, non-goals, constraints, user decisions that affect delivery, and the basis for acceptance. Describe which modules and key files the change creates, modifies, or deletes, along with anything deliberately excluded. Use a directory tree or a list.

For example, the `login-error-message` brief can limit the change to sign-in error messages and preserve the server response codes and rate-limiting rules. Write separate acceptance criteria for incorrect credentials and rate-limited requests. Mark unresolved user decisions with `[blocking]`, update the affected material when the user makes a decision, and then ask for confirmation of the complete Shape.

### Target Spec and Delta

The `specs/<capability>/spec.md` inside the change describes the capability's complete behavior after Archive. State what this change adds or updates and preserve the rules that still apply.

- For a new capability, the Agent writes the complete target Spec.
- For an associated existing capability, the Agent maintains the changes in `delta.yaml` using stable requirement IDs. The Runtime generates the complete target Spec from the current project Spec for Shape review and Verify.
- To remove an existing capability, use the capability removal operation in the [Native command overview](/en/scripts/comet-native). Deleting a file cannot record that decision.

In the sign-in example, the project's `specs/authentication/spec.md` contains the current rules. The target Spec inside the change describes the proposed message behavior. The Runtime applies the approved changes to the project Specs during Archive.

### `children.yaml`

A Supervisor Change uses this file to record child tasks, their dependencies, and the acceptance criteria each child covers. Children reference the original criteria by ID. The parent change retains the complete acceptance scope. See [Supervisor Change](/en/native/supervisor-change) for parallel execution.

## Read the state and reports Comet maintains

| File or record | Location | Purpose |
| --- | --- | --- |
| `comet-state.yaml` | The change directory. | Shows stage and acceptance state. Saves checkpoints at key boundaries so Comet can restore the original Run. |
| `verification.md` | The change directory, including after archiving. | Shows individual verdicts, actual checks, the review method, and known limitations. |
| `.comet/current-change.json` | In the current project's `.comet/` directory. | Records the selection used by commands without a change name and by Hook routing. Update it with `comet native select`. |
| Local Run and execution records | In `~/.comet/workspaces/<workspace-id>/runtime/` by default. | Stores progress, actions, decisions, and local records for transactions. The main workspace and each Git worktree have separate storage. |

Use `comet native status` to check progress, and use the returned operation to submit decisions and results. Editing the state file or report cannot advance a Run. See [Task progress and interruption recovery](/en/native/continuation-and-checkpoints) for missing or damaged records.

## Decide what to sync with the project

Review the implementation and formal artifacts together. Deliver the archived change with the updated project Specs. Keep the state file and verification report with the change according to project rules so collaborators can review decisions and evidence.

To continue the same task on another device, sync the actual code, formal artifacts, `comet-state.yaml` with a valid checkpoint, referenced artifacts, and project configuration. A checkpoint saves recorded progress. Check unsynced work, independent child worktrees, and background tasks on the original platform separately.

Each workspace maintains its selection and local Runtime directory. You do not need to commit the local Run directory to Git. For active tasks, keep the local records so you can reconcile original results and unfinished transactions.
