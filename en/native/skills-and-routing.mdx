One entry, one Skill, and across sessions it picks up from disk. Native does not split the workflow into multiple Skills, nor does it pass context that can be lost between phases — a single `/comet-native` reads disk state and continues from the current phase. It also does not depend on external Skills like OpenSpec or Superpowers.

## User entry point

The most common entry is `/comet`. It only reads `.comet/config.yaml` and forwards to the matching workflow per `default_workflow`:

```yaml
schema: comet.project.v1
default_workflow: native
workflows:
  - native
  - classic
```

To bypass routing and enter Native directly, or to diagnose "why did it not enter Native", use `/comet-native`. It is invoked by the host Skill, not a shell command; the underlying commands are uniformly `comet native ...`.

<Note>
  Comet does not guess which mode to use from task size, prompt wording, or model name. To change
  the default, change the configuration; selecting another entry does not migrate existing changes.
</Note>

## Why one Skill is enough

Native's four phases (Shape → Build → Verify → Archive) share the same `/comet-native`, and unlike Classic do not need to hand off between multiple phase Skills. On every entry, the Skill rereads the configuration, selection, `comet-state.yaml`, brief, target spec, and current repository state, then continues from the current phase.

The direct benefits:

- **No context-handoff loss**. Between phases there is no need to generate design context, compression projections, or handoff documents to carry state — every fact is written in files, and the Skill just rereads them.
- **Progress survives across sessions**. After an interruption, re-entering the Skill restores from disk continuation to the exact position before the break, with no dependence on chat memory.
- **Phase transitions are controlled by the Runtime**. Phases are linked by a structured `continuation`: pass and continue, hit something that needs your decision and it waits for you, hit a blocker and it follows the recovery flow.

For each of the four phases' responsibilities and required outcomes, see [Native workflow](/en/concepts/native-workflow#four-phase-workflow).

## Write ownership

Comet records which change is currently being written in `.comet/current-change.json`, ensuring one write lands on exactly one requirement and reducing wrong-requirement writes and repeated blocking. `status` and `show` are read-only and never silently change this pointer — so inspecting state will not accidentally bind subsequent writes to another requirement.

If the selected change has already been deleted or archived, Comet lets you re-select one from the currently active changes:

```bash
comet native select <change-name>
```
