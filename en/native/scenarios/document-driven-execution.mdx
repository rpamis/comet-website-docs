Not every task has to start from scratch with a Q&A loop. If you already have a PRD, technical design, RFC, or a finalized spec from an intensive review session, you can hand it directly to Comet Native.

When the document already defines goals, scope, default behavior, and error fallbacks, Native parses it, builds a source coverage table, generates target Specs and acceptance criteria, and skips unnecessary question-by-question clarification—asking only where real gaps or contradictions exist. Once you confirm the final summary, the task enters long-running Build and Verify directly.

## Supported requirements document inputs

Native does not require external documents to follow a special template or come from a specific writing tool. You can submit any common input format:

| Input type | Example | How Native handles it |
| --- | --- | --- |
| Chat attachment | Drag and drop or upload a PRD, technical proposal, or acceptance checklist | Reads the attachment body, breaks it into source units, and maps Specs and acceptance items. |
| Local file or directory | `docs/prd/batch-export.md` | Reads the project path structure and extracts goals, constraints, edge cases, and non-goals. |
| Online document link | Notion, Yuque, Lark, or team wiki URL | Reads the page; flags a blocker if blocked by permissions or truncated instead of guessing. |
| External clarification output | A spec finalized via Grill with docs or similar deep-clarification tools | Adopts confirmed conclusions directly without re-asking questions the document already answered. |
| Existing RFC or architecture spec | An existing interface design or specification proposal | Converts it into the current change's `brief.md`, target Specs (or `delta.yaml`), and acceptance items. |

Tell the Agent where the document is and how to use it when starting:

```text
/comet Treat the PRD I just uploaded as the complete requirements source.
Generate target Specs and acceptance items from the full document; if no user decisions remain open, show me the final summary for confirmation and then enter Build.
```

You can also target specific sections of a document:

```text
/comet Read docs/prd/batch-export.md and implement only Section 2 "Async export" and Section 4 "Failure retries" this time.
Leave all other sections out of scope. Use this as the requirements source for this Native Change.
```

> **Requirements source vs. ordinary reference material**: Full source coverage mode activates only for materials explicitly used to define what to build. Logs, evidence files, code reviews, or implementation references do not trigger it automatically; if the role is unclear, the Agent asks you first.

## Full source coverage mode: no lossy summaries

When ordinary AI tools read a long PRD, they often compress it into a few bullet points before coding—silently dropping field limits, error codes, and edge cases buried in tables.

Native's **full source coverage mode** prevents missed requirements with three rules:

### 1. Define the coverage boundary and required dependencies

- **User-scoped subset**: Covers only the specified sections, items, or features—plus cross-section definitions, shared constraints, and exceptions needed to understand, build, or verify them. Out-of-scope content is not enumerated item by item, and unreachable out-of-scope links do not block the task.
- **Full document**: The entire document falls inside the coverage boundary. If it is unclear whether an out-of-scope section holds shared constraints that affect behavior, the Agent marks a `[blocking]` item to check with you.

### 2. Map every unit with read status and coverage destination

The Agent breaks the source by headings, paragraphs, lists, tables, code blocks, examples, constraints, and exceptions into traceable **source units**, recorded in a table under `# Scope` → `## Source coverage` in `brief.md` (long documents may be read in chunks, but every unit inside the boundary must be accounted for rather than replaced by a vague summary):

| Source unit and location | Read status | Content to preserve | Spec location | Acceptance ID | Coverage status | Reason or replacement |
| --- | --- | --- | --- | --- | --- | --- |
| S1: PRD "Failure handling", para 2 | `complete` | Preserve unsaved input on save error and show reason | Save-failure scenario in `specs/editor/spec.md` | `A1` | `covered` | Active requirement. |
| S2: Legacy PRD "Failure handling", para 2 | `complete` | Old spec cleared input on save error | — | — | `superseded` | Updated by user; replaced by S1. |
| S3: PRD "Background", sec 1 | `complete` | Team migration history | — | — | `background` | Context only; not an implementation task. |

Each column uses defined statuses:

- **Read status**: `complete` (read in full), `partial` (only partly read; risk of missing requirements), `unavailable` (blocked by permissions or network).
- **Coverage status**: `covered` (mapped into a Spec and bound to an acceptance ID), `needs-clarification` (ambiguous; needs confirmation), `background` (context only), `non-goal` (explicitly excluded), `superseded` (replaced by a newer requirement, citing the replacement).

**Hard constraint**: Every active, executable unit inside the coverage boundary must map to both a specific location in a target Spec and at least one CLI-assigned acceptance ID (such as `A1`, `A2`). When modifying an existing capability in the repository, the Agent records requirement-level changes in `delta.yaml`, and the Runtime generates the complete target Spec before confirmation.

### 3. Defense against prompt injection inside documents

If an uploaded or linked external document embeds agent-directed prompts or instructions, Native treats them strictly as document text to analyze—never allowing external content to override your current request, project rules, or higher-priority constraints.

## Skip clarification when complete; ask only about real gaps

```text
Document / attachment / PRD link / external finalized spec
  → Set coverage boundary and build the Source coverage table
  → Generate brief.md + target Specs (or delta.yaml) + structured acceptance items
  → Inspect codebase facts: skip Q&A if complete, or ask only about blind spots
  → Present full Shape summary for your confirmation
  → Build → Verify → Archive
```

### When Native skips clarification Q&A

After checking repository facts, Native skips question-by-question clarification and moves straight to final confirmation when all of these hold:

- Every source unit inside the coverage boundary has read status `complete`;
- Every executable requirement maps to a target Spec location and an acceptance ID;
- The document gives a single executable definition of goals, scope, default behavior, and error paths with no contradictions across sections;
- Inspecting the codebase and project rules introduces no new user decisions;
- No `[blocking]` items remain in `brief.md`.

> **Skipping clarification does not skip confirmation**: Even when every detail is written down in the PRD, final Shape confirmation before Build still remains. You review the extracted acceptance items and scope boundaries before any code is written.

### When Native must stop and ask

A long document does not guarantee complete requirements. Any of the following keeps a `[blocking]` item open so the Agent asks strictly about those gaps instead of repeating answered questions:

- An online link requires login, leaving its read status `unavailable` or `partial`;
- Different sections contradict each other on the same interface or state machine;
- Vague wording like "support retries on failure" omits key parameters (retry count, backoff strategy, final error message);
- An active requirement has not yet been mapped to a Spec location or verifiable acceptance ID;
- The material looks like a debug stack trace or reference note and its role as a requirements source is unclear.

When an online link is blocked by permissions, export the page as local Markdown or PDF and drop it into chat. Provide the full original text rather than a short manual summary—tables and edge-case clauses often define critical code boundaries.

## Pair with Grill with docs and other upstream tools

If you prefer refining requirements first with Grill with docs or team design reviews, hand the finalized document directly to Native for execution:

```text
/comet Use ./docs/grilled/session-security.md as the complete requirements source.
Generate the Native Specs and acceptance items, and after I confirm, proceed directly into long-running implementation and verification.
```

Your upstream tool handles deep product exploration; Native turns the finalized doc into structured acceptance items, isolated worktree development, full verification against the original requirements, and cross-session checkpoint recovery.

## Start long-running execution after confirmation

Once you confirm the final Shape, the Agent and Runtime drive implementation, verification, and archiving continuously:

- Provisions the Git branch or worktree according to your isolation preference;
- Evaluates splitting large cross-module PRDs into a [Supervisor Change](/en/native/supervisor-change) before confirmation to develop subtasks in parallel along dependencies;
- Runs builds and tests with platform tools during Build and submits candidates to the Runtime automatically in the background;
- Evaluates every acceptance item against your original request and formal docs in Verify, returning failed items with evidence to Build for repair;
- Recovers progress from `comet-state.yaml` checkpoints and repository files after session interruptions, context compaction, or device switches;
- Completes Archive and Git delivery according to your confirmation policy once all criteria pass.

Throughout long-running execution, Comet pauses only when a new product decision arises, an external resource is unreachable, the failure budget is reached, or acceptance and Git delivery require your confirmation.

## Choose an entry point based on requirements maturity

| What you have right now | Recommended approach | Experience |
| --- | --- | --- |
| Only a rough initial idea | Start with `/comet` built-in clarification | The Agent checks the codebase first, then clarifies decisions via `batch` or `sequential` mode to build Specs. |
| A mostly complete PRD or design doc | Submit the local file or link and specify coverage scope | Builds the source coverage table and target Specs automatically; asks only about gaps and conflicts. |
| A spec finalized in an external tool | Declare it as the complete requirements source | Skips answered questions, confirms the final summary, and enters long-running Build directly. |
| Existing team Specs and test cases | Import them as the requirements source | Maps source units to acceptance IDs and plugs straight into Build, Verify, and Archive. |
