## Why the parent task had to hold the final gate

The refactor spanned query planning, SQLite full-text indexing, knowledge-unit data models, plugin events, CLI commands, Dashboard frontend views, and evaluation scripts. Although each layer could be built in stages, the finished system had to satisfy five cross-cutting guarantees together:

1. **Retrieval and fallback**: Local Provider defaults to SQLite FTS5 + ripgrep hybrid recall and falls back cleanly to plain-text search when FTS5 is unavailable;
2. **Strict isolation from Personal Memory**: Project Knowledge and Personal Memory maintain separate storage, ownership, and token budgets;
3. **Verifiable provenance**: Every extracted knowledge unit links to concrete file sources—never fabricated and never replacing direct code verification;
4. **Failure isolation**: Index errors, unreadable files, or adapter failures must never block normal development workflows;
5. **End-to-end consistency**: CLI, Dashboard, context injection, Retrieval Eval, and Agent A/B tests share the exact same capability boundary.

Module-level unit tests alone could not prove these five constraints. All subtasks had to merge into the integration branch first so the parent could verify the entire system end to end.

## Splitting into 3 feature subtasks along real data dependencies

In `children.yaml` (`comet.native.children.v2` format), the plan was split along data dependencies into three sequential feature subtasks:

| Subtask name | Prerequisite | Deliverables | Independent commit |
| --- | --- | --- | --- |
| `project-knowledge-hybrid-retrieval` | None | Query planning, SQLite chunk indexing, hybrid recall pipeline, index lifecycle management, and Retrieval Eval | `d42226fb` |
| `project-knowledge-units` | `project-knowledge-hybrid-retrieval` | Knowledge-unit data model, rule-based fact extraction, source verification, and one-hop relation graph | `efe007c9` |
| `project-knowledge-learning-management` | `project-knowledge-units` | Post-change controlled learning flow, plugin event hooks, explicit sharing, CLI management, Dashboard views, and Agent A/B eval | `cca74993` |

The dependency chain was:

```text
project-knowledge-hybrid-retrieval (hybrid retrieval foundation)
  → project-knowledge-units (knowledge-unit model & extraction)
    → project-knowledge-learning-management (learning flow, CLI & Dashboard)
```

One practical lesson from this case: **Supervisor Change is not only for embarrassingly parallel work—it is equally effective for layered refactors with strict upstream/downstream dependencies.** The Runtime moves a downstream child into the ready queue only after its upstream prerequisite passes child verification and merges into the integration branch, ensuring downstream code builds on a verified baseline instead of shifting interfaces.

## Isolated worktrees and serial merges into the integration branch

Each of the three feature subtasks was implemented and verified in its own Git worktree without touching the target main branch. Once verified, the Runtime merged them serially into the Supervisor integration branch, leaving three clean integration commits:

| Integration commit | What merged |
| --- | --- |
| `6a230657` | Merged `project-knowledge-hybrid-retrieval`, adding 19 core files for SQLite indexing, CLI scaffolding, and retrieval eval. |
| `576f4c25` | Merged `project-knowledge-units`, adding the knowledge-unit model, extraction pipeline, and unit tests. |
| `be58f9cc` | Merged `project-knowledge-learning-management`, wiring the learning flow, management commands, Dashboard UI, and Agent A/B eval. |

Keeping each child's implementation commit distinct from its integration merge commit preserves full traceability: the Runtime knows exactly which candidate passed local verification, whether the integration baseline satisfies downstream dependencies, and how to reject stale or duplicate callbacks.

## Parent final Verify surfaced two rounds of cross-module gaps

After all three feature subtasks merged, the change did not jump straight to Archive—it entered parent global Verify. The archived `verification.md` records two rounds of real cross-module defects:

| Cycle | Verify verdict | Cross-module issues uncovered |
| --- | --- | --- |
| Cycle 2 | `failed` | Several key requirements from upfront design research were not completely wired into the codebase. |
| Cycle 3 | `failed` | Source-validation boundaries, multi-worktree isolation, context activation conditions, incremental build overhead, and end-to-end eval coverage remained incomplete. |

Because these gaps spanned all three modules, single-module unit tests missed them. Unraveling the three already-integrated subtasks to patch them would have broken verified boundaries and blurred the scope of the new fixes. Instead, the Runtime preserved the integration branch and returned the parent to Shape to tighten acceptance criteria and update the subtask plan.

## Appending a repair subtask to close the gaps cleanly

In the final `children.yaml`, the parent kept the first three subtasks closed and appended a fourth dedicated closure subtask:

```yaml
- name: project-knowledge-closure
  depends_on: [project-knowledge-learning-management]
  covers: [A4, A8, A10, A15, A19, A20, A27, A29, A30, A31]
```

`project-knowledge-closure` targeted the exact 10 acceptance gaps surfaced by parent Verify (source boundaries, targeted incremental refreshes, activation conditions, multi-worktree isolation, and end-to-end evals). In commit `3cd0c25b`, it closed the edge cases across knowledge-unit parsing, learning flows, plugin integration, file persistence, and two eval scripts while preserving all three prior integration commits untouched.

## Full 49-item final acceptance and separating unrelated test noise

In cycle 4, Verifier attempt 2 passed completely. `verification.md` recorded the full evidence:

- **All 49 end-to-end acceptance criteria marked `passed`**;
- Child verifications, serial parent integrations, and the full parent check suite all completed;
- Focused tests, Native framework tests, TypeScript typecheck, and production build all passed;
- All 3 high-risk findings flagged by independent code review were resolved, with zero remaining critical blockers.

One realistic engineering detail stands out: during the full-repo test run, a pre-existing baseline test unrelated to the knowledge engine (`/comet` Skill length limit) raised a warning. Verify recorded that external pre-existing issue transparently without misclassifying it as a defect of this feature or letting unrelated noise obscure the verified evidence for all 49 core criteria.

## Unified Archive and a single clean merge to the target branch

Once parent final verification passed, the Runtime produced archive commit `de780ce2`, and commit `58b6dfb2` merged `comet/agent-project-knowledge-engine` into `040rc1`. The target branch saw one complete, fully audited merge:

```text
3 feature subtasks (each built & verified in its own worktree)
  → 3 serial merges into the parent integration branch
  → 2 rounds of parent global Verify exposing cross-module gaps
  → 1 appended repair subtask (project-knowledge-closure) closing the gaps
  → All 49 acceptance criteria passed
  → Unified Archive and single merge into 040rc1
```

## Takeaways: when to choose Supervisor Change

| Mechanism | Practical effect in this case |
| --- | --- |
| Dependency-driven splitting & scheduling | Downstream subtasks started only after upstream code merged into the integration branch, avoiding rework against shifting APIs. |
| Dedicated worktree isolation | Every subtask built and tested in isolation without touching the target branch; the Runtime handled all merges. |
| Parent full-suite final acceptance | Passing module unit tests did not equal done; the parent audited all 49 end-to-end criteria after integration. |
| Appendable repair subtasks | Cross-module gaps discovered in global Verify were closed via a named repair child without rewriting integration history. |

Deciding whether to use Supervisor Change is not just about opening multiple windows to save time—it comes down to three questions: **are module dependencies clear, can each slice be verified in isolation, and do you need a single unified final acceptance gate over the whole goal?**
