---
title: 'Recovery and troubleshooting'
description: 'Recover Native from disk facts, and handle cross-device discovery, unfinished transitions, root moves, Archive, locks, and evidence problems.'
---

On an interruption or error, run read-only diagnostics first, then recover with the specific action the Runtime returns. Native's recovery basis is project configuration, formal artifacts, and Runtime state — all disk facts, not chat history. Hard rule: do not hand-edit phase, hash, journal, or selection to bypass a check.

## Standard diagnostic sequence

```bash
comet status
comet native status
comet native show <change-name>
comet native status <change-name> --details
comet native doctor <change-name>
```

Work through them in this order:

1. Whether the enabled workflow, `native.artifact_root`, and `native.clarification_mode` in `.comet/config.yaml` are correct;
2. Whether `comet native status` can see the target change;
3. Whether `.comet/current-change.json` has selected the correct workflow/change;
4. The phase, findings, checkpoint, acceptance page, and continuation returned by `status --details`;
5. Whether doctor reports an unfinished transaction, a stale lock, a workspace identity problem, or an evidence cleanup issue.

When findings are truncated, handle the returned items first, then read the details again. When `acceptancePage.nextCursor` is non-null, page through them with `--acceptance-cursor`; do not treat acceptance items outside the current page as nonexistent.

## A change is not found on another device

Native discovers changes only under the configured artifact root. If you synced `docs/comet/changes/...` but the other device's `.comet/config.yaml` is missing, still points to `.`, or enables another default workflow, `resume-probe` correctly returns "no resumable change." A change's own `comet-state.yaml` does not select the project root in reverse.

To recover:

1. Confirm the actual synced directory, such as `docs/comet/changes/<name>`;
2. On the target device, restore the matching project configuration and managed assets via `comet init --workflow native --root docs`, or restore a trusted `.comet/config.yaml`;
3. Run `comet native status` and `show`;
4. Once the target is unambiguous, run `comet native select <change-name>`;
5. Continue from `/comet` or `/comet-native`.

Do not create a second change for the same requirement, and do not copy artifacts into another root to manufacture two writable states.

## Unfinished transition

An ordinary phase transition first writes `runtime/transition.json`, then updates Run state, `comet-state.yaml`, trajectory, and checkpoint. After an interruption, status and doctor report recovery required.

An ordinary transition supports continuation only:

```bash
comet native doctor <change-name> --repair --strategy continue
```

When the journal is malformed or the two ends of state cannot be proven consistent, the Runtime preserves the files and stops. Back up the scene and inspect the error first; do not stitch state together by hand.

## Interrupted Archive or root move

Archive and artifact root move are multi-step transactions. Doctor reports whether the current journal stage supports `continue` or `rollback`:

```bash
comet native doctor <change-name> --repair --strategy continue
comet native doctor <change-name> --repair --strategy rollback
```

After Archive writes its final completion marker, it has crossed the irreversible boundary and can only continue to wrap up. A root move continues or rolls back only when the identities and hashes of the source, staging, destination, and quarantine can all be proven; when the two trees differ, neither side is deleted arbitrarily.

If `native.pending_root_move` appears in `.comet/config.yaml`, run doctor first. Do not delete the field or move directories directly.

## Baseline or verification evidence problems

| Symptom                                       | Correct response                                                                                                                              |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `baseline-snapshot-missing` / `incomplete`    | Restore the creation-time baseline from a trusted backup, or create a new change after preserving requirements and implementation facts; do not rebuild history from current files |
| implementation scope stale                    | Follow the controlled `next` returned by status to retreat to Build, generate a new scope, and verify again                                    |
| verification/report/receipt stale             | Do not reuse the old pass; fall back to Build or Verify and form new evidence bound to the current contract/scope                              |
| canonical spec hash conflict                  | Reread the latest spec, run `spec rebase`, then repeat Build and Verify                                                                       |
| repair hard stop                              | Preserve the failure scene and let the user decide scope, constraints, or whether to stop; do not weaken checks                               |

## Locks and evidence retention

Ordinary `new`, `next`, `archive`, and `root move` do not automatically take over a lock that merely looks timed out. Only an explicit `doctor --repair` takes one over when the local owner no longer exists, the lock identity is unchanged, and there is no conflicting transaction. Active locks and locks whose source cannot be proven stay untouched.

Evidence retention only reports candidates by default. An explicit repair cleans up only derived evidence in active changes that is at least 30 days old, lies outside the latest 32 files of each evidence kind, and is proven unreferenced through the dependency closure; archived evidence, current references, unknown files, and transactions under recovery are not cleaned up.

## Save a snapshot before state changes

If an audit or handoff requires keeping the Runtime's response from before a transition, use machine-readable mode on the very first call before the state changes, and save stdout directly to the destination file:

```bash
comet native status <change-name> --details --json > native-before-transition.json
```

After confirming the file is complete, do not reconstruct or overwrite it after the transition. The snapshot only proves the state Runtime actually returned when it was generated; it does not represent later state.
