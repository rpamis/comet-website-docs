---
title: "Continuous Advancement and Stable Recovery Point"
description: "Understand how Native advances its work through continuation and resumes interrupted tasks based on the stable boundaries in comet-state.yaml. "
---

Native saves "Current Progress" and "Next Action" in a file. Each time the Agent completes a Runtime action, it reads the latest `continuation` and continues with implementation, acceptance, or archiving. Even if the conversation is interrupted, the Agent is changed, or the native Runtime is lost, the process can return to the most recent trusted state.

In this article, the "recovery point" refers to the stable workflow boundary recorded by `comet-state.yaml`. RC1 no longer provides the publicly available `comet native checkpoint` command, nor does it require you to manually create checkpoint files.

## continuation decides the next step

Commands such as `comet native new`, `status`, `next`, `archive` and `doctor` will all return `continuation.v2`. It simultaneously describes the process status, Agent actions and the information that users need to know.

|Field|Function|Usage method|
| --- | --- | --- |
| `disposition` |Indicate that it should continue, wait for the user, handle the block or end at present|First, determine whether the process can be advanced automatically|
| `action` |Specify the current action, such as confirming Shape, submitting Builder handoff, initiating Verifier or archiving|Only perform this one action|
| `commandArgs` |The complete command parameters generated by the Runtime|Keep the state protection parameters as they are and only fill in the placeholder values|
| `commandAlternatives` |Commands corresponding to multiple mutually exclusive user decisions|After the user makes a decision, they only select one of them|
| `inputOptions` |Describe the fields required by the command and provide a JSON template|Only fill in the content disclosed in the template|
| `runnerAction` |The Agent should submit the implementation handover, start the Verifier, wait for the result or retry|Used to coordinate the Builder and Verifier|
| `userCommunication` |Explain whether it is currently necessary to report to the user and wait for a reply|When `required: true`, pause the propulsion|

There are four possible outcomes for `disposition`:

|Result|Meaning|Subsequent processing|
| --- | --- | --- |
| `continue` |The next step has been made clear.|Execute `action`, `commandArgs` or `runnerAction`|
| `await-user` |Users need to confirm, select or supplement external information|Paraphrase the instructions given by the Runtime and wait for a reply|
| `blocked` |The workspace, status, concurrent relationships, or execution budget prevent the continuation|Preserve the scene and handle it according to the recovery action or the result of `doctor`|
| `done` |change has been archived|The process ends after checking the final results of the workspace|

`continue` does not necessarily correspond to a Shell command. After entering Build, `runnerAction` may require the Builder to complete the implementation first. After entering Verify, it may request to start a new read-only Verifier. The Agent should read these fields simultaneously and not just look at `commandArgs`.

## How can Native be continuously advanced

The main process of a regular change is as follows:

```text
Confirm Shape
The Builder has completed the implementation and read-only code review
→ Submit Builder handoff
The Runtime performs necessary checks
The new read-only Verifier checks each item one by one
After passing, enter the Archive
Complete the archiving and wrap up the workspace
```

When the Verifier discovers an implementation gap, the Runtime returns the Build and writes the unresolved acceptance items to the next step. When the requirements or acceptance criteria change, the Runtime returns the Shape to start a new target cycle. When an independent acceptance task lacks external information, fails to execute consecutively, or reaches the Loop budget, the process enters `await-user` or `blocked`.

For Verifiers coordinated by Skill but whose independent identities cannot be confirmed by Runtime, the passing results still need to be explicitly accepted by the user. At this point, `commandAlternatives` will respectively provide:

- Accept the current results and prepare for archiving;
- Retain the requirements and go back to Build to modify the implementation.
- Modify the requirements or acceptance criteria and return to Shape.

These three decisions are mutually exclusive. The Agent only executes commands that are consistent with the user's selection.

## Where is the stable recovery point saved

The portable state of an active change is saved in the change directory:

- `brief.md`: Objectives, scope, user decisions and acceptance requirements;
- `specs/<capability>/spec.md`: The complete target behavior after archiving;
- `comet-state.yaml`: Stage, status version, acceptance result, Loop progress, Builder handoff, blocking cause, limited history and Next step;
- `verification.md`: User-readable acceptance report generated by Runtime.

Among them, `comet-state.yaml` represents the authoritative status of the recovery process. `verification.md` is used for reading and can be rebuilt based on YAML when it is missing or the version is outdated.

The execution information of this machine is saved in `.comet/runtime/native/`

```text
.comet/runtime/native/
├── changes/<change-name>/state.json
├── logs/
├── locks/
└── transactions/
```

These files record the checks, logs, locks and short-term transactions that are running on this machine. They can be cleaned up or rebuilt, not used as the basis for cross-device synchronization, nor can they overwrite updated versions of `comet-state.yaml`.

## How to recover at different stages

The Runtime will determine the recovery location based on the stable state and the local execution state.

|Stable boundary|Recovery behavior|
| --- | --- |
| Shape |Maintain Shape, continue clarification or perform unfinished confirmations|
| Build |Retain the confirmed requirements and the current implementation, and continue the Builder work or submit handoff|
|Verify `verify-ready`|Reuse the still valid candidate and check information, re-run the necessary checks and start the new Verifier|
|Verify is waiting for Verifier|When the original task has been lost, start a new attempt from the stable Verify boundary|
|Archive's `archive-ready`|When the local Runtime is lost or the device is changed, first go back to Verify and re-verify the implementation after synchronization|
| `await-user` / `blocked` |Retain the original blockage cause, handling responsibility and permitted actions|
| `done` |Display in archived status and complete deterministic directory or workspace cleaning when necessary|

The recovery operation itself does not increase the number of failed rounds or the stop count. When a new Verifier is actually started, `attempt` will increase.

## How does Runtime handle local state exceptions

Each local `state.json` is associated with change and `state_version`. When the Runtime reads it, the following situations will be distinguished:

- ** Status Matching ** : Continue from the current stable boundary;
- ** Missing, invalid or outdated file ** : Rebuild the local execution status based on `comet-state.yaml`;
- ** Check Execution Interrupt ** : Mark a running check as an interrupt; Safely repeatable checks can be re-executed.
- ** Non-repeatable check interrupt ** : Return to Build and request Builder to generate a new candidate before acceptance;
- **Verifier task lost ** : Retain candidate and completed checks, and start a new acceptance attempt from the Verify boundary;
- ** The result to be archived loses the local execution basis ** : Revoke the current conclusion to be archived and conduct a full acceptance of the synchronized implementation again.

Processes, Agent sessions, and log connections on old devices will not continue across devices. The Runtime only restores facts that have been written to a stable state.

## The status version prevents expired operations

Each time the stable state changes, `state_version` will increase. Commands involving user decisions or stage transitions will carry:

```text
--expected-state-version <version>
--expected-action <action>
```

The Runtime will simultaneously verify the status version and the expected action. The confirmation in the old dialogue, the late return of the Verifier, or the expired command cannot override the new state. After the command is rejected, the latest `continuation` should be re-read and the new action should be continued.

The paging cursor of `status --details` is also bound to the status version. When the status has changed, the old cursor will be rejected to avoid mixing different versions of acceptance items, history and workspace information together.

## Cross-session and cross-device continuation

New sessions on the same device can usually continue directly with the current demand. Comet will first locate the active change and then return to the workspace and the next action. Run when manual viewing is required:

```bash
comet native status <change-name> --details --json
```

Before changing the equipment, the following contents need to be synchronized:

- Project code and corresponding branches or Worktrees;
- `.comet/config.yaml`；
- The `brief.md`, Specs and `comet-state.yaml` in the change directory;
- The generated `verification.md` file can also be rebuilt on the target device.

The target device does not need to copy `.comet/runtime/native/`. The Runtime will check the project root directory, branches, worktree and change bindings. When the binding is consistent, it reconstructs the local execution state from the stable boundary. When binding is inconsistent, code is not synchronized, or there is a conflict with the active/archive directory of the same name, it will keep the existing file and wait for processing.

## When to use doctor

The daily progress shall be based on the latest `continuation`. The following situations are suitable for running read-only diagnostics:

```bash
comet native doctor <change-name>
```

- The Runtime file is missing, invalid or from an old version;
- active change requires migration;
- Archiving or directory movement transaction interruption;
- The status, lock or workspace relationship cannot be determined.
- `continuation` explicitly requires diagnosis.

`--repair` will only run when `doctor` explicitly gives a security repair action. When the state is corrupted, there is a conflict with directories of the same name, or the source of recovery is unclear, the scene should be retained and the blocking cause returned by the Runtime should be handled.
