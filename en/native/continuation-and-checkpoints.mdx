---
title: 'Continuation and recovery'
description: 'Understand how Native uses Runtime continuations to move through Build, Verify, and Archive, and how it recovers from stable files.'
---

Native does not require the Agent to remember the previous chat or the user to switch phases manually. Each Runtime operation returns the next action; the Skill follows only that continuation and stops when a user decision or an exceptional condition needs attention.

## Continuation outcomes

| `status` / `stage` | Meaning                                                            | Skill action                                                                    |
| ------------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| `continue`         | The current action completed and the next step is clear            | Read `continuation` and run its command or handoff                              |
| `await-user`       | A user decision, confirmation, or external resolution is required  | Show the reason and choices; do not guess                                       |
| `blocked`          | State damage, a concurrency conflict, or an exhausted error budget | Follow the recovery action, run doctor when requested, or return to Shape/Build |
| `done`             | Archive completed                                                  | End the change                                                                  |

The normal Native Loop is:

```text
Shape → Build → Runtime checks → fresh Verifier →
  pass → Archive
  fail → Build (iteration + 1)
```

During Verify, extra checks are requested through `request-checks` in the current attempt. Equivalent completed checks are reused; the normal Archive path does not run acceptance again.

## The stable boundary

The files that must travel across sessions and devices are:

- `.comet/config.yaml`;
- the change's `brief.md`, complete Specs, and `comet-state.yaml`;
- `verification.md` when it exists (a missing or stale report can be rebuilt from YAML).

`.comet/runtime/native/` contains the local `state.json` overlay, logs, locks, and transactions. If it is missing, stale, or belongs to another change, Runtime discards and rebuilds it; it is never portable truth. An in-flight check is treated as interrupted, and an old Verify pass is reconfirmed on a new device.

## How the Skill continues

Start with:

```bash
comet native status <change-name> --details --json
```

Then use only `continuation.commandArgs` or `inputOptions.template` from that response. If the command is rejected, the Verifier is unavailable, execution fails, a semantic result is blocked, or migration/recovery is needed, read [comet status](/en/cli/status) and the [recovery playbook](/en/native/recovery-playbook); do not build internal JSON by hand.

`await-user` is neither a failure nor a skippable hint. After confirmation, Runtime creates a new state version. If the implementation changed, it must return to Build and start again with a new Builder and a new Verifier.

## Cross-device recovery

After moving devices, verify that the code, artifact root, and branch/worktree match, then run `status`. If the target is ambiguous, code is unsynced, active/archive directories conflict, or parallel changes target the same capability, Runtime returns `await-user` or `blocked` instead of changing directories automatically. Shape and Build can recover without `verification.md`; Verify and `archive-ready` first rebuild the necessary local execution state and reconfirm the result.

Continue with [Verification and repair](/en/native/verification-and-repair), [Artifacts and state](/en/native/artifacts-and-state), and [Recovery and troubleshooting](/en/native/recovery-playbook).
