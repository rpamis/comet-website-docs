---
title: 'User decisions and clarification protocol'
description: 'Understand how Native separates product decisions from implementation choices, and why Build stays locked until shared understanding exists.'
---

The strength of a strong model is thinking through how to do it itself. Native's boundary is therefore clear: **the outcome is the user's decision, the method is the strong model's decision.** It will not trade fewer phases for vague requirements, nor will it treat industry conventions or existing code defaults as your authorization.

## What the user must decide

Any unresolved branch that changes any of the following is a user decision:

- user-visible output, default behavior, or error results;
- compatibility, scope, or accepted risk;
- data deletion, migration, or other irreversible results;
- the observable semantics of a new capability at boundary conditions.

Conversely, implementation structure, library choice, internal algorithms, and test organization are the model's own choices as long as they do not change the above outcomes — Native does not surface them as questions to you.

Taking "add avatar uploads to the user profile" as an example:

| User decision (must ask)                                | Model decision (not asked)                                  |
| ------------------------------------------------------- | ----------------------------------------------------------- |
| On upload failure, keep the original avatar or clear it | Which HTTP client to send the request with                  |
| Whether deleting an existing avatar is allowed          | Whether image cropping happens on the front end or back end |
| Maximum avatar size and format limits                   | Which directory to store temp files in                      |
| Whether server-side compression is needed               | Whether to compress with sharp or jimp                      |

Every item on the left changes behavior the user sees; on the right, swap one implementation for another and the outcome is unchanged. Native asks only the left side and leaves the right to the model.

## How questions are ordered

Shape writes key actions as input→output or trigger→result examples, then checks defaults, boundaries, failure paths, and compatibility. If one counterexample can distinguish two reasonable interpretations, shared understanding has not yet formed.

When several issues are found, Native does not send out a fixed questionnaire; it first pins down each question's prerequisite decisions and the repository facts needed. The default `sequential` mode asks one upstream question per round; `batch` mode asks, in one go, every question whose prerequisites are already settled and that do not depend on each other. Every question includes:

1. **Question**: the observable behavior the user must determine;
2. **Recommendation**: a proposal based on goals and tradeoffs;
3. **Impact**: how each option changes the result.

The question is written into `brief.md` as a `[blocking]` item. Before the user answers, the model may investigate the repository or create a change, but it cannot turn an option into settled spec, modify the project implementation, or advance to Build.

## Final confirmation

A single correct answer does not mean the combined scope, non-goals, default behavior, and acceptance criteria are free of contradiction. So Native requires one final step: only when there are no more currently answerable questions in the round, and a strong model without the current chat history could implement and verify from the brief, target spec, and repository facts alone, may the Agent present the final shared-understanding summary.

You must explicitly confirm that summary before Native enters Build. The user initially proposing the feature does not equal this confirmation; Runtime records the confirmation for the current requirement, and it cannot be bypassed by hand-editing state. Both Sequential and Batch require this explicit confirmation — without it, the Shape → Build transition fails outright.

<Warning>
  "Preserve existing behavior" can only protect outcomes that already exist; it cannot define the
  semantics of a brand-new behavior on its own. Adjacent features, dependency defaults, and the
  minimal-change principle can only help form a recommendation, not replace the user's answer.
</Warning>
