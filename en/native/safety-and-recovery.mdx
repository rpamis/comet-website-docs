The Skill makes the model follow the requirement and phase contracts; the Runtime backstops it with verifiable state, evidence, and transaction checks. The first is "how it should be done"; the second is "what it must do" — a prose rule alone is not an unbypassable invariant. The Runtime is the state machine you cannot route around.

## One write belongs to one change

Comet runs an attribution check behind every write you make: one write lands on at most one change, reducing wrong-requirement writes and double blocking.

How exactly writes are routed depends on which change is currently selected and which workflow your configuration has enabled. Read-only operations such as reading state or checking progress never trigger the write check, so you can use `status` and `show` freely without accidentally binding later writes to another requirement.

Note that this protection covers only the writes Comet can observe. For writes from a shell, an external process, or anything a platform does not expose to a Hook, the Runtime's state and evidence checks remain the final authority.

## The immutable baseline

Every new change must obtain a complete baseline — a snapshot of the project's initial state — when it is created. This is an immutable fact. The Runtime does not fill gaps by guessing; it never treats a missing path as a deletion.

For a change already in use, a missing or corrupted baseline is not a problem `doctor` can repair automatically, because rebuilding from current files would erase the historical differences since creation. The only recourse is to restore the original baseline from a trusted backup, or preserve the requirement documents and implementation facts and create a new change.

The sole exception is an upgrade from an older schema: before any state write, `doctor --repair` captures a complete baseline at the migration timepoint, and if the capture is incomplete it leaves the old state untouched. Post-migration evidence covers only changes after the upgrade and cannot inherit a pre-upgrade scope or pass.

## The boundary of evidence and repair

These two topics are covered in full at [Verification evidence and autonomous repair](/en/native/verification-and-repair). Here we state only the safety-relevant conclusions:

- **Verification evidence goes stale**: a conclusion is bound to the brief, spec, implementation scope, and revision. If any of them changes, the old evidence is void.
- **Repair has a ceiling**: when the same semantic gap recurs for the third time with no progress, repair stops; by default the same contract tolerates at most five Verify failures. When the budget is exhausted, the Runtime hands the decision back to the user.
- **Fail-closed**: no integrity failure can be bypassed by hand-editing evidence.

## Ambient recovery

`comet resume-probe` is a read-only probe. After a session is interrupted, it reads the default workflow from your configuration and inspects only that side for a resumable change.

| Result         | Meaning                                                                |
| -------------- | ---------------------------------------------------------------------- |
| `auto_resume`  | One unique target and a request that does intend to continue; resume through `nextCommand` |
| `ask_user`     | Several candidates or unclear ownership; one short choice is required  |
| `out_of_scope` | The request does not intend to enter a resumable workflow              |
| `none`         | No change can be resumed                                               |

When configuration or state is damaged, the probe stops and states the reason rather than scanning another directory to guess. `ambient_resume: false` turns off automatic probing for ordinary requests; an explicit `/comet` call is unaffected.

## Dashboard responsibility

Dashboard is read-only display: phase, whether evidence is valid, the current continuation, structured findings, conflict summary, and archive-readiness. It does not re-derive facts, nor does it offer write buttons for progression, repair, or Archive — every write goes through the CLI/Runtime.
