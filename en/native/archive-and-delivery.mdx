---
title: 'Archive and delivery'
description: 'Accept a Native verification result, check archive readiness, apply Spec changes, and verify commits, pushes, or pull requests.'
---

Native enters Archive after the current verification result is accepted. The Runtime applies approved Spec changes and moves the change to the archive directory. How code and formal artifacts reach Git depends on the delivery scope you approve. Verify Archive and Git delivery separately.

## Accept the current verification result

After Verify passes, read the criteria, actual checks, and known limitations in `verification.md`. Acceptance applies to this implementation and verdict. If the implementation needs repair, follow the current instructions to return to Build. If the requirements or criteria need to change, confirm the affected Shape decisions first.

If you explicitly requested automatic acceptance and archiving after all criteria pass, the Agent can apply that decision when it submits the passing result. Otherwise, it waits for your acceptance. You can specify delivery at the same time, for example “Accept the result, archive the change, and commit it to the current branch without pushing.”

## Check readiness and archive

After accepting the result, inspect the outcome if the Runtime says Archive is complete. If an Archive action is pending, the Agent runs the current command in the returned workspace. Use `--dry-run` to check readiness. For example, check whether `login-error-message` is ready.

```bash
comet native archive login-error-message --dry-run --json
```

Read `ready` and `blockers` in the response. The command can succeed while `ready: false` indicates the change is still waiting for a prerequisite. Address the causes listed in the response, such as pending acceptance, a workspace mismatch, or a conflict with the project Spec. The preview does not apply Spec changes or move the change.

During Archive, the Runtime checks the current Run, accepted result, formal artifacts, and destination. When those checks pass, it applies the project Spec changes, moves the active change directory, and records the archive result. For example, the Runtime applies requirements from the `login-error-message` target Spec to `docs/comet/specs/authentication/spec.md` and moves the brief and verification report with the change to the returned directory under `docs/comet/archive/`. If the project uses a custom artifact root, use the returned paths.

If another change updated the same capability, read the latest project Spec and the conflict details. After aligning the requirements, have the Agent check which approvals and evidence still apply and follow the returned instructions for any additional verification. See [Parallel changes and conflict control](/en/native/multi-change-and-conflicts) for archive conflicts across worktrees.

## Verify the archive result

After Archive completes, status should show that the Run has ended. Verify that the archive directory is readable and that the project Specs include the approved changes. Check that the report and state file moved with the change. To see how a particular behavior was checked, open `verification.md` in the archive directory returned by the Runtime.

If the command is interrupted, inspect the original change and its archive destination, then follow the returned recovery command to continue the original transaction. The Runtime checks completed steps against their records so it can avoid applying the same Spec changes or creating a second archive. See [Task progress and interruption recovery](/en/native/continuation-and-checkpoints).

## Complete and verify Git delivery

Before taking Git actions, the Agent checks the current branch, target branch, and files belonging to this change. Stage the implementation, updated project Specs, and formal archive artifacts for this change. Review the staged diff and follow the project's commit rules and Git hooks. Preserve unrelated uncommitted edits.

| Delivery scope you approve | What to verify |
| --- | --- |
| Archive and keep the workspace | The archive path and the edits that remain in the workspace. |
| Commit to the current branch | The commit SHA, branch, and commit contents. |
| Merge into the target branch | The target branch includes the delivered changes. If you used a squash merge or similar method, check the resulting commit. |
| Push to the remote | The remote, destination branch, and remote commit match the intended delivery. |
| Open a pull request | The pull request URL, head branch, base branch, and included commits. |

For example, if you ask for `login-error-message` to be committed and pushed to the change branch, verify both the local commit and remote branch. If the push is interrupted, check what the remote branch actually points to before completing the remaining Git work.
