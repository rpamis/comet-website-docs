---
title: 'Archive and delivery'
description: 'Accept Native verification results, understand how Archive checks prerequisites and merges Specs, and verify Git commits, merges, pushes, or pull requests.'
---

Once you accept a verification result, Native executes Archive: it merges the confirmed Spec changes into your project's official Specs and moves the change directory into the archive history directory. How code and archived artifacts enter Git—left in your working tree, committed, merged, pushed, or opened as a pull request—depends on the delivery scope you specify in chat. Everyday archiving runs automatically via the Agent in the background without manual commands; at wrap-up, verify "Archive completed" and "Git delivery completed" separately.

## Accept the current verification result

After Verify passes, review the per-item verdicts, check evidence, and known limitations in `verification.md` (or the summary reported by the Agent). Your acceptance applies to this specific implementation and verdict:

- If you spot anything else to fix, tell the Agent in chat to revise the implementation and return to Build;
- If requirements or acceptance criteria need to change, describe the new requirement to return to Shape and reconfirm;
- If you explicitly told the Agent "accept and archive automatically once everything passes" (or enabled `native.archive_confirmation: automatic` in project configuration and all safety conditions hold), the Runtime accepts and advances into Archive automatically after a passing verdict.

You can specify your Git delivery scope when accepting, for example: "Accept this result, archive it, and commit to the current branch without pushing yet."

## Check prerequisites and execute Archive in the background

After you accept the result, the Agent advances the archive pipeline automatically in the background (archive preflight, Spec merge, and directory move):

- **Preflight fails (`ready: false`)**: The Runtime lists the exact blockers—such as unaccepted verification, a workspace binding mismatch, or a conflict with the project's official Spec—without modifying any Specs or directories. Resolve the blockers before retrying.
- **Preflight passes**: The Runtime merges the confirmed Spec changes into your project's official Specs (for example, `docs/comet/specs/authentication/spec.md`) and moves the change directory—along with `brief.md`, `comet-state.yaml`, and `verification.md`—into the archive directory under `docs/comet/archive/` (or your configured custom artifact root).

If another parallel change recently updated the same capability Spec, Archive pauses and flags the conflict. Sync with the latest project Spec and rerun affected checks before archiving. See [Parallel changes and conflict control](/en/native/multi-change-and-conflicts).

## Verify the archive result

When Archive finishes, the Run status becomes `completed` and the workflow status becomes `done`. Confirm three things:

- The archive directory is readable and contains `brief.md`, `comet-state.yaml`, and `verification.md`;
- Your project's official Specs include the approved additions or updates;
- If Archive was interrupted partway through, ask the Agent in chat to run diagnostics and recover the original transaction—completed writes are never repeated. See [Native task recovery](/en/native/recovery-playbook).

## Complete and verify Git delivery

Before running Git commands, the Agent checks the current branch, target branch, and files belonging to this change. Staging includes only this change's implementation code, updated project Specs, and formal archive artifacts. The Agent inspects the staged diff before committing and respects project commit conventions and Git hooks while leaving unrelated workspace edits untouched.

| Delivery scope you confirm | What to verify |
| --- | --- |
| Archive only; keep workspace | Confirm the archive path and that workspace edits remain intact. |
| Commit to the current branch | Confirm the commit SHA, branch name, and commit contents. |
| Merge locally into the target branch | Confirm the target branch contains the delivered changes (or the resulting commit if squashed). |
| Push to remote | Confirm the remote name, target branch, and remote commit match expectations. |
| Create a pull request | Confirm the PR link, head branch, base branch, and included commits. |

If pushing or opening a pull request is interrupted, check the actual remote branch and PR state first to see which steps already succeeded before completing the rest—do not blindly re-commit.

Everyday archiving is handled automatically by the Agent in the background. If you want to inspect archive readiness yourself in a terminal beforehand, you can run the read-only preview command below; it does not modify any files.

<Accordion title="Terminal read-only preview command (normally run by the Agent; optional for manual readiness checks)">

```bash
# Run a read-only preflight check showing ready, blockers, and pending Spec changes without writing files
comet native archive <change-name> --dry-run --json
```

</Accordion>
