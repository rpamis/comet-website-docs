## Basics and workflow selection

<AccordionGroup>
  <Accordion title="How should I choose between Native and Classic?">
    Prefer Native when using strong cloud reasoning models: these models already handle code comprehension and task decomposition well, so Native focuses on requirement and acceptance boundaries plus evidence-based verification while leaving implementation methods to the model. Choose Classic (combining OpenSpec and Superpowers) if your model is less capable or your team prefers advancing through a fixed five-phase document and plan workflow. Both workflows can be enabled or switched per project in `.comet/config.yaml`.
  </Accordion>

  <Accordion title="Does Native require installing OpenSpec, Superpowers, or other external skills?">
    No. Native includes the complete Shape, Build, Verify, and Archive workflow along with the SDK Runtime built in. You only need to install OpenSpec and Superpowers when using the Classic workflow.
  </Accordion>

  <Accordion title="Do I need to memorize and type comet native commands manually in daily use?">
    No. Daily development happens in natural language inside Agent chat (starting with `/comet <your request>`). All underlying `comet native ...` commands—creating changes, advancing phases, submitting verification results, and passing confirmation guards—are executed automatically by the Agent in the background. You only need terminal commands when you want to inspect progress outside chat (`comet status` / `comet native doctor`) or move a Supervisor child task across checkouts (`comet native transfer`).
  </Accordion>

  <Accordion title="Why can't a change be archived right after the Builder says coding is done?">
    Code submitted by the Builder is only a candidate implementation. Verify must still check every acceptance criterion against your original request and formal Specs. Routine tasks can complete verification in a read-only role within the current session (recorded as `self-reviewed`), or you can request an independent read-only review session. Only after all criteria pass—and according to your confirmation or automatic archive policy—does the change enter Archive. See [Verification and repair](/en/native/verification-and-repair).
  </Accordion>

  <Accordion title="What if extra test commands need to run during Verify?">
    The Agent runs the required build, unit test, typecheck, or static analysis commands directly through platform tools and records the command, working directory, exit status, and log reference faithfully in the verification evidence. The Runtime does not re-execute ordinary commands and never accepts fabricated or unrun checks as passes.
  </Accordion>

  <Accordion title="Why do new projects default to batch clarification mode?">
    `batch` mode asks all independent decision points whose prerequisites are already clear in a single round, cutting down on back-and-forth turns. If requirements are still exploratory and earlier answers directly change downstream branches, switch to `sequential` in `.comet/config.yaml` to clarify one question at a time. In either mode, you confirm the complete final Shape before entering Build.
  </Accordion>

  <Accordion title="Does a missing verification.md affect interruption recovery or cross-device continuation?">
    No. `verification.md` is only a human-readable view rendered by the Runtime from structured verification verdicts. The local Run and repository files—`comet-state.yaml` (including `run_checkpoint`), `brief.md`, and target Specs—are the basis for recovery. If the report file is missing, it is automatically re-rendered from recorded verdicts without losing evidence, and editing the Markdown file by hand cannot change verification outcomes.
  </Accordion>

  <Accordion title="What is the difference between comet-state.yaml in the repository and the local Run directory?">
    The complete local Run lives in the Comet data directory under your home directory (`~/.comet` by default, isolated per workspace and Git worktree) and records every action claim, submission, and transaction log in real time without being committed to Git. `comet-state.yaml` inside the repository displays business state and writes a tamper-evident recovery checkpoint (`run_checkpoint`, with redacted tokens and in-flight actions downgraded to `unknown`) at key boundaries for cross-device recovery or restoring lost local records.
  </Accordion>

  <Accordion title="Can multiple independent Native changes be developed in parallel?">
    Yes. You can plan multiple Shapes on the same branch and defer Build at confirmation time. When you start implementing, if other active tasks remain in the same directory, the Runtime automatically creates an independent branch and Git worktree and hands the task off. You can also create a change directly in an independent worktree from the start. If two parallel changes edit the same capability Spec, Archive runs requirement-level checks and pauses on conflicts so you can set the archive order. See [Multi-change parallelism and conflict control](/en/native/multi-change-and-conflicts).
  </Accordion>
</AccordionGroup>

## Supervisor Change

<AccordionGroup>
  <Accordion title="When should I use Supervisor Change versus multiple independent changes?">
    Use Supervisor Change when a large goal splits into two or more child tasks that can be coded and verified independently but must merge into an integration branch for unified end-to-end verification (layered refactors with sequential dependencies also fit). If requirements are independent and can ship separately, create multiple independent Native changes. If edits concentrate heavily in the same core file, keep a single change and advance sequentially.
  </Accordion>

  <Accordion title="What is the difference between multi-session and single-session mode in Supervisor?">
    Child decomposition, dependency order, child verification, and integration rules are identical; only the execution carrier differs. In `multi-session`, the main session coordinates concurrent progress using independent sessions or Claude Code Agent Teams based on platform capability (default limit `2`, adjustable via `native.max_parallel_children`, falling back automatically to subagents when unsupported). In `single-session`, the current session completes children sequentially in dependency order (concurrency fixed at `1`). Your choice is saved in `comet-state.yaml` and reused automatically on recovery.
  </Accordion>

  <Accordion title="What if a multi-session child task's window closes or its session is lost?">
    Return to the original workspace and ask the Agent to continue. Comet first checks with the original platform whether the child task is still running and never treats a disconnected session as complete. If the original independent session or Agent Team is unavailable, Comet automatically continues via subagent under `multi-session` instead of silently downgrading to single-session. To move an in-progress child task across machines or checkouts, use `comet native transfer export/import`.
  </Accordion>
</AccordionGroup>

## Recovery and troubleshooting

<AccordionGroup>
  <Accordion title="What if requirements change after Verify passes or while waiting to archive?">
    Describe the change directly in conversation. If you are only fixing the internal implementation of the original requirement, the Agent takes the implementation revision path back to Build while keeping the confirmed Shape. If user-visible behavior or acceptance criteria change—and archive writes have not executed yet—the Agent returns to Shape, presents a before/after change summary, and asks you to re-confirm while keeping all existing code intact. See [Continuing a Native change after requirement changes](/en/native/scenarios/requirement-changes).
  </Accordion>

  <Accordion title="How do I recover a task after switching devices or clearing local cache?">
    As long as your code, `comet-state.yaml`, `brief.md`, target Specs (and `.comet/config.yaml` when using a custom root) are committed to the repository, pull the repository on the new device and ask the Agent to diagnose the task. Once the checkpoint is verified valid, the Agent restores the original Run in the background via `comet native doctor <change-name> --repair --confirmed` (which you can also run manually in the terminal for offline troubleshooting) without redoing completed Shape or Build work.
  </Accordion>

  <Accordion title="After upgrading Comet, are existing Compat or older changes affected?">
    No. Upgrading never force-migrates in-flight legacy changes or modifies their existing state and verification contracts; newly created changes automatically use the new SDK Runtime. If completed historical Runs indicate that storage partitioning needs to be finalized, upgrade both the CLI and platform hooks and let the Agent (or run in the terminal) perform the one-time history migration. See [Native recovery playbook](/en/native/recovery-playbook).
  </Accordion>

  <Accordion title="What are the standard read-only terminal commands for offline troubleshooting?">
    Preserve the current workspace as-is without manually editing `comet-state.yaml` or `.comet/current-change.json`, and run read-only diagnostics to inspect state and exact blockers:

    ```bash
    comet status
    comet native status <change-name> --details --json
    comet native doctor <change-name> --json
    ```

    Then follow the matching scenario in [Native recovery playbook](/en/native/recovery-playbook).
  </Accordion>
</AccordionGroup>
