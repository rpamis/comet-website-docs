Frequently asked questions about Native's use cases, four-stage workflow, portable state, verification, recovery, and conflicts.

## Basic concepts

<AccordionGroup>
  <Accordion title="How should I choose between Native and Classic">
    Prefer Native when your main model is Fable 5, GPT-5.6, or a peer: such models can plan and implement autonomously, so imposing methodology wastes their ability — Native hands the method choice to the model and locks only outcomes and evidence. Use Classic for models below that tier or tasks that need clearer process constraints; it provides open, design, build, verify, archive governance through OpenSpec and Superpowers. The choice lives in `.comet/config.yaml`; Comet does not guess from task size.
  </Accordion>

<Accordion title="Does Native depend on OpenSpec, Superpowers, or another external Skill">
  No. Native ships its own Shape, Build, Verify, Archive, and Runtime flow. OpenSpec, Superpowers,
  and their references are installed and used only by Classic.
</Accordion>

<Accordion title="Why can a Builder's completion claim not archive a change">
  A Builder submits an implementation handoff. Runtime runs necessary checks and dispatches a fresh
  read-only Verifier over every A1…An item. When Skill coordination has no independent Verifier
  execution, Archive also requires one explicit user confirmation and the report marks the degraded
  assurance.
</Accordion>

<Accordion title="Why does Verify return to Build">
  A failed acceptance item, failed check, incomplete Verifier response, or invalid coverage becomes
  a concrete continuation and returns the change to Build. The next round repairs those gaps and
  starts again with a new Builder and Verifier.
</Accordion>

<Accordion title="Can I recover without verification.md">
  Yes. Shape and Build need the synced brief, Specs, and `comet-state.yaml`; `verification.md` is a
  rebuildable report. On another device, Verify and `archive-ready` rebuild local execution state
  and reconfirm the result instead of reusing an old local result directly.
</Accordion>

<Accordion title="What is portable state versus local Runtime">
  `comet-state.yaml` is the cross-device boundary for phase, Loop, acceptance, handoff, check
  summaries, Verifier verdict, blockers, and next action. `.comet/runtime/native/` stores only local
  `state.json`, logs, locks, and transactions; missing or mismatched overlays are rebuilt.
</Accordion>

<Accordion title="Why is Batch the default for new projects">
  Batch resolves question dependencies first and asks every currently answerable question in a
  round, reducing repeated turns. Sequential remains available and asks one upstream question per
  round; both require shared-understanding confirmation before Build.
</Accordion>

<Accordion title="What if I need an extra check">
  The current Verifier requests it through `request-checks`. Runtime deduplicates equivalent plans,
  limits request rounds, and returns the result. Do not create a manual receipt or fill a pass field
  yourself.
</Accordion>

  <Accordion title="Can several Native changes run in parallel">
    Yes. When appropriate, change creation presents `current`, `branch`, and `worktree` choices. `.comet/current-change.json` selects ownership for the next write but does not limit the number of active changes. If two changes target the same capability, Archive asks for an explicit order.
  </Accordion>
</AccordionGroup>

## Recovery and troubleshooting

Start with:

```bash
comet status
comet native status <change-name> --details --json
comet native doctor <change-name>
```

Do not edit `comet-state.yaml`, `.comet/current-change.json`, or `.comet/runtime/native/` by hand. If code, artifact root, branch/worktree, or active/archive layout does not match, Runtime returns a concrete `await-user` or `blocked` action.

Change-local Runtime files, old receipts/evidence, and `native.snapshot` settings left by an older version are migration and read-only compatibility inputs only. New beta17 changes do not create them. Run `comet update`, then `comet native doctor <change-name> --repair` when migration needs an explicit repair.

Continue with [Native configuration](/en/native/configuration), [Artifacts and state](/en/native/artifacts-and-state), [Verification and repair](/en/native/verification-and-repair), and [Recovery and troubleshooting](/en/native/recovery-playbook).
