<h2 id="foreword">Preface</h2>

In this article, I explain what Comet does and the design principles behind it.

Comet first became known to the public in May when it was just open-sourced: [LINUX DO community discussion thread](https://linux.do/t/topic/2232510/52).

I also released a series of videos. I have had little time to promote Native mode, so the older videos still attract much of the attention. **Many people know Comet as an OpenSpec + Superpowers orchestration layer, but combining those two was never the goal, as we said in the first video. Comet has since grown beyond a Skill.** We needed a capable Skill with a stable execution flow to develop a reusable Runtime/Harness for real work and production use. I will walk through the major releases in chronological order and explain the problems each one set out to solve.

<h2 id="history">Open-source history</h2>

**1. May: The first open-source OpenSpec + Superpowers workflow**

At this point in May, there were no strong models like Fable 5 or GPT-5.6 with the Superpowers-style reasoning on the market yet. Under this premise, OpenSpec and Superpowers were still very effective methods on the models at that time. Before it was open-sourced, I had been deeply using this type of SDD for a long time (about several months). At that time, mattpocock/skills had not yet gone viral in China, and there was no official account to promote it everywhere.

At that point in time, when I was using this type of SDD, I mainly faced several problems:
1. More than 90% of the time, I am clicking "yes". There are too many Skill names to remember, but many processes are relatively fixed and need to be called manually.
2. Superpowers does not have the ability to natively manage requirements, while OpenSpec does, but the clarification dimension is insufficient.

So, because I wanted to be lazy, I combined the two of them and encapsulated them in an SOP. At first, they were arranged in plain text in CLAUDE.md.

But soon I discovered a series of problems with such long chains of nested Skill calls as follows:
1. After multiple context compressions, the Agent completely forgot what Skill to call next.
2. The Agent did not actually trigger the Skill but did something similar to what the Skill required, and there was forgetting in the process.
3. The Agent skipped the key Skill process and directly started writing code. For instance, it could only start writing code after the link required clarification was completed. The Agent started working without asking you any questions.
4. There is no cross-device context recovery (which often requires re-explaining context), no reliable state transition, no intent recognition, and no mandatory access control protection. It all depends on the Agent's self-awareness.

Meanwhile, we also have **other real job demands**:
1. **For individuals**: **Everyone has their own Skill preferences**. For instance, one person might prefer grill-me, while another might like brainstorming. Consistent with most of the friends in the comment section, we like to select useful skills to assemble by ourselves.
2. **For the team**: In business, we often need to interface with skills from other teams. These skills were not written by us, but as the orchestration chain became long, how to stably execute them under the model capabilities at the time became a problem. That is to say, as mentioned above, it's very easy to fall into traps.
3. **For the industry**: There are a great many ready-made and useful skills available. If we need Word or Excel capabilities, using the official ones is definitely much better than having the AI write them temporarily.

With these questions in mind, I first connected the OpenSpec + Superpowers link of Comet, focusing on solving how to stabilize Skill triggering, cross-device context recovery, state machine, intent recognition, and phased access control protection on long-range nested skills, and then carried out open-source work. This is the initial version of Comet that everyone has seen. The question being considered is that if we can obtain a reusable Skill Harness practice based on this set of long-term task skills, then the problem of subsequently combining skills and stably executing them can be well solved.

Second, in June and July, major companies began to promote the same practices. Comet started to work on Eval evaluation and Skill combination, and gained more best practices for progressive loading.

In June and July, we observed that many major domestic and foreign companies and organizations, such as LangChain, Apache, Tencent, Alibaba, and ByteDance, began to promote Skill practices with similar ideas. At the time of our open source, there were no such articles.

So later on, we wrote a special article **to show how Comet shares the same practical approach with leading industry practices worldwide**: [Comet vs Industry Practices](/en/tech-blog/comet-vs-industry).

During those two months, we focused on refining Comet's progressive loading, introducing more atomic references, including user pause points (HITL), auto-advancing Skill protocols, context recovery protocols, workspace standards, and more.

**These files are concise, but their principles are clear—anyone can learn valuable engineering patterns from their corresponding mechanisms.**

Meanwhile, with the rapid iteration of Comet Skill, we urgently needed an evaluation mechanism to measure whether each Skill change introduced regressions, and whether the Skill truly improved. **As our user base grew, we could no longer rely on intuition and guesswork. In the past, I've met many Skill authors who iterated rapidly using AI, but whose features were unstable—whether a prompt worked or not depended entirely on gut feel. That is not a sound engineering iteration model.**

Back then, we still rarely saw rigorous eval work on social platforms; most were academic papers, or simple benchmarks unsuited for Coding Agents that frequently interact with users.

We have done a lot of solid work on Eval, **including how to evaluate any Skill using Claude Code and Codex (which users use most frequently), how to make the entire evaluation process fully automated, how to evaluate Skills using Rubric, Pass@k, and Pass^k scores, and how to integrate LangSmith and Langfuse**.

To turn Skill iteration into a systematic engineering discipline, we overcame numerous obstacles, evaluated prompts with real-world token consumption, named this system Comet Eval, and open-sourced all of its code.

In addition, I delved deeper into the problem left from May: "how to compose Skills." **I chose not to build a visual Skill orchestration UI like Dify—I felt that wasn't AI-native enough and would quickly become obsolete.** Ultimately, it evolved into an AI-native Skill like `/comet-any`, which can adapt Comet's original five-phase workflow, **or generate a customized Skill workflow based on user preferences, infused with the runtime experience accumulated by Comet.**

**3. July–August: The Birth of Comet Native Workflow**

With the release of Fable 5 and GPT-5.6, I quickly sensed that model capabilities had reached a new milestone. GPT-5.6 demonstrated chains of thought remarkably similar to Superpowers, validating what I had maintained in several videos: **"If a Skill's trajectory is relatively structured, it can definitely be evaluated; as long as we build solid evaluations and treat metrics as ground truth, we can create datasets, and models can be trained."**

Having realized this, and benefiting from our already polished runtime, I open-sourced Comet Native Skill just a few days after the release of GPT-5.6. My core insights were:

1. When model capabilities become powerful enough, **Skills are poised for a transition similar to the Agent Loop shifting from workflow-driven state machines to ReAct-driven loops**.
2. The rigid engineering rules in Superpowers **tend to clash with the native reasoning chains of strong models**, yet several practices remain well worth preserving, such as TDD and Brainstorming.
3. Skills should focus on what to record, what to do, and how to verify—**we no longer need to micromanage every implementation step**. A few lightweight guidance files are more than enough.

The **Native Skill built this way achieved its core mission with only 100+ lines of Skill instructions**. Meanwhile, we natively integrated grill-me style high-intensity clarifications, supporting both linear and batch modes; **this yielded a 75% reduction in token consumption and a 45% reduction in execution time on benchmarks, without any loss in accuracy**. **The core is driven by Loop Engineering and includes a Supervisor Change mode**, closely mirroring real work environments: complex tasks break down into sub-tasks, and Native uses a DAG to detect dependencies, running parallelizable work concurrently and waiting on dependent steps.

The Native workflow also introduced more flexible, ReAct-style implementation mechanisms.

**We don't mandate any specific implementation technique in Native workflow. However, if you have methodological Skills like TDD or BDD installed locally, the Agent will autonomously decide and initiate a TDD workflow during implementation.**

**This returns us to the essence of Skills: the model inspects the Skill name and description to decide when to invoke it, rather than being forced through an inflexible pipeline.**

When using Native Skill, you have immense flexibility: you can bypass Native's clarification and provide existing documentation directly, treating Native purely as an execution loop that drives your specifications to completion.

<h2 id="design">Design principles</h2>

**4. Finally, Our Design Principles**

Comet exercises deliberate restraint against feature bloat. Here is our thinking:

1. Self-evolving memory, self-evolving Skills, and automatic document extraction

These are popular directions. My research into self-evolution began before Agent Skills became an official standard; my related PR was submitted to Spring AI Alibaba DeepResearch: [Spring AI Alibaba DeepResearch PR #20](https://github.com/spring-ai-alibaba/deepresearch/pull/20).

The goal was to help the Agent understand user characteristics across multi-turn dialogues seamlessly, guiding responses in real time.

Back then (early December 2025), this was a niche area mostly confined to research papers, with only occasional superficial posts on social platforms.

We all know what happened next: in February 2026, the explosion of Hermes thrust these directions into the spotlight.

However, architecturally, we still prefer not to cram all of this directly into Skills—or at least not in such an overweight fashion.

**Because Memory and RAG are extensive systems engineering domains** involving complex pipelines: Memory requires continuous background evaluation and daemons—an area where specialized teams build dedicated vertical solutions. It should properly remain an independent service that Coding Agents plug into. Similarly, RAG requires evaluating recall, precision, and LLM-as-judge, alongside embedding models and document chunking pipelines. **Each direction represents an extensive domain in its own right, making a full implementation inside a single Skill largely unnecessary. When developers neglect evaluation and lack proper benchmarks, many attempts degenerate into vanity metrics.** Academic literature has already demonstrated that outputs from many self-evolving memory and Skill mechanisms underperform in practical workflows. This remains an active subject demanding rigorous research.

2. Cross-Agent Harness File Injection

What works well here is filling the gaps in rule mechanisms across various Coding Agents by selectively injecting rule documents via Hooks. In the long run, rule injection is straightforward for Coding Agent vendors. In fact, linters alone can achieve a great deal: for instance, packaging rules as linter plugins so non-compliant code fails compilation or checks. Once the Agent encounters the error, it naturally knows how to fix it—providing a deterministic post-hoc guardrail.

3. About the CLI

Many developers hold the misconception that a CLI is built merely for easy multi-platform distribution. **In Comet, however, the CLI serves as the entry point for the Runtime/Harness: we turn codeable logic into deterministic CLI commands, enabling the Agent within a Skill to identify when to run a specific command for complex, rule-bound operations** (such as Comet state transitions). The advantage is drastically reducing the prompt size inside Skills by moving stable execution paths into deterministic code. The Agent doesn't need to know low-level mechanics; it only needs to know their functional interface—just like pressing a power switch on an appliance without needing to understand its internal wiring.

<h2 id="contribute">Contribute</h2>

**5. In Closing**

Comet warmly welcomes contributions from the developer community, including documentation improvements. **We hope everyone gains practical, production-ready engineering knowledge from Comet**, rather than merely hopping between superficial Skill novelties. If you're curious about Comet, just run `/comet` and kick off your first change!
