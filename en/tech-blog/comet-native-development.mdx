Comet Native is neither Classic Spec with a few phases removed nor a long prompt compressed into a short one. It began with a more fundamental question: **when a coding model can already investigate, design, implement, and debug autonomously, how much process should a workflow still prescribe?**

Our answer changed several times. The final boundary is: make requirements and acceptance conditions detailed, but keep the execution method light. The model owns judgment and implementation; the Runtime owns mechanical facts, recovery, safety boundaries, and evidence freshness.

This article preserves the real iteration history, including rejected directions and questions that experiments have not yet answered. It does not rewrite development as a path that was obvious from the start.

## The starting point: Spec still matters, but HOW became too heavy

Classic Spec solved real problems. When less capable models faced complex work, explicit Open, Design, Build, Verify, and Archive phases—plus planning, TDD, debugging, and review protocols—reduced missed files, skipped steps, and unsupported completion claims.

The same constraints create new costs for strong models:

- A model can choose an implementation from repository facts but still has to answer multiple workflow-mode questions.
- Phase Skills repeatedly load similar context and lose information during handoffs.
- Process files grow alongside implementation files, making real requirements harder to distinguish from execution scaffolding.
- “Complete every step” can replace “satisfy the goal and provide evidence.”

Native therefore does not reject Spec. It redefines Spec as **giving the model enough information and completion conditions**, rather than prescribing every step of its reasoning.

<Note>
  Native and Classic remain independent products. Native serves strong models that can execute
  autonomously; Classic serves models that benefit from explicit method guidance. There is no
  automatic upgrade, conversion, or shared change between them.
</Note>

## Why a very short clarification prompt can work better

Early discussion drew inspiration from grill-me-style prompts, but Native never made one an external dependency. The valuable idea was not the Skill name. It was concentrating conversational pressure into a few high-value actions:

1. Find the unknown decision that would genuinely change the result.
2. Ask only the most important one.
3. Give a recommended answer and rationale.
4. Explain each option's practical effect on scope, compatibility, risk, or user experience.
5. Persist the answer as an executable condition instead of leaving it only in chat.

It works because a long questionnaire does not dilute attention. Native Shape kept this principle and added two constraints: investigate facts already available in the repository first, and allow implicit confirmation when no high-impact unknown exists instead of inventing questions merely to “complete clarification.”

The completion standard also became stricter: another strong model with no original conversation should be able to implement and accept the change from the brief, complete target specifications, and repository facts without guessing user-visible behavior.

## 2026-07-14: separate the product concepts first

The first design established several boundaries:

- Native uses Comet-owned `comet/`, not OpenSpec changes.
- A project may place its artifact root under a relative path such as `docs`.
- Native and Classic state, selection, and archives are completely isolated.
- Native depends on neither Superpowers, OpenSpec, grill-me, nor any external Skill.
- One `/comet-native` Skill continues according to the current phase instead of splitting into phase Skills.
- Shape, Build, Verify, and Archive describe outcome states; Plan, TDD, Debug, and Review are not mandatory phases.

Why insist on one Skill? The Runtime already expresses phase order deterministically. Splitting it into four Skills would reintroduce Skill selection, phase routing, and context handoff. A strong model needs one behavioral entry that continues from disk state, not a new method specification at every phase.

The first Runtime focused on mechanical facts: project configuration, change state, four-phase guards, complete target specifications, trajectory, selection, archive, and a bundled Runtime. It did not think for the model, but it made the phase and directory reproducible.

## 2026-07-15: from “having state” to “consistent state”

The first version quickly exposed a problem. State lived across `change.yaml`, Run state, trajectory, and checkpoint. Validating each file independently could not prevent a process exit between writes from leaving files that were individually valid but mutually contradictory.

Phase 1.5 introduced a transition journal and split phase progression into an idempotently recoverable write sequence. The Runtime first records deterministic before/after state, then updates Run, change, trajectory, and checkpoint. The next `next` or doctor continues from the journal instead of guessing which file is true.

That iteration established a durable division of responsibility:

| Question                                                    | Owner                                      |
| ----------------------------------------------------------- | ------------------------------------------ |
| How to implement, test, and debug                           | Strong model                               |
| What the user must decide                                   | Skill's lightweight clarification protocol |
| Which phase, which inputs, and whether recovery is possible | Runtime                                    |
| Whether the model actually improved                         | Eval, not prompt self-description          |

## 2026-07-16: fix evaluation semantics before discussing performance

Early Native and 0.4.0 Classic reports used different sample counts, execution windows, and duration calculations, so direct comparison was invalid. In particular, an older report took only the final `result.duration_ms` from each sample and omitted earlier model calls in a multi-turn run.

We aligned Native to the 16 business tasks already run for Classic, repeated each task three times, and paired strictly by `task_id + repetition`. Duration became the sum of every top-level result in a sample.

Both groups reached 16/16 `pass@3`. Native showed a favorable direction on strict pass@1, `pass³`, and corrected duration. But the groups ran in different windows without fully controlled machine load or service conditions, so the numbers cannot prove how much speed came from removing any one phase.

That correction shaped later Waves: define business-verification and workflow-verification contracts separately; establish trustworthy sample identity and timing first; and when no real model artifact exists, report fixture and validator results as mechanical coverage rather than model-behavior conclusions.

## From 58 ideas to 14 + 1 capabilities

As we asked how Native could better serve strong models, Runtime, UX, and Eval expanded into 58 checkpoints. Shipping each independently would make Native heavy again, so they were compressed into 14 vertical capabilities plus one cross-wave boundary.

### Wave A: foundational safety and trustworthy metrics

State moved to schema v3 with a migration journal, revision/CAS, baseline/current snapshots, and Protected Run I/O. A new Runtime cannot silently present old state as current evidence; doctor must migrate it under control.

This adds no user step. It lets the Runtime distinguish “safe to continue,” “migration required,” and “damaged.”

### Wave B: resumable decisions and in-phase progress

The original `next: auto` was only a human-readable hint. It could not tell a host whether to continue the same Skill, await the user, or repair the Runtime. Wave B turned this into structured continuation and added in-phase checkpoints.

`continue-same-skill` does not mean a background daemon runs the model. It tells the host or next session that context may be compressed, but work should resume in the same Native Skill and change.

### Wave C: verification must still be valid

Saving `verification.md` alone does not prove completion. A report may correspond to old requirements, an old implementation, or an old acceptance set.

Wave C binds evidence to three facts:

- Contract and Acceptance IDs derived from the brief and complete target specifications.
- Implementation scope derived from baseline, current files, and declared artifacts.
- Current change revision.

Changing any input makes an old pass, receipt, or partial allowance stale. The Runtime does not dictate a test framework, but it can answer which requirements and implementation a conclusion actually verified.

### Wave D: autonomous repair that can also stop across sessions

Strong models should repair Verify failures autonomously, but “keep trying” cannot become an infinite loop. Native never reads chain of thought. It forms a semantic signature from failure categories, failed check IDs, contract, and scope.

The third identical failure under an unchanged scope becomes a manual stop. An episode hard-stops at 12 failures. Genuine scope progress closes the old episode. Stopping therefore depends on evidence progress, not on mechanically counting phase transitions.

### Wave E: promise only parallel safety provable inside the current Native root

An early design considered Git branch, HEAD, and changed paths as parallel-work signals. Security review removed the path completely.

Users may not use Git, repositories may be in detached HEAD, untracked files can matter, and Git relationships do not prove that two models have no semantic conflict. Final conflict inspection uses only Runtime-owned capability, operation, base hash, contract, and bounded implementation scope. Native neither creates worktrees automatically nor upgrades Git guesses into a safety guarantee.

### Wave F: Dashboard is read-only, not a second Runtime

Dashboard may display phase, evidence freshness, checkpoint, continuation, archive readiness, and conflict summary, but it consumes only Runtime projection. It does not recompute state, cache a second fact set, or expose progression controls.

This conservative boundary prevents a difficult class of bugs: the CLI thinks a change is in Verify while Dashboard independently decides it is already in Archive.

### Cross-wave boundary: reject a general command executor

“Let the Runtime execute project tests and sign a receipt” sounds attractive. It also means owning shell parsing, environment variables, credentials, process trees, timeouts, output truncation, platform differences, and command injection—turning Comet into another task-execution platform.

That direction was rejected. `comet native check` runs only a built-in, narrow, reproducible, read-only text policy. It invokes no Git, shell, project script, external Skill, or arbitrary process. The model still chooses real tests from repository facts and risk.

## Lightweight does not mean a simplistic Runtime

Native exposes only four phases, but its Runtime is not casual. Complexity lives below the surface:

- Configuration, change, brief/spec, Run, trajectory, journals, and directory enumeration each have hard budgets.
- Inputs use protected handles and revalidate file and parent-directory identity before and after opening.
- Status/list, findings, and Acceptance IDs use content-bound paginated cursors.
- Build/Verify complete pure inspection before persisting final evidence, so failed attempts cannot leave false conclusions.
- Archive dry-runs first and commits through a preflight hash.
- Directory deletion first renames into transaction quarantine for deterministic continue or rollback.
- Summaries, reasons, and skip explanations are length-bounded and screened for credential-like content before persistence.

These mechanisms add implementation code without adding phases for the model or forms for the user. **The lightweight goal is to reduce cognitive protocol, not sacrifice factual consistency.**

## Directions explicitly removed

To keep future iteration from quietly turning Native back into Classic, non-goals remain product boundaries:

- No phase-specific Skills.
- No external Skill dependency.
- No Native-to-Classic upgrade or conversion.
- No mandatory Plan, TDD, Debug, or Review phases.
- No LLM calls inside the Runtime.
- No background daemon.
- No automatic Git branch/worktree management.
- No arbitrary shell execution and signing.
- No Dashboard write surface.
- No checkpoint expansion into a project-management system.

These are not ordinary backlog items. Reopening one requires evidence that it will not break the Native/Classic boundary.

## What we can and cannot conclude today

The implementation can mechanically prove that state and evidence are schema/CAS constrained; interrupted transitions, Archive, and root moves recover from journals; changed inputs stale old evidence; repair has semantic stops; and conflict inspection and Dashboard projection reuse the same Runtime facts.

Those tests alone cannot claim that:

- Models recall every hidden decision without explicit prompting.
- Continuation auto-runs in every host.
- Repair reduces token use or duration on real tasks.
- Dashboard improves team collaboration.
- Wave A–F has a stable real-model win rate over other workflows.

Those questions require new real-model experiments, not more static assertions. The historical Native/0.4.0 aligned experiment provides directional evidence. Current Wave A–F fixtures, validators, and adversarial tests prove that mechanical contracts execute, not that they replace behavioral measurement.

## The final principle

Comet Native converged on one sentence:

> Give “how to complete it” to the strong model, and give “completion conditions, facts, and irreversible boundaries” to the Runtime.

Native can therefore combine detailed requirements, a real state machine, automatic progression, recovery, verification evidence, concurrency protection, and safe archive without making the model execute a heavyweight method checklist for the workflow itself.
