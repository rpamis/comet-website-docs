Comet 0.3.9 connected OpenSpec and Superpowers with Bash scripts and stored the five-stage state. Version 0.4.0 addresses two groups of problems.

The first group comes from the existing runtime:

- Windows users must install Git Bash or WSL to run the entire process;
- The routing of `/comet` relies entirely on the Agent to re-read the prompt word and "guess" it once. If it is wrong, there is no way to review it.
- After the interruption and return, all states are crammed into one `.comet.yaml`, with machine fields and human fields polluting each other.

The second group covers missing product entry points:

- Users can only consume the `/comet` series commands pre-installed by Comet. They have no way to create their own skills, let alone combine any Skill into a reusable package as useful as `/comet`.
- There is no means to quantify "whether this Skill is good or not", and improvement depends entirely on feelings.
- When a change is halfway through, if you want to see what it has produced and where it is stuck, you can only go through the files.

0.4.0-beta.1 rewrote the runtime and added Skill Creator, Eval, and Dashboard. See the [Changelog](/en/changelog) for the complete feature list; this article records the background and boundaries of each change.

## I. Node runtime

This is the biggest refactoring in 0.4.0, and it directly removes the need for Windows users to install Git Bash or WSL.

** State of 0.3.9 ** : The core logics such as state machine, phase guard, handover, and archiving are handled by seven Bash scripts. The logic itself is fine, but the premise that "there must be a shell compatible with Bash" keeps a considerable number of users out. On Windows, either install Git Bash or use WSL. Path escape, shell differences, and loss of executable permissions (the classic `100644` → `100755` issue on macOS) are all recurring hidden dangers.

** Decision for 0.4.0 ** : Rewrite all scripts as the Node `.mjs` launcher, backed by a shared TypeScript runtime (`domains/comet-classic/`). Each `.mjs` is a single-file package generated by esbuild, and dependencies such as `yaml` are inlined together.

** Why change it like this ** :

|Motivation| 0.3.9 | 0.4.0 |
| --- | --- | --- |
|Cross-platform|Windows requires Git Bash/WSL|Only 20+ Node.js is needed|
|Path reliability|shell escape, CRLF, executable bit|Native processing of Node|
|Achieve consistency|Scattered shell logic|Single TypeScript transfer semantic table|

The key lies in the "single transfer semantic table" : `comet-state transition` and `comet-guard --apply` now share the same `classic-transitions.ts`, so the behaviors of the two advancement paths are exactly the same, and there will no longer be the inconsistency of "guard allows but state rejects ".

<Info>
The most important commitment for old users: The behavior of all ZXQ1, QXZ/comet*ZXQ2, QXZ commands remains unchanged. You don't need to switch to the method. The underlying structure has been changed from Bash to Node, but the workflow remains the same.
</Info>

## II. Routing context

** Status 0.3.9 ** : The `/comet` entry is determined by a natural language rule in the main body of the Skill to proceed with `full`/`hotfix`/`tweak`. The problem is that this rule is unexplainable, unverifiable and unrecoverable. The route is wrong. You don't know which signal has gone wrong. After an interruption and re-entry, the Agent can only guess again.

**0.4.0 Decision ** : Transform "What the user wants to do" into a structured routing context (implementation type named `CometIntentFrame`), and then re-score it by the runtime according to a fixed priority to provide an interpretable final route.

** Why change it this way ** : The core contradiction is the "issue of trust". The old practice trusted the routing suggestions put forward by the Agent itself. The new approach ** does not trust suggestions but only evidence ** - at runtime, the confidence level, risk signals, and repository context in the routing context are recalculated. When they are inconsistent with the Agent's suggestions, the differences are written into the diagnostic log.

The most representative aspect of this design is that the risk signal takes precedence over the oral process: you say "go hotfix", but if `public_api_change` is hit, the runtime will pause and you will be asked to confirm whether to continue this lightweight process that affects external contracts. This is Comet's safety bottom line: High-risk shortcuts always require you to clearly confirm.

For details, please refer to [Intent Recognition and Routing ](/en/concepts/intent-routing)

## III. Skill Creator

The first two items are to make the existing capabilities more stable. Starting from this section, it's the ability that has been newly added in 0.4.0.

** Status 0.3.9 ** : Users can only consume the `/comet` series commands preset by Comet. Do you want to create your own workflow Skill? Can't do it. Do you want to combine the skills `brainstorming` + `writing-plans` + `systematic-debugging` + `verification-before-completion` into a "Team PR Review Assistant" for packaging and distribution? Comet has no such path at all - it is merely a consumed workflow, not a factory that can produce skills.

Decision 0.4.0: Position `/comet-any` as a complete Skill creation platform. It helps users create skills with the ability to run stably, distribute and review by combining any Skill.

** Why build a Platform ** : Creating a reusable, distributable, and reviewable Skill package requires a more complete toolchain than generating a prompt word. A Skill that can be on par with `/comet` requires:

1. ** Deterministic skeleton ** - The routing table, runtime script, and manifest must be reproducible and cannot change each time they are generated;
2. ** Reviewable creative content ** - The decision-making core of the entry and the guidance of the nodes are written by the LLM, but they must be reviewable by humans and backed by evidence.
3. ** Release Evidence Chain ** - eval evidence binds to the current draft hash, manually approves the binding to the current hash, and forces preview before distribution.

So `/comet-any` produces a ** stable combination Skill Bundle** containing multiple types of products:

```text
<bundle-draft>/
  bundle.yaml
  skills/<entry-skill>/
SKILL.md # The entry point that users actually invoke
    comet/
skill.yaml # Internal Runtime Plan
guardrails.yaml # Constraints generated by preferences and risk policies
checks.yaml # Run Completion check
      eval.yaml                 # Eval manifest
    reference/
resolved-skills.json # True Skill source, hash, Select evidence
composition-report.md # Composition Scheme, Deviation explanation, risk
scripts/ # Steadily advance the control plane of the process
  rules/
  hooks/
```

For this main line, ordinary users only need to remember one sentence:

```text
/ Comet-any create -> comet eval verify -> comet creator status/next
  -> comet publish review/approve/run -> comet publish distribute --preview
  -> comet publish distribute
```

`/comet-any` will also read project-level preferences (`.comet/skill-preferences.yaml`) : which skills you prefer to reuse first, what to do when missing or ambiguous, and whether scripts/hooks are allowed. It must first present the combination plan to you for confirmation, and only write the Bundle draft after you nod - this is the starting point of "reviewability".

For details, please refer to [Complete Process of Skill Creator ](/en/skill-creator/workflow).

## IV. Eval

`/comet-any` has solved the problem of "being able to produce", but being able to produce does not mean being able to produce well. If no one can quantify whether a Skill is good or not, improvement can only be based on feelings, and there will be no reliable direction for the evolution of skills. `comet eval` is the new system that fills this gap. It is the decision-maker for whether Comet's Skill can be released and in which direction it should evolve. **

** Status 0.3.9 ** : Whether a Skill is good or not depends entirely on feeling. You have written a workflow Skill. Whether team members can use it, whether it is stable, and whether the token is worth spending - there are no quantitative means, nor is there an objective threshold of "whether it can be released or not".

**0.4.0 Decision ** : `comet eval` is a Skill evaluation framework based on pytest. It is not merely about "running it to see if it passes", but rather uses a set of indicator systems to break down the matter of "good or bad" into comparable figures.

** Why does eval determine the evolution direction ** : Because the results of eval are directly bound to the release access control - ** Without the eval evidence of the current draft hash, if the eval fails, or if the eval evidence is for an old hash, it cannot be published **. In other words, eval is an essential step for a Skill to move from a draft to distribution, and its scoring dimension serves as a compass for where the Skill should focus its efforts.

eval distinguishes "capability" and "reliability" using two key indicators:

|Indicator|Meaning|The questions answered|
| --- | --- | --- |
|`pass@k` (Capacity Limit)|The probability of success at least once out of k independent attempts|Can this Skill be achieved?|
|`pass^k` (Lower Reliability Limit)|The probability of success in all k independent attempts|Can it be done every time?|

Why do we need both? Because for workflow-related skills - things that users will run repeatedly - reliability is more important than capability. High `pass@k` and low `pass^k` mean that Skill can occasionally get it right, but the outcome of a single attempt is still hard to predict. This gap (`pass@k − pass^k`) is the most crucial quality signal: a Skill with high capability and low reliability. The next step should prioritize stability.

To score different types of skills based on matching dimensions, eval provides three sets of rubric:

| Profile |Purpose|"Dimension"|
| --- | --- | --- |
| `generic` |Arbitrary Skill|Seven dimensions (Completion degree, Skill invocation, product, instruction compliance, interaction, efficiency, security boundary)|
| `comet-workflow` |Comet Workflow|9 dimensions (including main process evidence, stage guard, specification drift, and recoverability)|
| `authoring-skill` |`/comet-any` generation package|11 Dimensions|

When a failure occurs, eval will also perform "failure attribution", dividing the failure into four categories and telling you what to fix next:

- `harness` - Mostly due to eval environment, Docker, or path issues;
- `workflow` - Most likely, the Skill execution process did not meet expectations (** The Skill needs to be repaired **);
- `task` - Mostly issues related to task definition and verification conditions;
- `model` - Mostly due to unstable model behavior or tool usage.

For ordinary users, it's a two-step process: First, `--collect` conducts a low-cost discovery pre-check, and then `--html` runs a real assessment to obtain a searchable report.

```bash
comet eval ./generated-skill/comet/eval.yaml --collect
comet eval ./generated-skill/comet/eval.yaml --html
```

For more details, please refer to [Evaluate any Skill](/en/eval/quickstart)

## V. Dashboard: view artifacts and state

The Skill has been created and evaluated, but during the process of running a change, a large number of products will be produced - proposals, designs, tasks, plans, verifyreports, handoff, checkpoints... At 0.3.9, these items were scattered in different directories such as `openspec/changes/`, `docs/superpowers/`, and `.comet/`. To see where a change is now, what it has produced, or if it is stuck, one can only go through the files. `comet dashboard` is the new system that fills this gap: it provides a visual platform for the documentation management of products. **

** Status 0.3.9 ** : No visualization means. Diagnosing a stuck change means opening YAML one by one, finding the pointer, jumping to the corresponding directory and piecing together the full picture yourself.

** Decision for 0.4.0 ** : `comet dashboard` starts a local read-only browser interface and puts the ** full picture ** of each change into a panel.

** Why "Product Management Visualization "** : The dashboard divides all products into three groups by source, allowing you to clearly see at a glance what a change should have, what is already there, and what is still lacking:

|Grouping|Product|Source|
| --- | --- | --- |
| **OpenSpec** | proposal、design、tasks、deltaSpec |Change the specification files in the directory|
| **Superpowers** | designDoc、plan、verifyReport |Design/plan/review evidence under `docs/superpowers/`|
| **Comet** | `.comet.yaml`、handoff、checkpoint、brainstorm、subagentProgress |The intermediate products in `.comet/`|

Each product will be marked with status - ** Generated ** (previewable), ** Not Generated ** (expected but not created yet), ** Not needed to be generated ** (not applicable to the current mode/stage). This has transformed "Is the product of this change complete?" from flipping through files to looking at the panel.

In addition to the product, the dashboard also presents stage progress, task progress, verify status, next action suggestions, risk signals, and Git context on the same panel. The same snapshot can also be consumed by scripts and CI:

```bash
comet dashboard . --json          # Output a snapshot for the script /CI
comet dashboard . --port 4399     # Specified port
GET /api/dashboard                # HTTP interface, the same snapshot
```

eval and dashboard share the same runtime evidence path - the issues reported by `comet status` and `comet doctor` are the ones that the script actually intercepts. This has transformed Comet's "recoverability" and "observability" from slogans into verifiable commitments.

For more details, please refer to [Dashboard Overview ](/en/dashboard/overview)

## VI. State layers

**0.3.9 status ** : All statuses are stuffed into a `.comet.yaml` - user-readable workflow fields and machine-managed runtime checkpoints are mixed together. The result is that users are prone to mistakenly modify machine fields, and changes in machine fields also contaminate human-readable projections.

**0.4.0 Decision ** : The status of each change is split into three layers:

|"File|Belonging|"Content|
| --- | --- | --- |
| `.comet.yaml` |User-readable|Workflow projection (`workflow`/`phase`, etc.) + `run_id` link|
| `.comet/run-state.json` |Machine management|Runtime checkpoints: current step, iteration, pending action|
| `.comet/state-events.jsonl` |Supplementary audit|A complete record of a successful transfer|

** Why change it this way ** : Single responsibility. Users can directly understand "which stage it is at now", but they cannot touch the machine field. Machine fields are written by runtime atoms, and `comet-state set` will refuse to write them directly. Audit logs only append and do not overwrite, providing you with a traceable status history. Old changes are automatically migrated when they are read for the first time without the need for manual processing.

## Version scope

If we look at these six items together, the main thread of 0.4.0 is very clear: **Comet has transformed from a "workflow layer" to a "workflow + Skill platform "**, and these three things support each other and form a closed loop:

- "Create it" - `/comet-any` enables everyone to combine any Skill into a reusable package as useful as Comet.
- ** Quantitative conclusion ** - `comet eval` makes the effect of Skill quantifiable and uses it as a release access control to determine which direction Skill will evolve.
- ** Visible ** - `comet dashboard` provides a visual panel for the documentation management of products.

The following three things keep the platform stable:

- The runtime is cross-platform (Node), so the platform can be implemented in more environments.
- The routing can be interpreted (routing context), so the behavior of the platform is trustworthy.
- The status is stratified, so the platform is recoverable and auditable.

0.3.9 resolved the issue of "How to make a workflow recoverable"; 0.4.0 addresses the issue of "how to make workflows and skills a platform that is creative, quantifiable, clear, trustworthy, and scalable." This is what this major version leap truly aims to do.
