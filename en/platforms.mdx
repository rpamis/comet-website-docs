Comet installs Skills, Rules, and Hooks in each target platform's standard directory. You can choose one or more platforms in `comet init`. Comet currently supports 37 AI coding platforms.

## Capability summary

### Rule formats

Comet supports four rule formats:

| Format    | Platforms                                        |
| --------- | ------------------------------------------------- |
| `md`      | Most platforms that support rules                 |
| `mdc`     | Cursor and Oh My Pi; Oh My Pi uses always-apply MDC |
| `copilot` | GitHub Copilot only                               |
| `dsh`     | DeepSeek Harness only; written into a managed `AGENTS.md` block |

### Hook formats

The 17 hook platforms in the current list use 12 hook formats:

| Hook format | File written                     | Platforms                           |
| ----------- | -------------------------------- | ------------------------------------ |
| `claude-code` | `settings.local.json`          | Claude Code, Codex, Amazon Q, Grok   |
| `qwen`        | `settings.json`                | Qwen Code                            |
| `qoder`       | `settings.json`                | Qoder                                |
| `codebuddy`   | `settings.json`                | CodeBuddy, WorkBuddy                 |
| `gemini`      | `settings.json`                | Gemini CLI                           |
| `windsurf`    | `hooks.json`                   | Devin Desktop (formerly Windsurf)    |
| `copilot`     | `hooks/<id>.json`              | GitHub Copilot                       |
| `kiro`        | `hooks/<id>.kiro.hook`         | Kiro                                 |
| `omp`         | `hooks/pre/comet-hook-router.ts` | Oh My Pi                           |
| `dsh`         | `hooks.json`                   | DeepSeek Harness                     |
| `trae`        | `hooks.json`                   | Trae, Trae CN                        |
| `zcode`       | `config.json`                  | ZCode                                |

### OpenCode-based platforms

OpenCode, ZCode, and MimoCode all run on the OpenCode runtime and support OpenCode-style slash commands and mirrored OpenSpec output:

| Platform  | Mirroring behavior                                                  |
| --------- | -------------------------------------------------------------------- |
| OpenCode  | Native support                                                        |
| ZCode     | Migrates and mirrors `.opencode/{skills,commands}` output to `.zcode/` |
| MimoCode  | Mirrors OpenSpec output to `.mimocode/`                               |

## Special installation paths

The following platforms use a global installation directory that differs from their project-level directory:

| Platform         | Project directory | Global directory           |
| ---------------- | ----------------- | --------------------------- |
| Codex Skill      | `.agents`         | `~/.agents`                 |
| OpenCode         | `.opencode`       | `~/.config/opencode`        |
| MimoCode         | `.mimocode`       | `~/.config/mimocode`        |
| Antigravity      | `.agents`         | `~/.gemini/antigravity`     |
| Antigravity 2.0  | `.agents`         | `~/.gemini/config`          |
| Pi               | `.pi`             | `~/.pi/agent`               |

All other platforms install globally into a directory with the same name (for example, Claude Code globally at `~/.claude`, CodeBuddy at `~/.codebuddy`, WorkBuddy at `~/.workbuddy`). Junie, CoStrict, Crush, Factory Droid, iFlow, Bob Shell, and ForgeCode do not support global installation.

<Note>
  WorkBuddy project-level Skills live in <code>.workbuddy/skills/</code>, and user-level
  Skills in <code>~/.workbuddy/skills/</code>. The blocking hook is written only to the
  project-level <code>.workbuddy/settings.json</code>; a global installation does not add a
  global blocking hook, so no hook configuration outside the project is needed.
</Note>

<Note>
  Codex's Skill discovery root differs from its configuration root: project and global
  Skills use <code>.agents/skills</code>, while Codex-specific configuration, rules, hooks,
  and the plugin cache stay in <code>.codex</code>. The 0.4.0-beta.4 update/uninstall
  migrates Comet-managed legacy <code>.codex/skills</code> installations and preserves other
  Skills and shared directories. Since 0.4.0-beta.5, Codex's phase-guard hook is written to
  the supported <code>.codex/hooks.json</code>. Grok also uses the claude-code hook format,
  but writes to <code>.grok/hooks/comet.json</code> and additionally matches Grok's native
  <code>write</code>/<code>search_replace</code> tools.
</Note>

<Note>
  Antigravity and Antigravity 2.0 share the project-level <code>.agents/</code> Skill
  directory, so <code>comet init</code> selects both during auto-detection. To install for
  only one of them, uncheck the other in the interactive install flow (without
  <code>--yes</code>).
</Note>

<Tip>
  `comet init` automatically detects platform configuration directories that already exist
  in the project and pre-selects them. You can also pass `--yes` to skip the prompts and
  install to every detected platform automatically.
</Tip>

## Choosing project-level or global

| Scope   | Best for                                            | Characteristics                                    |
| ------- | --------------------------------------------------- | --------------------------------------------------- |
| project | Team projects, repository conventions, committed configuration | Configuration is written into the current project for collaboration |
| global  | A personal default environment shared across projects | Configuration is written to the user directory; switching projects is easier |

<Tip>
  If you are not sure, start with a project-level installation. It is the easiest way for
  team members to see the same Comet behavior.
</Tip>

## Installation mode: copy vs symlink

After you select platforms, `comet init` and `comet update` ask for the **install mode**. Since 0.4.0-beta.1 a symlink mode is available:

| Mode               | Behavior                                                                                       | Best for                                                            |
| ------------------ | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| **Copy** (default) | Copies each platform's Skills, rules, and scripts as an independent copy into the target directory | The traditional approach; platform isolation; cross-device sync via the repository |
| **Symlink**        | Links Comet-managed Skills inside each platform's existing `skills/` directory, sharing the central `.comet/skills/` store | Multi-platform development, saving disk space, updating every platform at once |

### How symlink mode works

With Symlink selected, Comet no longer copies a per-platform set of Comet Skills. Instead, it creates symbolic links in each platform's existing `skills/` directory that point to the project's central `.comet/skills/`:

```text
.comet/skills/          ← central store (the only copy)
├── comet-open/
├── comet-design/
└── ...
.claude/skills/comet-*  →  .comet/skills/comet-*   (symbolic links created by Comet)
.cursor/skills/comet-*  →  .comet/skills/comet-*   (symbolic links created by Comet)
.agents/skills/comet-*  →  .comet/skills/comet-*   (symbolic links created by Comet)
```

Running `comet update` refreshes only the central store and takes effect on every platform immediately. The terminal summary shows `symlink created` or `symlink creation failed`.

<Warning>
  Symbolic links depend on filesystem support. Some Windows setups or sync tools (such as
  certain cloud drives) may not handle symbolic links correctly. If you run into problems,
  switch back to <strong>Copy</strong> mode.
</Warning>

<Note>
  If the target platform already has its own <code>skills/</code> directory, Comet keeps the
  directory and any local or third-party Skills inside it, creating or refreshing only the
  Comet-managed links.
</Note>

<Note>
  The mode you choose does not change Comet's behavior, only how files land on disk. When
  committed to a repository, Copy mode produces real files; Symlink mode produces symbolic
  links (team members usually run <code>comet init</code> themselves).
</Note>

## Generic skills registry platforms

Some AI coding platforms manage Skills through the generic `skills` CLI registry. For these platforms (including OpenClaw, Hermes, and others), install the Comet skill package with the generic command:

```bash
npx skills add rpamis/comet
```

This command pulls the Comet skill package from the generic skills registry and installs it where the platform expects it, without a global Comet installation. It coexists with `comet init` without conflict.

## Hooks and enforcement

Some platforms support hooks. Comet merges the hook configuration it manages non-destructively and keeps your existing configuration.

If the file already contains plugins, hooks, or other user settings, Comet preserves them. If the JSON cannot be parsed, the installation fails with an explicit error and leaves the original file unchanged.

## Post-install verification (optional)

```bash
comet doctor
```

If a platform directory, Skill file, script, or hook is missing, `doctor` reports the diagnosis. To refresh, run:

```bash
comet update
```
