Comet installs Skills, Rules, and Hooks into the directories expected by each AI coding platform. Choose one or more platforms during `comet init`. Comet currently supports **35** AI coding platforms.

Platform support grows layer by layer through Skills, Rules, and Hooks.

## Capability summary

### Rules formats

Comet supports three Rules formats:

| Format | Platforms |
| --- | --- |
| `md` | Most platforms that support Rules |
| `mdc` | Cursor only (Cursor MDC frontmatter) |

### Hook formats

The 14 Hook-capable platforms listed here use nine Hook formats:

| Hook format | Written file | Platforms |
| --- | --- | --- |
| `claude-code` | `settings.local.json` | Claude Code, Codex, Amazon Q, Grok |
| `qwen` | `settings.json` | Qwen Code |
| `qoder` | `settings.json` | Qoder |

| --- | --- |
| OpenCode | Native support |

| MimoCode | Mirrors OpenSpec output to `.mimocode/` |

## Special install paths

The global install directory differs from the project directory for these platforms:

| Platform | Project directory | Global directory |
| --- | --- | --- |
| Codex Skills | `.agents` | `~/.agents` |
| OpenCode | `.opencode` | `~/.config/opencode` |
| MimoCode | `.mimocode` | `~/.config/mimocode` |
| Antigravity | `.agents` | `~/.gemini/antigravity` |
| Antigravity 2.0 | `.agents` | `~/.gemini/config` |
| Pi | `.pi` | `~/.pi/agent` |

Other platforms use the same directory name for global installs, such as `~/.claude`, `~/.codebuddy`, and `~/.workbuddy`. Junie, CoStrict, Crush, Factory Droid, iFlow, Bob Shell, and ForgeCode do not support global installs.

<Note>
  WorkBuddy project Skills live in <code>.workbuddy/skills/</code>, while user Skills live in{' '}
  <code>~/.workbuddy/skills/</code>. As with CodeBuddy, Comet writes its blocking Hook only to the
  project-level <code>.workbuddy/settings.json</code>; a global install does not add a global
  blocking Hook.
</Note>

### Codex Skills and config use different roots

Codex discovers project and global Skills under `.agents/skills`. Codex-specific config, Rules, Hooks, and plugin cache remain under `.codex`. Update and uninstall migrate Comet-managed legacy `.codex/skills` content while preserving unrelated Skills and the shared directories. Starting in 0.4.0-beta.5, Codex phase-guard Hooks are written to the supported `.codex/hooks.json` location, and Comet safely migrates its managed entries from the previously generated `settings.local.json` without changing user-defined Hooks or settings ([#199](https://github.com/rpamis/comet/issues/199)). Grok uses the claude-code Hook format, writes to `.grok/hooks/comet.json`, and also matches Grok-native `write`/`search_replace` tools.

### CodeBuddy and WorkBuddy hooks preserve existing settings

Project-level CodeBuddy and WorkBuddy installs merge the Comet PreToolUse hook into `.codebuddy/settings.json` and `.workbuddy/settings.json`, respectively. Existing plugins, hooks, and other user settings remain intact. Global installs provide Skills under the user directory; blocking Hooks remain project-scoped. If the JSON is invalid, installation reports the failure and leaves the original file unchanged.

<Note>
  Antigravity and Antigravity 2.0 share the project-level <code>.agents/</code> Skills directory, so{' '}
  <code>comet init</code> selects both when it detects them. To install to only one, clear the other
  platform in the interactive flow without <code>--yes</code>.
</Note>

<Tip>
  `comet init` detects existing platform configuration directories and preselects them. Use `--yes`
  to skip the interactive prompts and install to all detected platforms.
</Tip>

## Choosing project-level or global

| Install scope | Best for | Characteristics |
| --- | --- | --- |
| project | Team projects, repository conventions, committed configuration | Writes configuration to the current project for collaboration |
| global | Personal defaults shared across projects | Writes configuration to the user directory |

<Tip>
  If you are unsure, start with a project-level install. It makes the same Comet behavior visible to the team.
</Tip>

## Install mode: Copy vs Symlink

After you choose platforms, `comet init` and `comet update` ask for an **install mode**. Symlink mode was added in 0.4.0-beta.1:

| Mode | Behavior | Best for |
| --- | --- | --- |
| **Copy** (default) | Copies each platform's Skills, Rules, and scripts as **independent files** into the target directory | Traditional installs, platform isolation, and cross-device sync |
| **Symlink** | Links Comet-managed Skills inside each platform's existing `skills/` directory to the shared `.comet/skills/` store | Multi-platform development, saving disk space, and updating all platforms at once |

### How Symlink mode works

With Symlink mode, Comet creates links for Comet-managed Skills in each platform's existing `skills/` directory instead of copying a separate set for every platform:

```text
.comet/skills/          <- central store (one copy)
|-- comet-open/
|-- comet-design/
`-- ...
.claude/skills/comet-*  -> .comet/skills/comet-*   (Comet-managed symlink)
.cursor/skills/comet-*  -> .comet/skills/comet-*   (Comet-managed symlink)
.agents/skills/comet-*  -> .comet/skills/comet-*   (Comet-managed symlink)
```

`comet update` only needs to update the central store, so all platforms take effect immediately. The terminal summary reports `symlink created` or `symlink creation failed`.

<Warning>
  Symlinks depend on filesystem support. Some Windows configurations and sync tools may not handle
  them correctly. Fall back to <strong>Copy</strong> mode if you encounter a problem.
</Warning>

<Note>
  If a target platform already has its own <code>skills/</code> directory, Comet preserves the directory
  and its local or third-party Skills. It only creates or refreshes Comet-managed links.
</Note>

<Note>
  The mode changes how files are placed on disk, not Comet behavior. Copy mode produces real files
  when committed to a repository; Symlink mode produces symbolic links, so team members usually run
  <code>comet init</code> separately.
</Note>

## Generic Skills registry platforms

Some AI coding platforms use the generic `skills` CLI registry instead of a platform-specific directory convention. For these platforms, including OpenClaw and Hermes, install the Comet Skill bundle with:

```bash
npx skills add rpamis/comet
```

This command downloads the Comet Skill bundle from the generic registry and installs it where the platform expects it. It does not require a global Comet install and can coexist with `comet init`.

## Hooks and executable capability

Some platforms support Hooks. Comet merges its managed Hook configuration non-destructively and preserves existing user settings.

If a file already contains plugins, Hooks, or other user settings, Comet keeps them. If the JSON is invalid, installation fails clearly and leaves the original file unchanged.

## Verify after install (optional)

Run:

```bash
comet doctor
```

If platform directories, Skill files, scripts, or Hooks are missing, `doctor` reports them. Run this command when you need to update the installation:

```bash
comet update
```
