Comet is a recoverable workflow and Skill platform for AI coding. It provides two independent requirement workflows:
- Native patterns for strong models such as Fable 5 and GPT-5.6
- Classic mode for lower capability tier models, combining OpenSpec and Superpowers

Both, together with Skill Creator, Eval and Release Access control, form a toolchain from requirements to archiving and then to Skill distribution.

## What can you do with Comet

- Use `/comet` to enter Native or Classic by project configuration, and advance a product or code change from an idea to an archive.
- Use `/comet-any` to organize your workflow into reusable skills.
- Evaluate your skills with `comet eval`.
- Use [`comet dashboard`](/en/dashboard/overview)] to view the stages, tasks, acceptance, risks, products, and Git context of Classic, Native, and Supervisor Changes in your local browser; the Dashboard remains read-only and will not advance or modify the changes.
- Review, approve, release and distribute `/comet-any` products with `comet publish`.
- Use `comet status` and `comet doctor` to clearly understand the current stage, the next step and the recovery suggestions.

## The differences from ordinary prompt words

Common prompt words rely on the conversation history. Comet relies on documented states and verifiable evidence.

|Points of concern|There is no Comet|Use Comet|
| -------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
|Interruption recovery|The Agent needs to recall the context, and a large amount of tokens are consumed before even starting to write the code|Restore from the respective states and running evidence of `.comet/config.yaml` and Native/Classic, and guess the scene without relying on the original dialogue|
|Stage boundary|Agents tend to skip requirements or verifications, such as when the code implementation is completed but the documentation is not checked, or directly writing code at stages where it should not be written|Native constraints Shape/Build/Verify the result of the Archive and evidence; Classic offers a five-stage process with clear quality control. ** If the task is not completed in the corresponding stage, the current stage cannot be exited **, forcing the Agent to complete all tasks in the corresponding stage|
|Automatic propulsion|A large number of Skill sequences need to be memorized manually and gradually taken over|** Automatic advancement ** Comet will automatically advance the core Skill process, ** without the need for users to take over except for necessary HITL interaction points **|
|Workspace Management|Developers need to manually create, switch and remember the branch and worktree corresponding to each task|When creating a change, select `current`, `branch` or `worktree`; Comet creates or reuses workspaces, records branch bindings, and locates the correct directory during recovery. Stop advancing when there is a mismatch between branches or directories|
|Parallel collaboration|Developers need to break down tasks, determine dependencies, allocate work directories, track completion status and merge results by themselves|Supervisor Change ** only schedules sub-tasks that meet dependencies and can be started **, prepares an ** independent worktree** for each sub-task, and concludes uniformly with validation and integration status|
|Personal Memory|Users need to repeatedly state their language preferences, communication styles and collaboration habits in different tasks|**Personal Memory saves user preferences and personal collaboration experiences that are still helpful for future tasks **, and is injected after filtering by the current task; Users can view, correct, forget and roll back without having the Agent get to know you again every time|
|Project Knowledge|Each Agent has to re-explore the project structure, dependencies, decisions, processes and constraints, repeatedly consuming time and tokens|**Project Knowledge: Accumulate project facts with sources and verified experiences **, and retrieve relevant content by task; When the source changes, old records will become invalid to prevent outdated knowledge from continuing to affect development|
|Constraint strength|It is difficult for the same set of processes to be adapted to different capability level models simultaneously|Strong models use Native with light method constraints; The lower-capability models use Classic, and there are also lightweight presets such as hotfix/tweak|
|Combine the product form of Skill|It's just a single file named `SKILL.md`, which cannot be combined, have dependencies, or be distributed|`/comet-any` generates stable "combined Skill Bundle" - can assemble rule, hook, and Engine metadata; ** Reviewer **, ** distributable ** (like `comet init`, it can be implemented on 35 AI coding platforms through `comet publish distribute`)|
|Skill Quality Verification|It depends on your sense of touch. If the Agent runs through once and no errors are reported, it is considered to have passed|`comet eval` runs ** real tasks ** in an isolated environment, quantifies ** capabilities and reliability with multi-dimensional scoring and `pass@k`/`pass^k` **, and automatically ** attributes ** where to change when failing - comparing each round of iteration with baseline data, whether the improvement is effective is clear at a glance. Skill evolution relies on evidence rather than feeling|

## Main entrance

When making project changes, uniformly call `/comet`. It will read the project configuration and enter the following Native or Classic workflow. Workflow-specific skills are internal permanent entry points and can also be used for advanced debugging, but they are not daily must-remember commands.

## What will you get after installation

`comet init` will install Comet skills, Rules, hooks, scripts and platform adaptation files to the project-level or global location of your choice.

The runtime of Comet 0.4.0-beta.1 only relies on Node.js. Built-in state, guard, handover, and archiving scripts are all executed through the Node entry, no longer treating Bash, Git Bash, or WSL as workflow prerequisites.
