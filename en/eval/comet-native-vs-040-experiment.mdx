This rerun asks a specific question: after strengthening Native Sequential clarification and the pre-Build confirmation lock, did the established 16-task breadth baseline regress?

We ran the current Native workflow on the same 16 tasks, three repetitions each, for 48 runs. Those reports are strictly aligned by `task + repetition` with 48 historical 0.4.0 Classic runs.

<Note>
  Native and Classic are separate workflows for different model capability levels. Native does not
  upgrade into Classic. Business tasks and repetitions are aligned, while workflow artifacts are
  still validated against each workflow's own contract.
</Note>

## Alignment

The historical Classic records predate complete execution-identity manifests. The comparison reconstructs their task-core hashes from the current canonical task tree. This proves comparison-time task-structure parity, not exact historical-checkout identity.

## Headline results

| Metric            | Current Native | 0.4.0 Classic |     Difference |
| ----------------- | -------------: | ------------: | -------------: |
| Strict run pass   |          47/48 |         43/48 | Native +4 runs |
| Task-macro pass@1 |           0.98 |          0.90 |   Native +0.08 |
| Task-macro pass@3 |           1.00 |          1.00 |           Tied |
| Task-macro pass^3 |           0.94 |          0.75 |   Native +0.19 |

Both workflows reach `pass@3 = 1.00`, meaning every task succeeds at least once in three attempts. Native reaches `pass^3 = 0.94`: 15 tasks pass all three runs. Classic reaches 0.75: 12 tasks pass all three.

The only current Native failure is `comet-cross-file-refactor#r3`. The business implementation completed, but the terminal Native brief, specification, or verification evidence was incomplete. The other 15 tasks passed 3/3.

## Execution efficiency where both pass

The primary efficiency view contains the 42 same-task repetitions where both workflows strictly pass:

| Metric                       | Current Native | 0.4.0 Classic | Native difference |
| ---------------------------- | -------------: | ------------: | ----------------: |
| Model starts/resumes         |           1.17 |          2.98 |            -60.8% |
| Agent turns                  |          57.93 |         92.52 |            -37.4% |
| Tool calls                   |          55.76 |         82.95 |            -32.8% |
| Non-cache input tokens       |         39,498 |        82,315 |            -52.0% |
| Output tokens                |         10,662 |        14,012 |            -23.9% |
| Total tokens including cache |      2,077,084 |     3,928,545 |            -47.1% |
| Model cost                   |         $1.480 |        $2.738 |            -45.9% |
| Cumulative model duration    |           429s |          353s |            +21.4% |

Native still uses materially fewer Agent turns, tool calls, tokens, and model cost. Wall duration, however, is 21.4% higher in this run. The new data therefore does not support the earlier report's claim that Native duration was about 47% lower.

<Warning>
  Classic is historical and Native is current; machine load, service windows, and telemetry
  completeness differ. Tokens, turns, and tool calls have stronger structural interpretation. Wall
  duration remains directional and must not be presented as a controlled causal estimate.
</Warning>

## Change from the July 16 Native report

The previous Native baseline was 46/48 with `pass^3 = 14/16`. The current rerun is 47/48 with `pass^3 = 15/16`, and the failure surface contracts from two terminal-evidence gaps to one.

This supports the conclusion that clarification and Runtime hardening did not regress breadth: canonical business-task breadth remains strong at 47/48.
