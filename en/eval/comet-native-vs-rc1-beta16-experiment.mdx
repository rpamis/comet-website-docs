<Note>
  The RC1 experiment ran on 2026-08-28. The beta16 48-run baseline is the existing experiment from 2026-08-27—28 and was reused rather than rerun. The two releases use the same 16 tasks and three repetitions, but their Native artifact and trajectory contracts are version-specific.
</Note>

This experiment asks whether the Native changes in RC1 improve reliability and execution cost relative to beta16, while keeping the business task set and repetition count fixed.

Both sides use the same 16 business tasks, repeated 3 times each: 48 runs per release and 96 runs in the comparison.

<Note>
  The final RC1 analysis set is 48 unique `task + run` records. Four earlier recovery attempts produced `harness_trigger_suspect` / exit-125 shells and are excluded as Docker noise; their missing nodes were replaced by the later exact reruns. No report is counted twice.

  The raw RC1 snapshot initially recorded 47/48 because its parser treated a shell glob in `find ... -path '*/.claude/skills/*'` as an unexpected Skill named `*`. After the parser fix, the same raw stdout contains only the explicit `comet-native` invocation, so this report uses the corrected 48/48 analysis without editing the original snapshot.
</Note>

## How the experiment is aligned

The business task and validator stay the same. Workflow checks follow each release's actual Native contract rather than applying beta16 checks unchanged to RC1.

| Observation | RC1 | beta16 |
| ----------- | --- | ------ |
| Business tasks | Same 16 tasks | Same 16 tasks |
| Repetitions | 3 per task, 48 runs | 3 per task, 48 runs |
| Business validation | Same task validators | Same task validators |
| Workflow validation | RC1 Native Skill, artifacts, state, loop, isolation | beta16 Native Skill, artifacts, state, trajectory, isolation |
| Model selection | `deepseek-v4-flash[1m]` | `deepseek-v4-flash[1m]` |
| Interaction | `auto_user`, max 12 turns | `auto_user`, max 12 turns |
| Experiment ID | `native_rc1_20260828_0952` + exact resume batch | `native_beta16_20260827_2308` |
| Analysis set | 48/48 included, high confidence | 48/48 included, high confidence |

Strict pass means that both the business validator and the version-appropriate Native workflow checks pass. Business validation is reported separately so a workflow-evidence failure is not confused with a code/task failure.

## Main results

| Metric | RC1 | beta16 | Difference |
| ------ | --: | -----: | --------: |
| strict pass@1 | 48/48, 100.00% | 46/48, 95.83% | RC1 +4.17 pp |
| pass@3 | 16/16, 100.00% | 16/16, 100.00% | Tied |
| pass^3 | 16/16, 100.00% | 14/16, 87.50% | RC1 +12.50 pp |
| Business validator pass | 48/48 | 47/48 | RC1 +1 run |
| Corrected mean duration | 391.3s | 503.6s | RC1 −22.3% |
| Corrected median duration | 369.1s | 476.5s | RC1 −22.5% |

Both releases reach task-level `pass@3 = 100%`: every task succeeds at least once. RC1 has 2 more strict pass(es) and 2 more task(s) with all three repetitions passing. The duration reduction is directional evidence because the baseline is a reused historical run rather than a same-window controlled rerun.

## Why pass@3 and pass^3 both matter

`pass@3` measures whether at least one of three attempts succeeds; it describes capability coverage. `pass^3` measures whether all three observed attempts succeed; it describes repeated-run reliability.

The two metrics separate “the release can complete the task” from “the release completes it consistently.” Here, both releases cover all 16 tasks, while RC1 has 16/16 tasks with three strict passes and beta16 has 14/16.

## Completed-task execution efficiency

The efficiency view includes the 46 matching task repetitions that both versions strictly passed. This avoids treating an early failure as a cheap run. A model start/resume is one evaluator entry into the subject model; Agent turns are the turns inside those invocations.

| Metric | RC1 | beta16 | RC1 difference |
| ------ | --: | -----: | -------------: |
| Model starts/resumes | 1.15 | 1.89 | −39.1% |
| Agent turns | 83.39 | 77.54 | +7.5% |
| Tool calls | 97.35 | 74.65 | +30.4% |
| Cumulative model duration | 396.3s | 501.6s | −21.0% |
| Non-cache input tokens | 75,102 | 73,632 | +2.0% |
| Output tokens | 35,445 | 46,604 | −23.9% |
| Total tokens including cache | 4,474,779 | 3,730,902 | +19.9% |
| Model cost | $4.003 | $3.348 | +19.6% |

In the paired strict-success view, RC1 enters the model fewer times and has lower cumulative duration and output tokens. The complete table also shows the trade-off: RC1 uses more Agent turns, tool calls, total tokens, and average cost than beta16 in these 46 pairs. The result is therefore a shorter-but-not-cheaper execution profile, not a general efficiency win.

Both sides preserve peak-context telemetry for all 48 runs. Mean peak context is 102,470 tokens for RC1 and 104,208 for beta16; this comparison does not use LLM Judge prose.

## Corrected duration methodology

Duration is recomputed from raw stdout by summing every top-level `result.duration_ms` in a sample, rather than taking only the last result event. It excludes Docker setup and task-validator execution time.

- RC1: 48 observable samples, mean 391.260s and median 369.053s.
- beta16: 48 observable samples, mean 503.552s and median 476.481s.

Under this methodology, RC1 reduces mean model duration by 22.3% and median duration by 22.5%. This is a comparison of two execution windows, not a controlled causal estimate.

<Warning>
  RC1 and beta16 were not run in the same service window. The task set, model selection, interaction mode, and repetition count are aligned, but machine load, provider timing, and release-specific workflow contracts are not fully controlled.
</Warning>

## Failure attribution

The corrected RC1 analysis has no remaining strict failure; beta16 has two. The original RC1 snapshot's one failure was a parser false positive, confirmed by re-reading the same raw stdout after the shell-glob fix:

| Release | Task / run | Failed signal | Business validation |
| ------- | ---------- | ------------- | ------------------- |
| beta16 | `cross-file-refactor` r3 | Missing `.comet/config.yaml`, terminal archive state, and complete Native trajectory | Passed |
| beta16 | `noise-distractor` r2 | Invoice tax calculation failed, alongside missing artifact/state/trajectory evidence | Failed |

The beta16 failures contain one workflow-only failure and one combined business/workflow failure. This is why the business-validator row is 48/48 for RC1 and 47/48 for beta16.

## About the LLM Judge

This comparison uses deterministic task and workflow validators, final `passed` state, and raw result duration. It does not use qualitative LLM Judge prose as a substitute for those checks.

## How to read the result

1. **Coverage is unchanged.** RC1 and beta16 both reach 16/16 task-level `pass@3`.
2. **RC1 is slightly more reliable in this sample.** Strict pass@1 is 4.17 percentage points higher and `pass^3` is 12.50 points higher.
3. **RC1 is faster but not cheaper in the paired success view.** Mean and median raw model duration fall by about 22%, while average cost and total tokens rise. Those are empirical trade-offs, not a single scalar “better” result.

The experiment supports evaluating RC1 as a more reliable, shorter Native release on this task set, while keeping beta16 as a valid historical baseline. It does not prove a universal release-level advantage or replace same-window controlled reruns.
