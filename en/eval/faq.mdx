This page answers four groups of questions: what the evaluation system is, how to prepare the environment, how to read reports, and how evidence reaches publishing.

## Basic concepts

<AccordionGroup>
  <Accordion title="What exactly does comet eval evaluate">
    `comet eval` executes Skill workflows against real tasks, producing auditable pre-release evidence.
    It verifies whether a Skill reliably meets delivery standards rather than succeeding merely by chance.
    Pytest execution, task registries, profiles, and report generation are fully automated by the harness without manual configuration.
    See [Evaluation system overview](/en/eval/overview) for details.
  </Accordion>

<Accordion title="What are the differences between comet eval and comet skill check">
  `comet eval` evaluates a Skill's task performance and reliability, outputting reproducible reports.
  It can consume `comet/eval.yaml` (typically generated by `/comet-any`) or directly evaluate a local Skill directory.
  When no manifest is provided, a standard run dynamically generates and caches 2–4 evaluation tasks; passing `--quick` runs a fixed `generic-skill-smoke` test.
  `comet skill check` only verifies whether a specific run generated required artifacts or state transitions, without executing model tasks or generating release evidence (reads `comet/checks.yaml`).
  Release readiness requires complete `comet eval` evidence.
  See [Runtime check](/en/eval/runtime) for details.
</Accordion>

<Accordion title="Do I need to understand pytest or Docker">
  No. Daily use only requires choosing the right input: `--manifest` or `--skill-path`.
  Underlying containerization and test runners are handled entirely by the harness.
  See [Eval harness](/en/eval/harness) for details.
</Accordion>

  <Accordion title="What do the two sets of assessment systems mean">
Creation-time evaluation (`comet eval`, reading a local Skill directory or `comet/eval.yaml`) and runtime checks (`comet skill check`, reading `comet/checks.yaml`) are separate. The former produces release evidence; the latter checks Run completion. See [Evaluation overview · Two evaluation systems](/en/eval/overview#two-evaluation-systems).
  </Accordion>
</AccordionGroup>

## Environmental preparation

<AccordionGroup>
  <Accordion title="What environment is needed to run eval">
You need `uv`, Python 3.11+, Docker, the selected Agent CLI, and its model credentials. Core Comet Runtime does not require them; only `comet eval` does. See [Evaluation quickstart · What you need before running](/en/eval/quickstart#what-you-need-before-running).
  </Accordion>

<Accordion title="The evaluation passed instantly, but it looks like it never ran">
In most cases the environment is not ready, so samples are skipped.
Common causes are Docker not running, missing model credentials, or an unavailable Agent CLI.
These runs are marked as "skip", not as failure. Verify the environment first, then rerun.
</Accordion>

<Accordion title="How to install uv">
  On macOS or Linux, run `curl -LsSf https://astral.sh/uv/install.sh | sh`. On Windows PowerShell, run `powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"`. `uv` manages the Python version and `eval/.venv` for you.
</Accordion>

<Accordion title="What is the difference between eval harness missing and uv missing">
`Eval harness is missing at ...` means the bundled `eval/` directory in the npm package is incomplete, or `--project` points to the wrong repository. Reinstall `@rpamis/comet` or correct the project path. `uv is not installed or not in PATH` means the harness was found and only `uv` needs to be installed or repaired. Most npm users do not need to clone the Comet repository.
</Accordion>

  <Accordion title="How to configure an API key">
`export ANTHROPIC_API_KEY=sk-ant-...`, or configure it in the user-level `%USERPROFILE%\.comet\eval\.env`/`~/.comet/eval/.env` (`comet eval` will load automatically). When using proxy credentials (BigModel/OpenRouter), use `ANTHROPIC_AUTH_TOKEN`.
  </Accordion>
</AccordionGroup>

## Two entrances

<AccordionGroup>
  <Accordion title="Which one should be used, --manifest or --skill-path">
To evaluate any local Skill directory, use `--skill-path` (just pass the directory; when there is no manifest, a task will be generated during normal operation). This is the default entry. When a fixed smoke is needed, explicitly add `--quick`. Evaluate the complete package generated by `/comet-any` (with `comet/eval.yaml`) and run the entire profile task set with `--manifest`. The result is the evidence for release. To enter the release readiness, the full package manifest must be used. The two are mutually exclusive.
  </Accordion>

  <Accordion title="Does the current-bundle-hash in the manifest need to be replaced manually">
No. The `<current-bundle-hash>` placeholder generated by `/comet-any` resolves to the active Bundle draft hash prior to collect/run and is written to a temporary manifest. Comet does not modify the source Bundle or `comet/eval.yaml`. Errors only occur if the manifest leaves its original Bundle, `bundle.yaml` is missing, or the draft cannot be loaded.
  </Accordion>

<Accordion title="What is --quick, and what is the default task">
  `--quick` is used together with `--skill-path` and explicitly selects the `generic-skill-smoke`
  task. A normal run on a directory generates and caches 2–4 tasks from the Skill snapshot. `--quick`
  is a low-cost smoke run; it is not complete pre-release evidence. Before release, follow the full
  package manifest path.
</Accordion>

<Accordion title="Why collect before run">
  `collect` only runs discovery pre-checks (manifest, task, path). It makes no model calls, so it is
  the cheapest step. `run` performs the actual evaluation. Collecting first clears configuration and
  path problems, which avoids wasting evaluation resources. See [Quick Start](/en/eval/quickstart)
  for details.
</Accordion>

  <Accordion title="What are the differences between authoring-skill and generic profile">
`authoring-skill` (an 11-dimension rubric with `auto_user` and `maxTurns=8` outer round trips) evaluates Skills generated by `/comet-any`. It checks package integrity, resolved-Skill evidence, the Engine contract, routing consistency, authoring lanes, and review gates. `generic` (a 7-dimension rubric with one round by default) handles general Skill smoke tests. See [Evaluation overview · Profile](/en/eval/overview#profile).
  </Accordion>
</AccordionGroup>

## Reports and Failures

<AccordionGroup>
  <Accordion title="Where can I find the report">
The CLI output prints `Report path`, commonly `.comet/eval/runs/<experiment-id>/summary.html`. Always trust the current run's `Experiment` and `Report path` values. For details, see [Read the Evaluation Report](/en/eval/reports).
  </Accordion>

<Accordion title="The evaluation failed. How do I tell where the problem is">
  Start with failure attribution in the report. `harness` usually means an environment, dependency,
  or path problem. `workflow` means the Skill flow did not meet expectations. `task` means the task
  definition or fixture is wrong. `model` means model behavior or tool calls are unstable. The
  attribution decides whether you change the environment, the task, or the Skill. See
  [Read the Evaluation Report](/en/eval/reports) for details.
</Accordion>

  <Accordion title="collect reports that it cannot find the target">
Check if the path is correct: The local Skill directory should contain `SKILL.md`, and `comet/eval.yaml` should point to a real existing file. If it is not in the root directory of the Comet repository, adding `--project <dir>` will point to the correct root directory.
  </Accordion>

<Accordion title="Should I rerun when the attribution is model">
  `model` attribution means model behavior or tool use is unstable, and rerunning usually helps. If it
  keeps failing, reduce how much the Skill depends on non-deterministic behavior.
</Accordion>

  <Accordion title="If the Rubric score is very low but all the checks are passed, does that count as passing">
It's considered passed. Rubric is an informative score (`[RUBRIC]` line and `RubricAvg`), which does not directly determine whether one passes or not. The true pass/fail is determined by the invocation of the validator and the required skill. A low Rubric score is a diagnostic signal and can be used to optimize skills without affecting the release of access control.
  </Accordion>
</AccordionGroup>

## Publish evidence

<AccordionGroup>
  <Accordion title="Can it be published once Eval is approved">
Eval passing is just one of the conditions. `/comet-any` or the backend will include the eval evidence in readiness: no evidence, failure, or the corresponding old hash cannot be published. Only after passing and hash matching can you enter review/publish. See [Overview of the Evaluation System](/en/eval/overview) for details.
  </Accordion>

<Accordion title="What does it mean when eval evidence matches an old hash">
  It means the Skill changed after the last evaluation (the draft hash moved on), so the old results
  are no longer valid. Run `comet eval ... --html` again to produce evidence bound to the current
  hash.
</Accordion>

<Accordion title="Can I write the report path into the publish status by hand">
  No. `/comet-any` records structured evidence through the Bundle backend. Editing Bundle state or
  its internal JSON by hand breaks the hash binding and the readiness check.
</Accordion>

  <Accordion title="Can a quick smoke run count as release evidence">
No. `--skill-path --quick` is an early smoke run with limited coverage. Before release, `/comet-any` must generate `comet/eval.yaml`, and a full evaluation must run with `--manifest`.
  </Accordion>
</AccordionGroup>
